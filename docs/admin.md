# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on a Unix socket of its own, apart from the client API ([Listeners](#listeners)); access is the socket's file permissions, its owner alone. The API has two endpoints: `/admin/policy` reads the deployment's policy package and writes the next one, the one way the deployment changes, and `/admin/query` reads the deployment's observation store with SQL, the one way its state is read. Everything an operator does to a serving deployment is an option of its package ([Operations](#operations)), and everything the deployment executes, owns and did is a row of the store's two tables, `stats` and `events` ([Observation](#observation), [Status](#status)). `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of the API among others ([The manager](#the-manager)).

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/policy[?revision=N]` | The deployment's policy package, the current revision's or revision `N`'s, as a tar archive of its directory: `config.toml`, with the options it states, what programs wrote included, and its defaults left out, and `programs/` ([Policy](#policy)). Its `ETag` is the revision's number (`"42"`); `404` before the deployment has a revision, or for a revision the state directory no longer keeps |
| `PUT /admin/policy[?force=true]` | Apply: the body is a tar archive of a package directory (`config.toml` and `programs/`, nothing else), which replaces the deployment's target whole: what it states becomes the target, and what it does not state takes its default. `If-Match: "N"` applies it only while revision `N` is current, answered `412` otherwise; `force=true` applies a target a rollback marked unavailable. The change does the least its options' effects need ([Updates](#updates)) and answers once it ended: `200` with the revision's record once the deployment converged; `202` with the record, `"result": "converging"`, when the daemon's own options changed and its successor converges the rest ([Hot restarts](#hot-restarts)); and an error status with the reason when it did not converge: `400` for a package a start would refuse or a target a rollback marked unavailable, `409` for an update that was abandoned or rolled back, `503` while the deployment does not serve. A package equal to the current revision's answers that revision's record and changes nothing |
| `GET /admin/query?q=SQL`, `POST /admin/query` | One read-only SQL statement over the tables `stats` and `events` ([Observation](#observation)), as the query parameter `q` or, for a long statement, the same parameter form-encoded in a `POST` body (as the Prometheus HTTP API takes one). The answer's format is the one `Accept` prefers: a JSON array of row objects (`application/json`, the default), an Arrow IPC stream (`application/vnd.apache.arrow.stream`), or a stream of server-sent events over `events` (`text/event-stream`). A statement that does not plan, or that defines, changes or writes anything, is answered `400` |

Every other path of the admin socket answers `404`. An error's body is `{"error": {"message": "..."}}`. `/admin/query` and `GET /admin/policy` answer whatever the node serves; a `PUT` answers `503` until the deployment serves ([Nodes](#nodes)).

## Policy

A deployment's configuration is its policy package (`docs/configuration.md`, Policy package), and every change of it is the next package, applied whole: `PUT /admin/policy` replaces the target with the package it carries, and the leader compares the target with the current revision option by option through each option's declared effect, writes it as the next revision of the deployment's persistent state, executes it and makes it current once the deployment converged (`docs/configuration.md`, Revisions). A start is the same apply from nothing. Writers are the operator, an external system (the Dynamo sidecar's planner decisions, writer `dynamo`, `docs/configuration.md`, `dynamo_config`) and the deployment's programs; no option has an owner, the last write wins, and every revision records its writer. A writer that changes some options reads the current package with `GET /admin/policy`, changes it and puts it back with `If-Match` set to the `ETag` it read, so a change another writer made meanwhile is refused (`412`) rather than overwritten:

```bash
curl --unix-socket "$admin" -D headers.txt -o current.tar http://admin/admin/policy
mkdir next && tar -xf current.tar -C next
# edit next/config.toml
tar -cf next.tar -C next .
curl --unix-socket "$admin" -X PUT -H "If-Match: $(sed -n 's/^etag: //Ip' headers.txt | tr -d '\r')" \
  --data-binary @next.tar http://admin/admin/policy
```

To undo a change that converged, apply the package of the revision before it (`GET /admin/policy?revision=N`) as the next change.

The package's programs write through the same apply (`docs/configuration.md`, Programs). A control program's output is a change whose revision names the program as its `writer`: the options it changed of the revision it read take its values, the rest keep those of the revision that serves when it is applied, and an output a start would refuse writes no revision. A `PUT` replaces the running programs: a program whose `source`, `args` and module are unchanged keeps its instance, and any other gets a new one, restored from the old one's saved state when the arguments are the same and the state decodes. What a program logs, an output refused, a route the leader refused and a program that ended are `log` events of `/admin/query` with the program's name as their `writer`, and the outcome of each write is its revision's `revision` event:

```sql
SELECT time, labels, fields FROM events WHERE kind = 'log' AND labels['writer'] = 'chunk' ORDER BY time DESC LIMIT 20
```

`uniserve_replica_module` states, for every replica and every module it runs (`op`, `backend`, `revision`), the git commit its Build Server revision was installed from and whether that tree was clean (`commit`, `clean` labels; a policy package's own program crate has no commit): `1` for a module the replica runs, `0` once it no longer does, so `SELECT * FROM stats WHERE name = 'uniserve_replica_module' AND value = 1 AND labels['clean'] = 'false'` finds the replicas that run a revision no release holds.

## Operations

Each operation on a serving deployment is an option of its package, applied as every change is: read the current package, change the option, and put it back whole ([Policy](#policy)). The option's effect states when the change takes effect (`docs/configuration.md`, Effects), and the `PUT` answers once it did.

| Operation | Option | Effect | What a change does |
| --- | --- | --- | --- |
| Hold new requests, and serve them again | `paused` (`false` unless stated) | `step` | While `true`, new requests wait in the daemon from the next request on (`uniserve_requests_held`); the requests in flight go on. `false` lets the held requests through |
| Sleep, and wake | `asleep` (`false` unless stated) | `step` | While `true`, the engines give back their KV cache and CUDA graph storage and keep their weights, from their next step boundary, and new requests wait; once `false` again, the cache and graph storage are restored, the token requests that were in flight are recomputed and the video requests continue from their stored step ([The KV cache's storage](#the-kv-caches-storage-and-the-weights)) |
| Flush the prefix cache | `flush` (a count, `0` unless stated) | `step` | Each change of the number revokes every cached prefix page at the engines' next step boundary; the requests in flight keep the pages they hold. To flush, state the next number |
| Load and unload LoRA adapters | `[adapters]` (name to directory) | `step` | An entry added loads the adapter into a free slot of the workers' adapter pool, an entry removed unloads it, from the next request on ([LoRA adapters](#lora-adapters)) |
| Redistribute the routed experts | `[moe_config.expert_order]` (module path to expert IDs in physical-slot order) | `order` | The experts' new order is prepared beside the batches and committed at one computation boundary, within the serving epoch ([Expert redistribution](#expert-redistribution)) |
| Serve other weights or another model | `model`, `model_dir`, `load_config.weights` (the model's files), with `dtype` and `quantization` | `epoch` | A new epoch's engines load the other checkpoint beside the serving ones and serve on trial ([Updates](#updates)). Files that process requests as the served ones do take over the requests in flight; files that process them otherwise (another tokenizer, chat template, generation defaults or model facts) serve with a request processor of their own from the switch on, while the serving epoch runs every request it holds to its end, none migrating |
| Profile | `[profiling_config.session]` (the session request) | `step` | While stated, the serving epoch's workers run the session from the engine's next step boundary; a change ends the running session, every worker writing its file, and starts the new one, and removing the table ends it (`docs/profiling.md`, Profiling sessions) |
| Rename the served model | `served_model_name` | `step` | From the next request on, the API serves under the new name and refuses a request naming the former one; the requests in flight under it end as they would have |
| Switch the fence probes | `profiling_config.fence_probes`, `fence_probes_off` | `step` | Every worker writes its device switch at the engine's next step boundary; the captured graphs keep their probes (`docs/profiling.md`, Fence probes) |
| Restart the daemon in place | any daemon option (`server_config`, `admin_config`, `logging_config`, ...), for example `logging_config.level` | `daemon` | A successor daemon takes the deployment over without closing a connection, and converges the rest of the change ([Hot restarts](#hot-restarts)). Putting the current package again restarts nothing |
| Release the storage when the deployment comes down | `retire` (`false` unless stated) | `step` | Read when the deployment comes down at its stop signal ([Nodes](#nodes)): `true` stops the deployment's Storage Server on the leader's node, releasing its weights and caches; `false` keeps them retained for a start of the same deployment |
| Bring the deployment down | — | — | SIGTERM or SIGINT to its `uniserve serve` process ([Nodes](#nodes)) |

A change of several operations takes them together: an engine that wakes does so before anything else of the change reaches it, and one that falls asleep does so last. A step option a replica does not take (an adapter that does not load, a session a worker refuses, an order that is no permutation) fails the change, which answers with the reason and records its revision `rolled_back`. For example, to hold new requests:

```bash
curl --unix-socket "$admin" -D headers.txt -o current.tar http://admin/admin/policy
mkdir next && tar -xf current.tar -C next
sed -i '1i paused = true' next/config.toml   # a top-level option, before the first table; current.tar states none yet
tar -cf next.tar -C next .
curl --unix-socket "$admin" -X PUT -H "If-Match: $(sed -n 's/^etag: //Ip' headers.txt | tr -d '\r')" \
  --data-binary @next.tar http://admin/admin/policy
```

## Observation

The deployment's observation store lives on its leader daemon (`crates/daemon/src/observation/`), and Apache DataFusion runs each statement over it. It has two tables:

| Table | A row | Columns |
| --- | --- | --- |
| `stats` | The value of one metric series in one time bucket | `time` (the bucket's start), `name`, `labels`, `value`, `histogram`, `revision` |
| `events` | One thing that happened | `time`, `kind`, `labels`, `fields`, `revision` |

`time` is a UTC timestamp in nanoseconds, and `CAST(time AS BIGINT)` its nanoseconds since the Unix epoch; `now()` is the daemon's clock, so a reader that waits for an event reads `SELECT CAST(now() AS BIGINT)` before it causes it and then the events after that moment. `labels` and `fields` are maps of strings to strings: `labels['replica']` reads an entry, `NULL` when it is absent, and a JSON answer writes a map as an object. A field whose value is not a string is its JSON text. `revision` is the configuration revision the row was measured under: an engine's report states the revision of the step values its scheduler last read, and what the daemon measures carries the revision it serves.

A `stats` value is a counter's increase within the bucket, a gauge's latest reading in it, or a histogram's mean observation, whose distribution (`count`, `sum`, `min`, `max` and `buckets`, each with its `lower` and `upper` bounds and `count`) is the `histogram` column, null for counters and gauges. The store keeps one-second buckets for an hour and one-minute buckets for seven days, and past both a summary per series and revision; the table reads them as one timeline without overlap, so an aggregate over it counts every write once, and the sum of a counter's values is its total since the oldest bucket the store keeps. `events` keeps the events of the last hour. Metric names follow the Prometheus conventions: the `uniserve_` prefix, seconds and bytes, counters ending in `_total`. The engine, request and HTTP metrics are written in `crates/daemon/src/observation/record.rs`, the profiling ones are listed in `docs/profiling.md`, and the gauges of the deployment's state in [Status](#status).

An event's `kind` is one of five:

| `kind` | One row | `labels` | `fields` |
| --- | --- | --- | --- |
| `request` | A request that ended | `replica`, `scheduler` | `arrival` (seconds since the Unix epoch), `outcome` (`stop`, `length`, `repetition`, `cache_capacity`, `abort`, `error`), `latency`, and for a request with usage `prompt_tokens`, `cached_tokens`, `output_tokens`, `queue`, `ttft`, `tpot` (seconds) |
| `revision` | How a revision's change ended | `writer` (`start`, `operator`, or a program's name) | The revision's record: `revision`, `time`, `writer`, `changes` (each changed option with its effect and its value before and after), `effect`, `result` (`converged`, `rolled_back`, `abandoned`), `reason`, `seconds` |
| `process` | A state an engine process of the deployment entered | `host`, `group`, `rank` | `generation` (its launch generation), `pid`, `epoch`, `state` (`starting`, `serving`, `parked`, `stopped`, `failed`), `reason` |
| `span` | A host stage a request passed through, or a kernel timed on the device | `replica`, `process` (`daemon`, `scheduler`, `worker`, `storage`), `rank` (a worker's) | `start`, `end` (nanoseconds since the Unix epoch), `request` or `batch`, `stage` or `kernel` (`docs/profiling.md`, Request timelines) |
| `log` | A log line of the daemon's state or of a program | `source` (the daemon's, [Status](#status)) or `writer` and `level` (a program's) | `message` (the daemon's line) or `text` (a program's), and what its source states |

With `Accept: text/event-stream`, `/admin/query` follows `events`: the statement reads `events` alone, and each message is its rows over the events appended since the previous message, as a JSON array (`data:`), with the identity of the last of those events (`id:`); a delta of no rows sends nothing, and the stream ends when the client closes it. It starts from the oldest event the store keeps, or after the event a reconnecting client names in `Last-Event-ID`; event identities start over with each daemon, so an identity a hot restart's predecessor issued starts the stream from the oldest event again. A statement that fails over a delta ends the stream with its error.

```bash
q() { curl -s --unix-socket "$admin" -G http://admin/admin/query --data-urlencode "q=$1"; }
# requests that ended, by outcome, since the oldest bucket the store keeps
q "SELECT labels['outcome'] AS outcome, sum(value) AS requests FROM stats
   WHERE name = 'uniserve_requests_total' GROUP BY 1 ORDER BY 1"
# mean time to first token of the requests that ended under revision 42
q "SELECT avg(CAST(fields['ttft'] AS DOUBLE)) AS ttft FROM events WHERE kind = 'request' AND revision = 42"
# the last ten revisions and how they ended
q "SELECT fields['revision'] AS revision, labels['writer'] AS writer, fields['result'] AS result,
   fields['reason'] AS reason FROM events WHERE kind = 'revision' ORDER BY time DESC LIMIT 10"
# every new update phase, as it is appended
curl -N --unix-socket "$admin" -H 'Accept: text/event-stream' -G http://admin/admin/query \
  --data-urlencode "q=SELECT time, labels['update'] AS update, fields['phase'] AS phase FROM events
  WHERE kind = 'log' AND labels['source'] = 'update'"
```

## Status

What a deployment is doing is rows of its store (`crates/daemon/src/status.rs`). Each transition is a `log` event whose `source` label names what changed, with its human line as the `message` field:

| `labels['source']` | Other labels | Fields |
| --- | --- | --- |
| `node` | — | `state` (`starting`, `serving`, `stopping`, `idle`), `deployment` (the deployment's served name), `error` (why it did not come up or down, when it failed) |
| `engine` | `replica` | A replica's engine changed its lifecycle state: `from`, `to` (`starting`, `parked`, `serving`, `draining`, `stopped`, `failed`; `holding` while an engine is being replaced; `handed_over` once a hot restart's successor took it; `closed` once none will serve), `reason` when stated |
| `update` | `update` (the update's number: the revision of the change that started it) | An update entered a phase, with its report as it stood: `phase` (`preparing`, `switching`, `trial`, `committed`, `rolled_back`, `abandoned`), `change` (its form, `generation` or `epoch`), `update`, `epoch`, `generation` (the generation its engines numbered), `rollback`, `switch_ms` (how long its switch took), `trial_s` (how long it has been on trial), `deadline_s`, `failure` (its `kind` and `reason`), `uncompared` (the operators the engines could not compare), `claim_failed`, `epoch_form` (an epoch update's `build`, serving and target `engines`, `drain_s`, `shrink`, `previous_epoch_kept`, `host_refused`, `moved_to_host_bytes`), `trial` (what the trial's thresholds read: the thresholds, the requests that ended and failed on trial, and each replica's baseline and rates), `transfers` (the serving epoch's steps against their baseline while the target prepares); every field that is not a string is its JSON text |
| `profile` | `replica`, `session` | A replica's profiling session entered a state: as it starts, at each of the quality-of-service guard's actions and as it ends, with the session as it stands (`state`, `end_reason`, the steps and bytes recorded, the step time before and during it, the guard's actions, each worker's file and its collectors' states; `docs/profiling.md`, Profiling sessions) |

What stands at a moment is a gauge the leader samples every second; the latest bucket of a gauge holds what stands now, and a series that ended (a reservation released, an epoch retired, a state left) is absent from it:

| Gauge | Labels | Value |
| --- | --- | --- |
| `uniserve_requests_held` | — | The new requests the daemon holds before an engine takes them: while `paused`, while `asleep`, or while no engine is ready |
| `uniserve_requests_in_flight` | `replica` | The requests the replica's engine has in flight |
| `uniserve_replica_state` | `replica`, `state` | `1` for the lifecycle state the replica's engine is in (the `engine` events' states) |
| `uniserve_replica_epoch` | `replica` | The epoch the replica executes |
| `uniserve_replica_generation` | `replica` | The launch generation of the engine that serves, which names its `process` events by `generation`; absent while none serves |
| `uniserve_replica_standby_generation` | `replica`, `member` | The launch generation of each member of the replica's parked standby, member `0` being the one a promotion serves; absent without a standby |
| `uniserve_epoch_state` | `epoch`, `state` | `1` for each recorded epoch's state (`preparing`, `serving`, `trial`, `released`) |
| `uniserve_gpu_total_bytes` | `host`, `gpu`, `deployment` | The GPU's total storage; `gpu` is its UUID as the device reports it (`GPU-` and 32 hexadecimal digits in groups of 8, 4, 4, 4 and 12) |
| `uniserve_gpu_quota_bytes` | `host`, `gpu`, `deployment` | The deployment's quota limit on the GPU |
| `uniserve_gpu_reserved_bytes` | `host`, `gpu`, `deployment`, `item`, `scope`, `epochs` | The bytes the quota reserves for one item (the weights, a KV cache segment, a process, the Transfer Server's staging, ...), of one scope and set of epochs (`epochs` comma-joined, empty for none) |
| `uniserve_host_available_bytes`, `uniserve_host_reserve_bytes`, `uniserve_host_unallocated_bytes` | `host` | The host storage the node's Storage Server reads: what is available, the reserve it keeps, and what no deployment holds |

Beside them, `uniserve_replica_revision` states the revision each replica serves, and `uniserve_replica_module` the modules it runs ([Policy](#policy)). Each engine process's states are its `process` events, and each change's outcome its `revision` event. For example:

```sql
-- where the node's deployment is in its life
SELECT time, fields['state'] AS state, fields['deployment'] AS deployment, fields['error'] AS error
FROM events WHERE kind = 'log' AND labels['source'] = 'node' ORDER BY time DESC LIMIT 1;

-- each replica's engine now
SELECT labels['replica'] AS replica, labels['state'] AS state FROM stats
WHERE name = 'uniserve_replica_state'
  AND time = (SELECT max(time) FROM stats WHERE name = 'uniserve_replica_state');

-- the phases of update 42, the update revision 42 started
SELECT time, fields['phase'] AS phase, fields['failure'] AS failure FROM events
WHERE kind = 'log' AND labels['source'] = 'update' AND labels['update'] = '42' ORDER BY time;

-- each GPU's quota and what it reserves now
SELECT name, labels['host'] AS host, labels['gpu'] AS gpu, labels['item'] AS item, value FROM stats
WHERE name IN ('uniserve_gpu_quota_bytes', 'uniserve_gpu_reserved_bytes')
  AND time = (SELECT max(time) FROM stats WHERE name = 'uniserve_gpu_quota_bytes')
ORDER BY host, gpu, name;

-- the latest state of every engine process
SELECT labels['host'] AS host, labels['group'] AS "group", labels['rank'] AS rank,
       last_value(fields['state'] ORDER BY time) AS state,
       last_value(fields['generation'] ORDER BY time) AS generation
FROM events WHERE kind = 'process' GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;
```

## Updates

An update moves a deployment to another set of modules while it serves, as a trial that commits by itself or rolls back. A deployment runs the package revisions its epoch names; installing a package at the Build Server selects nothing, and an apply (`PUT /admin/policy`) is what moves them. The daemon fixes the target's module set once, when the package is applied, and records it in the revision's `lock.toml`: it asks the Build Server's `cover` for the revision of the engine package, the scheduling policy and every kernel package, builds every module on every host the target runs on, and compares the fixed set with what the serving epoch runs. A change then does the least it needs:

- **Nothing an engine executes** changed: options of the `step` effect take effect at each scheduler's next step and at the next turn of every main process's control loop, with no process started (the queue depths, the workers' bounds, report period and copy budget, the NVTX ranges, the prefix cache and host tier switched off, a lower `mem_fraction_static`; [`docs/configuration.md`](configuration.md), Options), the operations a package states (`paused`, `asleep`, `flush`, `[adapters]`, `[profiling_config.session]`, `served_model_name`, [Operations](#operations)) and the fence probes' switch (`profiling_config.fence_probes`, `fence_probes_off`) at the engines' next step, and the experts' order (`order`) at one computation boundary ([Expert redistribution](#expert-redistribution)); a target equal to the current revision changes nothing.
- **The daemon's own options** changed (the `daemon` effect: `server_config`, `admin_config`, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `migration_config`, `mm_processor_kwargs`, `build_config`, `update_config`): the daemon restarts itself in place (below), and its successor converges the rest of the change and records how it ended; the `PUT` answers `202` with the revision `converging`.
- **Kernel or policy packages** changed, the policy's parameters included (the module selections, `speculative_config.expected_speedup`, `refill_token_cost`, a newly installed revision at an unchanged configuration), or an option the graphs are captured with (`profiling_config.kernel_instance`, `fence_modules`, `moe_config.microbatches`, the graph options `cuda_graph_config`, `max_logprobs`, `speculative_config.num_draft_tokens` and `profiling_config.graph_pc_sampling`): an update in its **generation** form, inside the serving engines, which capture the buckets it changes in the background and switch bucket by bucket; a generation of other graph options captures every bucket of the shapes they give the runners, beside the serving graphs, and switches to them whole at one batch boundary with the schedulers' limits (a generation of other drafts loads the model again for them beside the serving weights, and a model that keeps a recurrent state lays it out for them beside the serving one, every running request's state moving into it at the switch and back at a rollback), the API admitting requests within the lower `max_logprobs` until it commits; the step and order options of the same change take effect in place at once, since a generation includes no step. A validation of such a change (a control program's `validate`) states what the generation takes of each GPU beside the serving graphs and the KV pages each cache demotes to host memory and gives back while both generations' graphs are held.
- **The engine package, the processing program, the build configuration or the checkpoint** changed (`worker_config.engine`, `worker_config.engine_revision`, `worker_config.processing`, `worker_config.processing_revision`, the parallel shape and block ownership, `hosts`, `dtype` or `quantization`, the KV layout, the graph buckets, the slot count, the model's files): an update in its **epoch** form, target engines started beside the serving ones.

A change of the model's files, `dtype`, quantization, load format or weight source loads the other keys from the files beside the serving epoch's; a change of the parallel configuration, the devices or the hosts spreads the weights differently, and the target's engines receive them from the serving epoch's retained chunks rather than reading the checkpoint where an epoch already holds them. Model files that process requests otherwise than the serving ones (another tokenizer, chat template, generation defaults or model facts) are an epoch change too. The target is bound to a request processor of its own once its engines joined, and a processor that does not bind ends the update before its switch. From the switch on, new requests are processed, and their outputs decoded, by the target's processor; every request keeps the processor it arrived with to its end. The serving epoch's engines drain completely (`Drain` with `complete`): no request migrates, the queued ones are admitted in their turn and every one runs there to its end, whatever `update_config.drain_s` states, and the trial begins once they ended. A rollback returns new requests to the previous processor, and the targets drain completely the same way.

### One update, two forms

An update has one phase machine in the daemon (`crates/daemon/src/updates/update.rs`), whatever it moves. Every phase ends on acknowledgements the engines make, never on an assumption about their progress.

| Phase | Meaning | Ends when |
| --- | --- | --- |
| `preparing` | The new is made ready beside the old; serving is untouched | Every engine acknowledged it is ready, or one failed: the update is `abandoned` and nothing changed |
| `switching` | Service moves at a boundary: to the new, or back to the kept side when the update rolls back (`"rollback": true`) | Every engine acknowledged the switch |
| `trial` | The new serves and the old is kept | It lasted `update_config.trial` and commits, or a fault or a threshold rolls it back |
| `committed`, `rolled_back` | The kept side is released | — |

| | Generation | Epoch |
| --- | --- | --- |
| Preparing | `Prepare` to each serving engine: it resolves the new modules, instantiates the policy, hands the buckets whose kernels changed to each worker's capture thread, which captures them again beside the graphs that serve, and shadows each changed kernel on a paired forward. `Prepared` acknowledges; `PrepareFailed` abandons | Every node's daemon starts the target's main processes for its host, of every replica the target's configuration places (each world's scheduler node and its peers), each from a launch file the leader made that states the epoch's whole module set, the engine it succeeds and its own launch generation; every node then claims the target epoch's storage. Each engine opens its session with its host's buffer pool, maps the weights it shares, resolves its modules, captures its graphs and parks. Every engine's `Parked` acknowledges |
| Switching | `Switch` to each serving engine: the policy changes at one batch boundary inside the process, then each bucket's graph as soon as every rank captured it, then the kernels whole. `Switched` acknowledges once the last bucket switched, so the trial counts from there | Both epochs step. `Promote` to every target engine, which opens admission and acknowledges with `Serving`; from the first `Serving` the daemon routes every new request to the target, and the serving engines go on with what they hold. Once every target serves, `Drain` to every serving engine with the deadline `update_config.drain_s` from then, and with `shrink` to each whose layout no target replica has: a draining engine admits nothing and steps its running requests until each ends by itself, and at the deadline ends the rest as migratable (a token request with its blocks committed under their keys, a video request at its next denoising step boundary with its trajectory saved), which the daemon resubmits to the target; with `shrink` it gives its device memory back as its requests end and the target grows into it. Every serving engine's `Drained` ends the switch |
| Kept during the trial | The previous generation, inside the engine | The previous epoch, as `update_config.previous_epoch` states: `parked` (its engines, drained and alive), `weights` or `host` (its engines stopped, its weights retained on the GPUs or in host storage) |
| Rollback | `Rollback` to each engine: every bucket returns to its kept graph and the kept policy serves, at a batch boundary. `RolledBack` acknowledges | The switch the other way: the previous epoch's parked engines are promoted again, or started again at the next launch generation on the weights they kept, and new requests return to them from the first `Serving`; then `Drain` to every target with the same deadline. A target that failed, or one never promoted, is stopped instead of drained |
| Commit | The epoch's record keeps the new modules; `Commit` tells each engine to release the previous generation's graphs and kernels after its last batch, and the KV cache grows back into what it gave the update | The target's record becomes `serving`; the previous epoch's engines are stopped and its storage is retired by a claim of the target's epoch |

A trial ends by itself. It commits once it lasted `update_config.trial` (30 seconds unless stated) with nothing rolling it back, and it rolls back on a process-fatal fault, a stalled job, non-finite logits or an engine's exit, or on a threshold the configuration sets (`update_config.rollback`: the failure rate of the requests that ended on trial, the step-time and throughput regressions over a window against the steps served before the switch). A commit records its decision, the phase and the epoch's record, before it releases anything, so an engine lost while the kept side is released is replaced by one of the committed modules. A rollback marks the target unavailable with its reason: applying the same build configuration and module set again needs `force`, and a revision installed later is another target. An update that was abandoned marks nothing.

One update is in flight at a time, and changes converge one after another. The `PUT` that started an update answers once the update committed, with the revision converged, or once it was abandoned or rolled back, with the update's failure as the reason and the revision recorded `rolled_back`; every phase the update enters is a `log` event of source `update` labelled by its number, the revision of the change that started it ([Status](#status)). `update_config.in_flight` states how the requests an epoch's switch migrates continue (`keep` or `recompute`). An update does not cross a daemon hot restart: the restart waits until it ends.

### Epochs, generations and launch generations

An **epoch** numbers one engine build with its build configuration, and keys its storage at the Storage Server. A **generation** numbers the set of kernel and policy modules an engine executes; the engine assigns it and states it in its `Prepared`, `Parked` and `Serving` reports. A **launch generation** identifies one process of a worker group and rank: a serving engine, its standby, an update's target, a relaunch. The daemon takes launch generations from one counter per group and rank, above every live one, and addresses every command by it.

The daemon keeps one record per epoch: the build configuration, the module set fixed when the configuration was applied, the modules a generation's trial keeps, the generation its engines numbered, and a status (`preparing`, `serving`, `trial`, `released`). The module set is part of every launch file made from the epoch, so a relaunch and a standby run exactly what their epoch runs.

An epoch update moves the replicas the change touches, each to a new epoch, and the others serve on in the epochs they serve, untouched: a replica is touched when its launch's build part differs from its target's (its parallel configuration, its model and precision, its cache options and whether it speculates; `EngineConfig::build_part`), or when it runs another engine package than the target's module set; a change of the number of replicas, and one that touches none, moves every replica. Each replica serves the epoch that last moved it, so a deployment runs several epochs at once, each with its own record (`epochs`), and the target's number lies above every recorded one. The update drains and stops only the moved replicas' engines; its commit retires a previous epoch on every node once no replica executes it, and otherwise ends that epoch's storage of the moved replicas' scopes alone (`Request::Unclaim`) while it keeps the other replicas'; a rollback serves each moved replica's epoch again, and an epoch that serves other replicas on a host keeps its storage there whatever `previous_epoch` states. When every replica moves, the two sides need not have the same number of nodes, main processes, schedulers or ranks: the target's shape is its configuration's, and nothing maps the engines of one epoch to the other's. Target replica `i` serves under the deployment's replica `i`; a serving replica past the target's last hands the requests it migrates to a target replica, and a rollback does the same the other way. A serving replica and a target replica have different layouts when they differ in their parallel configuration (degrees, forms, worker groups, devices, hosts), their slot count (`max_running_requests`) or their KV layout (`kv_cache_config.block_size`, the cache's precision); the cache's size, its tiers and the graph buckets are no layout, and neither is the number of replicas, so a replica that keeps its place when replicas are added or removed keeps its layout. A serving replica whose layout no target replica has drains with `shrink`, and the update's `epoch_form` field states `shrink` when any does. A migrated request carries its generated tokens and seed: on a target of the same layout and numerics it finds its committed blocks by their keys and pays one admission and the copy of its partial last block; on one of another layout or other numerics its keys reach nothing and it computes its state again, as it does with `update_config.in_flight = "recompute"` (`Promote.recompute`). Nothing of the cache is handed over.

### Startup

Starting is not an update. The daemon fixes the epoch's module set at the Build Server and has it built at the Build Server of every host the epoch runs on before any engine starts, and every engine starts from a launch file that states it: the engine resolves every module its profile runs name, captures its graphs and serves (`Serving`), or parks when its launch names the engine it succeeds (`Parked`).

### The standby

With `worker_config.standby`, the daemon keeps a parked engine of the serving epoch beside every serving engine, at the next launch generation and with its own CUDA contexts: a sticky error of the serving process cannot touch it. A standby is started as an epoch update's target is, from a launch file that states the epoch's module set and the engine it succeeds, and parks by itself with its graphs captured. A process-fatal fault promotes the whole failure domain (`Promote` on each standby's process link, every promotion issued before any is awaited), and each node then starts a new standby. Where a member of the domain has no parked standby, the domain is relaunched instead and finds its weights retained. A standby exists only while its epoch serves; an epoch that prepares or is on trial keeps none, and a generation's commit replaces the standby with one of the committed modules. `worker_config.standby_storage` states whether a standby keeps its graph pools on the device (`resident`) or gives them back until its promotion (`suspended`).

## Listeners

The daemon serves the admin API apart from the client API, on one Unix socket, and access is its file permissions. Every daemon owns an instance directory, `daemon.XXXXXX` inside UniServe's directory of the user's runtime directory (`$XDG_RUNTIME_DIR/uniserve`, mode `0700`), which it creates when it starts and removes when it ends; its socket lies there, and a caller reads its path from the daemon's readiness records. A daemon run without `XDG_RUNTIME_DIR` is refused.

| Listener | Socket | Mode | Serves |
| --- | --- | --- | --- |
| Client API | `admin_config.host`, `port` or `uds`; port `0`, the default, picks a free port | — | The OpenAI API, `/health`, `/version`; no `/admin` route |
| Admin API | `admin.sock` in the daemon's instance directory | `0600` | `GET` and `PUT /admin/policy`, `GET` and `POST /admin/query` |

The daemon binds all of its listeners when it starts, before it loads anything: the client listener, the admin socket and, on the leader of a deployment of several nodes, the join listener (`admin_config.join` on every interface). It reports what it bound in its readiness record, one JSON line written to the descriptor its caller passes with `--ready-fd FD` (as systemd's `sd_notify` reports a service's state): `{"state": "listening", ...}` once the listeners are bound, and `{"state": "serving", ...}` once it serves, after which the descriptor closes; a daemon that ends before it serves closes the descriptor without the second line. A record states the daemon's `pid`, its `instance` directory and its `endpoints`: `client`, `admin`, `join`, and, once it serves, the host Storage Server's `storage` socket and `peer` TCP endpoint (each `null` when absent; a Unix socket is written `unix:PATH`, a TCP endpoint `HOST:PORT`). Connections that arrive before the daemon serves wait in the listeners' backlog. A deployment's other nodes join the leader at the first host of the package's `hosts` and its `admin_config.join` port, which the record states as `join` (`docs/configuration.md`, Nodes).

A hot restart's successor goes on in its predecessor's instance directory, binds the admin socket over its predecessor's, which finishes the requests it accepted, and owns the directory once the handover completed. An example, reading the socket from the record:

```bash
uniserve serve qwen3 --ready-fd 3 3>ready.jsonl >serve.log &   # qwen3/config.toml states model = "Qwen/Qwen3-30B-A3B"
# once ready.jsonl holds the line whose state is "serving":
admin=$(jq -r 'select(.state == "serving") | .endpoints.admin | ltrimstr("unix:")' ready.jsonl)
curl --unix-socket "$admin" -G http://admin/admin/query \
  --data-urlencode "q=SELECT name, labels, value FROM stats WHERE name = 'uniserve_replica_state'
  AND time = (SELECT max(time) FROM stats WHERE name = 'uniserve_replica_state')"
curl --unix-socket "$admin" -X PUT --data-binary @next.tar http://admin/admin/policy   # next.tar: tar -cf next.tar -C next .
```


## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`crates/daemon/src/restart.rs`), as Envoy's hot restart does, when a change of the deployment's package changes one of the daemon's own options (the `daemon` effect, [Operations](#operations)). It starts its successor (`uniserve serve --predecessor`) from the base executable the package names (`executable`, [configuration](configuration.md#top-level)), or from its own image when the package names none, with a socket pair between them, and sends it its options, the window of versions of the engine interface it speaks, the versions of the engine interface its connections agreed on (its engines' links, their workers', its members' and its own clients') and the Storage Server protocol version of its claim. The successor may be of another build: it takes the deployment over when its windows hold every one of those versions ([Interface versions](architecture.md#interface-versions)) and agrees with the daemon on the newest version both speak, in which the daemon writes what it hands over. The options also carry the records of every replica the daemon will hand over, the arguments its engine serves with and its configuration, which the successor reads and resolves before it answers: their configuration sections refuse a field they do not know, so a record of another build that the successor cannot read ends the restart here rather than after the handover. A successor whose window misses one of those versions gives up and names it, as does one that cannot read a record or the options themselves and one the host's Storage Server does not serve (the server refuses the successor's hello with a typed version refusal naming both windows), before anything is handed over: the change is answered with the successor's reason and the daemon serves on as it was. A deployment moves to another build in place this way: a change of `executable` restarts the daemon into it while the engines serve on in the version they agreed on, and a later epoch update to an engine revision of that build starts engines that agree with the successor on the newest version both speak. The successor then loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. The successor takes each response in flight over at the position the daemon's response consumed (`Takeover`): the engine replays the events after it to the successor and counts the position as consumed, so the request's event window is the same whether the daemon's own last report of that position reaches the engine before the takeover or after it, or never. A request with stop strings goes on the same way: the handoff states the tokens the daemon received and acknowledged as completing no stop string, the successor states that acknowledgement to the engine again on its own connection, and its decoder acknowledges the tokens after it as the daemon's did, so the engine never holds the request for an acknowledgement that only the daemon's connection carried. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. With its deployment it ends every wait for an engine's dial on its own request socket. The engine and its workers are the same processes throughout, and serve on through the successor with their relaunches and their standby: an engine speaks the version of the engine interface its first hello agreed on for its whole life and attaches to the successor offering that version alone, which the successor's window holds; the successor refuses an engine whose window shares no version with its own at its hello with a typed refusal naming both windows. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits at the descriptor the last option of its command line names (`--lifeline FD`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A deployment's Storage Server restarts in place too (`uniserve storage-server restart --deployment NAME`, `crates/storage-server/src/restart.rs`), into the build of the `uniserve` that runs the command: the command passes its own executable to the server, which starts its successor from it. The deployment's daemon restarts it the same way, from its own build, when a change of `storage_config` or of the Mooncake connector states a setting the running server cannot take, and the successor serves with the new settings (`docs/configuration.md`, `storage_config`). Once the successor speaks the server's versions and no request, shoot-down, connector task, transfer or exposure to another host is in flight, the server stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's storage and every queue pair's memfd and doorbells, with its state and its buffer pools; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. A server speaks a window of versions of its protocol and one of the buffer pool's runtime interface (`storage::protocol::VERSIONS`, `storage::runtime::VERSIONS`), agreeing with each client at its hello and with each session at its `Open` on the newest version both speak and refusing a client or an `Open` whose window shares none, naming both windows, and reads the images of its buffer pools in a window of formats, writing its newest: before the handover the server states the protocol version each connection agreed on, the runtime version each session agreed on and the format of the image it writes, and a successor of another build takes it over when its windows hold every one of them. A successor that does not speak one gives the restart up, naming it, and the server goes on as it was; so does the server when a connection or a session agreed on a version outside the successor's windows after it answered. A restart into a new build therefore succeeds within the windows: `uniserve storage-server restart` run by that build's `uniserve` starts the successor from it. Another host's READs of this host's storage are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

A change that both restarts the daemon and needs an update has the daemon restart first and its successor run the update ([Updates](#updates)). The successor's observation store starts empty: what the predecessor recorded leaves with it, and the successor's event identities start over.

## The KV cache's storage and the weights

A device KV cache is split along its units into segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/engine/src/memory/cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses. A segment is the fewest units whose part of a layer's plane is whole allocation granules (32 units of 64 KiB planes on a GPU of 2 MiB granules, `crates/engine/src/memory/cache/segments.rs`), so the cache holds what its GPU's quota leaves it to within one granule of each of its allocations, when the engine starts, grows, wakes or gives memory back.

- A GPU belongs to one deployment, which its daemon claimed in the node's GPU registration file before an engine started on it (`docs/configuration.md`, A deployment's servers). Every GPU has a quota for the deployment, kept by the deployment's Storage Server on the node: the limit, `⌊total × mem_fraction_static⌋` of the whole GPU, the fraction being the shares of the deployment's ranks placed on it when its worker groups state their own (`docs/configuration.md`, the deployment file), and a reservation for every item the deployment's epochs and its Storage Server's Transfer Server hold there. The server reserves what it retains, each storage once however many epochs map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent buffers). The processes reserve what it cannot see: each warm worker its graph pool and its process storage (its CUDA context, PyTorch's and Rust's allocations, communicator buffers, the product storage it has yet to make resident, and while a `range_metrics` profiling session runs, its range profiler pass), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, copy thread or exposure to another host uses it any more. A quota without room for the context refuses it, and the transfer task that needed the GPU fails, naming the quota. The server refuses a reservation or a new device storage that would take a GPU past its quota, so a quota never exceeds it; a worker that does not fit its quota fails its startup with every entry of the quota. A reservation ends with the process that made it when the process ends in order; a lost worker's reservations stay reserved for the process that replaces it (its relaunch), until that process reserves them again or the epoch is retired; an epoch's storages end with the epoch, and the segments a successor maps become its own on the quota when the previous epoch is retired. Two epochs therefore size their caches against one quota: a worker's grant is the quota less everything the quota reserves beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the storage the fraction leaves, and reserve once promoted in place of the rank they stand by for; the processes of one scope and epoch count as their largest reservation.
- An epoch switch compares layouts replica by replica: a target replica of a serving replica's layout shares that replica's device regions; a serving replica whose layout no target replica has shrinks its regions as it drains, and the target replicas of layouts of their own grow theirs from the quota as that memory frees. Adding or removing data-parallel replicas therefore moves no memory of the replicas it leaves in place ([Epochs](architecture.md#epochs)). The daemon's own in-place changes (the scheduling limits) leave the cache alone.
- A package that states `asleep = true` holds new requests, recomputes the token requests in flight as a shrink does, preempts the video requests in flight at the denoising step boundary their calls in flight end at, with their trajectories stored in the host latent pools, which continue from that step once the deployment wakes, and lets a request whose denoising steps are all scheduled finish (`docs/architecture.md`, Video preemption); the workers then give back every segment and suspend their CUDA graph storage (`WeightBinding::sleep`, `crates/engine/src/process/binding.rs`), which the collectives captured in the graphs read and write without NCCL buffer registration, so that a wake that maps new storage at the same addresses leaves no peer mapping the old. The next package that states `asleep = false` creates the cache again, restores the graph storage and lets the held requests through.

- KV cache pages cross hosts through the hosts' Storage Servers and Mooncake Store. A decode replica imports each handed-off request's pages from its prefill replica through the Storage Servers of the two hosts (`architecture.md`, Transfers), and the host KV cache of every node reaches the others through Mooncake Store (`kv_cache_config.mooncake`). A replica that lends or imports across hosts runs its Storage Server with a TCP endpoint (`storage_config.tcp`, port `0` allowed; the server's readiness record and the daemon's state it as `peer`) and the NIXL package (`docs/nixl.md`); `uniserve storage-server list` shows each link the Transfer Server measured, another host's as `<endpoint> host`. The TCP endpoint is not authenticated: any process that reaches it can borrow a lend and read the host tensors of every deployment the host serves, so hosts that serve each other run on an isolated network.

## Expert redistribution

`moe_config.expert_order` states the order of the routed experts' weights in each routed expert layer's physical slots, preserving the number of physical slots on each rank: a table from a layer's module path to the layer's logical expert IDs in global physical-slot order, a complete permutation of them. Module paths are the routed expert layers the served model family states for its checkpoint (`nn::family::TextCheckpoint::expert_layers`). A layer the table does not name keeps the checkpoint's order. A change of the table takes the `order` effect: it redistributes the experts within the serving epoch, on every replica in turn, and an invalid permutation or an unknown layer is refused before copying starts. An epoch starts with the order its package states.

```toml
[moe_config.expert_order]
"layers.0.mlp.experts" = [3, 0, 1, 2, 7, 4, 5, 6]
```

A module path is `layers.N.mlp.experts`. Every rank's model is loaded with a logical-to-physical table for each of its routed layers, and the router's top-k writes each route's physical slot through it, in the launch that selects the experts: selecting over logical ids keeps which experts a token picks, and the order of equal scores, independent of where the experts lie, and a deployment that never redistributes pays no launch for it.

The serving scheduler reserves the additional storage of the ranks' prepared allocations on each GPU, releasing available KV tail segments as needed while requests continue. Each rank then publishes the stacks of the new order at the Storage Server, under the keys a load of that order asks for, copying the experts it holds over the device's own memory on a stream beside the batches, and reading an expert it does not hold from the checkpoint. At a common computation boundary the completed allocations and the new table are mapped at the addresses the graphs captured. The epoch, CUDA Graph addresses, request state and numerical weights remain the same. Once the redistribution commits, the cache can grow into the released storage, and the change's revision converges.

Distributed weight data parallelism (DWDP) prepares the resident shards, peer mappings and prefetch buffers of the requested distribution in the background; admission includes these allocations. Commit replaces the backing of the existing composite weight addresses and the prefetch copies together. A block that streams dense projections from host storage keeps those host allocations while its resident experts are redistributed.

The committed distribution is included in worker recovery launches and daemon handoff. A failure during preparation releases incoming copies and leaves the active distribution intact. A failure during publication triggers the existing engine recovery path with the committed distribution; an update on trial rolls back as its trial states. A redistribution that does not commit leaves the change's revision `rolled_back` with the reason. A redistribution that changes rank shapes is a change of the deployment's package (`PUT /admin/policy`).

## LoRA adapters

The `[adapters]` table of a package states the LoRA adapters the workers hold, each under the name a request states as its `model`, with its directory: a PEFT adapter directory whose tensors are its `adapter_model.safetensors`. A change of the table takes effect from the next request on. An adapter it adds is assigned the lowest free slot, and every rank publishes its tensors at the Storage Server, through the path every weight takes, and maps them read-only under the slot; its name serves once every replica loaded it, `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. An adapter the table no longer states, or states with another directory, leaves the registry at once, so requests naming it are refused, and every rank releases the slot's tensors. An engine that replaces another, after an epoch change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry. An adapter named as the served model is refused as a start refuses it.

```toml
[adapters]
tuned = "/models/adapters/tuned"
```

What computes with an adapter of a slot is a kernel package, and this repository holds none, so a request that names a loaded adapter as its `model` is refused rather than answered by the base model. The kernel package that provides it reads a slot's tensors and each token's slot. An adapter that a deployment serves for every request is fused into its weights at load instead, with `lora` or `lora_dir` ([Configuration](configuration.md)), and needs no slot.

## Nodes

Every leader daemon is a node, which serves through one path whatever it serves. Its listeners are bound when it starts and served for its whole life; its client API is the serving deployment's, and while none serves it answers `503` (`no_deployment`). The admin API is the node's own: `/admin/query` and `GET /admin/policy` answer while the deployment comes up, serves and comes down, and a `PUT /admin/policy` answers `503` until it serves. Where the deployment is in its life is its `node` events: `starting`, `serving`, `stopping`, and `idle` once it came down, with the error when it failed to come up or down ([Status](#status)). `uniserve serve PACKAGE` starts a node for the package's deployment, which it brings up at once and lives as long as. A package without a model is refused. A deployment of several nodes binds the leader's join listener as it starts, its endpoint the `join` of the readiness record; the leader serves once every node of `hosts` joined it. A node hands itself over in a hot restart whichever way it was started.

SIGTERM or SIGINT (Ctrl-C) to the `uniserve serve` process brings the deployment down: the node stops accepting connections, lets the requests in flight, streamed responses included, finish within `server_config.shutdown_timeout`, shuts its engines down and stops its daemon, and, when the serving package states `retire = true`, stops the deployment's Storage Server on the leader's node, which releases its weights and caches; without it the storage stays retained, so a start of the same deployment maps the weights it finds instead of loading them.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else. A node is named by its admin socket (`--node unix:PATH`, as the daemon's readiness record states it), or by the URL that socket is forwarded at from another host: a node never calls it or waits for it, so the manager attaches by reading a node's store and detaches by stopping.

`ADMIN` below is a daemon's admin socket as its readiness record states it (`endpoints.admin`, [Listeners](#listeners)).

```bash
uniserve-manager --node "$ADMIN" --node http://127.0.0.1:9000 status
uniserve-manager --node "$ADMIN" watch                # Ctrl-C detaches
uniserve-manager --node "$ADMIN" watch --from-start   # from the oldest event each node keeps
uniserve-manager --node "$ADMIN_A" --node "$ADMIN_B" apply qwen3   # the package directory qwen3/
uniserve-manager --node "$ADMIN" apply --force qwen3               # a target a rollback marked unavailable
```

`status` prints one line per node: its latest `node` event's state and deployment, with the error of one that failed, each replica's engine state, and the requests in flight and held, as the leader last sampled them (`idle` for a node that recorded no `node` event). `watch` follows each node's `events` through `/admin/query`'s event stream and prints each event as JSON with its node until interrupted, from now or, with `--from-start`, from the oldest event the node keeps. `apply` sends the package in a directory, its `config.toml` and `programs/` as one tar archive, to each node's `PUT /admin/policy` in the order given, prints each node's revision record, and stops at the first node whose change does not converge, naming it, the nodes after it left untouched. Every other operation is an option of the package the manager applies ([Operations](#operations)), and a node comes down at its process's stop signal. Each `--node` is the leader of one deployment, and a GPU belongs to one deployment, so the changes of several deployments never contend for a device. A node the manager cannot reach is asked again every `--retry-interval` seconds (5 unless stated).
