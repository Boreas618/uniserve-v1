# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on its HTTP address, with the same API key as the OpenAI API. Everything a deployment can do while it serves goes through it: `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of it among others. The designs are `specs/live-updates.md` and, for configuration changes and worlds, `specs/online-operations.md`.

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/status` | The deployment (name, model, engine state, paused, asleep, requests in flight, the engine's executable), the running and the last operation, and the next event's sequence number |
| `GET /admin/events?after=N&wait=S` | The events after sequence number `N`, waiting up to `S` seconds (at most 60) for one; `next` is the number to read after next, and `gap` says that events after `N` already left the log of 1024 |
| `GET /admin/config` | The configuration as TOML (as `--config` reads it) and its digest; the two slots' worlds, each with its state (`executing`, `preparing`, `parked`, `weights`, `failed` or `closed`); the change in progress and its phase, with a note when its successor's transfers start without a baseline of a scheduler's steps (`update_config.transfer_slowdown`); the trial: its world, how long it has served, the promotion's pause, the previous world's step time and throughput before the promotion and the trial's since; the configurations a rollback marked unavailable; what the last change, commit or rollback reported; and the memory ledgers (`ledgers`): for each host of the deployment, every GPU's ledger with its total, quota and each entry's item, scope, worlds, KV cache segment and bytes, and what the host admits of new host memory (below) |
| `PUT /admin/config` | A configuration change: `{"config": TOML, "set": ["PATH=VALUE", ...], "in_flight": "keep", "dry_run": false, "force": false, "wait": true}`, as `uniserve serve --config FILE --set PATH=VALUE` states a configuration; without `config` the target is the current configuration with the assignments. The change does the least the target needs (below). `dry_run` answers with the plan and changes nothing; the plan of a new world includes `memory`, whether it fits beside the serving world on every GPU and host (below); `force` applies a configuration a rollback marked unavailable |
| `POST /admin/config/commit` | Ends the trial of the world that executes: the previous world is released (below) |
| `POST /admin/config/rollback` | `{"reason": TEXT}`: rolls the world on trial back to the previous world, and marks its configuration unavailable with the reason |
| `POST /admin/pause_generation` | New requests wait; those in flight go on (SGLang's endpoint of that name) |
| `POST /admin/continue_generation` | New requests are served again |
| `POST /admin/flush_cache` | The engine revokes every cached prefix page; requests in flight keep theirs |
| `POST /admin/restart` | A hot restart of the daemon: `{"executable": PATH, "wait": true}`. A successor daemon of that build (this daemon's own when unset) takes the deployment over while this one finishes the requests it took (below); answers with the successor's process id once it serves |
| `POST /admin/shutdown` | Brings the deployment down as SIGTERM does, finishing what is in flight within `server_config.shutdown_timeout`, and releases its weights and caches at the host's Storage Server unless `{"retire": false}` |
| `POST /admin/update_weights` | `{"model_path": PATH, "in_flight": "keep"}`: the engine rewrites its weights in place from another checkpoint of the served model, a local directory, a Hugging Face repository or a plugin's weight source `scheme://...` (`docs/plugins.md`) (SGLang's `update_weights_from_disk`; below); `in_flight` is `keep` (the default), `recompute` or `abort` |
| `POST /admin/sleep`, `/admin/wake_up` | The engine gives back its KV cache and CUDA graph memory and keeps its weights, and restores both (vLLM's endpoints of those names; below) |
| `POST /admin/load_lora_adapter`, `/admin/unload_lora_adapter` | `{"lora_name": NAME, ...}`: the workers load a LoRA adapter into a slot of a plugin's adapter pool, or unload it (vLLM's endpoints of those names; below) |
| `POST /admin/profile` | Starts a profiling session on every worker of the executing world at the engine's next step boundary: `{"collectors": [...], "steps": N, "start_step": N, "seconds": S, "stages": [...], "workers": [...], "components": [...], "output_dir": PATH, "max_slowdown": F, ...}` (`docs/profiling.md`); answers with the session, each worker's file and its collectors' states. One session runs at a time: another is refused (`400`) until it ends |
| `GET /admin/profile` | The running session, or the last that ended: its state and why it ended, the steps and bytes its workers recorded, the step time before it and during it, the quality-of-service guard's actions and each worker's file; `null` before any |
| `DELETE /admin/profile` | Ends the running session at the engine's next step boundary, every worker writing its file |
| `POST /admin/hooks/NAME` | A worker hook a plugin adds (below) |

Each write is an operation: it has an identity, runs on a task of its own, and ends `succeeded` or `failed` in the status and in the event log, whether or not the client that asked stays connected. One operation runs at a time; another is answered `409`. `"wait": false` answers at once with `202` and the operation.

## Configuration changes and worlds

A world is the processes that execute one configuration of the deployment: an engine and its workers, their communicators, CUDA graphs and the memory they created. A deployment has two slots for worlds, and one world executes. `PUT /admin/config` resolves the target configuration as a deployment's start does and answers with the change it made (`change`):

- `none`: the target is the current configuration.
- `in_place`: the scheduling options alone (`max_running_requests`, `max_num_batched_tokens`, `scheduler_config` and the refill policy of `speculative_config`), within the batch the running workers were started for (at most as many calls and tokens a step and running requests), take effect at each scheduler's next step; a change of policy reorders the waiting requests by it. `profiling_config.fence_probes` alone switches every worker's fence probes at the engine's next step boundary, the captured graphs keeping them (`docs/profiling.md`).
- `daemon`: a change of the options the daemon reads alone (`server_config`, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `readout_config`, `migration_config`, `mm_processor_kwargs` and `diffusion_generation_config`) is a hot restart of the daemon with the target configuration (below); the answer carries the successor's process id.
- `world`: anything else a world executes (the build its engine and workers run, `worker_config.executable`, the CUDA graphs, FlashInfer, speculative decoding's `speculative_config.num_draft_tokens`, the workers' other options, scheduling beyond the workers' batch) starts a new world on trial; the answer reports both worlds and the time each step took.

A change of the served model name, the hosts, the product transport, the KV cache's size or the video options is refused, since a new world maps the serving world's weights and KV cache only where their keys stay. A change of the model's files, its dtype, its quantization, its load format or its weight source keeps the deployment's model (another checkpoint must keep the tokenizer, templates, generation defaults and model facts, or the change is refused): the successor loads the weights of other keys from the files beside the serving world's, mapping the serving world's weights only where their keys stay, and its plan and report say so (`"weights": "loaded"`, `reloads`). A change of the KV cache's element type, or of the compute dtype or quantization it follows, maps none of the serving world's cache: the successor lays out its own and the requests in flight compute their state again in it (`"kv_cache": "recomputed"`), as they do under `in_flight = "recompute"` when the successor loads its weights. A change of the parallel configuration (the tensor- and data-parallel sizes, the deployment file, the device or the hosts the ranks spread across, a generation tower's device), of the experts or of the KV cache's page size is a world change whose successor holds other regions of the weights on each GPU: its workers receive their weights from the serving world (below), and it lays its KV cache out for its own heads and pages, so it maps none of the serving world's segments and the requests in flight compute their tokens again on it. A change of both the daemon's options and what a world executes (its scheduling limits included) is applied in that order, the orchestrator before what it orchestrates: a hot restart of the daemon applies the daemon's options, and its successor then applies the rest in an operation of its own, which `GET /admin/status` reports; the answer names that step (`"then": "world"`). A step that fails stops the change, and the steps before it stay. A world change takes four steps:

1. **Preparation.** The serving world withdraws from allocation the tail of its KV cache past the limit each GPU's memory ledger leaves it beside the successor (below): the quota less everything else the ledger books and what the successor adds, namely a graph pool of its own (`graph_storage_budget_bytes`, a tenth of the device) when its graph policy captures and its model can be captured (none for a successor that serves every call eagerly, as a rank that captures nothing reserves no graph share in its own capacity plan either), process memory and storages beside the cache planes as large as the serving world's, a head segment of its own, the weights it loads (as large as the serving world's), and the units the requests in flight recompute in when it maps none of the serving world's cache; it adds no weights or KV cache of the keys it maps. A change whose limit cannot hold a GPU's first segment, which always stays, is refused before anything starts, naming each item's bytes on every GPU and host. Before the tail leaves, its idle cached pages reach the host KV cache: the pool verifies the copy of each page it was offloaded under, and copies a page it no longer holds there again, so a later prompt reads them back from there (a sliding-window group's pages and pages never offloaded are computed again). The requests holding the tail run on, and once none holds it the workers give it back; `update_config.preempt_after` recomputes the ones that still hold it after that long. The successor starts in the other slot: its workers map the serving world's weights of the same keys and its KV cache segments read-only, under hardware protection, create a head segment of their own, warm up on it and capture their graphs. A worker of a position no world loaded before, such as one of another parallel configuration, receives its weights instead of reading the checkpoint: it materializes its model without reading it, plans the chunks its weights take and frees that model; the workers that load together compute one copy manifest from the chunks the serving world retains on the host's GPUs to all their chunks and verify they computed the same digest; each maps the chunks of the same key on its GPU, creates the rest, and the Transfer Server copies the manifest's spans into them at the `Background` priority while the worker binds its model and builds its executor and expert exchange; once they arrived, the chunks are retained read-only. Only the regions no world holds are read from the checkpoint. The serving world executes throughout. A successor that does not start leaves the serving world serving, which creates its tail again.
2. **Promotion.** At a step boundary new requests wait and the serving world parks: it ends every token request that resumes from its generated tokens as migratable, ends every video request as migratable at its next denoising step boundary with its trajectory stored in the host latent pools, lets the others finish, offloads the pages it reserved for the host KV cache and executes nothing more, keeping its storage and its prefix cache index. The successor copies the cache flags and scales of the units it maps, imports that index into them, and serves: every migrated request is submitted again with the tokens it generated and reuses the pages of every complete page of them; in a successor that speculates, a request whose draft cache pages the serving world did not keep verifies no drafts until a refill completes its draft cache. The pause is the parked world's last step and one resubmission, whatever the requests' lengths. A successor that computes other numerics than the serving world (another model identity, `docs/plugins.md`, so another root of its pages' prefix hashes) reads none of its pages: new requests compute their prompts, and the requests in flight continue as `in_flight` states, `keep` (the default) with the state they reached, reading only the serving world's pages and writing none, since their later pages are neither world's, or `recompute`, from their tokens, exactly. A video request continues from the step its trajectory was stored at: on a successor whose denoising computes the same, exactly as if it had not been interrupted; on one that computes other numerics, with `keep` from the stored trajectory under the successor's numerics, and with `recompute` from noise. Until its commit a successor writes only to its own segments (its head, and the tail segments it creates as each GPU's ledger has room for them, as when a previous world kept as its `weights` exits and what its processes booked becomes the successor's): a change whose requests in flight need more of them than are free (all the units they held when they recompute, a page each otherwise) is refused at the promotion with both counts, and the serving world serves on. The change reports whether the numerics changed and how the requests in flight continued.
3. **Trial.** The successor executes and creates the rest of its KV cache as memory frees. The previous world is kept as `update_config.previous_world` states (`docs/configuration.md`): `parked`, or its `weights` alone: its processes exit, which ends their graph pools' and process memory's bookings, and every node's Storage Server keeps its weights alone, releasing its other storages the successor does not map (`KeepWeights`), all of which the successor's cache grows into at once. Kept in `host` memory, the weights the successor does not map then move to host memory as well: each node's Storage Server admits host memory of their whole size under its host-memory rule, has its Transfer Server copy every device storage of them there at background priority, and releases the device storages once every copy ended (`Offload`), so the successor's cache grows into them too. A node that cannot (no Transfer Server, or more than the host admits) keeps them on its GPUs, and the trial reports the previous world kept as `weights` with the reason (`host_refused`). The weights never go to another host. A dry run's plan states each host's admission beside what the previous world's weights would take there (`previous_world_weights`). A parked previous world whose cache the successor maps none of (the successor recomputes the requests in flight: another parallel configuration or KV cache encoding, or other weights under `in_flight = "recompute"`) keeps it for a rollback alone: it evicts every segment past its first once their idle pages reached the host KV cache, as the preparation does for its tail, and the successor's cache grows into them (`evicted` in the report). The trial ends only with `POST /admin/config/commit`, and refuses another change (`409`) meanwhile. It rolls back by itself on a fault of the successor (a worker error that leaves its workers unusable, such as an illegal memory access or a worker process's exit; a stalled job; non-finite logits; its engine process's exit) and past a threshold of `update_config.rollback`. A world on trial is never repaired: a fault fails it as a whole, and its requests leave as migratable for the previous world.
4. **Commit or rollback.** A commit releases the previous world: its processes exit, the successor takes the segments it mapped read-only and retires the previous world's memory at the Storage Server, grows its KV cache into the memory freed, and from then on relaunches its worker groups on a loss and keeps their standbys. A successor whose pages are keyed otherwise hits none of the pages the previous world published: at its commit every node's host KV cache discards the pages the successor did not publish (`DiscardPages`). A rollback parks and closes the successor, resumes the previous world, which creates the segments it evicted again and reads their pages back from the host KV cache on later prompts (or starts it again on its kept weights, which it binds rather than reads: its claim retires the successor's memory first, and weights kept in host memory return to the GPUs they left before its workers start, `Restore`), retires the successor's memory and marks the configuration unavailable with the reason: applying it again needs `force`. The requests continue on the previous world after every token they delivered: none fails or repeats a token, and the previous world reads the KV cache as it left it, since the successor never wrote it.

## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`POST /admin/restart`, `crates/daemon/src/restart.rs`), as Envoy's hot restart does. It starts its successor (`uniserve serve --takeover`) with a socket pair between them. The successor loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec, the admin's log and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. The engine and its workers are the same processes throughout. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits (`UNISERVE_LIFELINE`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A host's Storage Server restarts in place too (`uniserve storage restart [--executable PATH]`, `crates/storage-server/src/restart.rs`). The server starts its successor and, once no request, shoot-down, connector task, transfer or exposure to another host is in flight, stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's memory and every page pool's memfd, with its state; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. Another host's READs of this host's memory are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

## The KV cache's memory and the weights

A device KV cache is split along its units into eight segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/worker/src/memory/prefix_cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses.

- Every GPU has a memory ledger for each deployment that uses it, kept by the host's Storage Server: the quota, `⌊total × mem_fraction_static⌋` of the whole GPU, and every item the deployment's worlds and the host's Transfer Server hold there. The server books what it retains, each storage once however many worlds map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent banks). The processes book what it cannot see: each warm worker its graph pool and its process memory (its CUDA context, PyTorch's and Rust's allocations, communicator buffers and the product storage it has yet to make resident), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, lane or exposure to another host uses it any more. A ledger without room for the context refuses it, and the transfer task that needed the GPU fails, naming the ledger. The server refuses a booking or a new device storage that would take a ledger past its quota, so a ledger never exceeds it; a worker that does not fit its quota fails its startup with every entry of the ledger. A booking ends with the process that made it; a world's storages end with the world, and the segments a successor maps become its own on the ledger when the previous world is retired. Two worlds therefore size their caches against one quota: a worker's grant is the quota less everything the ledger books beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the memory the fraction leaves, and book once promoted in place of the rank they stand by for; the processes of one scope and world count as their largest booking.
- A world change shrinks the serving world's cache by its tail (above). Each worker reports its segments with its GPU's ledger; the scheduler computes the limit the ledger leaves the serving world's cache beside the successor and withdraws the units of the segments past it from allocation (the first segment, which holds the padding and warmup units, always stays), and once no request holds a withdrawn unit the workers give the tail back. A request recomputed past `update_config.preempt_after` ends as migratable and the daemon submits it again with its generated tokens, recomputed on the units left, as vLLM's recompute preemption does. The plan of a change (`memory`, also in a dry run's answer and the change's report) gives for each GPU its host, the worker's scope and world, the quota, the serving world's weights, graph pool, process memory, exclusive storages, staging and KV cache, what the successor adds (weights it does not map, graph pool, process memory, exclusive storages, head segment, the requests in flight), the Transfer Server's items, the limit, the segments kept and every ledger entry; and for each host what it admits of new host memory, of which a successor that shares the serving world's page pools needs none. Each GPU's plan also states what each step that relieves the device frees there (`steps`, `specs/online-operations.md` §6.5): in the preparation, the tail's idle prefix pages and the rest of the tail, the warm copies a successor that recomputes the requests in flight would otherwise prepare on the device, and the serving world's graph pool; in the trial, a parked previous world's segments past its first that the successor does not map, the weights a previous world kept in host memory moves there, and what a previous world kept as its weights or in host memory releases with its processes; and how long a promotion that moves the KV cache of the requests in flight through host memory would wait for it at the host link's bandwidth the Transfer Server measured (`promotion_stall_ms`), which each GPU's ledger states. A successor's cache grows as each ledger has room: at once by what a previous world kept as its `weights` released when its processes exited, and to its whole size after the commit retired the previous world.
- `/admin/sleep` holds new requests, recomputes the token requests in flight as a shrink does, preempts the video requests in flight at their next denoising step boundary with their trajectories stored in the host latent pools (`docs/architecture.md`), which continue from that step once the deployment wakes, and lets the other requests finish; the workers then give back every segment and suspend their CUDA graph memory (`uniserve.sleep`). `/admin/wake_up` creates the cache again, restores the graph memory and lets the held requests through. A sleeping deployment refuses world changes.
- `/admin/update_weights` checks that the daemon would process the new checkpoint's requests as the served model's (the same `tokenizer.json`, tokenizer settings, generation defaults and chat template, and the same model facts) and holds new requests. Every worker loads the checkpoint into new memory as it loaded the model and copies every tensor into place once all of them match in representation, shape and element type (`uniserve.loading.rank.update_weights`). The requests in flight continue as `in_flight` says (vLLM's `keep` and `abort`, SGLang's `in_place`, `retract` and `abort`): with `keep`, once the batches in flight complete, the workers load the checkpoint beside the KV cache, giving back their CUDA graph memory for the load when the free memory alone does not hold it (and refusing the update, unchanged, when even both do not), and every request in flight continues on the new weights with the KV cache it reached; what it computes afterwards follows neither checkpoint, so it publishes no page. A video request in flight continues its trajectory on the new weights with `keep`, a trajectory of neither checkpoint. With `recompute` the engine recomputes the token requests in flight, preempts the video requests in flight as a sleep does (they continue from noise, since the new weights compute other trajectories) and lets the others finish, and with `abort` it ends every request it holds, aborted; then it puts its workers to sleep, so that the cache's memory holds the new checkpoint as it loads, and wakes them after. A checkpoint that loads other tensors leaves the weights as they were. The workers rename their retained weights after the new checkpoint at the Storage Server, which a relaunch on it binds, and the engine flushes its prefix cache and keys host KV cache pages by the new weights. Weights streamed from host memory and DWDP experts are not updated in place: such a deployment is brought up again on the new checkpoint.

## LoRA adapters

The adapters are an extension point: a plugin keeps the adapter pool at fixed device addresses, allocated before the CUDA graphs are captured, and implements the worker hooks `load_lora_adapter` and `unload_lora_adapter`. `/admin/load_lora_adapter` assigns the adapter the lowest free slot of the pool and has every worker run `load_lora_adapter` with the request's body and the slot (`adapter`); from then on a request that names the adapter as its `model` computes with it, `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. The worker writes each request's slot into its per-slot state at admission, and the causal LM runner fills, inside every forward, captured or not, the slot of every token's adapter into a fixed `[T]` tensor, which the plugin's kernels read through `uniserve.adapters.tokens()` (0: no adapter). An engine that replaces another, after a world change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry, so requests naming it are refused. `/admin/unload_lora_adapter` removes the name at once and has every worker run `unload_lora_adapter` with the slot.

## Nodes

`uniserve serve --host H --port P` without a model runs a node's daemon serving no deployment. Its first `PUT /admin/config` with `{"config": TOML, "set": ["PATH=VALUE", ...]}` brings one up (`202`, with the deployment's name), as `uniserve serve --config` with those assignments would, and the node serves its API and admin routes on the same address once it starts, every later `PUT /admin/config` being the deployment's; `GET /admin/config` of an idle node reports no configuration; `GET /admin/node` reports `idle`, `starting`, `serving` or `stopping` and the last deployment's error. The deployment's `POST /admin/shutdown` brings it down and releases its memory, after which the node takes the next deployment. A node serves one single-node deployment at a time.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else: a node never calls it or waits for it, so it attaches by reading a node's status and events and detaches by stopping.

```bash
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 status
uniserve-manager --node http://10.0.0.2:8000 watch            # Ctrl-C detaches
uniserve-manager --node http://10.0.0.2:8000 apply --config qwen3.toml   # an idle node deploys
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 apply --set cuda_graph_config.decode_batch_sizes=1,2,4,8 --commit-after 300
uniserve-manager --node http://10.0.0.2:8000 config
uniserve-manager --node http://10.0.0.2:8000 commit                      # or rollback
uniserve-manager --node http://10.0.0.2:8000 shutdown
```

`apply` is rolling: one node after another, stopping at the first that fails, so the other nodes serve while one changes. A node that changes world stays on trial; with `--commit-after S` the manager commits it once it served on trial for `S` seconds, before the next node changes, and stops the roll when the trial rolled back meanwhile. A change a node refuses (such as one of the KV cache's size or element type) is made by bringing a node down and up again with the new configuration while the other nodes serve.

## Worker hooks

A worker hook is a named operation that runs on every worker of the deployment at a step boundary, while no forward runs. A plugin implements it (`docs/plugins.md`):

```python
def register(registry):
    registry.hook("load_lora_adapter", load_lora_adapter)

def load_lora_adapter(payload, models):
    # payload: the request's JSON body; models: the modules the worker loaded
    ...
    return {"adapter": slot}
```

The endpoint answers with every worker's result. A hook no plugin implements fails with that reason. Hooks named `uniserve.*` are the engine's own (the cache's memory, sleep, wake, a world's promotion and commit, the weight update, the fence probes' switch and the profiling sessions), which run through their endpoints alone; a plugin cannot register one.
