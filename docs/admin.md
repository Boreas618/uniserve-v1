# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on its HTTP address, with the same API key as the OpenAI API. Everything a deployment can do while it serves goes through it: `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of it among others. The designs are `specs/live-updates.md` and, for configuration changes and epochs, `specs/online-operations.md`.

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/status` | The deployment (name, model, engine state, paused, asleep, requests in flight, the engine's executable), the running and the last operation, and the next event's sequence number |
| `GET /admin/events?after=N&wait=S` | The events after sequence number `N`, waiting up to `S` seconds (at most 60) for one; `next` is the number to read after next, and `gap` says that events after `N` already left the log of 1024 |
| `GET /admin/config` | The configuration as TOML (as `--config` reads it) and its digest; the engine that executes, with its epoch number (`world`) and state (`executing`: `preparing`, `executing`, `parked`, `unavailable` with the reason); each replica's own report as `replicas`; the configurations a rollback marked unavailable with their reasons (`unavailable`); what the last change, commit or rollback reported (`last`); every epoch's record and this daemon's main processes (below, Plans and status); the GPUs the deployment books storage on (`gpus`: each one's host, name as `nvidia-smi` prints its UUID, total, quota and the bytes booked); and the storage ledgers (`ledgers`): for each host of the deployment, every GPU's ledger with its total, quota and each entry's item, scope, `worlds`, KV cache segment and bytes, and what the deployment's transfer tasks copied there by priority (`transfers`) |
| `PUT /admin/config` | A configuration change: `{"config": TOML, "set": ["PATH=VALUE", ...], "in_flight": "keep", "dry_run": false, "force": false, "wait": true}`, as `uniserve serve --config FILE --set PATH=VALUE` states a configuration; without `config` the target is the current configuration with the assignments. An optional zero-based `replica` selects one independent replica; otherwise the change covers the deployment. The change does the least the target needs (below). `dry_run` answers with what the change would do and changes nothing: the layer it takes, and for an epoch change the epochs it switches between, the generations it uses and the build identity of the target; `force` applies a configuration a rollback marked unavailable |
| `POST /admin/config/commit` | Commits the epoch switch in flight (`specs/worker.md` §7.4): the target's processes stop being on probation and the previous epoch's are stopped. With no switch in flight it answers `{"commit": "no update in flight"}` and changes nothing |
| `POST /admin/config/rollback` | `{"reason": TEXT}`: reverts the epoch switch in flight — the target's processes are stopped or drained, the previous epoch serves again, and the target's build config is marked unavailable with the reason, so applying it again needs `force` |
| `POST /admin/pause_generation` | New requests wait; those in flight go on (SGLang's endpoint of that name) |
| `POST /admin/continue_generation` | New requests are served again |
| `POST /admin/flush_cache` | The engine revokes every cached prefix page; requests in flight keep theirs |
| `POST /admin/restart` | A hot restart of the daemon: `{"executable": PATH, "wait": true}`. A successor daemon of that build (this daemon's own when unset) takes the deployment over while this one finishes the requests it took (below); answers with the successor's process id once it serves |
| `POST /admin/shutdown` | Brings the deployment down as SIGTERM does, finishing what is in flight within `server_config.shutdown_timeout`, and releases its weights and caches at the host's Storage Server unless `{"retire": false}` |
| `POST /admin/update_weights` | `{"model_path": PATH, "in_flight": "keep"}`: the engine rewrites its weights in place from another checkpoint of the served model, a local directory or a Hugging Face repository (SGLang's `update_weights_from_disk`; below); `in_flight` is `keep` (the default), `recompute` or `abort` |
| `POST /admin/rebalance_experts` | `{"order": {MODULE_PATH: [EXPERT_ID, ...]}, "replica": INDEX}`: rearranges routed experts within the current epoch. Each list is a complete permutation of logical expert IDs in global physical-slot order. Omit `replica` to update every independent replica in sequence |
| `POST /admin/sleep`, `/admin/wake_up` | The engine gives back its KV cache and CUDA graph storage and keeps its weights, and restores both (vLLM's endpoints of those names; below) |
| `POST /admin/load_lora_adapter`, `/admin/unload_lora_adapter` | `{"lora_name": NAME, ...}`: the workers load a LoRA adapter into a slot of the adapter pool, or unload it (vLLM's endpoints of those names; below) |
| `POST /admin/profile` | Starts a profiling session on every worker of the executing epoch at the engine's next step boundary: `{"collectors": [...], "steps": N, "start_step": N, "seconds": S, "stages": [...], "workers": [...], "components": [...], "output_dir": PATH, "max_slowdown": F, ...}` (`docs/profiling.md`); answers with the session, each worker's file and its collectors' states. One session runs at a time: another is refused (`400`) until it ends, as is a session naming more than one of `pm_sampling`, `range_metrics` and `pc_sampling`, which share the device's performance monitors, and, while `profiling_config.graph_pc_sampling` keeps PC sampling enabled on every worker, a session of `pm_sampling`, `range_metrics` or a timeline that traces graphs whole. A `range_metrics` session books its range profiler pass's device storage in the ledger of each selected worker's GPU, as part of the worker's process item, until it ends: where a ledger lacks the room, the KV cache first gives back tail segments, as an epoch change's preparation does (the requests holding them run on, and the session starts once they let them go), and grows back once the session ends. A session for which even the segments past the first leave too little room is refused (`400`), naming the bytes and every ledger entry |
| `GET /admin/profile` | The running session, or the last that ended: its state and why it ended, the steps and bytes its workers recorded, the step time before it and during it, the quality-of-service guard's actions and each worker's file; `null` before any |
| `DELETE /admin/profile` | Ends the running session at the engine's next step boundary, every worker writing its file |
| `POST /admin/hooks/NAME` | A named worker hook (below) |

Each write is an operation: it has an identity, runs on a task of its own, and ends `succeeded` or `failed` in the status and in the event log, whether or not the client that asked stays connected. One operation runs at a time; another is answered `409`. `"wait": false` answers at once with `202` and the operation.

## Configuration changes and epochs

An epoch is one build of the main process serving a deployment: its executable and build identity, its parallel shape, its numerics, the programs it fills, and the KV cache it lays out. The daemon decides once, before anything starts, which layer a change moves on (`crates/daemon/src/updates/`):

- **Program layer** — only what the main processes execute differs (a new kernel revision, or another scheduling policy or another of its parameters, at an unchanged configuration). The serving epoch's processes install the programs and trial the new ones; nothing restarts.
- **Epoch layer** — the build config differs: the main-process executable (`worker_config.executable`), the parallel shape and block ownership, `dtype` or `quantization`, the KV layout, the graph tiers and the slot count. The daemon runs an epoch switch, below.
- **Host layer** — the options the daemon or the frontend read alone (`server_config` for the frontend, `admin_config` for the daemon's own listener, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `migration_config`, `mm_processor_kwargs`). The daemon restarts itself in place (below).

`PUT /admin/config` resolves the target against the serving configuration and answers with the layer that took it (`change`):

- `none`: the target is the current configuration.
- `in_place`: the schedulers' limits alone (`max_running_requests`, `max_num_batched_tokens`, and `scheduler_config`'s `max_batch`, `max_queued_requests` and `chunked_prefill_size`), within the batch the running processes were started for, take effect at each scheduler's next step. A change of the scheduling policy's own name or of the refill policy's parameters (`scheduler_config.policy`, `speculative_config.expected_speedup`, `refill_token_cost`) is a program change: they are the policy program's backend name and arguments (§7.7). `profiling_config.fence_probes` alone switches every worker's fence probes at the next step boundary, the captured graphs keeping them (`docs/profiling.md`).
- `daemon`: a change of the host layer's options is a hot restart of the daemon with the target configuration (`docs/admin.md` below); the answer carries the successor's process id.
- `epoch`: the epoch layer runs a switch; the answer reports the update and the epoch it targets.
- `program`: the program layer runs inside the serving epoch; the answer reports the update and the epoch it executes in.

A change of both the host layer and a deeper layer is applied in that order, the orchestrator before what it orchestrates: the hot restart applies the daemon's options, and its successor applies the rest in an operation of its own; the answer names that step (`"then"`). A step that fails stops the change, and the steps before it stay. A dry run reports the layer and the plan and changes nothing.

A change of the served model name is refused because it names the deployment. A change of the model's files, `dtype`, quantization, load format or weight source loads the other keys from the files beside the serving epoch's; a change of the parallel configuration, the devices or the hosts spreads the weights differently, and the target's processes receive them from the serving epoch's retained chunks rather than reading the checkpoint where an epoch already holds them. A change of the KV cache's element type or page size lays out its own cache, and the requests in flight continue from warm copies under an exact conversion of the encoding, or compute their state again (`in_flight`).

`engine_host` selects the joined node that runs the engine and the ranks without explicit hosts. Networked deployments expose their process and request connections on the leader's configured network interface; a daemon hot restart adopts them as it adopts local sockets. The epoch layer accepts one node today, one main process per node: a deployment that names more nodes is refused by name when the change is decided, because the launch file a main process reads names its peers' request addresses, and form (B) — the contents carried inside `process::Spawn` — is what a remote node needs.

### An epoch and its generations

The daemon keeps one record per epoch it knows: the build config, the programs it filled, the trial's policy, and a status (`Precopy`, `Serving`, `Probation`, `Purged`). The record names the generation the epoch's main processes gave the programs they execute, once a child reports it — a model generation, not a process's identity; the child numbers its own programs and the daemon never invents one. A process's identity is its launch generation, below. Every node's main process is a child of that node's daemon at a launch generation of the deployment's group and rank, taken from one counter per group and rank: the serving epoch's parked standby takes the next generation, the target epoch the one after, and a relaunch the next. The daemon writes each child's launch file (`crates/daemon/src/engine/launch.rs`) with that generation in its `engine` field.

### The switch

1. **Precopy.** Every node starts the target's main process as a standby at a generation above every live one, then claims the target epoch's storage for the node's scopes — the claim is held before the child maps storage, and it retires the epochs an earlier switch discarded. The child maps the epoch's weights and cache read-only, resolves its programs at the Program Server (an unchanged program is a hit), captures its graphs on its own scratch, warms the KV pages a changed layout needs, and parks. It reports `Parked { generation }`; the target must report the build identity the daemon expects — another executable's identity is fixed by its first child's `Hello`, and every other child must speak it.
2. **Switchover.** Every parked child is promoted in place (`Promote`, `Promoted { generation }`). The frontend is told to serve the target epoch and resubmit the requests it keeps, and the previous epoch's main processes are drained (`Drain { epoch }`): a token request ends migratable with the tokens it generated, a video request is preempted at its next denoising step boundary with its trajectory in the host latent pools. A drained process stays alive for the whole probation — it is what a revert serves again — and exits at the purge. The pause is the interval from the first promote to the last drained epoch; it is reported as the update's `pause_seconds`.
3. **Probation.** The target serves on trial; the epoch layer refuses another change meanwhile (`409`). A failure the target reports — a fault, a stalled job, non-finite logits, an exited process — reverts the update, and `POST /admin/config/rollback` starts a revert by hand.
4. **Commit.** Every target child acknowledges `Committed`; the target's record becomes `Serving`, the previous generation is stopped (its processes exit), and the previous epoch's storage is retired by a claim of the target's epoch.
5. **Revert.** The target is drained — a target that failed is not commanded again — and its epoch is retired, and the previous epoch serves again: the same drained, still-alive processes, resubmitted by the frontend with `Serve { epoch: previous, requests }`. Only when those processes are gone does the daemon start a fresh generation at the next launch generation, and the frontend is served it once it reports serving. The configuration is marked unavailable with the failure's reason, so applying it again needs `force`.

A target that fails before the switchover never reaches the frontend: its children are stopped where they were started, its epoch is retired by the next claim, and the previous epoch serves untouched.

### The standby main process

Beside every node's serving main process the daemon keeps a parked standby child of the same group, rank and epoch at the next generation, with its own CUDA contexts: a sticky error of the serving process cannot touch it. A process-fatal fault promotes the whole failure domain — every member's parked child, every promote issued before an answer is awaited — and each node then starts a new standby at the generation after. A device that needs a reset takes the standby with it; only migration to another node or replica helps. A standby exists only while its epoch serves: an epoch in precopy or on probation keeps none, and a fault there reverts the update. `worker_config.standby` and `worker_config.standby_storage` are the options (`docs/configuration.md`).

### Plans and status

A dry run reports the layer, the target's build identity and programs, and for an epoch change the epoch it claims and the generations it uses; it changes nothing. `GET /admin/config` reports each epoch's record — build identity, programs, policy, status and the serving generation — and this daemon's main processes, one row each: role, pid, epoch, generation, build and state (`Starting`, `Parked`, `Serving`, `Stopped`, `Failed`), the frontend included. The rows are written by the layer that owns the children, from the reports they send, never composed from assumptions about progress.

An update's record reports its phase (`precopy`, `promoting`, `serving`, `probation`, `committing`, `reverting`, `purged`, `abandoned`), the pause, the requests that ended and the requests that failed. A commit records an irrevocable decision before it publishes or retires anything. One change runs at a time: a second change is refused while a switch runs or a program update is on probation, and a daemon hot restart waits for the change to end, because the switch's children and phases and a program trial's record do not cross a handover.

Data-parallel replicas share the deployment's endpoint: the epoch layer's switch covers every node of the deployment, and a change that would move an epoch across replica boundaries is refused for a single replica.

## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`POST /admin/restart`, `crates/daemon/src/restart.rs`), as Envoy's hot restart does. It starts its successor (`uniserve serve --predecessor`) with a socket pair between them. The successor first restarts the host's Storage Server in place when that server speaks an earlier protocol than the successor's build, so that an update replaces the Storage Server before the daemon and the daemon before the epoch (a failure leaves the daemon serving as it was); it then loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec, the admin's log and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. The engine and its workers are the same processes throughout. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits (`UNISERVE_LIFELINE`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A host's Storage Server restarts in place too (`uniserve storage restart [--executable PATH]`, `crates/storage-server/src/restart.rs`). The server starts its successor and, once no request, shoot-down, connector task, transfer or exposure to another host is in flight, stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's storage and every page pool's memfd, with its state; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. Another host's READs of this host's storage are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

## The KV cache's storage and the weights

A device KV cache is split along its units into eight segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/executor/src/memory/prefix_cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses.

- Every GPU has a storage ledger for each deployment that uses it, kept by the host's Storage Server: the quota, `⌊total × mem_fraction_static⌋` of the whole GPU, and every item the deployment's epochs and the host's Transfer Server hold there. The server books what it retains, each storage once however many epochs map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent banks). The processes book what it cannot see: each warm worker its graph pool and its process storage (its CUDA context, PyTorch's and Rust's allocations, communicator buffers, the product storage it has yet to make resident, and while a `range_metrics` profiling session runs, its range profiler pass), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, lane or exposure to another host uses it any more. A ledger without room for the context refuses it, and the transfer task that needed the GPU fails, naming the ledger. The server refuses a booking or a new device storage that would take a ledger past its quota, so a ledger never exceeds it; a worker that does not fit its quota fails its startup with every entry of the ledger. A booking ends with the process that made it when the process ends in order; a lost worker's bookings stay reserved for the process that replaces it (its relaunch), until that process books them again or the epoch is retired; an epoch's storages end with the epoch, and the segments a successor maps become its own on the ledger when the previous epoch is retired. Two epochs therefore size their caches against one quota: a worker's grant is the quota less everything the ledger books beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the storage the fraction leaves, and book once promoted in place of the rank they stand by for; the processes of one scope and epoch count as their largest booking.
- A configuration change does not shrink or grow the serving engine's cache from the daemon's side: an epoch switch starts the target's own main processes, whose precopy maps the serving epoch's storage read-only and warms what it needs (`specs/worker.md` §7.4), and the daemon's own in-place changes (the scheduling limits) leave the cache alone.
- `/admin/sleep` holds new requests, recomputes the token requests in flight as a shrink does (an image-generating request continues from its stored denoising step, recomputing only if that trajectory is absent; `docs/architecture.md`, Image preemption), preempts the video requests in flight at their next denoising step boundary with their trajectories stored in the host latent pools (`docs/architecture.md`), which continue from that step once the deployment wakes, and lets the readouts finish; the workers then give back every segment and suspend their CUDA graph storage (`uniserve.sleep`). `/admin/wake_up` creates the cache again, restores the graph storage and lets the held requests through. A sleeping deployment refuses epoch changes.
- `/admin/update_weights` checks that the daemon would process the new checkpoint's requests as the served model's (the same `tokenizer.json`, tokenizer settings, generation defaults and chat template, and the same model facts) and holds new requests. Every worker loads the checkpoint into new storage as it loaded the model and copies every tensor into place once all of them match in representation, shape and element type. The requests in flight continue as `in_flight` says (vLLM's `keep` and `abort`, SGLang's `in_place`, `retract` and `abort`): with `keep`, once the batches in flight complete, the workers load the checkpoint beside the KV cache, giving back their CUDA graph storage for the load when the free storage alone does not hold it (and refusing the update, unchanged, when even both do not), and every request in flight continues on the new weights with the KV cache it reached; what it computes afterwards follows neither checkpoint, so it publishes no page. A video request in flight continues its trajectory on the new weights with `keep`, a trajectory of neither checkpoint. With `recompute` the engine recomputes the token requests in flight, image-generating ones included, preempts the video requests in flight as a sleep does (they continue from noise, since the new weights compute other trajectories) and lets the readouts finish, and with `abort` it ends every request it holds, aborted; then it puts its workers to sleep, so that the cache's storage holds the new checkpoint as it loads, and wakes them after. A checkpoint that loads other tensors leaves the weights as they were. The workers rename their retained weights after the new checkpoint at the Storage Server, which a relaunch on it binds, and the engine flushes its prefix cache and keys host KV cache pages by the new weights. Weights streamed from host storage and DWDP experts are not updated in place: such a deployment is brought up again on the new checkpoint.

## Expert redistribution

`POST /admin/rebalance_experts` changes the distribution of routed expert weights while preserving the number of physical slots on each rank. Module paths are the names of `FusedMoE` modules in the loaded model. Layers omitted from `order` keep their distribution. An invalid permutation or unknown layer is rejected before copying starts.

The serving scheduler reserves the copy plan's additional storage on each GPU, releasing available KV tail segments as needed while requests continue. The Transfer Server copies retained expert regions into that storage. At a common computation boundary, workers remap the completed allocations at their captured weight addresses and update logical-to-physical routing tensors. The epoch, CUDA Graph addresses, request state and numerical weights remain the same. Once the operation finishes, the cache can grow into the released storage. The response lists each replica's epoch, requested order and allocation plan.

Distributed weight data parallelism (DWDP) prepares the resident shards, peer mappings and prefetch buffers of the requested distribution in the background; admission includes these allocations. Commit replaces the backing of the existing composite weight addresses and the prefetch copy plans together. A component that streams dense projections from host storage keeps those host allocations while its resident experts are redistributed.

The committed distribution is included in worker recovery launches and daemon handoff. A failure during preparation releases incoming copies and leaves the active distribution intact. A failure during publication triggers the existing engine recovery path with the committed distribution; an epoch on probation follows the switch's revert policy. A redistribution that changes rank shapes requires a configuration change through `PUT /admin/config`.

## LoRA adapters

The adapters are an extension point. This repository holds no LoRA kernel program, so nothing implements the worker hooks `load_lora_adapter` and `unload_lora_adapter` yet and both endpoints fail with the hook's error. The mechanism below stays for the kernel program that provides them: it keeps the adapter pool at fixed device addresses, allocated before the CUDA graphs are captured, and implements the two hooks. `/admin/load_lora_adapter` assigns the adapter the lowest free slot of the pool and has every worker run `load_lora_adapter` with the request's body and the slot (`adapter`); from then on a request that names the adapter as its `model` computes with it, `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. The worker writes each request's slot into its per-slot state at admission, and the causal LM runner fills, inside every forward, captured or not, the slot of every token's adapter into a fixed `[T]` tensor, which the adapter's kernels read (0: no adapter). An engine that replaces another, after an epoch change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry, so requests naming it are refused. `/admin/unload_lora_adapter` removes the name at once and has every worker run `unload_lora_adapter` with the slot.

## Nodes

`uniserve serve --host H --port P` without a model runs a node's daemon serving no deployment. Its first `PUT /admin/config` with `{"config": TOML, "set": ["PATH=VALUE", ...]}` brings one up (`202`, with the deployment's name), as `uniserve serve --config` with those assignments would, and the node serves its API and admin routes on the same address once it starts, every later `PUT /admin/config` being the deployment's; `GET /admin/config` of an idle node reports no configuration; `GET /admin/node` reports `idle`, `starting`, `serving` or `stopping` and the last deployment's error. The deployment's `POST /admin/shutdown` brings it down and releases its storage, after which the node takes the next deployment. A node serves one single-node deployment at a time.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else: a node never calls it or waits for it, so it attaches by reading a node's status and events and detaches by stopping.

```bash
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 status
uniserve-manager --node http://10.0.0.2:8000 watch            # Ctrl-C detaches
uniserve-manager --node http://10.0.0.2:8000 apply --config qwen3.toml   # an idle node deploys
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 apply --set cuda_graph_config.decode_batch_sizes=1,2,4,8 --commit-after 300
uniserve-manager --node http://10.0.0.2:8000 config
uniserve-manager --node http://10.0.0.2:8000 commit                      # or rollback
uniserve-manager --node http://10.0.0.2:8000 shutdown
```

Each `--node` is the leader of one service (one served model name). When several services share GPUs and hosts, `apply` decides the order of their updates and calls each service's admin API in turn (`crates/manager/src/updates.rs`); every step within a service is the service's own, and no node waits for the manager. Before it starts a service's update, the manager reads the GPUs its epochs hold (`GET /admin/config`, `gpus`) and its plan (`PUT /admin/config` with `dry_run`): whether it starts a new epoch, the GPUs its successor prepares on (the storage plan's GPUs and the target ranks of its weights' plan), each host's host storage it requires and admits, and whether every GPU and host it uses has the storage it requires. Services are taken in the order given; a service whose update starts a new epoch starts only when no update in progress (preparing, or on trial until committed) holds one of its GPUs, so two services that share a GPU are never prepared at once, when its plan, made just then, fits, and when the host storage it requires on each host, beside what the updates in progress there required, is within what the host admits. Services that share no GPU and whose host storage fits together update at once. A service that cannot start waits and is planned again whenever an update in progress ends, since a commit releases the previous epoch's storage. With `--commit-after S`, the manager commits each new epoch once it served on trial `S` seconds and completes that service's remaining replica trials; without it, each new epoch stays on trial for the operator and holds its GPUs, and the services that share them wait for the next `apply`. A failed update or a trial that rolled back by itself stops the services not started, which the manager names with why each waited; the updates in progress go on to their end, and committed ones remain applied. A plan that fits nowhere while no update is in progress is a refusal. `--dry-run` prints each service's plan and the order the manager takes them in. An idle node's deployment names no GPUs before it starts, so the manager orders it by nothing but the order given.

## Worker hooks

A worker hook is a named operation that runs on every worker of the deployment at a step boundary, while no forward runs. The endpoint answers with every worker's result, and a hook nothing implements fails with that reason. Hooks named `uniserve.*` are the engine's own (the cache's storage, sleep, wake, an epoch's promotion and commit, the weight update, the fence probes' switch and the profiling sessions), which run through their endpoints alone.
