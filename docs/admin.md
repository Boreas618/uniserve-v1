# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on its HTTP address, with the same API key as the OpenAI API. Everything a deployment can do while it serves goes through it: `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of it among others. The designs are `specs/live-updates.md` and, for configuration changes and worlds, `specs/online-operations.md`.

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/status` | The deployment (name, model, engine state, paused, asleep, requests in flight, the engine's executable), the running and the last operation, and the next event's sequence number |
| `GET /admin/events?after=N&wait=S` | The events after sequence number `N`, waiting up to `S` seconds (at most 60) for one; `next` is the number to read after next, and `gap` says that events after `N` already left the log of 1024 |
| `GET /admin/config` | The configuration as TOML (as `--config` reads it) and its digest; each replica's two slots, each with its world and state (below); the change in progress (`update`): its phase, the bytes it moved, how long it has run, the promotion's pause and the serving world's step time against its baseline; the trial: its world, how long it has served, the promotion's pause, the requests that ended and failed on it, the rollback thresholds, the previous world's step time and throughput before the promotion and the trial's since; the configurations a rollback marked unavailable; what the last change, commit or rollback reported; the GPUs the deployment books storage on (`gpus`: each one's host, name as `nvidia-smi` prints its UUID, total, quota and the bytes booked); and the storage ledgers (`ledgers`): for each host of the deployment, every GPU's ledger with its total, quota and each entry's item, scope, worlds, KV cache segment and bytes, what the host admits of new host storage (below), and what the deployment's transfer tasks copied there by priority (`transfers`) |
| `PUT /admin/config` | A configuration change: `{"config": TOML, "set": ["PATH=VALUE", ...], "in_flight": "keep", "dry_run": false, "force": false, "wait": true}`, as `uniserve serve --config FILE --set PATH=VALUE` states a configuration; without `config` the target is the current configuration with the assignments. An optional zero-based `replica` selects one independent replica; otherwise the change covers the deployment. The change does the least the target needs (below). `dry_run` answers with the plan and changes nothing: for a new world, the steps it will execute in order, what becomes of each derived state, the bytes each step moves over each link, the expected promotion backfill, and `storage`, whether it fits beside the serving world on every GPU and host (below, Plans and status); `force` applies a configuration a rollback marked unavailable |
| `POST /admin/config/commit` | Commits the replica or group trial, or continues a pending commit decision; releases the predecessors and starts the next replica trial in a rollout (below) |
| `POST /admin/config/rollback` | `{"reason": TEXT}`: restores the predecessors of the replica or group on trial, stops the remaining rollout, and marks the target configuration unavailable with the reason |
| `POST /admin/pause_generation` | New requests wait; those in flight go on (SGLang's endpoint of that name) |
| `POST /admin/continue_generation` | New requests are served again |
| `POST /admin/flush_cache` | The engine revokes every cached prefix page; requests in flight keep theirs |
| `POST /admin/restart` | A hot restart of the daemon: `{"executable": PATH, "wait": true}`. A successor daemon of that build (this daemon's own when unset) takes the deployment over while this one finishes the requests it took (below); answers with the successor's process id once it serves |
| `POST /admin/shutdown` | Brings the deployment down as SIGTERM does, finishing what is in flight within `server_config.shutdown_timeout`, and releases its weights and caches at the host's Storage Server unless `{"retire": false}` |
| `POST /admin/update_weights` | `{"model_path": PATH, "in_flight": "keep"}`: the engine rewrites its weights in place from another checkpoint of the served model, a local directory, a Hugging Face repository or a plugin's weight source `scheme://...` (`docs/plugins.md`) (SGLang's `update_weights_from_disk`; below); `in_flight` is `keep` (the default), `recompute` or `abort` |
| `POST /admin/rebalance_experts` | `{"order": {MODULE_PATH: [EXPERT_ID, ...]}, "replica": INDEX}`: rearranges routed experts within the current world. Each list is a complete permutation of logical expert IDs in global physical-slot order. Omit `replica` to update every independent replica in sequence |
| `POST /admin/sleep`, `/admin/wake_up` | The engine gives back its KV cache and CUDA graph storage and keeps its weights, and restores both (vLLM's endpoints of those names; below) |
| `POST /admin/load_lora_adapter`, `/admin/unload_lora_adapter` | `{"lora_name": NAME, ...}`: the workers load a LoRA adapter into a slot of a plugin's adapter pool, or unload it (vLLM's endpoints of those names; below) |
| `POST /admin/profile` | Starts a profiling session on every worker of the executing world at the engine's next step boundary: `{"collectors": [...], "steps": N, "start_step": N, "seconds": S, "stages": [...], "workers": [...], "components": [...], "output_dir": PATH, "max_slowdown": F, ...}` (`docs/profiling.md`); answers with the session, each worker's file and its collectors' states. One session runs at a time: another is refused (`400`) until it ends, as is a session naming more than one of `pm_sampling`, `range_metrics` and `pc_sampling`, which share the device's performance monitors, and, while `profiling_config.graph_pc_sampling` keeps PC sampling enabled on every worker, a session of `pm_sampling`, `range_metrics` or a timeline that traces graphs whole. A `range_metrics` session books its range profiler pass's device storage in the ledger of each selected worker's GPU, as part of the worker's process item, until it ends: where a ledger lacks the room, the KV cache first gives back tail segments, as a world change's preparation does (the requests holding them run on, and the session starts once they let them go), and grows back once the session ends. A session for which even the segments past the first leave too little room is refused (`400`), naming the bytes and every ledger entry |
| `GET /admin/profile` | The running session, or the last that ended: its state and why it ended, the steps and bytes its workers recorded, the step time before it and during it, the quality-of-service guard's actions and each worker's file; `null` before any |
| `DELETE /admin/profile` | Ends the running session at the engine's next step boundary, every worker writing its file |
| `POST /admin/hooks/NAME` | A worker hook a plugin adds (below) |

Each write is an operation: it has an identity, runs on a task of its own, and ends `succeeded` or `failed` in the status and in the event log, whether or not the client that asked stays connected. One operation runs at a time; another is answered `409`. `"wait": false` answers at once with `202` and the operation.

## Configuration changes and worlds

A world is the processes that execute one configuration of the deployment: an engine and its workers, their communicators, CUDA graphs and the storage they created. A deployment has two slots for worlds, and one world executes. `PUT /admin/config` resolves the target configuration as a deployment's start does and answers with the change it made (`change`):

- `none`: the target is the current configuration.
- `in_place`: the scheduling options alone (`max_running_requests`, `max_num_batched_tokens`, `scheduler_config` and the refill policy of `speculative_config`), within the batch the running workers were started for (at most as many calls and tokens a step and running requests), take effect at each scheduler's next step; a change of policy reorders the waiting requests by it. `profiling_config.fence_probes` alone switches every worker's fence probes at the engine's next step boundary, the captured graphs keeping them (`docs/profiling.md`).
- `daemon`: a change of the options the daemon reads alone (`server_config`, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `readout_config`, `migration_config`, `mm_processor_kwargs` and `diffusion_generation_config`) is a hot restart of the daemon with the target configuration (below); the answer carries the successor's process id.
- `world`: anything else a world executes (the build its engine and workers run, `worker_config.executable`, the CUDA graphs, FlashInfer, speculative decoding's `speculative_config.num_draft_tokens`, the workers' other options, scheduling beyond the workers' batch) starts a new world on trial; the answer reports both worlds and the time each step took.

Device quotas, queue depth, product transport, KV-cache options and video execution options also change through a world. The planner accounts for the target ranks' fixed buffers, graph pools and cache capacity before starting it. A cache with a different token capacity uses its own segments and warms the requests' prefixes into them, so a smaller target does not inherit segments beyond its capacity. Host-cache limits take effect in the successor's host pools.

`engine_host` selects the joined node that runs the engine and ranks without explicit hosts. A change prepares the successor on that node and continues the HTTP streams through the existing daemon. Networked deployments expose their process and request connections on the leader's configured network interface; generated artifacts travel in bounded frames into shared host storage at the receiver. A daemon hot restart adopts these connections as it adopts local sockets.

A change of the served model name is refused because it changes the deployment identity. A change of the model's files, its dtype, its quantization, its load format or its weight source keeps the deployment's model (another checkpoint must keep the tokenizer, templates, generation defaults and model facts, or the change is refused): the successor loads the weights of other keys from the files beside the serving world's, mapping the serving world's weights only where their keys stay, and its plan and report say so (the weights `recomputed`, `reloads`). A change of the KV cache's element type, or of the compute dtype or quantization it follows, maps none of the serving world's cache: the successor lays out its own, and the requests in flight continue from warm copies under an exact conversion of the encoding and compute their state again in it without one (the K/V pages `recomputed`), as they do under `in_flight = "recompute"` when the successor loads its weights and computes other numerics. A change of the parallel configuration (the tensor- and data-parallel sizes, the deployment file, the device or the hosts the ranks spread across, a generation tower's device), of the experts or of the KV cache's page size is a world change whose successor holds other regions of the weights on each GPU: its workers receive their weights from the serving world (below), and it lays its KV cache out for its own heads and pages, so it maps none of the serving world's segments and warms compatible request prefixes into its own cache before promotion. A change of both the daemon's options and what a world executes (its scheduling limits included) is applied in that order, the orchestrator before what it orchestrates: a hot restart of the daemon applies the daemon's options, and its successor then applies the rest in an operation of its own, which `GET /admin/status` reports; the answer names that step (`"then": "world"`). A step that fails stops the change, and the steps before it stay. A world change takes four steps:

1. **Preparation.** The serving world withdraws from allocation the tail of its KV cache past the limit each GPU's storage ledger leaves it beside the successor (below): the quota less everything else the ledger books and what the successor adds, namely a graph pool of its own (`graph_storage_budget_bytes`, a tenth of the device) when its graph policy captures and its model can be captured (none for a successor that serves every call eagerly, as a rank that captures nothing reserves no graph share in its own capacity plan either), process storage and storages beside the cache planes as large as the serving world's, a head segment of its own, the weights it loads (as large as the serving world's), and the units the requests in flight recompute in when it maps none of the serving world's cache; it adds no weights or KV cache of the keys it maps. A change whose limit cannot hold a GPU's first segment, which always stays, is refused before anything starts, naming each item's bytes on every GPU and host. Before the tail leaves, its idle cached pages reach the host KV cache: the pool verifies the copy of each page it was offloaded under, and copies a page it no longer holds there again, so a later prompt reads them back from there (a sliding-window group's pages and pages never offloaded are computed again). The requests holding the tail run on, and once none holds it the workers give it back; `update_config.preempt_after` recomputes the ones that still hold it after that long, and a request holding it that cannot get a unit to continue, because the requests running hold every unit left to allocation, is recomputed at once. The successor starts in the other slot: its workers map the serving world's weights of the same keys and its KV cache segments read-only, under hardware protection, create a head segment of their own, warm up on it and capture their graphs. A worker of a position no world loaded before, such as one of another parallel configuration, receives its weights instead of reading the checkpoint: it materializes its model without reading it, plans the chunks its weights take and frees that model; the workers that load together compute one copy manifest from the chunks the serving world retains on the host's GPUs to all their chunks and verify they computed the same digest; each maps the chunks of the same key on its GPU, creates the rest, and the Transfer Server copies the manifest's spans into them at the `Background` priority while the worker binds its model and builds its executor and expert exchange; once they arrived, the chunks are retained read-only. Only the regions no world holds are read from the checkpoint. The serving world executes throughout. A successor that does not start leaves the serving world serving, which creates its tail again.
2. **Promotion.** At a step boundary new requests wait and the serving world parks: it ends every token request that resumes from its generated tokens as migratable, ends every video request as migratable at its next denoising step boundary with its trajectory stored in the host latent pools, lets the others finish, offloads the pages it reserved for the host KV cache and executes nothing more, keeping its storage and its prefix cache index. The successor copies the cache flags and scales of the units it maps, imports that index into them, and serves: every migrated request is submitted again with the tokens it generated and shares complete pages and copies its stored partial tail into writable units before appending; in a successor that speculates, a request whose draft cache pages the serving world did not keep verifies no drafts until a refill completes its draft cache. The pause is the parked world's last step and one resubmission, whatever the requests' lengths. A successor that computes other numerics than the serving world (another model identity, `docs/plugins.md`, so another root of its pages' prefix hashes) reads none of its pages: new requests compute their prompts, and the requests in flight continue as `in_flight` states, `keep` (the default) with the state they reached, reading only the serving world's pages and writing none, since their later pages are neither world's, or `recompute`, from their tokens, exactly. A video request continues from the step its trajectory was stored at: on a successor whose denoising computes the same, exactly as if it had not been interrupted; on one that computes other numerics, with `keep` from the stored trajectory under the successor's numerics, and with `recompute` from noise. Until its commit a successor writes only to its own segments (its head, and the tail segments it creates as each GPU's ledger has room for them, as when a previous world kept as its `weights` exits and what its processes booked becomes the successor's): a change whose requests in flight need more of them than are free (the whole cache a request with images reserved at admission, which it reserves again since its context is computed anew; of the others, all the units they held when they recompute, a page each otherwise) is refused at the promotion with both counts, and the serving world serves on. The change reports whether the numerics changed and how the requests in flight continued. It reports the promotion's pause, from the moment new requests wait until the successor admits them (`pause_seconds`), and the pause's parts: parking the serving world (`park_seconds`), evicting its cache segments when the warm copies were staged in host storage (`evict_seconds`), loading those copies into the successor (`materialize_seconds`), and promoting the successor (`promote_seconds`).
3. **Trial.** The successor executes and creates the rest of its KV cache as storage frees. The previous world is kept as `update_config.previous_world` states (`docs/configuration.md`): `parked`, or its `weights` alone: its processes exit, which ends their graph pools' and process storage's bookings, and every node's Storage Server keeps its weights alone, releasing its other storages the successor does not map (`KeepWeights`), all of which the successor's cache grows into at once. Kept in `host` storage, the weights the successor does not map then move to host storage as well: each node's Storage Server admits host storage of their whole size under its host-storage rule, has its Transfer Server copy every device storage of them there at background priority, and releases the device storages once every copy ended (`Offload`), so the successor's cache grows into them too. A node that cannot (no Transfer Server, or more than the host admits) keeps them on its GPUs, and the trial reports the previous world kept as `weights` with the reason (`host_refused`). The weights never go to another host. A dry run's plan states each host's admission beside what the previous world's weights would take there (`previous_world_weights`). A parked previous world whose cache the successor maps none of (the successor recomputes the requests in flight: another parallel configuration or KV cache encoding, or other weights under `in_flight = "recompute"`) keeps it for a rollback alone: it evicts every segment past its first once their idle pages reached the host KV cache, as the preparation does for its tail, and the successor's cache grows into them (`evicted` in the report). The trial ends only with `POST /admin/config/commit`, and refuses another change (`409`) meanwhile. It rolls back by itself on a fault of the successor (a worker error that leaves its workers unusable, such as an illegal memory access or a worker process's exit; a stalled job; non-finite logits; its engine process's exit) and past a threshold of `update_config.rollback`. A world on trial is never repaired: a fault fails it as a whole, and its requests leave as migratable for the previous world.
4. **Commit or rollback.** A commit releases the previous world: its processes exit, the successor takes the segments it mapped read-only and retires the previous world's storage at the Storage Server, grows its KV cache into the storage freed, and from then on relaunches its worker groups on a loss and keeps their standbys. A successor whose pages are keyed otherwise hits none of the pages the previous world published; they stay in the host KV cache, which other Replicas of the deployment may still read, until ordinary eviction replaces them. A rollback parks and closes the successor, resumes the previous world, which creates the segments it evicted again and reads their pages back from the host KV cache on later prompts (or starts it again on its kept weights, which it binds rather than reads: its claim retires the successor's storage first, and weights kept in host storage return to the GPUs they left before its workers start, `Restore`), retires the successor's storage and marks the configuration unavailable with the reason, the world on trial's first error, which for a worker fault names the batches it struck and their requests: applying it again needs `force`. The requests continue on the previous world after every token they delivered: none fails or repeats a token, and the previous world reads the KV cache as it left it, since the successor never wrote it. A parked previous world serves again as soon as the world on trial has parked: a scheduler of it that stopped on a fault handed its requests back as it stopped and is not waited for, the world on trial closes afterwards, and once its processes are gone the previous world retires its storage and creates again the segments it gave it. The rollback reports its pause, from the moment new requests wait until the previous world admits them (`pause_seconds`), and the pause's parts: stopping the world on trial (`stop_seconds`), resuming or starting the previous world again (`resume_seconds`), and restoring the cache the trial warmed (`restore_seconds`).

Independent data-parallel replicas have separate engines and world lifecycles behind the same HTTP endpoint. Requests are routed to a ready replica and retain that replica's continuation ownership during an update. `GET /admin/config` includes `replicas`, each with its configuration, slots and trial, and `pending_replicas` for the remaining rollout. `PUT /admin/config` accepts an optional zero-based `replica` index; without it, a world update starts the first replica's trial, and each commit advances to the next replica. The response includes `next_trial` when another replica starts and `rollout_error` if that next step fails after the preceding commit succeeded. Rollback stops the remaining rollout.

An independent replica's successor uses disjoint GPUs. Without explicit devices, the daemon selects free CUDA-visible GPUs on the declared hosts. Explicit devices must be available; an update with insufficient devices is refused without taking another replica's GPUs. Communicating expert-parallel ranks remain one replica. A change that joins or splits replica groups prepares all successors while the predecessors serve, then promotes the group together. Its status and reports use `worlds` and `previous_worlds` for the complete sets.

Commit records an irrevocable decision before publishing the successors and retiring predecessors. Publication is atomic within one Storage Server; the daemon completes it across all nodes before retirement. `GET /admin/config` reports a pending `commit`, including remaining nodes and engines, if completion fails. Calling commit again continues that decision; rollback is no longer allowed. A daemon hot restart transfers this decision and the remaining rollout and continues them in the successor.

### Plans and status

A world change decides once, before anything starts, the steps it executes and what becomes of each derived state of the serving world (`crates/daemon/src/worlds/change.rs`); the dry run reports these decisions and the change executes them. The one thing they depend on that is unknown before the successor's workers start is whether those workers compute other numerics than the serving world's: the root of their pages' prefix hashes and the seed of their stored trajectories, which the workers derive from the components they load. A plan therefore states each outcome under the same numerics, and beside it the outcome under other numerics where that differs (`when_numerics_change`); the change's report states the outcome it observed.

**Steps.** `steps` lists the steps in the order the change executes them, each as `{"step": NAME, ...}`, with `"when": "numerics_unchanged"` (or `"numerics_change"`) on a step taken under that outcome alone. The names are the phases `GET /admin/config` reports the change in:

| Step | What it does |
| --- | --- |
| `eager` | The serving world switches to eager forwards, releasing its graph pool to the successor (`update_config.eager_prepare`, or chosen by the storage plan) |
| `shrink` | The serving world gives back the tail of its KV cache past the limit each GPU's ledger leaves it beside the successor (they share GPUs) |
| `baseline` | After `eager`: the serving world's eager steps make the transfers' baseline |
| `prepare` | The successor starts: it maps, receives or loads its weights, maps or lays out its KV cache, warms up and captures its graphs |
| `warm_cache` | The Transfer Server copies the requests' complete pages into the successor's cache, or into host storage when staged (`"staged": true`) |
| `park` | New requests wait, and the serving world parks at a step boundary |
| `evict` | Staged only: the parked world evicts its cache segments, whose pages host storage holds |
| `materialize` | Staged only: the successor loads the copies staged in host storage |
| `promote` | The successor imports the parked world's index, takes the requests in flight and admits the waiting ones |
| `keep_previous` | The previous world is kept as `previous_world` states |
| `trial` | The successor serves on trial until a commit or a rollback |

A step that moves bytes names them per link (`links`): each entry is `{"source", "target", "bytes"}`, an end being `{"gpu": "GPU-…", "host": H}`, `{"host_storage": H}` or `{"remote": ENDPOINT, "gpu": …}`. `prepare` names the weight manifests' link loads of a successor of another parallel configuration (with their estimated `seconds`); `warm_cache` names the warm copies (with host staging also the serving world's rollback copies, `"copy": "rollback"`), from each GPU's in-flight KV cache in the successor's layout; `materialize` names the staged copies loaded over the host links and their wait (`stall_ms`, at the host link's measured bandwidth); `promote`, for a successor that maps the serving world's cache, names each GPU's partial last pages it copies into units of its own. A warm copy into a successor of other target ranks names its `sources`, the serving GPUs the storage plan read (none for a successor on GPUs of its own, whose plan reads no serving GPU), rather than one source: the cache manifest the warming plans from the layouts the successor's workers report divides it among them, and the change's report names the links it planned.

**Derived state.** `derived_state` gives each derived state's `treatment`: `mapped` (the successor reads the serving world's copy read-only, or the shared host tier it is keyed in), `moved` (the Transfer Server copies it into storage of the successor's own, laid out for it), `recomputed` (computed again: weights from the model's files, request state from the requests' tokens, optional state in the background), `continued` (the requests in flight continue with the state they reached under the serving world's numerics, `in_flight = "keep"`) or `dropped` (the successor holds none):

| State | Treatment |
| --- | --- |
| `weights` | `mapped` where every key stays; `moved` through copy manifests for another parallel configuration; `recomputed` from the model's files when they, the dtype, the quantization, the load format or the weight source change (tensors whose keys stay are mapped) |
| `kv_pages` | `mapped` when the successor maps the serving world's segments; `moved` by warm copies when it lays out its own; under other numerics `continued` (`keep`) or `recomputed` (`recompute`); `recomputed` without an exact conversion of a changed encoding (`without_exact_conversion`) |
| `recurrent_checkpoints` | As the K/V pages: they lie in the same pools, warm at exact page boundaries and are keyed alike |
| `draft_cache` | `dropped` in a successor that does not speculate; `recomputed` by refills where the serving world kept none or the successor lays out its own cache (warming copies the required groups alone); otherwise as the K/V pages |
| `encoder_outputs` | `mapped` from the host encoder pools every world maps, and `recomputed` for an output whose encoder computes otherwise: its key holds the encoder's identity, decided per output |
| `latents` | `moved`: stored in the host latent pools at the park and restored at the step they reached, laid out for the successor; under other numerics `continued` (`keep`) or `recomputed` from noise (`recompute`) |

**Backfill.** `promotion_backfill` is what the promotion fills in for the requests in flight while new requests wait: `bytes` it copies (the staged copies over the host links, or the partial last pages on each GPU; none for warmed requests without staging), `stall_ms` of the staged copies, the `requests` in flight, and `tail_tokens_per_request`, the most tokens each computes then: none when it maps its pages, at most `update_config.cache_tail_tokens` (else a page, at most 64 tokens unless `kv_cache_config.block_size` states it) when warmed, and `null` when it computes its whole state again.

A change's report has the same `steps` (each with the links it moved, from the cache manifests the warming and the staged load executed) and `derived_state` under the numerics observed; `encoder_outputs` keep both treatments, since the daemon never learns an encoder's identity.

**Status.** `GET /admin/config` reports each replica's two `slots`, the first holding the world that serves (or, while requests wait for a promotion or a rollback, the one that served last) and the second the world beside it, each as `{"world", "state"}`: `empty` (`"world": null`), `preparing` (a successor starting, or a previous world a rollback starts again), `executing`, `parked`, `weights` (its weights alone), `host` (its weights in host storage) or `unavailable`, with the `reason` (its engine failed or ended, or a rollback stops it). While a change or a rollback runs, `update` reports its `phase` (a step name, or `rollback`), `started` and `seconds` since, the successor's `world`, the promotion's `pause_seconds` while requests wait, `step_time` while the successor prepares (the largest ratio of a serving scheduler's step time to its baseline of the same batch size in the latest interval, the tolerated `slowdown`, whether the link budgets stand `halved`, and the `halvings` and `restorations` so far, `crates/daemon/src/interference.rs`), and `moved`: the bytes every node's Transfer Server copied for the deployment since the change began (`bytes`, of `submitted_bytes`, and both `by_priority`), from each node's Storage Server's counts, which a hot restart hands over (`null` while no engine reads the ledgers). One change runs at a time, so every transfer of the deployment since it began is the change's.

## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`POST /admin/restart`, `crates/daemon/src/restart.rs`), as Envoy's hot restart does. It starts its successor (`uniserve serve --predecessor`) with a socket pair between them. The successor first restarts the host's Storage Server in place when that server speaks an earlier protocol than the successor's build, so that an update replaces the Storage Server before the daemon and the daemon before the world (a failure leaves the daemon serving as it was); it then loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec, the admin's log and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. The engine and its workers are the same processes throughout. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits (`UNISERVE_LIFELINE`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A host's Storage Server restarts in place too (`uniserve storage restart [--executable PATH]`, `crates/storage-server/src/restart.rs`). The server starts its successor and, once no request, shoot-down, connector task, transfer or exposure to another host is in flight, stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's storage and every page pool's memfd, with its state; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. Another host's READs of this host's storage are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

## The KV cache's storage and the weights

A device KV cache is split along its units into eight segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/worker/src/storage/prefix_cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses.

- Every GPU has a storage ledger for each deployment that uses it, kept by the host's Storage Server: the quota, `⌊total × mem_fraction_static⌋` of the whole GPU, and every item the deployment's worlds and the host's Transfer Server hold there. The server books what it retains, each storage once however many worlds map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent banks). The processes book what it cannot see: each warm worker its graph pool and its process storage (its CUDA context, PyTorch's and Rust's allocations, communicator buffers, the product storage it has yet to make resident, and while a `range_metrics` profiling session runs, its range profiler pass), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, lane or exposure to another host uses it any more. A ledger without room for the context refuses it, and the transfer task that needed the GPU fails, naming the ledger. The server refuses a booking or a new device storage that would take a ledger past its quota, so a ledger never exceeds it; a worker that does not fit its quota fails its startup with every entry of the ledger. A booking ends with the process that made it; a world's storages end with the world, and the segments a successor maps become its own on the ledger when the previous world is retired. Two worlds therefore size their caches against one quota: a worker's grant is the quota less everything the ledger books beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the storage the fraction leaves, and book once promoted in place of the rank they stand by for; the processes of one scope and world count as their largest booking.
- A world change shrinks the serving world's cache by its tail (above). Each worker reports its segments with its GPU's ledger; the scheduler computes the limit the ledger leaves the serving world's cache beside the successor and withdraws the units of the segments past it from allocation (the first segment, which holds the padding and warmup units, always stays), and once no request holds a withdrawn unit the workers give the tail back. A request recomputed past `update_config.preempt_after`, or because it cannot get a unit to continue, ends as migratable and the daemon submits it again with its generated tokens, recomputed on the units left, as vLLM's recompute preemption does. The plan of a change (`storage`, also in a dry run's answer and the change's report) gives for each GPU its host, the worker's scope and world, the quota, the serving world's weights, graph pool, process storage, exclusive storages, staging and KV cache, what the successor adds (weights it does not map, graph pool, process storage, exclusive storages, head segment, the requests in flight), the Transfer Server's items, the limit, the segments kept and every ledger entry; and for each host what it admits of new host storage, of which a successor that shares the serving world's page pools needs none. Each GPU's plan also states what each step that relieves the device frees there, whether or not the plan takes it (`steps`, `specs/online-operations.md` §6.5): in the preparation, the tail's idle prefix pages and the rest of the tail, the warm copies a successor that recomputes the requests in flight would otherwise prepare on the device, and the serving world's graph pool; in the trial, a parked previous world's segments past its first that the successor does not map, the weights a previous world kept in host storage moves there, and what a previous world kept as its weights or in host storage releases with its processes; and how long a promotion that moves the KV cache of the requests in flight through host storage would wait for it at the host link's bandwidth the Transfer Server measured (`promotion_stall_ms`), which each GPU's ledger states. A successor's cache grows as each ledger has room: at once by what a previous world kept as its `weights` released when its processes exited, and to its whole size after the commit retired the previous world.
- `/admin/sleep` holds new requests, recomputes the token requests in flight as a shrink does (an image-generating request continues from its stored denoising step, recomputing only if that trajectory is absent; `docs/architecture.md`, Image preemption), preempts the video requests in flight at their next denoising step boundary with their trajectories stored in the host latent pools (`docs/architecture.md`), which continue from that step once the deployment wakes, and lets the readouts finish; the workers then give back every segment and suspend their CUDA graph storage (`uniserve.sleep`). `/admin/wake_up` creates the cache again, restores the graph storage and lets the held requests through. A sleeping deployment refuses world changes.
- `/admin/update_weights` checks that the daemon would process the new checkpoint's requests as the served model's (the same `tokenizer.json`, tokenizer settings, generation defaults and chat template, and the same model facts) and holds new requests. Every worker loads the checkpoint into new storage as it loaded the model and copies every tensor into place once all of them match in representation, shape and element type (`uniserve.loading.rank.update_weights`). The requests in flight continue as `in_flight` says (vLLM's `keep` and `abort`, SGLang's `in_place`, `retract` and `abort`): with `keep`, once the batches in flight complete, the workers load the checkpoint beside the KV cache, giving back their CUDA graph storage for the load when the free storage alone does not hold it (and refusing the update, unchanged, when even both do not), and every request in flight continues on the new weights with the KV cache it reached; what it computes afterwards follows neither checkpoint, so it publishes no page. A video request in flight continues its trajectory on the new weights with `keep`, a trajectory of neither checkpoint. With `recompute` the engine recomputes the token requests in flight, image-generating ones included, preempts the video requests in flight as a sleep does (they continue from noise, since the new weights compute other trajectories) and lets the readouts finish, and with `abort` it ends every request it holds, aborted; then it puts its workers to sleep, so that the cache's storage holds the new checkpoint as it loads, and wakes them after. A checkpoint that loads other tensors leaves the weights as they were. The workers rename their retained weights after the new checkpoint at the Storage Server, which a relaunch on it binds, and the engine flushes its prefix cache and keys host KV cache pages by the new weights. Weights streamed from host storage and DWDP experts are not updated in place: such a deployment is brought up again on the new checkpoint.

## Expert redistribution

`POST /admin/rebalance_experts` changes the distribution of routed expert weights while preserving the number of physical slots on each rank. Module paths are the names of `FusedMoE` modules in the loaded model. Layers omitted from `order` keep their distribution. An invalid permutation or unknown layer is rejected before copying starts.

The serving scheduler reserves the copy plan's additional storage on each GPU, releasing available KV tail segments as needed while requests continue. The Transfer Server copies retained expert regions into that storage. At a common computation boundary, workers remap the completed allocations at their captured weight addresses and update logical-to-physical routing tensors. The world, CUDA Graph addresses, request state and numerical weights remain the same. Once the operation finishes, the cache can grow into the released storage. The response lists each replica's world, requested order and allocation plan.

Distributed weight data parallelism (DWDP) prepares the resident shards, peer mappings and prefetch buffers of the requested distribution in the background; admission includes these allocations. Commit replaces the backing of the existing composite weight addresses and the prefetch copy plans together. A component that streams dense projections from host storage keeps those host allocations while its resident experts are redistributed.

The committed distribution is included in worker recovery launches and daemon handoff. A failure during preparation releases incoming copies and leaves the active distribution intact. A failure during publication triggers the existing engine recovery path with the committed distribution; a world on trial follows its normal rollback policy. A redistribution that changes rank shapes requires a configuration change through `PUT /admin/config`.

## LoRA adapters

The adapters are an extension point: a plugin keeps the adapter pool at fixed device addresses, allocated before the CUDA graphs are captured, and implements the worker hooks `load_lora_adapter` and `unload_lora_adapter`. `/admin/load_lora_adapter` assigns the adapter the lowest free slot of the pool and has every worker run `load_lora_adapter` with the request's body and the slot (`adapter`); from then on a request that names the adapter as its `model` computes with it, `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. The worker writes each request's slot into its per-slot state at admission, and the causal LM runner fills, inside every forward, captured or not, the slot of every token's adapter into a fixed `[T]` tensor, which the plugin's kernels read through `uniserve.adapters.tokens()` (0: no adapter). An engine that replaces another, after a world change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry, so requests naming it are refused. `/admin/unload_lora_adapter` removes the name at once and has every worker run `unload_lora_adapter` with the slot.

## Nodes

`uniserve serve --host H --port P` without a model runs a node's daemon serving no deployment. Its first `PUT /admin/config` with `{"config": TOML, "set": ["PATH=VALUE", ...]}` brings one up (`202`, with the deployment's name), as `uniserve serve --config` with those assignments would, and the node serves its API and admin routes on the same address once it starts, every later `PUT /admin/config` being the deployment's; `GET /admin/config` of an idle node reports no configuration; `GET /admin/node` reports `idle`, `starting`, `serving` or `stopping` and the last deployment's error. The deployment's `POST /admin/shutdown` brings it down and releases its storage, after which the node takes the next deployment. A node serves one single-node deployment at a time.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else: a node never calls it or waits for it, so it attaches by reading a node's status and events and detaches by stopping.

```bash
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 status
uniserve-manager --node http://10.0.0.2:8000 watch            # Ctrl-C detaches
uniserve-manager --node http://10.0.0.2:8000 apply --config qwen3.toml   # an idle node deploys
uniserve-manager --node http://10.0.0.2:8000 --node http://10.0.0.3:8000 apply --set cuda_graph_config.decode_batch_sizes=1,2,4,8 --commit-after 300
uniserve-manager --node http://10.0.0.2:8000 config
uniserve-manager --node http://10.0.0.2:8000 commit                      # or rollback
uniserve-manager --node http://10.0.0.2:8000 shutdown
```

Each `--node` is the leader of one service (one served model name). When several services share GPUs and hosts, `apply` decides the order of their updates and calls each service's admin API in turn (`crates/manager/src/updates.rs`); every step within a service is the service's own, and no node waits for the manager. Before it starts a service's update, the manager reads the GPUs its worlds hold (`GET /admin/config`, `gpus`) and its plan (`PUT /admin/config` with `dry_run`): whether it starts a new world, the GPUs its successor prepares on (the storage plan's GPUs and the target ranks of its weights' plan), each host's host storage it requires and admits, and whether every GPU and host it uses has the storage it requires. Services are taken in the order given; a service whose update starts a new world starts only when no update in progress (preparing, or on trial until committed) holds one of its GPUs, so two services that share a GPU are never prepared at once, when its plan, made just then, fits, and when the host storage it requires on each host, beside what the updates in progress there required, is within what the host admits. Services that share no GPU and whose host storage fits together update at once. A service that cannot start waits and is planned again whenever an update in progress ends, since a commit releases the previous world's storage. With `--commit-after S`, the manager commits each new world once it served on trial `S` seconds and completes that service's remaining replica trials; without it, each new world stays on trial for the operator and holds its GPUs, and the services that share them wait for the next `apply`. A failed update or a trial that rolled back by itself stops the services not started, which the manager names with why each waited; the updates in progress go on to their end, and committed ones remain applied. A plan that fits nowhere while no update is in progress is a refusal. `--dry-run` prints each service's plan and the order the manager takes them in. An idle node's deployment names no GPUs before it starts, so the manager orders it by nothing but the order given.

## Worker hooks

A worker hook is a named operation that runs on every worker of the deployment at a step boundary, while no forward runs. A plugin implements it (`docs/plugins.md`):

```python
def register(registry):
    registry.hook("load_lora_adapter", load_lora_adapter)

def load_lora_adapter(payload, models):
    # payload: the request's JSON body; models: the modules the worker loaded
    ...
    return {"adapter": slot}
```

The endpoint answers with every worker's result. A hook no plugin implements fails with that reason. Hooks named `uniserve.*` are the engine's own (the cache's storage, sleep, wake, a world's promotion and commit, the weight update, the fence probes' switch and the profiling sessions), which run through their endpoints alone; a plugin cannot register one.
