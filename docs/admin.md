# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on two Unix sockets of its own, apart from the client API: one for the operator, with every route, and one for a harness, with the verbs of an update ([Listeners](#listeners)). Access is the sockets' file permissions. Everything a deployment can do while it serves goes through it: `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of it among others. Its requests and responses are JSON of one typed schema, the interface crate's `proto::admin` (`crates/proto/src/admin.rs`), which the daemon serves and its clients read.

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/status` | What the node serves (`state`): `idle`, with why its last deployment failed to come up or down (`last_error`); `starting` or `stopping`, with the deployment's `name`; or `serving`, with the deployment (`deployment`: name, model, the engine's lifecycle state, paused, asleep, requests in flight, the new requests the daemon holds while generation is paused, the engine sleeps or no engine serves (`held`), the launch generation of the engine that serves (`generation`, which names its row of `GET /admin/config`'s `processes`), the parked standby's launch generations (`standby`, empty without one), the update in flight (`update`: its number and phase, `null` without one)) and the daemon's readiness record (`readiness`). Beside it, whatever the node serves: the running and the last operation (`operation`, `last_operation`: identity, kind, state, start and end, error) and the next event's sequence number (`next_event`) |
| `GET /admin/events?after=N&wait=S` | The node's events after sequence number `N`, waiting up to `S` seconds (at most `admin_config.event_log.longest_wait`, a minute unless stated) for one; `next` is the number to read after next, and `gap` says that events after `N` already left the log, which keeps the newest `admin_config.event_log.capacity` (1024 unless stated). Each event has its sequence number, time, message, category (`kind`) and what it carries (`data`): `operation`, an operation's start or end, with the operation; `engine`, a change of the serving engine's lifecycle state (`from`, `to`, `reason`); `update`, a phase an update entered, with the update as it stood; `deployment`, a deployment coming up, serving, holding or serving new requests, or coming down, with no data. The log is the node's: every deployment it serves writes it, and a hot restart hands it to the successor |
| `GET /admin/config` | The configuration as TOML (as `--config` reads it) and its digest; the engine that executes, with its epoch number (`epoch`) and lifecycle state (`executing`: `starting`, `parked`, `serving`, `draining`, or `unavailable` with the reason); each replica's own report as `replicas`; the update in flight or the last one (`update`), with its report; the targets a rollback marked unavailable with their reasons (`unavailable`); every epoch's record and this daemon's engine processes (below, Dry runs and status); the GPUs the deployment reserves storage on (`gpus`: each one's host, its UUID as the device reports it (`gpu`, `GPU-` and 32 hexadecimal digits in groups of 8, 4, 4, 4 and 12), total, quota and used bytes) and the quotas (`quotas`): for each host of the deployment, every GPU's limit and each reservation's item, scope, `epochs`, KV cache segment and bytes, and what the deployment's transfer tasks copied there by priority (`tasks`) |
| `PUT /admin/config` | Apply: a configuration change, `{"config": TOML, "set": ["PATH=VALUE", ...], "in_flight": "keep", "dry_run": false, "force": false, "deadline_s": SECONDS, "wait": true}`, as `uniserve serve --config FILE --set PATH=VALUE` states a configuration; without `config` the target is the current configuration with the assignments. An optional zero-based `replica` selects one independent replica for a change in place; otherwise the change covers the deployment. The change does the least the target needs (below). `dry_run` reports what the change would do and changes nothing; `force` applies a target a rollback marked unavailable; `deadline_s` states the seconds from the apply by which the update must be committed, after which the daemon rolls it back; `in_flight` is `keep` or `recompute` for the requests that migrate at an epoch's switch. On a node that serves no deployment it brings the deployment of `config` and `set` up instead ([Nodes](#nodes)). The operation's result states what the change did (`change`): `none`; `in_place`, with each replica's switch; `dry_run`, with the dry run's report; `generation` or `epoch`, with the update it started (`update`); `daemon`, with the successor daemon's process id and `"then": "update"` when the successor applies the rest; `deployment`, for a deployment an idle node brought up |
| `POST /admin/config/commit` | Commits the update in flight ([Updates](#updates)): its decision is recorded and the kept side is released. Asked before the trial began, the commit is kept and applied when it begins. Refused (`400`) with no update in flight |
| `POST /admin/config/rollback` | `{"reason": TEXT}`: rolls the update in flight back. The kept side serves again, the new is released, and the target is marked unavailable with the reason, so applying it again needs `force`. Asked while the update prepares, it abandons the update and marks nothing. Refused (`400`) with no update in flight |
| `POST /admin/pause_generation` | New requests wait; those in flight go on (SGLang's endpoint of that name) |
| `POST /admin/continue_generation` | New requests are served again |
| `POST /admin/flush_cache` | The engine revokes every cached prefix page; requests in flight keep theirs |
| `POST /admin/restart` | A hot restart of the daemon: `{"wait": true}`. A successor daemon, which re-executes the running daemon's own image, takes the deployment over while this one finishes the requests it took (below); answers with the successor's process id once it serves (`result.pid`) |
| `POST /admin/shutdown` | Brings the deployment down as SIGTERM does, finishing what is in flight within `server_config.shutdown_timeout`, and releases its weights and caches at the host's Storage Server unless `{"retire": false}` |
| `POST /admin/update_weights` | `{"model_path": PATH, "in_flight": "keep"}`: the engine rewrites its weights in place from another checkpoint of the served model, a local directory or a Hugging Face repository (SGLang's `update_weights_from_disk`; below); `in_flight` is `keep` (the default), `recompute` or `abort` |
| `POST /admin/rebalance_experts` | `{"order": {MODULE_PATH: [EXPERT_ID, ...]}, "replica": INDEX}`: rearranges routed experts within the current epoch. Each list is a complete permutation of logical expert IDs in global physical-slot order. Omit `replica` to update every independent replica in sequence |
| `POST /admin/sleep`, `/admin/wake_up` | The engine gives back its KV cache and CUDA graph storage and keeps its weights, and restores both (vLLM's endpoints of those names; below) |
| `POST /admin/load_lora_adapter`, `/admin/unload_lora_adapter` | `{"lora_name": NAME, ...}`: the workers load a LoRA adapter into a slot of the adapter pool, or unload it (vLLM's endpoints of those names; below) |
| `POST /admin/profile` | Starts a profiling session on every worker of the executing epoch at the engine's next step boundary: `{"collectors": [...], "steps": N, "start_step": N, "seconds": S, "stages": [...], "workers": [...], "modules": [...], "output_dir": PATH, "max_slowdown": F, ...}` (`docs/profiling.md`); answers with the session, each worker's file and its collectors' states. One session runs at a time: another is refused (`400`) until it ends, as is a session naming more than one of `pm_sampling`, `range_metrics` and `pc_sampling`, which share the device's performance monitors, and, while `profiling_config.graph_pc_sampling` keeps PC sampling enabled on every worker, a session of `pm_sampling`, `range_metrics` or a timeline that traces graphs whole. A `range_metrics` session reserves its range profiler pass's device storage in the quota of each selected worker's GPU, as part of the worker's process item, until it ends: where a quota lacks the room, the KV cache first gives back tail segments, as an epoch change's preparation does (the requests holding them run on, and the session starts once they let them go), and grows back once the session ends. A session for which even the segments past the first leave too little room is refused (`400`), naming the bytes and every quota entry |
| `GET /admin/profile` | The running session, or the last that ended: its state and why it ended, the steps and bytes its workers recorded, the step time before it and during it, the quality-of-service guard's actions and each worker's file; `null` before any |
| `DELETE /admin/profile` | Ends the running session at the engine's next step boundary, every worker writing its file |

Each write is an operation: it has an identity, runs on a task of its own, and ends `succeeded` or `failed` in the status and in the event log, whether or not the client that asked stays connected. One operation runs at a time; another is answered `409`. A write answers with its operation (`id`, `kind`, `state`, `started`, `ended`, `error`) and, once it succeeded, its result (`result`); `"wait": false` answers at once with `202` and the operation running. The status and the event log state an operation without its result, which the answer alone carries.

## Updates

An update moves a deployment to another set of modules while it serves, as a trial that is committed or rolled back. A deployment runs the package revisions its epoch names; installing a package at the Build Server selects nothing, and `PUT /admin/config` (apply) is what moves them. The daemon fixes the target's module set once, when the configuration is applied: it asks the Build Server's `cover` for the revision of the engine package, the scheduling policy and every kernel package, builds every module on every host the target runs on, and compares the fixed set with what the serving epoch runs. A change then does the least it needs:

- **Nothing an engine executes** changed: the options the workers switch in place (`profiling_config.fence_probes`, `fence_probes_off`) take effect at the engines' next step (`in_place`); a target equal to the serving configuration changes nothing (`none`).
- **The daemon's own options** changed (`server_config`, `admin_config`, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `migration_config`, `mm_processor_kwargs`, `build_config`, `update_config`): the daemon restarts itself in place (`daemon`, below), and its successor applies the rest of the change in an operation of its own (`"then": "update"`).
- **Kernel or policy packages** changed, the policy's parameters included (`scheduler_config`, the scheduling limits, `speculative_config.expected_speedup`, `refill_token_cost`, a newly installed revision at an unchanged configuration): an update in its **generation** form, inside the serving engines.
- **The engine package, the build configuration or the checkpoint** changed (`worker_config.engine`, `worker_config.engine_revision`, the parallel shape and block ownership, `dtype` or `quantization`, the KV layout, the graph buckets, the slot count, the model's files): an update in its **epoch** form, target engines started beside the serving ones.

A change of the served model name is refused because it names the deployment. A change of the model's files, `dtype`, quantization, load format or weight source loads the other keys from the files beside the serving epoch's; a change of the parallel configuration, the devices or the hosts spreads the weights differently, and the target's engines receive them from the serving epoch's retained chunks rather than reading the checkpoint where an epoch already holds them. Other model files serve the deployment only when requests are processed as the serving ones are: the same tokenizer, templates, generation defaults and model facts.

### One update, two forms

An update has one phase machine in the daemon (`crates/daemon/src/updates/update.rs`), whatever it moves. Every phase ends on acknowledgements the engines make, never on an assumption about their progress.

| Phase | Meaning | Ends when |
| --- | --- | --- |
| `preparing` | The new is made ready beside the old; serving is untouched | Every engine acknowledged it is ready, or one failed: the update is `abandoned` and nothing changed |
| `switching` | Service moves at a boundary: to the new, or back to the kept side when the update rolls back (`"rollback": true`) | Every engine acknowledged the switch |
| `trial` | The new serves and the old is kept | A commit or a rollback |
| `committed`, `rolled_back` | The kept side is released | — |

| | Generation | Epoch |
| --- | --- | --- |
| Preparing | `Prepare` to each serving engine: it resolves the new modules, rebinds the graphs whose launch table is unchanged and recaptures the others, instantiates the policy, and shadows each changed kernel on a paired forward. `Prepared` acknowledges; `PrepareFailed` abandons | Every node's daemon starts the target's main processes for its host, of every replica the target's configuration places (each world's scheduler node and its peers), each from a launch file the leader made that states the epoch's whole module set, the engine it succeeds and its own launch generation; every node then claims the target epoch's storage. Each engine opens its session with its host's buffer pool, maps the weights it shares, resolves its modules, captures its graphs and parks. Every engine's `Parked` acknowledges |
| Switching | `Switch` to each serving engine, at one batch boundary inside the process. `Switched` acknowledges | Both epochs step. `Promote` to every target engine, which opens admission and acknowledges with `Serving`; from the first `Serving` the daemon routes every new request to the target, and the serving engines go on with what they hold. Once every target serves, `Drain` to every serving engine with the deadline `update_config.drain_s` from then, and with `shrink` to each whose layout no target replica has: a draining engine admits nothing and steps its running requests until each ends by itself, and at the deadline ends the rest as migratable (a token request with its blocks committed under their keys, a video request at its next denoising step boundary with its trajectory saved), which the daemon resubmits to the target; with `shrink` it gives its device memory back as its requests end and the target grows into it. Every serving engine's `Drained` ends the switch |
| Kept during the trial | The previous generation, inside the engine | The previous epoch, as `update_config.previous_epoch` states: `parked` (its engines, drained and alive), `weights` or `host` (its engines stopped, its weights retained on the GPUs or in host storage) |
| Rollback | `Rollback` to each engine: it returns to the kept generation at a batch boundary. `RolledBack` acknowledges | The switch the other way: the previous epoch's parked engines are promoted again, or started again at the next launch generation on the weights they kept, and new requests return to them from the first `Serving`; then `Drain` to every target with the same deadline. A target that failed, or one never promoted, is stopped instead of drained |
| Commit | The epoch's record keeps the new modules; `Commit` tells each engine to release the previous generation after its last batch | The target's record becomes `serving`; the previous epoch's engines are stopped and its storage is retired by a claim of the target's epoch |

A trial ends by a decision (`POST /admin/config/commit`, `/rollback`), or by itself: on a process-fatal fault, a stalled job, non-finite logits or an engine's exit; on a threshold the operator set (`update_config.rollback`: the failure rate of the requests that ended on trial, the step-time and throughput regressions over a window against the steps served before the switch); and at the deadline the submitter stated when applying (`deadline_s`). A commit records its decision, the phase and the epoch's record, before it releases anything, so an engine lost while the kept side is released is replaced by one of the committed modules. A rollback marks the target unavailable with its reason: applying the same build configuration and module set again needs `force`, and a revision installed later is another target. An update that was abandoned marks nothing.

One update is in flight at a time, and one admin operation runs at a time. The `config` operation ends once the change is applied or its update started, so a commit or a rollback can follow at once; with `wait` (the default) the response comes when the update reached its trial or ended before it, with the update as it stands in `result.update` (`200` on trial, `409` when it was abandoned or rolled back). A commit asked while the update prepares or switches is kept and applied when the trial begins; a rollback asked while it prepares abandons it, and one asked while it switches is applied once the switch ended. An update does not cross a daemon hot restart: the restart waits until it ends.

### Epochs, generations and launch generations

An **epoch** numbers one engine build with its build configuration, and keys its storage at the Storage Server. A **generation** numbers the set of kernel and policy modules an engine executes; the engine assigns it and states it in its `Prepared`, `Parked` and `Serving` reports. A **launch generation** identifies one process of a worker group and rank: a serving engine, its standby, an update's target, a relaunch. The daemon takes launch generations from one counter per group and rank, above every live one, and addresses every command by it.

The daemon keeps one record per epoch: the build configuration, the module set fixed when the configuration was applied, the modules a generation's trial keeps, the generation its engines numbered, and a status (`preparing`, `serving`, `trial`, `released`). The module set is part of every launch file made from the epoch, so a relaunch and a standby run exactly what their epoch runs.

An epoch update covers the whole deployment: every node, every main process and every independent data-parallel replica of both epochs. The two epochs need not have the same number of nodes, main processes, schedulers or ranks: the target's shape is its configuration's, and nothing maps the engines of one epoch to the other's. Target replica `i` serves under the deployment's replica `i`; a serving replica past the target's last hands the requests it migrates to a target replica, and a rollback does the same the other way. A serving replica and a target replica have different layouts when they differ in their parallel configuration (degrees, forms, worker groups, devices, hosts), their slot count (`max_running_requests`), their KV layout (`kv_cache_config.block_size`, the cache's precision) or their graph buckets (`cuda_graph_config`); the cache's size and its tiers are no layout, and neither is the number of replicas, so a replica that keeps its place when replicas are added or removed keeps its layout. A serving replica whose layout no target replica has drains with `shrink`, and the status reports `shrink` when any does. A migrated request carries its generated tokens and seed: on a target of the same layout and numerics it finds its committed blocks by their keys and pays one admission and the copy of its partial last block; on one of another layout or other numerics its keys reach nothing and it computes its state again, as it does with `in_flight = recompute` (`Promote.recompute`). Nothing of the cache is handed over.

### Startup

Starting is not an update. The daemon fixes the epoch's module set at the Build Server and has it built at the Build Server of every host the epoch runs on before any engine starts, and every engine starts from a launch file that states it: the engine resolves every module its profile runs name, captures its graphs and serves (`Serving`), or parks when its launch names the engine it succeeds (`Parked`).

### The standby

With `worker_config.standby`, the daemon keeps a parked engine of the serving epoch beside every serving engine, at the next launch generation and with its own CUDA contexts: a sticky error of the serving process cannot touch it. A standby is started as an epoch update's target is, from a launch file that states the epoch's module set and the engine it succeeds, and parks by itself with its graphs captured. A process-fatal fault promotes the whole failure domain (`Promote` on each standby's process link, every promotion issued before any is awaited), and each node then starts a new standby. Where a member of the domain has no parked standby, the domain is relaunched instead and finds its weights retained. A standby exists only while its epoch serves; an epoch that prepares or is on trial keeps none, and a generation's commit replaces the standby with one of the committed modules. `worker_config.standby_storage` states whether a standby keeps its graph pools on the device (`resident`) or gives them back until its promotion (`suspended`).

### Dry runs and status

A dry run (`"dry_run": true`) reports what the change would do and changes nothing, by its form (`change`): `in_place`, with what each replica the change reaches would change (`daemon`, `scheduling`, `fence_probes`); `generation`, with the serving epoch and the module set the apply would fix; `epoch`, with the epoch it would create, the engine package, the number of replicas, each replica's engines with their hosts and launch generations, and whether the layouts differ (`shrink`); `deployment`, for the deployment an idle node would bring up.

`GET /admin/status` states the engine's lifecycle (`deployment.engine`: `starting`, `parked`, `serving`, `draining`, `stopped`, `failed`; `holding` while an engine is being replaced; `closed` once none will serve) and the update in flight (`deployment.update`: its number and phase). `GET /admin/config` reports the update in flight, or the last one, under `update`: its form (`change`), number, phase, epoch, the generation its engines numbered, how long its switch took (`switch_ms`), how long it has been on trial and how long until its deadline (`trial_s`, `deadline_s`), its failure, the operators the engines could not compare (`uncompared`), for an epoch update its serving and target engines (`engines`), the drain's deadline (`drain_s`) and whether the layouts differ (`shrink`), what the previous epoch is kept as, and what its trial and transfers read (`trial`, `transfers`). It also reports each epoch's record (`epochs`: its number, build configuration, packages by slot, the packages a generation's trial keeps, generation and status) and this daemon's engine processes (`processes`), one row each: group, rank, pid, epoch, launch generation, build and state (`starting`, `parked`, `serving`, `stopped`, or `failed` with its `reason`). Every phase an update enters is an `update` event in `GET /admin/events`, whose `data` is the update as it stood.

## Listeners

The daemon serves the admin API apart from the client API, on two Unix sockets, and access is their file permissions. Every daemon owns an instance directory, `daemon.XXXXXX` inside UniServe's directory of the user's runtime directory (`$XDG_RUNTIME_DIR/uniserve`, mode `0700`), which it creates when it starts and removes when it ends; its sockets lie there, and a caller reads their paths from its readiness records. A daemon run without `XDG_RUNTIME_DIR` is refused.

| Listener | Socket | Mode | Serves |
| --- | --- | --- | --- |
| Client API | `admin_config.host`, `port` or `uds`; port `0`, the default, picks a free port | — | The OpenAI API, `/health`, `/metrics`, `/version`; no `/admin` route |
| Operator | `admin.sock` in the daemon's instance directory | `0600` | Every admin route |
| Harness | `harness.sock` in the daemon's instance directory | `0660` | The verbs of an update and what a harness reads to decide one: `GET /admin/status`, `/admin/events`, `/admin/config`, `PUT /admin/config`, `POST /admin/config/commit`, `/admin/config/rollback` |

The daemon binds all of its listeners when it starts, before it loads anything: the client listener, the two admin sockets and, on the leader of a deployment other nodes may join, the join listener (`dist_init_addr`, port `0` allowed). It reports what it bound in its readiness record, one JSON line written to the descriptor its caller passes with `--ready-fd FD` (as systemd's `sd_notify` reports a service's state): `{"state": "listening", ...}` once the listeners are bound, and `{"state": "serving", ...}` once it serves, after which the descriptor closes; a daemon that ends before it serves closes the descriptor without the second line. A record states the daemon's `pid`, its `instance` directory and its `endpoints`: `client`, `admin`, `harness`, `join`, and, once it serves, the host Storage Server's `storage` socket and `peer` TCP endpoint (each `null` when absent; a Unix socket is written `unix:PATH`, a TCP endpoint `HOST:PORT`). Connections that arrive before the daemon serves wait in the listeners' backlog. `GET /admin/status` reports the same record (`readiness`). A deployment's other nodes join the leader at the `join` endpoint of its record (`uniserve serve --nnodes N --node-rank R --dist-init-addr JOIN`).

A harness is an agent program that observes the deployment, installs packages at the Build Server and applies, commits or rolls back. The operator grants it access through the harness socket's group. On the harness listener, `PUT /admin/config` takes assignments (`set`) only, for the package selections (`worker_config.engine`, `worker_config.engine_revision`, `scheduler_config.policy`, `attention_backend`, `prefill_attention_backend`, `decode_attention_backend`, `moe_runner_backend`, `moe_config.exchange`) and the options the operator lists in `admin_config.harness_options`; a whole configuration, one replica and `force` are refused with `403`. The operator's operations (weight update, sleep, wake, LoRA, expert rebalancing, pause, flush, profiling, shutdown, daemon restart) are not routes of the harness listener.

A hot restart's successor goes on in its predecessor's instance directory, binds both sockets over its predecessor's, which finishes the requests it accepted, and owns the directory once the handover completed. An example, reading the sockets from the record:

```bash
uniserve serve Qwen/Qwen3-30B-A3B --ready-fd 3 3>ready.jsonl >serve.log &
# once ready.jsonl holds the line whose state is "serving":
admin=$(jq -r 'select(.state == "serving") | .endpoints.admin | ltrimstr("unix:")' ready.jsonl)
harness=$(jq -r 'select(.state == "serving") | .endpoints.harness | ltrimstr("unix:")' ready.jsonl)
curl --unix-socket "$admin" http://admin/admin/status
curl --unix-socket "$harness" -X PUT http://admin/admin/config -d '{"set": ["attention_backend=trtllm"], "deadline_s": 600}'
```


## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`POST /admin/restart`, `crates/daemon/src/restart.rs`), as Envoy's hot restart does. It starts its successor (`uniserve serve --predecessor`) with a socket pair between them and sends it its options with the version of the engine interface it and its engines speak; a successor of another version gives up, as does one whose Storage Server protocol the host's Storage Server does not speak (the server refuses the successor's hello with a typed version refusal), and the daemon serves on as it was. Every interface has one version per release, so a restart in place stays within a release: a deployment moves to another release by a full restart. The successor then loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec, the admin's log and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. The engine and its workers are the same processes throughout, and serve on through the successor with their relaunches and their standby: the successor speaks the same version of the engine interface (`proto::ENGINE_INTERFACE_VERSION`), the one version a daemon serves; it refuses an engine of any other at its hello with a typed refusal naming both versions. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits at the descriptor the last option of its command line names (`--lifeline FD`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A host's Storage Server restarts in place too (`uniserve storage-server restart`, `crates/storage-server/src/restart.rs`), into the build of the `uniserve` that runs the command: the command passes its own executable to the server, which starts its successor from it. Once the successor speaks the server's versions and no request, shoot-down, connector task, transfer or exposure to another host is in flight, the server stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's storage and every queue pair's memfd and doorbells, with its state and its buffer pools; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. A server speaks one version of its protocol and one of the buffer pool's runtime interface (`storage::protocol::VERSION`, `storage::runtime::VERSION`), refusing a client of another protocol version at its hello with a typed refusal naming both, and an `Open` of another runtime version, and reads the image of its buffer pools in its build's format alone: before the handover the server states its protocol and runtime versions and its image's format, and a successor of another of them gives the restart up, and the server goes on as it was. Another host's READs of this host's storage are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

## The KV cache's storage and the weights

A device KV cache is split along its units into segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/engine/src/memory/cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses. A segment is the fewest units whose part of a layer's plane is whole allocation granules (32 units of 64 KiB planes on a GPU of 2 MiB granules, `crates/engine/src/memory/cache/segments.rs`), so the cache holds what its GPU's quota leaves it to within one granule of each of its allocations, when the engine starts, grows, wakes or gives memory back.

- Every GPU has a quota for each deployment that uses it, kept by the host's Storage Server: the limit, `⌊total × mem_fraction_static⌋` of the whole GPU, the fraction being the shares of the deployment's ranks placed on it when its worker groups state their own (`docs/configuration.md`, the deployment file), and a reservation for every item the deployment's epochs and the host's Transfer Server hold there. The server reserves what it retains, each storage once however many epochs map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent buffers). The processes reserve what it cannot see: each warm worker its graph pool and its process storage (its CUDA context, PyTorch's and Rust's allocations, communicator buffers, the product storage it has yet to make resident, and while a `range_metrics` profiling session runs, its range profiler pass), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, copy thread or exposure to another host uses it any more. A quota without room for the context refuses it, and the transfer task that needed the GPU fails, naming the quota. The server refuses a reservation or a new device storage that would take a GPU past its quota, so a quota never exceeds it; a worker that does not fit its quota fails its startup with every entry of the quota. A reservation ends with the process that made it when the process ends in order; a lost worker's reservations stay reserved for the process that replaces it (its relaunch), until that process reserves them again or the epoch is retired; an epoch's storages end with the epoch, and the segments a successor maps become its own on the quota when the previous epoch is retired. Two epochs therefore size their caches against one quota: a worker's grant is the quota less everything the quota reserves beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the storage the fraction leaves, and reserve once promoted in place of the rank they stand by for; the processes of one scope and epoch count as their largest reservation.
- An epoch switch compares layouts replica by replica: a target replica of a serving replica's layout shares that replica's device regions; a serving replica whose layout no target replica has shrinks its regions as it drains, and the target replicas of layouts of their own grow theirs from the quota as that memory frees. Adding or removing data-parallel replicas therefore moves no memory of the replicas it leaves in place ([Epochs](architecture.md#epochs)). The daemon's own in-place changes (the scheduling limits) leave the cache alone.
- `/admin/sleep` holds new requests, recomputes the token requests in flight as a shrink does, preempts the video requests in flight at their next denoising step boundary with their trajectories stored in the host latent pools (`docs/architecture.md`), which continue from that step once the deployment wakes; the workers then give back every segment and suspend their CUDA graph storage (`WeightBinding::sleep`, `crates/engine/src/process/binding.rs`), which the collectives captured in the graphs read and write without NCCL buffer registration, so that a wake that maps new storage at the same addresses leaves no peer mapping the old. `/admin/wake_up` creates the cache again, restores the graph storage and lets the held requests through. A sleeping deployment refuses epoch changes.
- `/admin/update_weights` checks that the daemon would process the new checkpoint's requests as the served model's (the same `tokenizer.json`, tokenizer settings, generation defaults and chat template, and the same model facts) and holds new requests. The main process walks the model's load over the new checkpoint first, reading nothing but its headers, and a checkpoint that loads other tensors is refused with the weights as they were. The load then runs through `WeightLoader` as the model's own load does, and every weight whose key moved is published at the Storage Server beside the one that serves; a file the two checkpoints share loads nothing. At a batch boundary each new allocation is mapped at the address of the weight it replaces, so the captured graphs replay it and nothing writes a published weight: the mapping stays read-only, the old allocation is released, and a relaunch on the new checkpoint finds the new allocation under its own keys. The requests in flight continue as `in_flight` says (vLLM's `keep` and `abort`, SGLang's `in_place`, `retract` and `abort`): with `keep`, the batches go on while the checkpoint loads beside the KV cache, and every request in flight continues on the new weights with the KV cache it reached; what it computes afterwards follows neither checkpoint, so it publishes no page. When the free storage does not hold the new weights the graph storage is given back for the load, which stops the batches for as long as it runs, and when even both do not the update is refused, unchanged. A video request in flight continues its trajectory on the new weights with `keep`, a trajectory of neither checkpoint. With `recompute` the engine recomputes the token requests in flight, preempts the video requests in flight as a sleep does (they continue from noise, since the new weights compute other trajectories), and with `abort` it ends every request it holds, aborted; then it sleeps, so that the cache's storage holds the new checkpoint as it loads, and wakes after. The engine flushes its prefix cache and keys host KV cache pages by the new weights. Weights streamed from host storage and DWDP experts are not updated in place: such a deployment is brought up again on the new checkpoint.

- KV cache pages cross hosts only through the hosts' Storage Servers. A deployment reads the published host KV cache pages of the hosts its `kv_cache_config.peers` names, and a prefill/decode deployment hands each request's cache units from its prefill group to its decode group through the Storage Server of the decode group's host, device to device, once its groups run as separate workers of the scheduler (`architecture.md`, Transfers). A host that serves peers, or a prefill group read from another host, runs its Storage Server with a TCP endpoint (`storage_config.tcp`, port `0` allowed; the server's readiness record and the daemon's state it as `peer`) and the NIXL package (`docs/nixl.md`); `uniserve storage-server list` shows each link the Transfer Server measured, a peer host's as `<endpoint> host`. The TCP endpoint is not authenticated: any process that reaches it can pin and read the published pages and the host tensors of every deployment the host serves, so hosts that serve each other run on an isolated network.

## Expert redistribution

`POST /admin/rebalance_experts` changes the distribution of routed expert weights while preserving the number of physical slots on each rank. Module paths are the routed expert layers the served model family states for its checkpoint (`nn::family::TextCheckpoint::expert_layers`). Layers omitted from `order` keep their distribution. An invalid permutation or unknown layer is rejected before copying starts.

A module path is `layers.N.mlp.experts`. Every rank's model is loaded with a logical-to-physical table for each of its routed layers, and the router's top-k writes each route's physical slot through it, in the launch that selects the experts: selecting over logical ids keeps which experts a token picks, and the order of equal scores, independent of where the experts lie, and a deployment that never redistributes pays no launch for it.

The serving scheduler reserves the additional storage of the ranks' prepared allocations on each GPU, releasing available KV tail segments as needed while requests continue. Each rank then publishes the stacks of the new order at the Storage Server, under the keys a load of that order asks for, copying the experts it holds over the device's own memory on a stream beside the batches, and reading an expert it does not hold from the checkpoint. At a common computation boundary the completed allocations and the new table are mapped at the addresses the graphs captured. The epoch, CUDA Graph addresses, request state and numerical weights remain the same. Once the operation finishes, the cache can grow into the released storage. The response lists each replica's epoch, requested order and allocations.

Distributed weight data parallelism (DWDP) prepares the resident shards, peer mappings and prefetch buffers of the requested distribution in the background; admission includes these allocations. Commit replaces the backing of the existing composite weight addresses and the prefetch copies together. A block that streams dense projections from host storage keeps those host allocations while its resident experts are redistributed.

The committed distribution is included in worker recovery launches and daemon handoff. A failure during preparation releases incoming copies and leaves the active distribution intact. A failure during publication triggers the existing engine recovery path with the committed distribution; an update on trial rolls back as its trial states. A redistribution that changes rank shapes requires a configuration change through `PUT /admin/config`.

## LoRA adapters

`/admin/load_lora_adapter` assigns the adapter the lowest free slot and has every rank publish the tensors of `lora_path`, a PEFT adapter directory whose tensors are its `adapter_model.safetensors`, at the Storage Server, through the path every weight takes, and map them read-only under the slot; `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. An engine that replaces another, after an epoch change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry, so requests naming it are refused. `/admin/unload_lora_adapter` removes the name at once and has every rank release the slot's tensors.

What computes with an adapter of a slot is a kernel package, and this repository holds none, so a request that names a loaded adapter as its `model` is refused rather than answered by the base model. The kernel package that provides it reads a slot's tensors and each token's slot. An adapter that a deployment serves for every request is fused into its weights at load instead, with `lora` or `lora_dir` ([Configuration](configuration.md)), and needs no slot.

## Nodes

Every leader daemon is a node, which serves through one path whatever it serves. Its listeners are bound when it starts and served for its whole life; its client API and admin routes are the serving deployment's, and while none serves the client API answers `503` (`no_deployment`), as does every admin route but the node's own: `GET /admin/status`, which states the node `idle` with the last deployment's error, `starting` or `stopping` with the deployment's name, or, through the serving deployment, `serving` with its status; `GET /admin/events`, the node's event log, which every deployment it serves writes; `GET /admin/config`, the configuration status with nothing in it; and `PUT /admin/config`. `uniserve serve MODEL` starts a node for that deployment, which it brings up at once and lives as long as: the deployment's `POST /admin/shutdown` or a stop signal ends both. `uniserve serve --host H --port P` without a model starts a node that serves no deployment and reports it serves at once; its `PUT /admin/config` with `{"config": TOML, "set": ["PATH=VALUE", ...]}` brings one up through the same step `uniserve serve --config` with those assignments takes, as a `config` operation that answers once the deployment serves (`"change": "deployment"`) or failed to come up, or at once (`202`) with `"wait": false`; a bring-up starts no update, so `replica`, `deadline_s` and `force` are refused, every later `PUT /admin/config` being the deployment's, and the deployment's `POST /admin/shutdown` brings it down (releasing its storage by default), after which the node serves no deployment and takes the next one. A deployment a node brings up takes the node's HTTP server (`server_config`) and admin options (`admin_config`), and the node's Build Server unless its configuration states `build_config`. A node brings up the deployments it leads, of one node or several (its join listener is bound then, and its endpoint is the `join` of the deployment's readiness in `GET /admin/status`), one at a time, and hands itself over in a hot restart whichever way it was started.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else; it reads and writes the admin schema the daemons serve (`proto::admin`). A node is named by its operator socket (`--node unix:PATH`), or by the URL that socket is forwarded at from another host: a node never calls it or waits for it, so it attaches by reading a node's status (`GET /admin/status`, which states it idle, starting, serving or stopping) and events and detaches by stopping.

`ADMIN` below is a daemon's operator socket as its readiness record states it (`endpoints.admin`, Listeners).

```bash
uniserve-manager --node "$ADMIN" --node http://127.0.0.1:9000 status
uniserve-manager --node "$ADMIN" watch            # Ctrl-C detaches
uniserve-manager --node "$ADMIN" apply --config qwen3.toml   # an idle node deploys
uniserve-manager --node "$ADMIN_A" --node "$ADMIN_B" apply --set 'cuda_graph_config.decode_batch_sizes=[1, 2, 4, 8]' --commit-after 300
uniserve-manager --node "$ADMIN" config
uniserve-manager --node "$ADMIN" commit                      # or rollback
uniserve-manager --node "$ADMIN" shutdown
uniserve-manager --node "$ADMIN_A" --node "$ADMIN_B" restart  # one node after another
```

`status` prints one line per node; `config` prints each node's configuration status as the node answers it; `watch` prints each event of each node's log as JSON until interrupted; `restart` restarts each node's daemon in place, re-executing its own image, and stops at the first that fails. What the manager waits for, the end of an operation a node runs on its own and the end of a trial, it reads from the node's event log by long poll: one request waits `--event-wait` seconds (30 unless stated, at most the node's `admin_config.event_log.longest_wait`) before the manager asks again, and a node the manager cannot reach is asked again every `--retry-interval` seconds (5 unless stated).

Each `--node` is the leader of one service (one served model name). When several services share GPUs, `apply` decides the order of their updates and calls each service's admin API in turn (`crates/manager/src/updates.rs`); every step within a service is the service's own, and no node waits for the manager. Before it starts a service's update, the manager reads the GPUs its epochs hold (`GET /admin/config`, `gpus`, each named by its host and UUID) and its update's dry run (`PUT /admin/config` with `dry_run`): whether it changes anything and whether it starts a new epoch, which prepares beside the serving one on the service's GPUs. Services are taken in the order given; a service whose update starts a new epoch starts only when no update in progress (preparing, or on trial until committed) holds one of its GPUs, so two services that share a GPU are never prepared at once. Services that share no GPU update at once. A service that cannot start waits, and its dry run is made again whenever an update in progress ends. A change of a daemon's own options restarts that daemon in place, and the manager follows the update its successor starts in an operation of its own through the node's event log. With `--commit-after S`, the manager commits each new epoch once it served on trial `S` seconds; a trial that ends by itself meanwhile, as the node's event log states, fails at once. Without it, each new epoch stays on trial for the operator and holds its GPUs, and the services that share them wait for the next `apply`. A failed update or a trial that ended without its commit stops the services not started, which the manager names with why each waited; the updates in progress go on to their end, and committed ones remain applied. `--dry-run` prints each service's dry run and the order the manager takes them in. An idle node's deployment holds no GPUs before it starts, so the manager orders it by nothing but the order given. A dry run states no storage the target requires, so the manager's order rests on the GPUs the services' epochs hold; whether a target fits its GPUs' quotas is the daemon's to find when the update prepares.
