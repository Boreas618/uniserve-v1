# Admin API, nodes and the manager

A deployment's leader daemon serves an admin API under `/admin` on two Unix sockets of its own, apart from the client API: one for the operator, with every route, and one for a harness, with what a writer of the deployment's policy reads and writes ([Listeners](#listeners)). Access is the sockets' file permissions. Everything a deployment can do while it serves goes through it: `uniserve serve` alone needs nothing else, and the optional `uniserve-manager` is one client of it among others. Its requests and responses are JSON of one typed schema, the interface crate's `proto::admin` (`crates/proto/src/admin.rs`), which the daemon serves and its clients read.

## Endpoints

| Endpoint | What it does |
| --- | --- |
| `GET /admin/status` | What the node serves (`state`): `idle`, with why its last deployment failed to come up or down (`last_error`); `starting` or `stopping`, with the deployment's `name`; or `serving`, with the deployment (`deployment`: name, model, the engine's lifecycle state, paused, asleep, requests in flight, the new requests the daemon holds while generation is paused, the engine sleeps or no engine serves (`held`), the launch generation of the engine that serves (`generation`, which names its row of the report's `processes`), the parked standby's launch generations (`standby`, empty without one), the update in flight (`update`: its number and phase, `null` without one)), what the deployment executes and owns (`report`, [Status](#status)) and the daemon's readiness record (`readiness`). Beside it, whatever the node serves: the running and the last operation (`operation`, `last_operation`: identity, kind, state, start and end, error) and the next event's sequence number (`next_event`) |
| `GET /admin/events?after=N&wait=S` | The node's events after sequence number `N`, waiting up to `S` seconds (at most `admin_config.event_log.longest_wait`, a minute unless stated) for one; `next` is the number to read after next, and `gap` says that events after `N` already left the log, which keeps the newest `admin_config.event_log.capacity` (1024 unless stated). Each event has its sequence number, time, message, category (`kind`) and what it carries (`data`): `operation`, an operation's start or end, with the operation; `engine`, a change of the serving engine's lifecycle state (`from`, `to`, `reason`); `update`, a phase an update entered, with the update as it stood; `deployment`, a deployment coming up, serving, holding or serving new requests, or coming down, with no data. The log is the node's: every deployment it serves writes it, and a hot restart hands it to the successor |
| `GET /admin/policy[?revision=N]` | The deployment's policy package, the current revision's or revision `N`'s, as a tar archive of its directory: `config.toml`, with the options it states and its defaults left out, and `programs/` ([Policy](#policy)). Its `ETag` is the revision's number (`"42"`); `404` before the deployment has a revision, or for a revision the state directory no longer keeps |
| `PUT /admin/policy[?force=true]` | Apply: the body is a tar archive of a package directory (`config.toml` and `programs/`, nothing else), which replaces the deployment's target whole: what it states becomes the target, and what it does not state takes its default. `If-Match: "N"` applies it only while revision `N` is current, answered `412` otherwise; `force=true` applies a target a rollback marked unavailable. The change does the least its options' effects need ([Updates](#updates)) and answers once it ended: `200` with the revision's record once the deployment converged; `202` with the record, `"result": "converging"`, when the daemon's own options changed and its successor converges the rest; and an error status with the reason when it did not converge: `400` for a package a start would refuse or a target a rollback marked unavailable, `409` for an update that was abandoned or rolled back or while another operation runs, `503` while the deployment does not serve. A package equal to the current revision's answers that revision's record and changes nothing |
| `POST /admin/pause_generation` | New requests wait; those in flight go on (SGLang's endpoint of that name) |
| `POST /admin/continue_generation` | New requests are served again |
| `POST /admin/flush_cache` | The engine revokes every cached prefix page; requests in flight keep theirs |
| `POST /admin/restart` | A hot restart of the daemon: `{"wait": true}`. A successor daemon, which re-executes the running daemon's own image, takes the deployment over while this one finishes the requests it took (below); answers with the successor's process id once it serves (`result.pid`) |
| `POST /admin/shutdown` | Brings the deployment down as SIGTERM does, finishing what is in flight within `server_config.shutdown_timeout`, and releases its weights and caches by stopping the deployment's Storage Server on the leader's node unless `{"retire": false}` |
| `POST /admin/update_weights` | `{"model_path": PATH, "in_flight": "keep"}`: the engine rewrites its weights in place from another checkpoint of the served model, a local directory or a Hugging Face repository (SGLang's `update_weights_from_disk`; below); `in_flight` is `keep` (the default), `recompute` or `abort` |
| `POST /admin/rebalance_experts` | `{"order": {MODULE_PATH: [EXPERT_ID, ...]}, "replica": INDEX}`: rearranges routed experts within the current epoch. Each list is a complete permutation of logical expert IDs in global physical-slot order. Omit `replica` to update every independent replica in sequence |
| `POST /admin/sleep`, `/admin/wake_up` | The engine gives back its KV cache and CUDA graph storage and keeps its weights, and restores both (vLLM's endpoints of those names; below) |
| `POST /admin/load_lora_adapter`, `/admin/unload_lora_adapter` | `{"lora_name": NAME, ...}`: the workers load a LoRA adapter into a slot of the adapter pool, or unload it (vLLM's endpoints of those names; below) |
| `POST /admin/profile` | Starts a profiling session on every worker of the executing epoch at the engine's next step boundary: `{"collectors": [...], "steps": N, "start_step": N, "seconds": S, "stages": [...], "workers": [...], "modules": [...], "output_dir": PATH, "max_slowdown": F, ...}` (`docs/profiling.md`); answers with the session, each worker's file and its collectors' states. One session runs at a time: another is refused (`400`) until it ends, as is a session naming more than one of `pm_sampling`, `range_metrics` and `pc_sampling`, which share the device's performance monitors, and, while `profiling_config.graph_pc_sampling` keeps PC sampling enabled on every worker, a session of `pm_sampling`, `range_metrics` or a timeline that traces graphs whole. A `range_metrics` session reserves its range profiler pass's device storage in the quota of each selected worker's GPU, as part of the worker's process item, until it ends: where a quota lacks the room, the KV cache first gives back tail segments, as an epoch change's preparation does (the requests holding them run on, and the session starts once they let them go), and grows back once the session ends. A session for which even the segments past the first leave too little room is refused (`400`), naming the bytes and every quota entry |
| `GET /admin/profile` | The running session, or the last that ended: its state and why it ended, the steps and bytes its workers recorded, the step time before it and during it, the quality-of-service guard's actions and each worker's file; `null` before any |
| `DELETE /admin/profile` | Ends the running session at the engine's next step boundary, every worker writing its file |

Each write is an operation: it has an identity, runs on a task of its own, and ends `succeeded` or `failed` in the status and in the event log, whether or not the client that asked stays connected. One operation runs at a time; another is answered `409`. A `PUT /admin/policy` runs as a `config` operation and answers with its revision's record; changes converge one after another, a `PUT` that arrives while another converges waiting for it and being compared with what that one converged to. Every other write answers with its operation (`id`, `kind`, `state`, `started`, `ended`, `error`) and, once it succeeded, its result (`result`); `"wait": false` answers at once with `202` and the operation running. The status and the event log state an operation without its result, which the answer alone carries.

## Policy

A deployment's configuration is its policy package (`docs/configuration.md`, Policy package), and every change of it is the next package, applied whole: `PUT /admin/policy` replaces the target with the package it carries, and the leader compares the target with the current revision option by option through each option's declared effect, writes it as the next revision of the deployment's persistent state, executes it and makes it current once the deployment converged (`docs/configuration.md`, Revisions). A start is the same apply from nothing. Writers are the operator, an external system and the deployment's programs; no option has an owner, the last write wins, and every revision records its writer. A writer that changes some options reads the current package with `GET /admin/policy`, changes it and puts it back with `If-Match` set to the `ETag` it read, so a change another writer made meanwhile is refused (`412`) rather than overwritten:

```bash
curl --unix-socket "$admin" -D headers.txt -o current.tar http://admin/admin/policy
mkdir next && tar -xf current.tar -C next
# edit next/config.toml
tar -cf next.tar -C next .
curl --unix-socket "$admin" -X PUT -H "If-Match: $(sed -n 's/^etag: //Ip' headers.txt | tr -d '\r')" \
  --data-binary @next.tar http://admin/admin/policy
```

To undo a change that converged, apply the package of the revision before it (`GET /admin/policy?revision=N`) as the next change.

## Updates

An update moves a deployment to another set of modules while it serves, as a trial that commits by itself or rolls back. A deployment runs the package revisions its epoch names; installing a package at the Build Server selects nothing, and an apply (`PUT /admin/policy`) is what moves them. The daemon fixes the target's module set once, when the package is applied, and records it in the revision's `lock.toml`: it asks the Build Server's `cover` for the revision of the engine package, the scheduling policy and every kernel package, builds every module on every host the target runs on, and compares the fixed set with what the serving epoch runs. A change then does the least it needs:

- **Nothing an engine executes** changed: options of the `step` effect take effect at each scheduler's next step, and the fence probes' switch (`profiling_config.fence_probes`, `fence_probes_off`) at the engines' next step; a target equal to the current revision changes nothing.
- **The daemon's own options** changed (the `daemon` effect: `server_config`, `admin_config`, `logging_config`, `chat_config`, `image_fetch_config`, `media_config`, `video_job_config`, `migration_config`, `mm_processor_kwargs`, `build_config`, `update_config`): the daemon restarts itself in place (below), and its successor converges the rest of the change and records how it ended; the `PUT` answers `202` with the revision `converging`.
- **Kernel or policy packages** changed, the policy's parameters included (the module selections, `speculative_config.expected_speedup`, `refill_token_cost`, a newly installed revision at an unchanged configuration): an update in its **generation** form, inside the serving engines.
- **The engine package, the build configuration or the checkpoint** changed (`worker_config.engine`, `worker_config.engine_revision`, the parallel shape and block ownership, `hosts`, `dtype` or `quantization`, the KV layout, the graph buckets, the slot count, the model's files): an update in its **epoch** form, target engines started beside the serving ones.

A change of the served model name is refused because it names the deployment. A change of the model's files, `dtype`, quantization, load format or weight source loads the other keys from the files beside the serving epoch's; a change of the parallel configuration, the devices or the hosts spreads the weights differently, and the target's engines receive them from the serving epoch's retained chunks rather than reading the checkpoint where an epoch already holds them. Other model files serve the deployment only when requests are processed as the serving ones are: the same tokenizer, templates, generation defaults and model facts.

### One update, two forms

An update has one phase machine in the daemon (`crates/daemon/src/updates/update.rs`), whatever it moves. Every phase ends on acknowledgements the engines make, never on an assumption about their progress.

| Phase | Meaning | Ends when |
| --- | --- | --- |
| `preparing` | The new is made ready beside the old; serving is untouched | Every engine acknowledged it is ready, or one failed: the update is `abandoned` and nothing changed |
| `switching` | Service moves at a boundary: to the new, or back to the kept side when the update rolls back (`"rollback": true`) | Every engine acknowledged the switch |
| `trial` | The new serves and the old is kept | It lasted `update_config.trial` and commits, or a fault or a threshold rolls it back |
| `committed`, `rolled_back` | The kept side is released | — |

| | Generation | Epoch |
| --- | --- | --- |
| Preparing | `Prepare` to each serving engine: it resolves the new modules, instantiates the policy, hands the buckets whose kernels changed to each worker's capture thread, which captures them again beside the graphs that serve, and shadows each changed kernel on a paired forward. `Prepared` acknowledges; `PrepareFailed` abandons | Every node's daemon starts the target's main processes for its host, of every replica the target's configuration places (each world's scheduler node and its peers), each from a launch file the leader made that states the epoch's whole module set, the engine it succeeds and its own launch generation; every node then claims the target epoch's storage. Each engine opens its session with its host's buffer pool, maps the weights it shares, resolves its modules, captures its graphs and parks. Every engine's `Parked` acknowledges |
| Switching | `Switch` to each serving engine: the policy changes at one batch boundary inside the process, then each bucket's graph as soon as every rank captured it, then the kernels whole. `Switched` acknowledges once the last bucket switched, so the trial counts from there | Both epochs step. `Promote` to every target engine, which opens admission and acknowledges with `Serving`; from the first `Serving` the daemon routes every new request to the target, and the serving engines go on with what they hold. Once every target serves, `Drain` to every serving engine with the deadline `update_config.drain_s` from then, and with `shrink` to each whose layout no target replica has: a draining engine admits nothing and steps its running requests until each ends by itself, and at the deadline ends the rest as migratable (a token request with its blocks committed under their keys, a video request at its next denoising step boundary with its trajectory saved), which the daemon resubmits to the target; with `shrink` it gives its device memory back as its requests end and the target grows into it. Every serving engine's `Drained` ends the switch |
| Kept during the trial | The previous generation, inside the engine | The previous epoch, as `update_config.previous_epoch` states: `parked` (its engines, drained and alive), `weights` or `host` (its engines stopped, its weights retained on the GPUs or in host storage) |
| Rollback | `Rollback` to each engine: every bucket returns to its kept graph and the kept policy serves, at a batch boundary. `RolledBack` acknowledges | The switch the other way: the previous epoch's parked engines are promoted again, or started again at the next launch generation on the weights they kept, and new requests return to them from the first `Serving`; then `Drain` to every target with the same deadline. A target that failed, or one never promoted, is stopped instead of drained |
| Commit | The epoch's record keeps the new modules; `Commit` tells each engine to release the previous generation's graphs and kernels after its last batch, and the KV cache grows back into what it gave the update | The target's record becomes `serving`; the previous epoch's engines are stopped and its storage is retired by a claim of the target's epoch |

A trial ends by itself. It commits once it lasted `update_config.trial` (30 seconds unless stated) with nothing rolling it back, and it rolls back on a process-fatal fault, a stalled job, non-finite logits or an engine's exit, or on a threshold the configuration sets (`update_config.rollback`: the failure rate of the requests that ended on trial, the step-time and throughput regressions over a window against the steps served before the switch). A commit records its decision, the phase and the epoch's record, before it releases anything, so an engine lost while the kept side is released is replaced by one of the committed modules. A rollback marks the target unavailable with its reason: applying the same build configuration and module set again needs `force`, and a revision installed later is another target. An update that was abandoned marks nothing.

One update is in flight at a time, and changes converge one after another. The `PUT` that started an update answers once the update committed, with the revision converged, or once it was abandoned or rolled back, with the update's failure as the reason and the revision recorded `rolled_back`; the update as it stands is the status's `report.update` throughout, and every phase it enters is an event. `update_config.in_flight` states how the requests an epoch's switch migrates continue (`keep` or `recompute`). An update does not cross a daemon hot restart: the restart waits until it ends.

### Epochs, generations and launch generations

An **epoch** numbers one engine build with its build configuration, and keys its storage at the Storage Server. A **generation** numbers the set of kernel and policy modules an engine executes; the engine assigns it and states it in its `Prepared`, `Parked` and `Serving` reports. A **launch generation** identifies one process of a worker group and rank: a serving engine, its standby, an update's target, a relaunch. The daemon takes launch generations from one counter per group and rank, above every live one, and addresses every command by it.

The daemon keeps one record per epoch: the build configuration, the module set fixed when the configuration was applied, the modules a generation's trial keeps, the generation its engines numbered, and a status (`preparing`, `serving`, `trial`, `released`). The module set is part of every launch file made from the epoch, so a relaunch and a standby run exactly what their epoch runs.

An epoch update covers the whole deployment: every node, every main process and every independent data-parallel replica of both epochs. The two epochs need not have the same number of nodes, main processes, schedulers or ranks: the target's shape is its configuration's, and nothing maps the engines of one epoch to the other's. Target replica `i` serves under the deployment's replica `i`; a serving replica past the target's last hands the requests it migrates to a target replica, and a rollback does the same the other way. A serving replica and a target replica have different layouts when they differ in their parallel configuration (degrees, forms, worker groups, devices, hosts), their slot count (`max_running_requests`), their KV layout (`kv_cache_config.block_size`, the cache's precision) or their graph buckets (`cuda_graph_config`); the cache's size and its tiers are no layout, and neither is the number of replicas, so a replica that keeps its place when replicas are added or removed keeps its layout. A serving replica whose layout no target replica has drains with `shrink`, and the status reports `shrink` when any does. A migrated request carries its generated tokens and seed: on a target of the same layout and numerics it finds its committed blocks by their keys and pays one admission and the copy of its partial last block; on one of another layout or other numerics its keys reach nothing and it computes its state again, as it does with `update_config.in_flight = "recompute"` (`Promote.recompute`). Nothing of the cache is handed over.

### Startup

Starting is not an update. The daemon fixes the epoch's module set at the Build Server and has it built at the Build Server of every host the epoch runs on before any engine starts, and every engine starts from a launch file that states it: the engine resolves every module its profile runs name, captures its graphs and serves (`Serving`), or parks when its launch names the engine it succeeds (`Parked`).

### The standby

With `worker_config.standby`, the daemon keeps a parked engine of the serving epoch beside every serving engine, at the next launch generation and with its own CUDA contexts: a sticky error of the serving process cannot touch it. A standby is started as an epoch update's target is, from a launch file that states the epoch's module set and the engine it succeeds, and parks by itself with its graphs captured. A process-fatal fault promotes the whole failure domain (`Promote` on each standby's process link, every promotion issued before any is awaited), and each node then starts a new standby. Where a member of the domain has no parked standby, the domain is relaunched instead and finds its weights retained. A standby exists only while its epoch serves; an epoch that prepares or is on trial keeps none, and a generation's commit replaces the standby with one of the committed modules. `worker_config.standby_storage` states whether a standby keeps its graph pools on the device (`resident`) or gives them back until its promotion (`suspended`).

### Status

`GET /admin/status` states the engine's lifecycle (`deployment.engine`: `starting`, `parked`, `serving`, `draining`, `stopped`, `failed`; `holding` while an engine is being replaced; `closed` once none will serve) and the update in flight (`deployment.update`: its number and phase). The status's `report` states what the deployment executes and owns: the first replica's configuration as TOML with its digest (`config`, `digest`) and the epoch it executes with the engine's lifecycle state there (`executing`: `starting`, `parked`, `serving`, `draining`, or `unavailable` with the reason), each replica's own as `replicas`, the targets a rollback marked unavailable with their reasons (`unavailable`), the GPUs the deployment reserves storage on (`gpus`: each one's host, its UUID as the device reports it (`gpu`, `GPU-` and 32 hexadecimal digits in groups of 8, 4, 4, 4 and 12), total, quota and used bytes) and the quotas (`quotas`: for each host of the deployment, every GPU's limit and each reservation's item, scope, `epochs`, KV cache segment and bytes, and what the deployment's transfer tasks copied there by priority (`tasks`)). It states the update in flight, or the last one, under `update`: its form (`change`), number, phase, epoch, the generation its engines numbered, how long its switch took (`switch_ms`), how long it has been on trial (`trial_s`), its failure, the operators the engines could not compare (`uncompared`), for an epoch update its serving and target engines (`engines`), the drain's deadline (`drain_s`) and whether the layouts differ (`shrink`), what the previous epoch is kept as, and what its trial and transfers read (`trial`, `transfers`). It also reports each epoch's record (`epochs`: its number, build configuration, packages by slot, the packages a generation's trial keeps, generation and status) and this daemon's engine processes (`processes`), one row each: group, rank, pid, epoch, launch generation, build and state (`starting`, `parked`, `serving`, `stopped`, or `failed` with its `reason`). Every phase an update enters is an `update` event in `GET /admin/events`, whose `data` is the update as it stood.

## Listeners

The daemon serves the admin API apart from the client API, on two Unix sockets, and access is their file permissions. Every daemon owns an instance directory, `daemon.XXXXXX` inside UniServe's directory of the user's runtime directory (`$XDG_RUNTIME_DIR/uniserve`, mode `0700`), which it creates when it starts and removes when it ends; its sockets lie there, and a caller reads their paths from its readiness records. A daemon run without `XDG_RUNTIME_DIR` is refused.

| Listener | Socket | Mode | Serves |
| --- | --- | --- | --- |
| Client API | `admin_config.host`, `port` or `uds`; port `0`, the default, picks a free port | — | The OpenAI API, `/health`, `/metrics`, `/version`; no `/admin` route |
| Operator | `admin.sock` in the daemon's instance directory | `0600` | Every admin route |
| Harness | `harness.sock` in the daemon's instance directory | `0660` | What a writer of the deployment's policy reads and writes: `GET /admin/status`, `/admin/events`, `GET` and `PUT /admin/policy` |

The daemon binds all of its listeners when it starts, before it loads anything: the client listener, the two admin sockets and, on the leader of a deployment of several nodes, the join listener (`admin_config.join` on every interface). It reports what it bound in its readiness record, one JSON line written to the descriptor its caller passes with `--ready-fd FD` (as systemd's `sd_notify` reports a service's state): `{"state": "listening", ...}` once the listeners are bound, and `{"state": "serving", ...}` once it serves, after which the descriptor closes; a daemon that ends before it serves closes the descriptor without the second line. A record states the daemon's `pid`, its `instance` directory and its `endpoints`: `client`, `admin`, `harness`, `join`, and, once it serves, the host Storage Server's `storage` socket and `peer` TCP endpoint (each `null` when absent; a Unix socket is written `unix:PATH`, a TCP endpoint `HOST:PORT`). Connections that arrive before the daemon serves wait in the listeners' backlog. `GET /admin/status` reports the same record (`readiness`). A deployment's other nodes join the leader at the first host of the package's `hosts` and its `admin_config.join` port, which the record states as `join` (`docs/configuration.md`, Nodes).

A harness is an agent program that observes the deployment, installs packages at the Build Server and applies packages. The operator grants it access through the harness socket's group. On the harness listener it reads the status, the events and the policy, and applies a package with `PUT /admin/policy` as any writer does, which its revision records as every `PUT`, with the writer `operator`. The operator's operations (weight update, sleep, wake, LoRA, expert rebalancing, pause, flush, profiling, shutdown, daemon restart) are not routes of the harness listener.

A hot restart's successor goes on in its predecessor's instance directory, binds both sockets over its predecessor's, which finishes the requests it accepted, and owns the directory once the handover completed. An example, reading the sockets from the record:

```bash
uniserve serve qwen3 --ready-fd 3 3>ready.jsonl >serve.log &   # qwen3/config.toml states model = "Qwen/Qwen3-30B-A3B"
# once ready.jsonl holds the line whose state is "serving":
admin=$(jq -r 'select(.state == "serving") | .endpoints.admin | ltrimstr("unix:")' ready.jsonl)
harness=$(jq -r 'select(.state == "serving") | .endpoints.harness | ltrimstr("unix:")' ready.jsonl)
curl --unix-socket "$admin" http://admin/admin/status
curl --unix-socket "$harness" -X PUT --data-binary @next.tar http://admin/admin/policy   # next.tar: tar -cf next.tar -C next .
```


## Hot restarts

A daemon restarts in place without closing a connection or failing a request (`POST /admin/restart`, `crates/daemon/src/restart.rs`), as Envoy's hot restart does. It starts its successor (`uniserve serve --predecessor`) with a socket pair between them and sends it its options with the version of the engine interface it and its engines speak; a successor of another version gives up, as does one whose Storage Server protocol the host's Storage Server does not speak (the server refuses the successor's hello with a typed version refusal), and the daemon serves on as it was. Every interface has one version per release, so a restart in place stays within a release: a deployment moves to another release by a full restart. The successor then loads the model's files and binds a request socket of its own; the daemon then stops its service thread between two rounds and hands the successor, as descriptors, its HTTP listener, its process socket with every engine and member connection it serves, its processes, the claim at the Storage Server and the connection its engine's process lives under, with the served spec, the admin's log and the video jobs; and it commands the engine to attach to the successor. From then on both accept on the listener: the engine serves both daemons, each its own requests. Once the successor serves, the daemon stops accepting, finishes the requests and video jobs it took (relaying each job's later changes and artifact to the successor), closes its engine connection without shutting the engine down, and exits. The engine and its workers are the same processes throughout, and serve on through the successor with their relaunches and their standby: the successor speaks the same version of the engine interface (`proto::ENGINE_INTERFACE_VERSION`), the one version a daemon serves; it refuses an engine of any other at its hello with a typed refusal naming both versions. A process ends with its daemon through its lifeline, a pipe whose write end the daemon holds and whose read end the process inherits at the descriptor the last option of its command line names (`--lifeline FD`): the engine and the workers exit once they read the pipe's end, which arrives when the daemon ended however it did; a hot restart hands the write end to the successor with the processes, which it supervises from then on through their pidfds, so the pipe stays open across the restart.

A deployment's Storage Server restarts in place too (`uniserve storage-server restart --deployment NAME`, `crates/storage-server/src/restart.rs`), into the build of the `uniserve` that runs the command: the command passes its own executable to the server, which starts its successor from it. The deployment's daemon restarts it the same way, from its own build, when a change of `storage_config` or of the Mooncake connector states a setting the running server cannot take, and the successor serves with the new settings (`docs/configuration.md`, `storage_config`). Once the successor speaks the server's versions and no request, shoot-down, connector task, transfer or exposure to another host is in flight, the server stops its connector and its Transfer Server and hands the successor its listening socket and its lock, every client's connection and pidfd, every tensor's storage and every queue pair's memfd and doorbells, with its state and its buffer pools; the successor goes on with every connection and starts a connector and a Transfer Server of its own, and the server exits. Clients see no connection close; a request sent meanwhile waits in its connection. A server speaks one version of its protocol and one of the buffer pool's runtime interface (`storage::protocol::VERSION`, `storage::runtime::VERSION`), refusing a client of another protocol version at its hello with a typed refusal naming both, and an `Open` of another runtime version, and reads the image of its buffer pools in its build's format alone: before the handover the server states its protocol and runtime versions and its image's format, and a successor of another of them gives the restart up, and the server goes on as it was. Another host's READs of this host's storage are one-sided, so the server does not see them: one in flight when the Transfer Server stops fails its task on that host, and the successor's Transfer Server registers the regions again when that host asks.

## The KV cache's storage and the weights

A device KV cache is split along its units into segments, each of every layer's planes an allocation of its own mapped back to back at a fixed address (`crates/engine/src/memory/cache/planes.rs`), so that its tail can be given back to the device and created again in place while CUDA graphs keep their addresses. A segment is the fewest units whose part of a layer's plane is whole allocation granules (32 units of 64 KiB planes on a GPU of 2 MiB granules, `crates/engine/src/memory/cache/segments.rs`), so the cache holds what its GPU's quota leaves it to within one granule of each of its allocations, when the engine starts, grows, wakes or gives memory back.

- A GPU belongs to one deployment, which its daemon claimed in the node's GPU registration file before an engine started on it (`docs/configuration.md`, A deployment's servers). Every GPU has a quota for the deployment, kept by the deployment's Storage Server on the node: the limit, `⌊total × mem_fraction_static⌋` of the whole GPU, the fraction being the shares of the deployment's ranks placed on it when its worker groups state their own (`docs/configuration.md`, the deployment file), and a reservation for every item the deployment's epochs and its Storage Server's Transfer Server hold there. The server reserves what it retains, each storage once however many epochs map it: the weights, each KV cache segment and the other exclusive storages (the cache's flags and scales, the buffer pool, the latent buffers). The processes reserve what it cannot see: each warm worker its graph pool and its process storage (its CUDA context, PyTorch's and Rust's allocations, communicator buffers, the product storage it has yet to make resident, and while a `range_metrics` profiling session runs, its range profiler pass), and the Transfer Server its staging, and its CUDA context, at the bytes it measured when it started, only while it holds the context: from the first task that needs the GPU until no task, copy thread or exposure to another host uses it any more. A quota without room for the context refuses it, and the transfer task that needed the GPU fails, naming the quota. The server refuses a reservation or a new device storage that would take a GPU past its quota, so a quota never exceeds it; a worker that does not fit its quota fails its startup with every entry of the quota. A reservation ends with the process that made it when the process ends in order; a lost worker's reservations stay reserved for the process that replaces it (its relaunch), until that process reserves them again or the epoch is retired; an epoch's storages end with the epoch, and the segments a successor maps become its own on the quota when the previous epoch is retired. Two epochs therefore size their caches against one quota: a worker's grant is the quota less everything the quota reserves beside its own process and less what its process holds. A standby rank group's processes (`worker_config.standby`) live beside the quota, on the storage the fraction leaves, and reserve once promoted in place of the rank they stand by for; the processes of one scope and epoch count as their largest reservation.
- An epoch switch compares layouts replica by replica: a target replica of a serving replica's layout shares that replica's device regions; a serving replica whose layout no target replica has shrinks its regions as it drains, and the target replicas of layouts of their own grow theirs from the quota as that memory frees. Adding or removing data-parallel replicas therefore moves no memory of the replicas it leaves in place ([Epochs](architecture.md#epochs)). The daemon's own in-place changes (the scheduling limits) leave the cache alone.
- `/admin/sleep` holds new requests, recomputes the token requests in flight as a shrink does, preempts the video requests in flight at their next denoising step boundary with their trajectories stored in the host latent pools (`docs/architecture.md`), which continue from that step once the deployment wakes; the workers then give back every segment and suspend their CUDA graph storage (`WeightBinding::sleep`, `crates/engine/src/process/binding.rs`), which the collectives captured in the graphs read and write without NCCL buffer registration, so that a wake that maps new storage at the same addresses leaves no peer mapping the old. `/admin/wake_up` creates the cache again, restores the graph storage and lets the held requests through. A sleeping deployment refuses epoch changes.
- `/admin/update_weights` checks that the daemon would process the new checkpoint's requests as the served model's (the same `tokenizer.json`, tokenizer settings, generation defaults and chat template, and the same model facts) and holds new requests. The main process walks the model's load over the new checkpoint first, reading nothing but its headers, and a checkpoint that loads other tensors is refused with the weights as they were. The load then runs through `WeightLoader` as the model's own load does, and every weight whose key moved is published at the Storage Server beside the one that serves; a file the two checkpoints share loads nothing. At a batch boundary each new allocation is mapped at the address of the weight it replaces, so the captured graphs replay it and nothing writes a published weight: the mapping stays read-only, the old allocation is released, and a relaunch on the new checkpoint finds the new allocation under its own keys. The requests in flight continue as `in_flight` says (vLLM's `keep` and `abort`, SGLang's `in_place`, `retract` and `abort`): with `keep`, the batches go on while the checkpoint loads beside the KV cache, and every request in flight continues on the new weights with the KV cache it reached; what it computes afterwards follows neither checkpoint, so it publishes no page. When the free storage does not hold the new weights the graph storage is given back for the load, which stops the batches for as long as it runs, and when even both do not the update is refused, unchanged. A video request in flight continues its trajectory on the new weights with `keep`, a trajectory of neither checkpoint. With `recompute` the engine recomputes the token requests in flight, preempts the video requests in flight as a sleep does (they continue from noise, since the new weights compute other trajectories), and with `abort` it ends every request it holds, aborted; then it sleeps, so that the cache's storage holds the new checkpoint as it loads, and wakes after. The engine flushes its prefix cache and keys host KV cache pages by the new weights. Weights streamed from host storage and DWDP experts are not updated in place: such a deployment is brought up again on the new checkpoint.

- KV cache pages cross hosts only through the hosts' Storage Servers. A deployment reads the published host KV cache pages of the hosts its `kv_cache_config.peers` names, and a prefill/decode deployment hands each request's cache units from its prefill group to its decode group through the Storage Server of the decode group's host, device to device, once its groups run as separate workers of the scheduler (`architecture.md`, Transfers). A host that serves peers, or a prefill group read from another host, runs its Storage Server with a TCP endpoint (`storage_config.tcp`, port `0` allowed; the server's readiness record and the daemon's state it as `peer`) and the NIXL package (`docs/nixl.md`); `uniserve storage-server list` shows each link the Transfer Server measured, a peer host's as `<endpoint> host`. The TCP endpoint is not authenticated: any process that reaches it can pin and read the published pages and the host tensors of every deployment the host serves, so hosts that serve each other run on an isolated network.

## Expert redistribution

`POST /admin/rebalance_experts` changes the distribution of routed expert weights while preserving the number of physical slots on each rank. Module paths are the routed expert layers the served model family states for its checkpoint (`nn::family::TextCheckpoint::expert_layers`). Layers omitted from `order` keep their distribution. An invalid permutation or unknown layer is rejected before copying starts.

A module path is `layers.N.mlp.experts`. Every rank's model is loaded with a logical-to-physical table for each of its routed layers, and the router's top-k writes each route's physical slot through it, in the launch that selects the experts: selecting over logical ids keeps which experts a token picks, and the order of equal scores, independent of where the experts lie, and a deployment that never redistributes pays no launch for it.

The serving scheduler reserves the additional storage of the ranks' prepared allocations on each GPU, releasing available KV tail segments as needed while requests continue. Each rank then publishes the stacks of the new order at the Storage Server, under the keys a load of that order asks for, copying the experts it holds over the device's own memory on a stream beside the batches, and reading an expert it does not hold from the checkpoint. At a common computation boundary the completed allocations and the new table are mapped at the addresses the graphs captured. The epoch, CUDA Graph addresses, request state and numerical weights remain the same. Once the operation finishes, the cache can grow into the released storage. The response lists each replica's epoch, requested order and allocations.

Distributed weight data parallelism (DWDP) prepares the resident shards, peer mappings and prefetch buffers of the requested distribution in the background; admission includes these allocations. Commit replaces the backing of the existing composite weight addresses and the prefetch copies together. A block that streams dense projections from host storage keeps those host allocations while its resident experts are redistributed.

The committed distribution is included in worker recovery launches and daemon handoff. A failure during preparation releases incoming copies and leaves the active distribution intact. A failure during publication triggers the existing engine recovery path with the committed distribution; an update on trial rolls back as its trial states. A redistribution that changes rank shapes is a change of the deployment's package (`PUT /admin/policy`).

## LoRA adapters

`/admin/load_lora_adapter` assigns the adapter the lowest free slot and has every rank publish the tensors of `lora_path`, a PEFT adapter directory whose tensors are its `adapter_model.safetensors`, at the Storage Server, through the path every weight takes, and map them read-only under the slot; `/v1/models` lists it, and its prefix cache and encoder cache entries are kept apart from the base model's and every other adapter's. An engine that replaces another, after an epoch change, a rollback or a relaunch, loads every adapter again before it serves; one that does not load leaves the registry, so requests naming it are refused. `/admin/unload_lora_adapter` removes the name at once and has every rank release the slot's tensors.

What computes with an adapter of a slot is a kernel package, and this repository holds none, so a request that names a loaded adapter as its `model` is refused rather than answered by the base model. The kernel package that provides it reads a slot's tensors and each token's slot. An adapter that a deployment serves for every request is fused into its weights at load instead, with `lora` or `lora_dir` ([Configuration](configuration.md)), and needs no slot.

## Nodes

Every leader daemon is a node, which serves through one path whatever it serves. Its listeners are bound when it starts and served for its whole life; its client API and admin routes are the serving deployment's, and while none serves the client API answers `503` (`no_deployment`), as does every admin route but the node's own: `GET /admin/status`, which states the node `idle` with the last deployment's error, `starting` or `stopping` with the deployment's name, or, through the serving deployment, `serving` with its status; `GET /admin/events`, the node's event log, which every deployment it serves writes; and `GET` and `PUT /admin/policy`, a `PUT` answering `503` until the deployment serves. `uniserve serve PACKAGE` starts a node for the package's deployment, which it brings up at once and lives as long as: the deployment's `POST /admin/shutdown` or a stop signal ends both. A package without a model is refused. A deployment of several nodes binds the leader's join listener as it starts, its endpoint the `join` of the readiness record; the leader serves once every node of `hosts` joined it. A node hands itself over in a hot restart whichever way it was started.

## The manager

`uniserve-manager` manages deployments across nodes through their admin API and depends on nothing else; it reads and writes the admin schema the daemons serve (`proto::admin`). A node is named by its operator socket (`--node unix:PATH`), or by the URL that socket is forwarded at from another host: a node never calls it or waits for it, so it attaches by reading a node's status (`GET /admin/status`, which states it idle, starting, serving or stopping) and events and detaches by stopping.

`ADMIN` below is a daemon's operator socket as its readiness record states it (`endpoints.admin`, Listeners).

```bash
uniserve-manager --node "$ADMIN" --node http://127.0.0.1:9000 status
uniserve-manager --node "$ADMIN" watch            # Ctrl-C detaches
uniserve-manager --node "$ADMIN_A" --node "$ADMIN_B" apply qwen3   # the package directory qwen3/
uniserve-manager --node "$ADMIN" apply --force qwen3               # a target a rollback marked unavailable
uniserve-manager --node "$ADMIN" shutdown
uniserve-manager --node "$ADMIN_A" --node "$ADMIN_B" restart  # one node after another
```

`status` prints one line per node; `watch` prints each event of each node's log as JSON until interrupted; `apply` sends the package in a directory, its `config.toml` and `programs/` as one tar archive, to each node's `PUT /admin/policy` in the order given, prints each node's revision record, and stops at the first node whose change does not converge, naming it, the nodes after it left untouched; `shutdown` brings each node's deployment down, releasing its storage unless `--keep-storage`; `restart` restarts each node's daemon in place, re-executing its own image, and stops at the first that fails; `pause`, `continue` and `flush-cache` are each node's generation and cache operations. Each `--node` is the leader of one deployment, and a GPU belongs to one deployment, so the changes of several deployments never contend for a device. What the manager waits for beyond an apply's answer, the end of an operation a node runs on its own, it reads from the node's event log by long poll: one request waits `--event-wait` seconds (30 unless stated, at most the node's `admin_config.event_log.longest_wait`) before the manager asks again, and a node the manager cannot reach is asked again every `--retry-interval` seconds (5 unless stated).
