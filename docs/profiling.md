# Execution profiling

A serving deployment profiles itself without restarting a process or pausing service. Every main process subscribes to NVIDIA's CUPTI once, as it starts, and every collector below shares that subscription: two counters and the fence probes are always on and exported as Prometheus metrics, and a profiling session (`/admin/profile`) attaches further collectors to the executing epoch at a step boundary and detaches them at another, writing one SQLite file per rank that `uniserve-profile` reads and converts to a Perfetto trace. It also reads captures of Nsight Systems and cProfile, producing hints about host waits, GIL ownership, copies and language crossings. Neither changes execution, rejects a request or establishes that an operation is unnecessary: inspect each finding in its workload context, then measure any optimization without the diagnostic instrumentation.

## CUPTI in a main process

A main process loads CUPTI as `libcupti.so.13`, the soname NVIDIA's CUPTI package of CUDA 13 installs on the loader's default search path, and accepts CUPTI 13.4.92 (API version 130401) or later: an older CUPTI is refused with an error naming the release to install, and the process logs that CUPTI is not subscribed and serves without it. Earlier CUDA 13 releases fail the work they record: the CUDA 13.0 toolkit's own CUPTI (2025.3.0, API version 130000) stalls a process that replays CUDA graphs while kernels are recorded and faults inside `cuGraphLaunch` once graph launches traced by node have filled the device buffers it pre-allocates, and 13.0.85 has the device write kernel timestamps into host records that may already be freed. The same CUPTI is the process's NVTX injection: the `uniserve-engine` executable registers it with NVTX, so the `uniserve.worker` ranges reach a timeline with no variable in the process's environment, and a profiler that names its own NVTX injection library (Nsight Systems) takes them instead. CUPTI accepts one subscriber per process, so the process subscribes once, before it loads a module, and the counters and every session collector enable the callbacks and activity records they need on that subscription and release them when they stop. A process a profiler already subscribed, such as Nsight Systems tracing CUDA, logs that CUPTI is not subscribed: it reports neither counter, and a session reports every CUPTI collector unavailable on it; the fence probes do not use CUPTI and stay on. The subscription lasts as long as the process.

CUDA graph executables are instantiated in their current CUPTI tracing mode: whole-graph records (`CUPTI_ACTIVITY_KIND_GRAPH_TRACE`) or node records. The always-on counters' whole-graph record is held from before a worker's warmup captures, so that the executables are instantiated once, in the mode they serve in; switched on after the warmup, it would have the first batch instantiate every captured graph again, which takes tens of seconds for Qwen3-30B-A3B's buckets on one GB200. When a timeline changes this mode, each executable is replaced before its next replay, from the retained source graph, with the parameters a rebind set on it. This preserves captured addresses without recapturing computation or synchronizing the device. A process subscribed to CUPTI replaces its executables the same way after it unmaps or maps again storage its graphs address (a sleep and wake, a cache's giving back or growth, a change of the weights' mappings, a committed expert redistribution): with `nvidia-cuda-cupti` 13.0.85 and driver 580.82.07 on GB200, an executable CUPTI instrumented by node before such a remapping faults inside CUPTI in `cuGraphLaunch` at its next launch, while one instantiated after it replays correctly. Executables instantiated for whole-graph tracing must not run in node mode: with `nvidia-cuda-cupti` 13.0.85 on GB200, that combination retains timestamp slots until CUPTI exhausts its profiling buffers.

## Watch host waits and stream idle time while serving

A serving rank reports two counters from CUPTI with every batch result, which reach the daemon with the scheduler's statistics and which it exports as Prometheus metrics:

| Metric | Labels | What it counts |
| --- | --- | --- |
| `uniserve:worker_blocking_calls` | `thread`, `call` | Driver calls that made a serving thread wait for the device: stream, event and context synchronization, synchronous copies, `cuMemFree`, `cuMemFreeHost` and `cuMemUnmap`. `thread` is `device` (a rank's device thread, which waits for its own work by design) or `control` (the control thread, which must not wait) |
| `uniserve:worker_stream_us` | `stream`, `state` | Microseconds of the device time of each observed stream, `device` (the streams a rank's runners compute on), from CUPTI's activity records of the kernels, copies and fills on the stream and of its graph launches (a launch is one record, or one per node while a session traces graphs by node and in a deployment that keeps PC sampling enabled, which refuses the whole-graph record): `busy` is the length of the union of their intervals, `gap` the time the stream had nothing to run between its first operation and its latest end, whether it waited for the host, for another stream or for any work, and `late` the time of records that arrived after the two seconds of device time the union keeps behind the stream's latest end, counted in neither; and `copy` (the streams a rank's copies between its device and the host regions run on), whose `busy` is the time between CUDA events recorded before and after each issue of copies, since CUPTI records no batch of copies (`cuMemcpyBatchAsync`) |

Both counters stay on while the process serves. On GB200, one request of Qwen3-30B-A3B in bfloat16 decoded 149.2 tokens a second with neither CUPTI nor probes, 146.8 with the counters and 146.3 with the default probes as well. Recording each node of a graph, which the counters do not, costs every kernel timestamps: the same request decoded 133.0 tokens a second.

## Fence probes

Fence probes time the model's modules on the device, inside CUDA graphs, at every step. A model runs each of its modules' forwards as a profiler range (`nn::profiler::range`), naming the module's class, such as `models.qwen3.transformer.TransformerLayer`, and its path. A capture puts a probe at the entry and one at the return of every module whose class matches `profiling_config.fence_modules` (`docs/configuration.md`). A probe is a single-thread kernel launched on the forward's stream: a forward captured into a CUDA graph at warmup captures its probes, which each replay runs. The kernel is the `range_marker` operator's package (`crates/ops/kernels/range_marker`), which the Build Server builds for each device's architecture and each main process installs before its warmup as it installs every operator's package; `uniserve keys` lists its two kernels, the probe and a clock read, for a deployment that places probes. A rank's device thread brackets each batch's execution with step markers of the same kernel on the runner's stream, the end marker launched behind the batch's last launch whatever the batch's launches returned, which store the batch's id where the probes between them read it, so every record names its step. Qwen3 states `Transformer`, `TransformerLayer`, `Attention` and `MoE`, its drafter's `Drafter` and its vision tower's `VisionBlock`; MiniMax-H3 states its denoiser's `Transformer` and `TransformerBlock`, its VAEs' `VideoEncoder`, `VideoDecoder`, `AudioEncoder` and `AudioDecoder`, and its text encoder's `TransformerLayer`.

A probe first reads a device switch, a word per module class and a master word in device storage; off, it returns at once. On, it reads `%globaltimer` and writes its time, its probe and its step into the next slot of a double buffer in pinned host storage the process allocated, 4096 records of 16 bytes a half; the probe that completes a half publishes it. A record's tagged word and a half's publication are stores with release semantics at system scope, so a published half holds no record the host cannot see yet. Each device thread reads its device's records after every batch, without any device synchronization: its complete halves, and the records of the half being filled up to the first the device has not written yet; a record tags its half's fill, so one the device overwrote before the host read it is counted as lost (`uniserve:worker_fence_records_lost`), and the steps begun before a loss are not counted. At each step's end marker the reader pairs each module instance's entry and exit in time order, sums the durations of a class's instances in the step, and counts the sum in the histogram of the step's stage and the class (the `module` label), beside the step's span between its markers (`module` `step`):

| Metric | Labels | What it counts |
| --- | --- | --- |
| `uniserve:worker_fence_step_seconds` | `stage`, `module` | A histogram of per-step durations on the device: for each step of the stage (its call kind, such as `prefill` or `decode`), the summed time of the probed instances of the module class `module` names, or the step's span for `step`; buckets from 10 µs to 10 s |
| `uniserve:worker_fence_records_lost` | | Probe records overwritten before a reader read them |

**Cost.** Every probe is a kernel launch in each replay of a captured graph, whether it records or not. The always-on budget is LMTracer's reported 0.58%. On GB200 with Qwen3-30B-A3B in bfloat16 (decode of 512 tokens per request, 60 s per point, probes switched off and on alternately in one server, four pairs per point), the step time measured:

| Probed classes | Probes per step | On against off, 1 request | On against off, 32 requests | Off against no probe |
| --- | --- | --- | --- | --- |
| `*Transformer` (the default) | 2 | −0.73%, −0.19% | −3.5%, +5.8% | within the ±5–10% spread between servers |
| `*.TransformerLayer` | 96 | +1.71% (+0.79 to +2.76%) | +1.15% (−3.54 to +3.32%) | within the spread between servers |
| `*` | 2028 | +18.4% | +18.6% | +21% to +36% |

Each probe thus costs about a microsecond of every step even when switched off, and about another microsecond when it records, so the default probes each model's decoder or denoiser stack only; probing every layer costs 1–2% and every module 15–35%.

`profiling_config.fence_probes = false` switches every probe off in place: `PUT /admin/config` with that assignment has the process write its devices' switches, and the graphs keep their probes, each of which then returns at once. Changing `fence_modules` changes which modules carry probes in the captured graphs, which is a new epoch (`docs/admin.md`).

## Profiling sessions

A session attaches collectors to every worker of the executing epoch for a window of steps or seconds, and leaves one SQLite file per worker in a directory it names. One session runs at a time:

The routes are the admin API's, on the daemon's operator socket, whose path the daemon's readiness record states (`$admin`, as [Listeners](admin.md#listeners) reads it):

```bash
curl --unix-socket "$admin" -X POST http://admin/admin/profile -H 'Content-Type: application/json' -d '{
  "collectors": ["timeline", "fence_timeline", "pm_sampling"],
  "stages": ["decode"], "start_step": 10, "steps": 200,
  "output_dir": "profiles", "max_slowdown": 0.1}'
curl --unix-socket "$admin" http://admin/admin/profile             # its state
curl --unix-socket "$admin" -X DELETE http://admin/admin/profile   # end it now
```

| Field | Default | Meaning |
| --- | --- | --- |
| `collectors` | Required | The collectors below, at least one |
| `steps` | Unbounded | The steps of the selected stages each worker records |
| `start_step` | `0` | The steps of the selected stages each worker skips before its window opens |
| `seconds` | Unbounded | How long the session lasts from its start |
| `stages` | Every stage | The steps recorded, by call kind (`prefill`, `decode`, `verify`, `denoising`, ...) |
| `workers` | Every worker | The workers recorded, by rank |
| `modules` | Every probed class | Name patterns (`*` matches any run) of the module classes whose fence records `fence_timeline` keeps |
| `output_dir` | Required | The directory each worker writes `profile-SESSION-epochEPOCH-rankRANK.sqlite` into, created when absent; a relative path resolves against the server's working directory |
| `timeline`, `pm_sampling`, `range_metrics`, `pc_sampling` | Below | Each collector's options |
| `sampler_read_ms` | `100` | How often each worker reads its armed samplers (`pm_sampling`, `pc_sampling`), in milliseconds (below) |
| `max_slowdown` | Unguarded | The quality-of-service guard's bound, a fraction of the step time before the session |
| `baseline_s` | `60` | The span before the session, in seconds, whose average step time the guard compares the session's with; at most the span the deployment keeps its statistics for (`update_config`'s `baseline` and `rollback.window`, [configuration](configuration.md)) |
| `guard_window_s` | `10` | The span of the session, in seconds, the guard averages its step time over, and the least time between two of its actions |

The session starts at the engine's next step boundary: the workers prepare their collectors and create their files, and answer with each collector's state, `prepared` or `unavailable` with the reason (a worker without CUPTI's subscription, a metric set that needs more than one pass). Each worker arms its collectors before the forward of the first step its window takes and disarms them after the forward of the last, as jobs that step's forward waits for, so that what CUPTI records begins and ends at step boundaries; it disarms them before a step of another stage and arms them again before the next selected one. A step is one batch's forward; every step during the session is listed in the file with whether the window took it. A session ends when every selected worker's window of steps ended, its seconds passed, the operator ends it, the quality-of-service guard ends it, or its epoch stops executing: an epoch change ends it before it parks the serving epoch, and a rollback ends the session of the epoch on trial; neither carries a session into the next epoch. Ending has every worker of a serving epoch disarm, release its collectors, write what remains and close its file.

`GET /admin/profile` answers with the running session, or the last that ended, under one identity on every replica of the deployment: its state (`running` while a replica's session records, `ending` while one writes its files, `ended` once every one ended), every worker's answer to its start (`workers`) and, once it ended, why and each worker's file and its rows by table (`end_reason`, `files`); the steps and the bytes the workers recorded so far (`steps`, `bytes_written`), reported with their batch results; the collectors still running; and each replica's own session (`replicas`), with the step time before the session and over its last `guard_window_s` (`overhead`) and the quality-of-service guard's actions.

| Collector | Mechanism | Options | What its file holds |
| --- | --- | --- | --- |
| `timeline` | CUPTI's activity records of kernels (`CONCURRENT_KERNEL`, which keeps kernels concurrent), copies, fills, NVTX marks and their data, storage allocations and the NVLink and PCIe topology, and the callbacks of every runtime and driver API call; a CUDA graph's launch is one record, or one per node | `graphs`: `whole` (default) or `nodes` | `kernel`, `copy`, `fill`, `graph`, `marker`, `marker_data`, `storage`, `nvlink`, `pcie`, `api` |
| `fence_timeline` | Every fence probe record the worker reads, of the selected classes and the step markers | | `fence`, with `fence_probe` |
| `pm_sampling` | CUPTI's PM sampling: hardware counters of the whole device every interval of device time, in one pass | `metrics` (PM sampling metric names; default `gr__cycles_active.avg`, `sm__cycles_active.avg`, `dram__throughput.avg.pct_of_peak_sustained_elapsed`), `interval_ns` (default 100000; a worker refuses an interval its reads cannot keep up with, which it measures as the session starts) | `pm_sample` |
| `range_metrics` | CUPTI's range profiler with metrics one pass collects, never replaying work | `metrics` (default `gpu__time_duration.sum`), `ranges`: `kernel` (a range per kernel launch, a CUDA graph's launch being one: the worker pushes a CUPTI user range as each launch's driver call enters and pops it as the call returns, and no other launch of the process, from any thread, is issued in between) or `module` (a range per probed module instance's call, which only calls outside a CUDA graph's replay push: a replay runs no host code), `pass_ranges` (the ranges one pass holds, at least 32; default 512) | `range_metric` |
| `pc_sampling` | CUPTI's PC sampling in continuous mode, which samples warps without serializing kernels | `period`: each SM samples a warp every `2^period` cycles, from 5 to 31, the periods CUPTI accepts (default 17); `hardware_buffer_mib`: CUPTI's hardware buffer, from 1 to 512 MiB (default 512, CUPTI's own); a period whose samples fill the hardware buffer between reads is released as failed | `pc_sample`, `pc_take`, `pc_stall_reason` |

**Sampler reads.** Neither PM nor PC sampling states an event for the samples it gathered, so a worker reads its armed samplers every `sampler_read_ms` (100 ms by default) on a thread of their own: PM samples, which it decodes and evaluates, and PC samples. Steps do not wait for a read, except that arming or disarming the collectors, which a step's forward waits for, waits for a read in progress. A PM read decodes into one counter data image, which CUPTI fills no further: the records past a full image are lost (on GB200 with `nvidia-cuda-cupti` 13.0 no later read finds them). The image and PM sampling's hardware buffer, both process host storage, therefore hold twice the samples of one read period at the session's interval, the buffer at the image's bytes per sample: on GB200 with the default metrics, 13.6 KB of image per sample, against the 8 KiB of hardware buffer a sample was measured to take. A read that fills its image, and a buffer that wraps before a read (which can also fail the next read, `CUPTI_ERROR_UNKNOWN`), lose samples, which the worker logs. Decoding and evaluating a sample of the default metrics took about 14 µs on GB200's CPU: at an interval of 20 µs, reads every 100 ms kept every sample over 5 s and one thread about 70% busy; at 10 µs the reads fell behind and lost samples. A worker therefore measures its own reads as the session starts: it samples at the session's interval for one read period, decodes those samples, and refuses the interval (the collector is `unavailable`, with what it measured) when decoding one period's samples takes the period or longer. PC sampling keeps its records in CUPTI's hardware buffer, of the size the session states (below), which a read empties; when it fills, the samples are lost and the read fails, which the worker logs.

**Range profiler passes.** `range_metrics` collects into passes of `pass_ranges` ranges and reads each every `pass_ranges / 32` steps the window records, so a pass holds up to 32 kernel and graph launches per step. CUPTI takes a pass's device storage at its first start and keeps it until the collector is released, and states no size for it, so each worker measures it as the session starts: the device's free storage the pass's first start took, with nothing of the rank in flight (an allocation of another process on the device in that moment moves the measure). On GB200 with `nvidia-cuda-cupti` 13.4.92 a pass took 1,420,288 bytes per range, its total rounded up to whole 2 MiB, the same for one to four metrics (passes of 512, 1,229, 2,048 and 4,096 ranges). A read whose stop or restart CUPTI refuses releases the collector: the file's `collectors` table records it `failed`, with CUPTI's result as its detail, and the ranges of a failed stop are lost. The storage is reserved in the GPU's quota (below), so the default of 512 ranges is chosen by its storage cost, as measured on GB200:

| `pass_ranges` | 512 (default) | 2048 | 65536 |
| --- | --- | --- | --- |
| Device storage | 727,711,744 bytes (0.73 GB) | 2,908,749,824 bytes (2.9 GB) | 93,079,994,368 bytes (93 GB) |
| Read every | 16 steps | 64 steps | 2048 steps |

CUPTI also needs free device addresses among the lowest ones for a pass's storage: on GB200, address reservations without a hint that take the addresses up to 1 TiB leave a pass of 2048 ranges unable to start (`CUPTI_ERROR_UNKNOWN`), whatever the device has free. A worker's own reservations (its graph pools and the mappings of its weights and KV cache) are therefore placed from 4 TiB on. PyTorch's expandable segments (`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, the ranks' default) still reserve from the lowest addresses, 0.9 to 1.1 TB of a warmed-up Qwen3-30B-A3B rank's address space; beside them, a pass of 65,536 ranges starts on such a rank after warmup, with 128 GB of the device free, where with the rank's own reservations among the lowest addresses too no pass past 1,407 ranges started.

**Device storage of a session.** A `range_metrics` session reserves its pass's device storage, as each selected worker measured it at the session's start, in the quota of that worker's GPU, with the worker's process item, while it runs. Where a quota lacks the room (a KV cache sized by the quota leaves none), the worker ends the session there and states the bytes; the daemon ends it on the others, the KV cache gives back tail segments for those bytes, as an epoch change's preparation does (the requests holding them run on), and the session starts once more. The cache grows back once the session ends. A session for which even every segment past the first leaves too little room is refused, naming the bytes and every quota entry; a device without free storage for the pass's first start refuses the collector with CUPTI's error.

**Collectors that share a device.** `pm_sampling`, `range_metrics` and `pc_sampling` each hold the device's performance monitors while they run, and CUPTI gives the monitors to one profiler at a time: on GB200 with `nvidia-cuda-cupti` 13.0, whichever of two starts second fails (`CUPTI_ERROR_HARDWARE_BUSY`, or an invalid parameter between the range profiler and PC sampling). A session therefore runs at most one of them, and a request naming two is refused; `timeline` and `fence_timeline` run beside any of them. CUPTI also refuses to enable activity records while PC sampling is enabled (`CUPTI_ERROR_NOT_COMPATIBLE`), so a worker enables PC sampling each time it arms its collectors, after the timeline started, and disables it each time it disarms them, before the timeline stops.

**PC sampling and CUDA graphs.** CUPTI attributes the samples of a CUDA graph's kernels to their program counters only when PC sampling was enabled when the graph was captured, and stayed enabled since; otherwise it counts them as samples of non-user kernels, without records (on GB200 with `nvidia-cuda-cupti` 13.0, over replays of a captured graph: every one of 1.8 million samples, against all but about 1,300 when PC sampling was enabled before the capture; instantiating the graph again under PC sampling does not change it). A worker captures its graphs at warmup, so by default a session's own sampler attributes the kernels launched outside CUDA graphs, and `pc_take` counts the samples of graph kernels among its non-user samples. A deployment that profiles its graphs' kernels sets `profiling_config.graph_pc_sampling` (`docs/configuration.md`): every worker then enables PC sampling, stopped, before it captures its graphs and keeps it enabled for its life (having first enabled the activity kinds of its always-on stream record, which CUPTI refuses to enable once PC sampling is), and a session only sets the sampler's period and buffer at its first arm, starts it at each arm and stops it at each disarm. While PC sampling is enabled CUPTI refuses PM sampling (`CUPTI_ERROR_HARDWARE_BUSY`), the range profiler and the whole-graph activity record (`CUPTI_ERROR_NOT_COMPATIBLE`), so every worker of such a deployment refuses sessions of `pm_sampling`, `range_metrics` and timelines that trace graphs whole, naming the option, and the session is refused; timelines with `"graphs": "nodes"` run.

**PC sampling buffer.** CUPTI keeps the samples in a hardware buffer of process host storage, which its own thread empties; a buffer too small for the sampling rate fills, and its samples are lost. A session states the buffer with its period (`pc_sampling.hardware_buffer_mib`, from 1 MiB to CUPTI's largest, 512 MiB, its default); a deployment that keeps PC sampling enabled holds the smallest buffer while no session samples, and a session sets its own at its first arm. A device samples at its own rate (its SMs times their clock over `2^period`), so the session measures whether the period fits the buffer on it: the first read whose buffer filled releases the collector as failed, naming the period and the buffer, and the file's `collectors` table records it. The smallest buffer that held each period on GB200 with every SM busy (a size holds when no window of 0.6 s fills it), a guide for a session that states a smaller buffer; even 512 MiB filled below period 12:

| `period` | 19 to 31 | 18 | 17 | 16 | 15 | 14 | 13 | 12 | 11 and below |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Smallest size that held | 1 MiB | 2 MiB | 3 MiB | 16 MiB | 16 MiB | 64 MiB | 128 MiB | 512 MiB | none (512 MiB fills) |

**Quality-of-service guard.** The daemon averages each replica's executing epoch's step time over the `baseline_s` before the session and, as each statistics report of the replica arrives, over the session's last `guard_window_s`. With `max_slowdown`, a step time past the earlier one by more than that fraction turns off the costliest collector still running, at most once every `guard_window_s` so that each change is measured; a slowdown that remains with no collector left ends the session. The collectors are turned off in this order: `range_metrics`, `pc_sampling`, `timeline`, `pm_sampling`, `fence_timeline`. Every action, with the slowdown that caused it, is in the session's state.

**NVTX.** The `uniserve.worker` ranges, one per turn of a worker's job named by its kind (`uniserve.worker.execute`, `.capture`, `.prepare`, `.control` and the others) with the batch it belongs to as its payload, the scheduler's (`uniserve.scheduler.update`, a batch's output applied, with the batch as its payload; `uniserve.scheduler.step`, one step of its loop) and the main process's control thread's (`uniserve.process.event` and `uniserve.process.terminal`, one request's event written to its daemon, with the request as its payload), follow a run-time switch, which starts as `profiling_config.nvtx_ranges` states (`docs/configuration.md`) and which a `timeline` collector turns on while it records and restores after. NVTX reaches CUPTI through the injection the `uniserve-engine` executable registers in process, which hands NVTX's marks to the CUPTI the process loads at its first NVTX call; a profiler that names its own injection library in the environment, as Nsight Systems does, receives them instead.

**Ranks of one process.** A main process serves every rank of its node, and CUPTI's records have one consumer, so its ranks share one timeline: the first to arm starts it and the last to disarm stops it, and a record reaches the file of the rank whose device ran it. An API call and a topology record name no device, so every recording rank's file holds them. The other collectors are each rank's own.

### Session files

Each rank writes one SQLite file per session, in UniServe's own schema: every raw record kind has a table, beside `metadata` (the session, the epoch (`epoch`), the rank, the device, its chip, the CUPTI library and version, the request, and `doc.*` entries stating what every table's identifiers and clocks mean), `strings` (kernel, API, NVTX and domain names by id), `clocks`, `steps` and `collectors` (each collector's state over the session, the guard's releases among them). The schema is the engine's file `crates/engine/src/profiling/schema.sql`, which states every table and the format's version; a file states the version it was written in (`schema_version`), and a release writes one version. A writer thread of the process waits for the records on a channel, writes what arrives in transactions of at most 200 ms, and checkpoints the write-ahead log into the file when the session ends; a worker that exits during a session leaves what it committed in the file and its log.

Every time is in nanoseconds of one of two clocks: CUPTI's (about `CLOCK_REALTIME`), for CUPTI's records, the steps and PM samples; and each device's `%globaltimer`, for the fence records. `clocks` holds samples of them at the session's start and end: CUPTI's clock with `CLOCK_REALTIME` and `CLOCK_MONOTONIC`, and each device's `%globaltimer`, read by a kernel that stores it into pinned host storage, followed on its stream by a host function that reads the host's clocks once the kernel completed, with half the host's time from the kernel's launch to that function as the sample's uncertainty. A client aligns a clock through the sample of least uncertainty. CUPTI's records carry the correlation id of the API call that issued them, a graph's nodes that of its launch.

```bash
cargo build --release -p profile     # target/release/uniserve-profile
target/release/uniserve-profile summary profiles/profile-1-epoch1-rank0.sqlite
target/release/uniserve-profile perfetto profiles/profile-1-*.sqlite -o trace.json
```

`summary` states each file's session, worker, collectors and rows by table. `perfetto` writes one trace of a session's files in the Trace Event Format, which the Perfetto UI opens: a process per worker, with a track per CUDA stream, host thread and device's fence probes (each probed module instance's call a slice, nested as the calls nest), the steps, and counter tracks for PM samples, all on CUPTI's clock. Any SQLite client reads a file by the schema; `uniserve-profile` is the `profile` crate's command line (`tools/profile`).

## Capture and inspect a CUDA timeline with Nsight Systems

Set `profiling_config.nvtx_ranges = true` in the deployment to start its ranges on; a session's `timeline` collector also switches them on while it runs. Each worker, the thread of one device, marks every job it runs with a synchronous range of the `uniserve.worker` domain named for the job's kind: `uniserve.worker.execute`, `resume`, `pass`, `shadow`, `map`, `stamp`, `capture`, `prepare`, `switch`, `commit`, `rollback`, `profile` and `control`; `execute`, `resume` and `shadow` carry the batch ID as a numeric payload. Native ranges use the NVIDIA NVTX SDK directly and issue no CUDA operations. Nsight Systems holds CUPTI's subscription in the processes it traces, so their sessions run no CUPTI collector.

Capture a representative workload with Nsight Systems. `CAPTURE` is an output prefix; run the fixed workload against the server the command starts.

```bash
nsys profile \
  --trace=cuda,nvtx --cuda-trace-all-apis=true \
  --cuda-graph-trace=graph --sample=process-tree \
  --cudabacktrace=sync:0,storage:0 \
  --export=sqlite --output="$CAPTURE" \
  uniserve serve "$MODEL" --set profiling_config.nvtx_ranges=true

target/release/uniserve-profile trace "$CAPTURE.sqlite"
target/release/uniserve-profile trace "$CAPTURE.sqlite" --json
```

The reader uses the Nsight Systems 2025.4 SQLite export schema. It opens the file read-only. `--scope PREFIX` selects synchronous NVTX ranges by name, defaulting to `uniserve.`; repeated `--rule NAME` options select individual rules. Hints do not cause a failing exit status. Invalid inputs or unreadable exports do.

| Rule | Execution expectation | Evidence and interpretation |
| --- | --- | --- |
| `host-sync` | Batch advancement should enqueue work or query readiness without waiting for unrelated device completion. | A Runtime or Driver device, context, stream or event synchronization call occurred inside the selected scope. Immediate result consumption, initialization, shutdown and failure cleanup may require it. Stream event waits and queries are not host waits. |
| `gil-held-wait` | A native GPU wait should release the GIL so independent Python work can proceed. | A CUDA host synchronization call overlaps a GIL ownership interval on the same thread. The hint reports overlap duration and retains any other threads in the process waiting for the GIL during that overlap. No duration threshold establishes harm; trace overhead, interpreter identity and workload dependencies limit the conclusion. |
| `sync-copy` | Host/device copies should overlap independent work when their consumer allows it. | A synchronous copy API has a correlated host/device transfer. An immediately consumed result or startup transfer can justify synchronous execution. |
| `pageable-copy` | Repeated asynchronous host/device transfers should use reusable pinned host buffers when useful. | A correlated copy uses pageable host storage. An Async API may stage or block; a one-time transfer may not justify pinning. |
| `device-roundtrip` | Intermediate numerical values and device decisions should stay on device when practical. | A D→H copy completes before an H→D submission on the same thread, device and NVTX scope. This ordering does **not** establish that the copies carry the same data; independent inputs or required CPU computation can explain it. |

Each hint retains API names, nanosecond intervals, global thread and CUDA correlation IDs, enclosing scope, batch number when available, native stacks when captured, and correlated copy sizes, streams and memory kinds. Nested numerical scopes inherit the native batch number. Backtrace activity records contribute stacks to their API call rather than another invocation. Copy correlation includes the process, keeping rank-local correlation IDs separate.

GIL evidence comes from Nsight's `GIL Trace` NVTX domain, including the original holding and waiting intervals. The reader matches domains within each process and ownership on the CUDA caller's thread. It omits unclosed intervals and reports the coverage gap. Missing GIL tracing means ownership is unknown; CUDA wait duration and cProfile cannot supply it. A captured waiter establishes temporal contention evidence, not a proven deadlock or a dependency on that GPU operation. The export does not identify individual Python interpreter locks. CPU-only GIL contention, mutex waits and callback dependencies are outside this rule's coverage.

CUDA Graph execution does not itself need the GIL once submitted. Python preparation, submission, callbacks, result handling and final-reference destruction can still acquire or hold it. Use the same GIL rule for graph and eager workloads; it describes observed waits rather than assuming that graph replay eliminates language interaction. Nsight's [Python GIL tracing](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#python-gil-tracing) supports CPython 3.9 or later on Arm SBSA, Linux x86 and Windows, excluding interpreters built with `Py_GIL_DISABLED=1`.

Coverage counts describe recorded activities. A missing activity, missing stack or unmatched scope is a coverage gap. No hints does not mean no unnecessary synchronization. GPU graph-level capture does not expose every graph node; Python metadata accesses and dependency relationships between independent batches are not inferred from CUDA timing. Use Nsight's timeline and native reports for GPU gaps, utilization and stream dependencies.

CUDA's [synchronization semantics](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html) depend on operation and memory kind. Nsight's [analysis guide](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html) describes the export and built-in reports. The `trace` rules are advisory interpretations of those activities.

## Inspect Python/native call edges

A Python client of the server can be read the same way: standard cProfile captures some Python/native calls and callbacks. Select the native function names to inspect; the analyzer matches builtin labels, with no assumptions about installation paths.

```bash
.venv/bin/python -m cProfile -o "$CALLS" "$CLIENT"
target/release/uniserve-profile calls "$CALLS" \
  --native "$NATIVE"
```

`NATIVE` is a substring of the builtin's cProfile label, such as `torch._C`; repeat `--native` to select more.

The report shows repeated edges in both directions, call counts and inclusive time. Use it to locate repeated metadata conversion or per-row callbacks for further investigation. A repeated batch numerical call is expected. Inclusive time includes the callee's work and must not be summed or interpreted as FFI overhead.

cProfile supplies no temporal ordering or batch attribution. Its capture does not automatically cover native worker threads; many C API attribute accesses and extension constructors are absent. The report lists the selected native functions actually captured and reports an unknown coverage result when none match. Use this evidence alongside the CUDA timeline, not as a complete crossing count.
