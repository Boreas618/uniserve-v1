# Architecture

UniServe is a Rust serving system with a Python numerical library. Rust owns the control and data planes: HTTP, scheduling, the worker processes and the channel to them, request state, storage and device memory, CUDA streams, transfers, collective orchestration and observability. The Python package `uniserve` owns numerical computation: model definitions, layers, kernel bindings, samplers and solvers. A video model's numerical execution in a worker is Python's whole, behind one executor (`uniserve.executor`): request metadata and shapes, CUDA graph capture and replay, and media codecs and containers. Text, diffusion LM and image models execute through runners whose Rust halves still hold their graphs and graph policy (`crates/worker/src/runner`). The two languages meet only in function calls through TVM-FFI.

This document describes how a deployment is organized, how a worker divides its work between Rust and Python, and how a request travels through it. A host is one machine; a worker is one process that executes batches, holding one device or none; a worker group is the workers launched, connected and replaced together; a rank is a worker's index within its group; a scheduler is the scheduling of one DP rank (data-parallel rank).

## Principles

1. **Rust decides.** Every decision and every piece of request state is Rust's: requests, slots, progress, sampling policy, random streams, storage assignment, graph policy, stream ordering, transfers and failure handling.
2. **Python is stateless.** Python provides resources and numerical execution on demand and keeps nothing about a request between calls.
3. **The languages meet only in function calls.** A call passes tensors, scalars, flat lists of integers or floats, strings and opaque handles, and returns the same. Neither side depends on a memory layout, record or encoding that the other defines.
4. **Each behavior is implemented once.** A forward's computation is one method of a runner, used by serving, by graph capture and by Python callers alike. A rule both languages need is written in one of them and called from the other.
5. **Python never runs concurrently with itself.** In a worker at most one thread executes Python at any instant, so no thread waits for the GIL.

## Processes

| Process | Language | Role |
| --- | --- | --- |
| `uniserve serve` (daemon) | Rust | One per node, for the deployment's lifetime. Every node's daemon starts, reaps and reports the processes of its node and holds the node's Storage Server claim. The leader's (node rank 0) also serves the HTTP API, processes every request's input (the model profile, chat templates, tokenization, multimodal inputs, request lowering) and output (detokenization, stop strings, reasoning and tool parsing, response assembly), and starts the engine process |
| `uniserve engine` (engine process) | Rust | One per deployment, on the leader's node, started by the leader's daemon. Runs one scheduler per DP rank (scheduling, the KV cache, the worker groups it drives), routes each request to a scheduler and serves the request interface to the leader's daemon |
| `uniserve worker` | Rust, hosting a Python interpreter | One per GPU worker and per CPU worker; executes the batches the engine sends |
| `uniserve storage serve` | Rust | One per host and serving user; keeps the memory that outlives the engine and the workers (see Memory and storage) |

A deployment of several nodes starts `uniserve serve` on each with `--nnodes`, its `--node-rank` and the leader's `--dist-init-addr HOST:PORT`; the leader binds that address and waits until every other node's daemon has joined it. Only the leader takes a model; another node's daemon serves the leader until the leader's connection closes, then ends its processes and exits.

Every process runs the one `uniserve` executable, installed into the Python environment's `bin/`, as one of its commands. The daemon and the engine process contain no Python. A worker starts as `uniserve worker`; the executable finds the environment from its own path, asks the environment's interpreter where its shared `libpython`, `libtvm_ffi` and the worker library `uniserve/_worker` (a TVM-FFI library, not a Python extension module) are, loads the first two into the process's global scope and then the library, the very file Python resolves `uniserve._worker` to, and calls the library's `worker_main` on the process's main thread. `worker_main` spawns the worker's builder thread, which initializes CPython with the environment's interpreter as its executable and no signal handlers, calls `uniserve.worker.attach()` (logging, faulthandler dumps on SIGQUIT and SIGUSR1, and the TVM-FFI global function `uniserve.worker.import_path`, the one function through which Rust reaches the library), releases the GIL and serves Python calls; the main thread is the control thread. The process exits with the status `worker_main` returns, without Python finalization. Python processes still load the library, for tests, harnesses and the video rules it exports, and in a worker that load returns the instance the executable loaded.

### The request interface

The leader's daemon and the engine process exchange the request interface (`crates/proto/src/request.proto`), Protobuf that changes only by additions, so a daemon keeps serving engines of later builds.

- **Start.** The leader's daemon binds its request socket, a Unix socket in the user's runtime directory, and has its own daemon start `uniserve engine --requests unix:PATH --processes unix:PATH --engine N`, where `N` numbers the deployment's engine processes. The engine process connects to the request socket and says hello with its protocol version, build and number; the daemon compares major versions and answers with the engine spec: the serving options that concern the engine and what the daemon resolved from the checkpoint (its generation limits, control tokens, context length, a block-diffusion model's canvas sampling). The engine reports `Starting`, starts its schedulers and their workers, and reports `Ready` with what it serves: the generation limits resolved against its workers' capacities, a video denoiser's description and its scheduler count; or `Failed` with the error. The daemon serves HTTP only once its engine is ready. Every request then passes the leader's hold (`RequestHold`): while an engine is ready it goes straight to it, and while none is it waits instead of being refused; once the engine is lost (its workers failed or its process ended) and none takes its place, held and later requests fail with the reason and `/health` answers `503`.
- **Requests.** A submission carries tokenized requests under the daemon's identities. The engine routes each to its least loaded live scheduler and answers `Accepted`, naming the scheduler, or ends it at once with a `Rejected` event. Every event names its request. A request's events flow under a credit window: the engine sends at most 64 events (`EVENT_WINDOW`) beyond those the daemon reports consumed, so a slow client holds back its own request only.
- **Commands.** Per request: cancel (the client went away), stop (the daemon's decoder matched a stop string), acknowledge (this many public tokens complete no stop string), abort and consumed. For the engine: drain, after which it admits nothing more, reports `Draining` and ends every token request that generates text alone as migratable while the others finish; and shutdown, which ends every request as aborted, closes the workers and exits.
- **Migration.** A token request that generates text alone can move between engines. Its engine ends it with a `Migratable` event, naming the cause (a drain or a loss of the workers that held it), after every token it generated there; the leader's `Migrator` submits it again through the hold, carrying those tokens (`generated_token_ids`), to the engine that serves next. That engine computes the tokens' cache as part of the prompt and generates after the last of them at the position the request had reached, and counts them as generated: against the token limit and `min_tokens`, in the penalties and bad words, and in the request's usage, which charges only its own prompt as prompt. The daemon keeps its own state (the detokenizer, the stop-string matcher, the response being assembled), so the client reads one uninterrupted stream. A request that names no seed takes one from the migrator when it is first submitted, so its draws, keyed by its seed and token positions, repeat on every engine. Migrations caused by a drain are not counted; a request survives `migration_config.max_migrations` migrations caused by losses. Images, readouts and videos do not migrate.
- **Artifacts.** A generated image or video reaches the daemon as an artifact event whose shared memory travels as a file descriptor beside its frame (`SCM_RIGHTS`); the daemon maps it read-only and serves its bytes.
- **Statistics.** Each scheduler's statistics travel once a second as a snapshot the daemon exports as metrics.

### Hot update

The leader's daemon replaces the engine with another build or other engine options without failing a request (`POST /admin/update`, `Leader::update`; `docs/admin.md`):

1. It starts a standby engine of that build, whose spec names the running engine's prefix cache units per worker group (`EngineSpec::standby`). The standby's workers start beside the running ones under the daemons' claim: they map the retained weights and the exclusive storages (cache planes, buffer pools, latent banks) without write access, warm up and capture their graphs on the warmup scratch units, and park; the engine reports `Standby`.
2. The leader holds new requests and drains the running engine: it admits nothing more, ends its token requests as migratable, whose migrations wait in the hold, and lets its other requests finish.
3. Once the running engine holds no request, the leader shuts it down: it writes its last published pages to the host KV cache and closes its workers, which give up write access with their storages' contents intact, and its process exits.
4. The leader promotes the standby (`Promote`): each worker takes write access once the Storage Server has the previous writer out, and the engine reports `Ready`.
5. The hold serves the new engine, which takes every held and migrated request; a migrated request reads its prompt's pages from the host KV cache and computes the rest.

The pause, from holding requests to the new engine serving them, covers the drain, the old engine's close and the promotion; the update reports it and each of those stages, and the leader logs how long each migrated request waited, from its migration to its first token on the new engine. A standby that does not start leaves the running engine serving; a promotion that fails leaves no engine, and held requests fail.

### The channel

The engine and each worker exchange the messages of `ipc` (`NewRequest`, `Batch`, `BatchOutput`, `WorkerInfo`) over one stream connection per worker.

- **Connection.** The engine process listens on one Unix socket path and one TCP port. A worker connects to the engine when it starts: through the Unix socket on the engine's node, through TCP from any other node. Workers and daemons accept no channel connection; the connections workers accept are their group's peer mesh and its collective store.
- **Registration.** A worker's first frame registers it: worker group, rank, launch generation and build. The engine numbers each launch of a worker group, and a relaunch takes the next number; the build is the package version plus a digest of the sources every artifact is compiled from, so the engine and workers of one build carry the same value. The engine refuses a registration of another build or of a launch that is not the group's current one, and otherwise answers with the worker's launch descriptor, which carries every other launch value, among them the deployment's name of the worker's host, its identity in transfers.
- **Lifetime.** The same connection then carries requests and responses, and its close is the only death signal of a registered worker: the engine treats the worker as dead and the worker exits. Before a worker registers, the engine learns of its exit from the daemon that started it.
- **Frames.** A frame is a length followed by one message in a serde binary encoding (MessagePack). The engine and its workers are built from one workspace and replaced together, so the message types are the protocol's only definition. A frame carries a message of any size its `u32` length states; no launch setting bounds it further.
- **Waiting.** Each side blocks on its socket together with one local wake descriptor, which its own threads fire for work that did not arrive on the socket.
- **Processes.** The engine starts no process itself. It asks the leader's daemon, over the daemon's Unix socket, to start each worker on the node its placement names, to reserve the socket a group's first rank serves the group's collective store on, to stop a group ahead of its relaunch, and to claim the deployment at a node's Storage Server; the leader serves its own node and forwards the rest to the node's daemon over that daemon's join connection, and every exit comes back the same way, naming the node, group, rank and launch generation. These messages are the process interface (`crates/proto/process.proto`), Protobuf that changes only by additions: a daemon keeps running while engines of later builds connect to it, and the two compare major versions when they connect. A worker is its daemon's child, leads a process group of its own and dies with the daemon; an engine whose connection closes takes its remaining workers on every node with it.
- **Data.** Tensors, prefix cache pages, latents and products move through the transfer mechanisms. Only a host product routed between hosts travels on the channel.

## The threads of a worker

A worker's threads are named by their role: the control thread, one execution thread per lane, and the builder thread.

| Thread | Name | Owner | Blocks only on | Does |
| --- | --- | --- | --- | --- |
| Control thread | the main thread | `Service`, `Executor`, the Rust half of each runner | Its socket and wake descriptor | Serves the channel, holds request state, admits batches, prepares each forward's inputs, picks its graph, builds its job, applies completions, retires storage |
| Execution thread | one per lane (`lane-N`) | `Lane`, `Job` | The work on its own stream | Owns the lane's stream: input copies, graph launches, event records and waits, output reads; hands Python work for its stream to the builder thread and waits for it |
| Builder thread | `builder` | `Interpreter` | The interpreter | Executes every Python call, one at a time: it builds the worker (loading the model, binding its weights, creating execution contexts, capturing forwards, at startup and when a promotion captures again) and runs the forwards served eagerly, a video executor's plans and steps, and releases |

Threads exchange messages only. The control thread submits jobs and receives completions; it calls neither the driver nor Python while it serves, so a slow launch, a driver call that waits on the device, or a stopped lane does not keep it from serving the channel, handling cancellation or reporting status. A lane's execution thread is the only issuer of work on its stream, so the stream's order is that thread's order. A lane posts a job's completion once it has issued the job's work, not once the device has finished it: memory a job used is read, rewritten or freed afterwards only behind something that waited for the device (a read in the job, a stream wait the job recorded, events the job completes after, or the fences that retire storage). Every Python call runs on the builder thread, in arrival order: an execution thread hands it a call and waits for the result; the control thread submits work that owns what it uses and never waits for it; a released Python object is dropped there in queue order, and nobody waits for the drop.

Eager expert forwards with several microbatches are the one exception to a single thread per lane: each forward stays suspended inside Python at its expert dispatch points, so each microbatch has a thread of its own, and those threads call Python themselves as cooperative turns, exactly one at a time, so they never contend for the GIL.

Blocking host work runs on host lanes, threads (`<lane>-<index>`) that each serve one kind of work and hand any Python call to the builder thread like every other thread: image preparation (`uniserve-image`), prefix cache imports (`worker-cache-import`), transfer reads (`uniserve-<kind>-read`) and shared-memory retirement (`uniserve-posix-shm-retire`). Signals (`worker-signals`), VMM descriptor grants (`worker-descriptor-grants`), a video executor's host reports (`uniserve-host-reports`) and, during startup, the engine watch (`uniserve-engine-watch`) are dedicated threads. The builder thread is created by Rust and is Python's main thread; Python installs no signal handlers in a worker. The builder thread releases the GIL while it waits for work, so the Python threads a video executor starts run beside it: its media host lane (`uniserve-media`), which reads condition media and encodes and muxes video, and the thread it starts for each reference video's FFmpeg decode.

## How Rust calls Python

Rust reaches the library by import path, for example `uniserve.runner.causal_lm.CausalLMRunner.decode`; there is no table of entry points and no map of named buffers.

- Arguments and results are tensors, scalars, flat lists, strings and opaque handles. A function names every tensor it reads or writes as a parameter.
- Each view of Rust storage is wrapped once with `torch.from_dlpack`; the torch tensor crosses as an opaque Python object, so every call that takes the view receives that same tensor with no per-call conversion. The tensor retains the Rust allocation, and its handle is released on the builder thread with the view's last clone.
- Resident tensors (prefix cache planes, slot tables) are passed once, to a runner's constructor; tensors and sizes that change per forward are parameters of its methods. A tensor only Python reads and writes is a Python intermediate and does not cross.
- A Python object that outlives a call is held by Rust as a handle: a model, an execution context, a runner, a graph. A method does not depend on state an earlier call left in Python, with one exception: a host-planned attention reader's launch plan, which the runner's `plan_*` method builds on the builder thread immediately before the forward, in the same job.
- A Python exception crosses with its kind, message and traceback (`uniserve.errors`).

### The video executor

A video model's rank is served by one Python object, `uniserve.executor.Executor`, which Rust constructs once the model is loaded (`crates/worker/src/worker/video.rs`) and calls through `PythonExecutor` (`crates/worker/src/executor/python.rs`). Rust holds no knowledge of the model's components, shapes or graphs; it reads what it plans from the executor's manifest and what each batch reads and writes from the executor's plan of that batch.

| Call | When | Does |
| --- | --- | --- |
| `manifest()` | after loading | the products every component publishes, the denoiser's description, each request slot's latent pages and state bytes, whether the rank stores the latent pool and the media units of the longest video; capacity planning sizes the rank from it (`crates/worker/src/capacity/video.rs`) |
| `bind(memory, ...)` | after capacity planning | constructs the runners on what Rust allocated: one stream per component the rank holds, the scratch of each stream, each capturing component's graph pool, the latent banks and the descriptor of the report pipe |
| `warmup()` | startup | prepares, warms and captures every shape the rank admits, in the order every rank of the group shares |
| `start(requests)` | the first job of a batch that starts requests | admits them and returns those it refuses with the reason |
| `plan(step)` | the second job of every batch | what each call reads and writes: input indices, each output's shape, region and memory, whether a host task fills it, and its publication |
| `execute(step, tensors...)` | the third job of every batch | runs the calls on the tensors Rust leased and bound, in plan order; returns how each call's forward ran (eager, replay or capture) |
| `release(slots)` | when request slots retire | drops the slots' request state; Rust hands the call to the builder thread and does not wait |
| `kernels()`, `close(aborted)` | the kernel report, shutdown | |

A video batch runs as jobs on the lane of its first call kind. The first job binds the calls to their requests and reads their host-gated predicates (`Opening`). The second asks the executor to plan the batch from a JSON step that names every call with its request, slot, inputs and outputs. Rust then leases every read, binds every write and takes each denoising trajectory's banks from its ledger (`LatentLedger`: which of a slot's two latent banks holds its committed sample and how many steps it took); the third job runs `execute` on those tensors, followed by the producer fences and exports of what the calls wrote, and the ledger applies the steps once the job completed. A write a host task fills (condition media, an encoded unit, the muxed MP4) is deferred: the executor's media host lane fills it and sends one report per finished task through a pipe (batch, call, row, status, a value and a payload such as the MP4's bytes); the `uniserve-host-reports` thread reads them into a mailbox and wakes the control thread, which completes each deferred call once its reports arrived.

### Runners

Text, diffusion LM and image capabilities each have one runner in two halves with the same class and file name: `uniserve/runner/<name>.py` and `crates/worker/src/runner/<name>.rs`. The Rust half prepares a forward's inputs, picks its graph, records its job and applies its outputs. The Python half is the forward itself, captured into a graph or run eagerly; a Python caller, including a video model's executor, uses it directly.

| Capability | Runner | Python methods | Request state (Rust memory) |
| --- | --- | --- | --- |
| `CausalLM` | `CausalLMRunner` | `prefill`, `decode`, `select`, `score`, `score_prompt`, `verify`, `commit`; `plan_prefill` and `plan_decode` for a host-planned attention reader | prefix cache units, slot tables and lengths, continuation tokens, sampling positions and draws, logit biases |
| `DiffusionLM` | `DiffusionLMRunner` | `attend`, `finish`, `readout`, `denoise`; `plan_attention` for a host-planned reader | prefix cache units, each slot's token sequence |
| Image vision and latent encoders | `EncoderRunner` | `encode`, `warm`, `prepare_image`, `prepare_resident`, `draw_noise` | products, page-locked prepared images, posterior noise |
| Image denoisers | `DenoiserRunner` | `draw_noise`, `prepare_latents`, `encode_conditions`, `denoise`, `plan`, `plan_denoise`, `step` | prefix cache units, latent pages, per-slot state rows |
| Image decoders | `DecoderRunner` | `decode`, `quantize` | latent pages, products |

Video request rules (canvases, frame counts, how each condition is prepared and the conditioner's presentation) are implemented in the `models` crate: the leader's daemon plans and presents every request with them before submission. The executor reaches the canvas rule, the training buckets, the canvas a target names, the frame count of a duration and a condition image's vision grid through functions the worker library exports (`rules.rs`); it does not plan or present requests.

A method that can be captured meets four conditions: its shapes are fixed by its scalar arguments; every value that changes between forwards enters as tensor contents; it performs no host planning or synchronization; it draws no random numbers, because draws and noise are inputs the control thread generates (for example a latent encoder's posterior noise, drawn by `draw_noise` from the request's seed).

### Library functions and functions Rust gives Python

Besides the runners, Rust calls:

- `uniserve.loading.rank`: read a checkpoint's configuration and the model's description, load this worker's modules;
- `uniserve.loading.host_weights`: the layer stack of a component that keeps its weights in host memory, its layout in a layer slot, and the rebinding of its projections to the slots Rust allocates;
- `uniserve.distributed`: process groups, created in the order Rust fixes; `collectives.NativeCollectives`, which wraps Rust's collectives for layers; `experts`, with `uniserve.backends.experts.HostBootstrap`, for expert unions;
- `uniserve.executor.Executor`: a video model's executor (see above);
- `uniserve.bindings.context.Scratch`: the transient work area that the execution contexts serialized on one stream share (a runner prepares its own execution context with `uniserve.runner.context.execution_context`);
- `uniserve.cuda_graph`: graph pools, `capture_begin`, `capture_end`, `break_graph`;
- `uniserve.prefix_cache`: the cache's page plan, unit resets, imported-page conversion;
- `uniserve.backends.kernel_choices`, `uniserve.profiling` and `uniserve.media`;
- `torch` and `gc` functions as they are.

In the other direction, Rust passes Python the collectives of a communicator on one stream, the host group's `all_gather`, `broadcast`, `barrier` and `split`, the peer-mapped storage Rust allocates for split expert weights (a storage tensor and every member's address), expert dispatch and weight prefetch, and the hooks that make a host-resident layer readable before its projections run and record their reads after.

### Attention providers

The library's provider registry (`uniserve.backends.attention.PROVIDERS`, with `resolve`) is the one list of attention providers: `auto` (a native kernel per call, chosen from the device and the installed kernel libraries), `flashinfer`, `trtllm`, `flash_attn_4`, `torch`, `prefix_block`, `flash_attn` and `sgl_kernel`. `attention_backend` passes its value to the workers unchanged, and a worker refuses a name the registry does not provide when it loads its model; the engine reports that startup error. A provider declares whether serving captures its calls (`Backend.captures`); the portable `torch` provider does not. A host-planned provider's plan is shared by every layer of one execution context that has the same layer shape and batch signature, so a forward plans once.

## CUDA graphs

This section describes the runners; a video model's executor captures and replays its own graphs (the last item). A captured forward is a CUDA graph, possibly breakable into segments separated by graph breaks. Every graph break is a break op (`BreakOp`, `crates/worker/src/cuda_graph/mod.rs`): native work the worker noted where the capture reached it and performs between the two segments at every launch, such as the copy of an expert layer's weight shards from its peers under weight data parallelism. Python records no work between segments, and torch replays only a graph without breaks (a Python caller's `uniserve.cuda_graph.capture`).

- **Capture.** The control thread picks a runner method, a shape and the tensors for that shape, and records the capture into a job of the lane that serves the forward: the builder thread calls `capture_begin`, the method and `capture_end`, and the completion carries the captured graph of each segment, which Rust instantiates into an executable it owns (`cuda::GraphExec`) before Python releases its graph objects (`handover`); Rust destroys the executables when the runner releases the graph. Warmups are eager calls recorded the same way. Each runner captures each kind of forward at its configured shapes largest first, so smaller captures reuse the pool blocks of larger ones.
- **Launch.** For a forward with a graph the control thread submits one job. The execution thread writes the inputs with native copies, launches each segment with `cuGraphLaunch`, performs the breaks between segments and records an event; once it completes, it reads the outputs and posts the completion. A forward whose breaks are all native and whose attention reader is device-driven runs no Python; with a host-planned reader, the job first runs the runner's `plan_*` method on the builder thread.
- **Eager.** A forward without a graph writes the same inputs, hands the same method with the same arguments to the builder thread, then records the event and reads outputs as a launch does.
- **Shape key.** Each runner keeps its graphs in its own table, keyed by the runner's key (the method, the shape bucket, the numerical variant and the output selection) and, for an expert forward, the agreed capacity. A runner's tensors are fixed when it is constructed, so they are not part of the key.
- **Policy.** Rust decides which shapes are captured, in which order and pool. Once startup seals the graph tables, a configured bucket that a forward selects without a resident graph is an error, never an eager fallback. The text catalogs hold every batch a worker admits: row buckets up to one past its largest batch, the largest decode batch its cache pool holds, the commit of every batch's calls (at a decode bucket, or at the binding's rows), and, for a model that places vision blocks in its prompts, a media variant whose graphs read each row's causality and the embedding columns on the device; a text forward no bucket holds is refused. The diffusion LM catalogs hold every pass a worker admits: `attend` row and token buckets up to its rows and token budget, `finish` slot buckets up to the token budget (captured per expert capacity when the final layer exchanges tokens) and `denoise` row buckets up to the blocks a step holds; a diffusion LM forward no bucket holds is refused. A text runner's selections hold every forward's tasks: a `select` graph per task bucket (powers of two up to its rows) and set of samplers its tasks take, a `score` graph per bucket of reporting tasks and top width whose words fit the forward's, and a `score_prompt` graph per top width, which a forward that scores its prompt launches once per block of prompt rows; a verification selects eagerly and is refused under graphs. The graph policy is resolved after loading: with an attention provider whose calls are not captured, `auto` serves every call eagerly and `full` is refused. The workers of a group capture the same shapes in the same order, since capture and launch include collectives. No host callback that enters Python is ever placed on a stream or inside a graph.
- **Video executor.** The executor captures each component's forwards with `uniserve.cuda_graph.capture` into the graph pool Rust reserved for that component, holds the graphs in torch and replays them inside `execute`, on the builder thread. It captures every layout the rank prepares at startup (under graphs a request with conditions evaluates in a startup layout widened to the deployment's condition capacity), one text encoder graph per prompt capacity, the decoders' unit shapes and the keyframe condition sets a conditioned layout admits; once the denoiser is sealed, a startup layout without a captured step is an error. The encoding of condition media whose shape no graph holds (a reference image or video of another size, a vision grid without a graph) runs eagerly, so requests with references serve under graphs.

## Memory and storage

| Owner | Allocated by | Contents |
| --- | --- | --- |
| Rust | the CUDA driver | everything that holds request state, is read or written natively, or crosses a process: the prefix cache unit pool, slot tables, the latent pool, product arenas, forward inputs and outputs, pinned staging, export ranges |
| Rust | the CUDA driver, through torch's caching allocator | graph pools and operator scratch: each a reserved address range whose physical memory Rust maps as torch's pluggable allocator asks for segments (`cuda::VirtualPool`, `crates/worker/src/cuda_graph/memory.rs`), at addresses that stay fixed while any graph addresses them; scratch has pools of its own, so no graph's activations share its blocks |
| PyTorch | its caching allocator | weights, activations of eager forwards |

Capacity planning measures free device memory after loading and assigns the remainder to the prefix cache and media storage. The process's own usage, as NVML reports it, counts with the device storages its scope keeps at the host's Storage Server; exclusive storages a predecessor left that no owner has taken yet count as free, and an owner that allocates new memory first releases them. Memory is organized by owner in `crates/worker/src/memory`:

- **Prefix cache** (`prefix_cache/`): the unit pool, block tables, unit accesses, transfer bases and pending imports of attention state.
- **Latent cache** (`latent/`): denoising trajectories in two banks of pages per slot, with versions exported to other workers.
- **Product store** (`products/`): tensors one call produces and another consumes, with their reads, writes, exports and imports.
- **Request slots** (`request_slots.rs`): the per-slot state banks of the requests a runner holds.
- **Buffers** (`buffer.rs`): the `BufferPool` of cross-call buffers, bound at the offsets the scheduler placed them. Each worker backs its own pool, sized to the products of the components it executes and of the components that read them (`MediaCall::readers`), and reports its bytes; the engine places each media request's products in the pool of every worker that backs them, and a token runtime's products at one offset on every worker.
- **Outputs and host buffers**: page-locked readback of results (one arena per runtime on each lane, allocated when that runtime starts, of blocks the size of its largest batch; a batch leases exactly its words), and the `PinnedPool` of page-locked blocks that host-prepared inputs (decoded images) are written into.

### The Storage Server

Each host runs one Storage Server (`uniserve storage serve`) per serving user, which the host's daemon starts when the host has none, in a session of its own, so restarting the daemon never ends it. Clients connect through a Unix socket owned by the user (`$XDG_RUNTIME_DIR/uniserve/storage.sock`, else `/tmp/uniserve-<uid>/storage.sock`) and pass file descriptors with `SCM_RIGHTS`. The server holds memory and never interprets it: it keeps the descriptors of CUDA VMM allocations (POSIX file descriptor handles) and host memfds, never creates a CUDA context, and moves no bytes; clients compute every key and copy on their own streams.

- **Claims.** The engine has each host's daemon claim the deployment (its served model name) at that host's server and hands each worker the claim's token in its launch descriptor. The daemon holds the claim for as long as it runs. A claim releases the scopes the engine no longer places; `uniserve storage retire --deployment NAME` releases a deployment that is no longer served, and `list` prints what the server holds.
- **Weights.** A GPU worker keeps its loaded parameters and buffers as read-only tensors, with a manifest of each tensor's checkpoint source and representation (`uniserve/loading/retained.py`). A tensor is keyed by its placement, its GPUs and the fingerprint of the checkpoint source it is loaded from (that source's files' headers and identities, the normalized configuration, the weight choices, and a digest of the numerical code the process has loaded: every loaded module of `uniserve` and `uniserve_kernels`, the packages' other sources and the kernel libraries' versions); the manifest and the tensors no source loads are keyed without the checkpoint's files. The manifest records the digest of every module loaded by the time the weights were published, and a worker binds them only while each module still has it. An in-place weight update (`/admin/update_weights`) rewrites the tensors where they lie and renames them after the new checkpoint at the server. A starting worker maps the tensors it finds read-only and binds them instead of reading the checkpoint. Loading is collective, so the workers that load together agree on what to read: the tensors any of them misses, or everything when one has no manifest; a change to one checkpoint source thus reloads only its tensors. Each worker moves what it read into retained memory (one allocation per torch storage, small ones packed), publishes it and maps it read-only. The host region of a layer stack streamed from host memory is a read-only host storage among them. Loading stores every encoded weight in the layout its kernel provider declares (`uniserve/loading/layout.py`), and preparation verifies it, so the retained bytes are those the kernels read.
- **Exclusive storages.** The prefix cache planes, the buffer pool and the latent banks are exclusive storages with one writer, keyed by their scope, name and shape; a device cache's value planes are eight segments of their units, each layer's part of a segment a storage of its own mapped back to back, so that the tail of the cache can be given back while a standby engine starts or the deployment sleeps and created again at its addresses (`docs/admin.md`): a restarted worker of the same scope takes the memory its predecessor left, after the server shoots that predecessor down if it still holds write access (SIGKILL to its process group, its exit, and NVML no longer listing it on the GPU). An owner resets only memory created for it; a storage a predecessor left keeps the finite values it last wrote. A standby maps them while its predecessor serves from them; after a crash the engine's cache index starts empty, so nothing reads them before a unit is recycled for its next owner.
- **Host KV cache.** The server keeps page pools of host memory, one memfd of equal slots per deployment, page layout and NUMA node, shared by every worker of the deployment whose pages have that layout, a standby engine's included: a page's key is seeded with the model's fingerprint and the digest of all the numerical code installed, so pages of other weights or code share the pool without matching; a worker takes the pool on the host NUMA node closest to its GPU, whose pages the server binds to that node. With `kv_cache_config.host_tier`, each GPU worker maps a pool for each of its cache groups, and the scheduler decides reuse in the host KV cache with the rules of each group's attention type that decide it in the device cache (`crates/engine/src/kv_cache/manager.rs`): a reuse ends at a page boundary every group accepts, full attention needing every page before the boundary and a sliding window only the pages of its window before it. At admission the scheduler pins every group's pages that follow the request's device prefix match, takes the deepest boundary every group accepts with them (a boundary one group rejects does not end the walk), and has the request's first prefill batch load the pages the boundary needs into new units: a full-attention group's pages from the device match on, a sliding window's pages of its window that the device does not hold. Full attention offloads every published prompt page into a reserved slot with a later batch, which its output commits; a sliding window offloads only the window before an aligned boundary: every `kv_cache_config.boundary_interval` pages of the largest block size, the last boundary a reissue of the prompt can reuse, and the last boundary of its published pages. The window's pages are reserved while the request's table still holds them, as one window the pool evicts whole, and with the last full-attention page before its boundary, its anchor (`crates/engine/src/kv_cache/offload.rs`, `crates/storage-server/src/pages.rs`). A rank issues a batch's page loads and offloads on its copy lane as soon as the batch arrives, so they overlap the forward the previous batch runs; the batch's forward waits only for its loads, and its output for its offloads. Before the engine closes its workers at shutdown, it lets the batches in flight complete and sends each group's remaining reserved offloads in a batch of page offloads alone, so every page it reserved reaches the host KV cache. A page is one page of one group on one rank, layer-major: keys, values, and FP8 scales.
- **KV storage.** With `kv_cache_config.mooncake`, the server runs a Mooncake connector, a child process it starts again when it ends (`crates/storage/src/connector.rs`). The connector maps every page pool, registers it with Mooncake, and writes each committed page to Mooncake as the object `uniserve_{page key}_{kv head offset}-{kv head count}`, which names no deployment or host. A lookup tells for each page key whether its page is in the pool, in Mooncake or absent. When the pages Mooncake holds would deepen the boundary every rank's pool holds by at least 256 tokens, admission prefetches them into reserved slots, waits for them at most 1 s plus 0.25 s per 1024 tokens, and computes the pages that did not arrive. Prefetches hold at most half of a pool's slots. Mooncake's master evicts objects; the connector never removes them.

### Transfers

Transfers go through one module per mechanism in `crates/worker/src/transfer`: `local` (in-process borrows), `posix_shm` (POSIX shared memory on one host), `vmm` (CUDA VMM allocations exported in place or through a pool, imported by fabric handle or by a descriptor from the exporter's grant socket) and `channel` (bytes carried in the location). A read runs on a transfer-pool thread with one stream per thread and device: it claims the chunk and waits on the host for the claim, orders its copy behind the handoff and the producer's event (a cross-device read waits for the producer on the host), copies, acknowledges, and drains its stream before its task completes, which returns its bytes and read credit. A VMM read imports the allocation's handle, maps it and opens its ready event. An export states whether its allocation is resident (the producer's arenas, pools and cache planes, kept until it closes) or made for that export alone: a reader keeps its mapping of a resident fabric allocation for every later read of it until its transport closes, and releases any other mapping with the read. A worker's transfers share one byte budget and one set of read credits; an exported product holds its bytes once, whatever number of mechanisms publish it, and they return when its last backing physically retires. A worker holds one read credit per queued call (a media worker at least one per concurrent artifact import of each slot and one per worker of the deployment) and reports their count (`WorkerInfo::transfer_tickets`); the engine keeps no more transfer calls reserved than the narrowest worker holds.

## Startup

Every worker of a group runs these phases in the same order, because several are collective:

1. The control thread connects to the engine, registers and receives the launch descriptor while the builder thread starts the interpreter; until serving starts, a watch ends the worker at once if the engine's connection closes. Once the interpreter is up, Rust checks the devices and makes their primary contexts current.
2. `read_config` describes the model; Rust validates placement.
3. Rust plans the process groups; Python creates them.
4. `load_model`, or binding the weights the worker retained when it last loaded the same model on the same placement; the checkpoint reader reads each source file front to back into the page cache before mapping its tensors, so workers loading one cold file do not fault it page by page. A worker that loaded moves its weights into retained memory and publishes them.
5. Rust creates the worker's streams and starts one execution thread per lane; expert unions and weight prefetch start, and a component placed with `"weights": "host"` moves its layer projections into a page-locked host region and a ring of device slots that Rust copies them into ahead of each layer.
6. Rust plans capacity from the model's sizes and measured memory, allocates request storage, and constructs a runner, with its execution context, for each placed component and lane. A video model's rank instead binds its executor to the streams, scratches, graph pools and latent banks Rust allocated, and the executor constructs its runners.
7. The executor and the profiler start.
8. Warmup: Rust sets each runner's graph budget and prepares it; then every captured method runs eagerly once at its shape, so kernels compile outside capture, and is captured, each runner's shapes largest first. Paths that always run eagerly (image prompts, uncaptured image denoising steps) run once too, so no serving request selects a kernel first. A video model's executor warms and captures its components in one call (`VideoWarmup`), encoders first, then the denoiser and the decoders.
9. The runners' graph tables and graph storage are sealed; Python's garbage collector is collected, frozen and disabled; the worker reports its capacities and the shapes it prepared to the engine: one image shape per captured guidance-branch count (`WorkerInfo::image_warmups`, a guided one with its model's framing of an empty negative prompt) the rows of one diffusion LM sampler chunk (`diffusion_lm_step_rows`), and the tokens its image denoiser's image-unconditional guidance branch attends to when that branch does not read the request's own context (`image_unconditional_token_ids`), which the engine reserves and prefills as a guidance prefix of its own beside the negative prompt's.
10. On GPU workers the engine warms the serving path with real requests through its scheduler (`crates/engine/src/warmup.rs`): a token request of a prefill and a decode, a group of equal one-block diffusion LM requests for each row count of a sampler chunk, each submitted in one command so its steps run with exactly that many rows (the one-row request generates a second block, so a commit prefill runs), and a two-step image request per image shape at the guidance scales of its branch count. A request the deployment's generation limits refuse a client is left out. Serving starts once every warmup request finished.

After startup the builder thread is idle except for eager forwards, host-planned attention plans, a video executor's batches and the little resource work issued while serving.

## Serving

**A text decode step.** The engine sends a `Batch` whose decode calls name request slots. `CausalLMRunner` picks the decode graph of the smallest row bucket that holds the batch and submits the job. The execution thread writes the forward's inputs (slot indices, finish flags, the rows' sampling parameters and draws) and launches: the graph gathers tokens, positions and attention metadata from slot state on the device, runs the model, projects the final-position logits and selects each row's token: greedily, or by sampling under the row's temperature, top-k (up to 128 candidates), top-p, min-p and penalties with the draws Rust generated from the request's random stream, all of them tensor contents of the graph. A batch that needs token sets, logit biases, typical-p, reported logprobs or a sampled top-k beyond the 128 candidates selects after the forward with the runner's `select` graph of its task bucket and samplers, whose controls are tensor contents (each task's sampler, parameters and draws, token sets as bitmasks, its slot's row of logit biases), with the same kept-set computation; its `score` graph reports logprobs, scored on the model's raw distribution. The commit graph installs the selections into slot state, so the next step can be queued before this one's result is read. When the forward's event completes the execution thread reads the selection words and posts the completion; the control thread updates request state and returns the `BatchOutput`. Prefill (which also carries verification rows) and commit have their own graphs, and a verification selects eagerly with `verify`; with tensor parallelism every worker launches the same graph and the collectives inside it were captured with it.

**A FastH3 video request.** The daemon plans the request with the `models` crate's rules. On every rank the executor admits it at its exact size (`start`), and a denoising rank holds the layout that serves it (without graphs, a request with conditions evaluates in a layout prepared for it). The text encoder's graph of the smallest prompt capacity that holds the prompt runs on its tensor-parallel group; latent preparation writes the request's noise and state rows; each denoising step copies the slot's committed latent pages from the bank the ledger names into the sample tensors, replays the layout's graph on every worker of the sequence-parallel group and copies the result into the other bank; video and audio decoding replay one graph per temporal unit; the decoded units transfer to the CPU workers, whose media host lane encodes each unit and muxes the MP4.

**Batches.** Every capability's batch goes through the same steps (`crates/worker/src/executor/batch.rs`): open (bind calls to their requests, read host-gated predicates), lease output storage, bind completion flags, seal (end reads, validate every owner's update), commit once the job carrying the device work completed (writes become visible, calls pending), and materialize once the output fences complete, finishing any host work such as image or video encoding (a video batch's host work completes through the executor's reports). A failure before the commit point fails the batch's calls and the worker keeps serving; a failure at or past it is fatal to the worker.

## Parallelism

- **Lanes.** A lane is a stream with its execution thread, optionally on its own SM partition; lanes overlap on the device and do not wait for each other on the host. A rank that maps a host page pool also has a copy lane, a full-device stream of the cache's device that serves no call kind and performs the batches' page copies (`crates/worker/src/lane`).
- **Collectives.** A layer calls its communicator; in serving its functions are Rust's NCCL collectives on the forward's stream, captured with the forward.
- **Expert forwards.** The workers of an expert union agree on each forward's source and capacity over their host group, then launch; a worker without tokens launches the join graph of the agreed capacity. Expert dispatch with host work, weight prefetch and microbatch boundaries are graph breaks.
- **Schedulers.** Each DP rank has a scheduler: its own thread, KV cache and the worker groups it drives. A replica is one of the groups a deployment file's `replicas = N` expands a group into.

## Failure handling

Errors cross with a stable code, whether they are fatal to the worker, and the phase they occurred in. A Python exception in an eager forward fails that forward's batch. An error in resource work fails startup, or at serving time the batch that needed the resource. A launch failure or a driver error is fatal to the worker, and the engine replaces its failure domain: the worker group, or every group that shares an expert world, whose workers hold that world's communicators. Every group of the domain terminates its workers; the token requests they held that generate text alone end as migratable (`MigrationCause::Loss`), and the daemon submits them again with their generated tokens, to wait for the relaunched workers, while the other requests fail. The domain is relaunched together, its groups form their communicators again, and their weights and exclusive memory come back from the host's Storage Server. The relaunch runs on a thread of its own (`Relaunch`, `crates/engine/src/worker/group/relaunch.rs`), so the scheduler keeps serving the scheduler's other groups while the relaunched workers start; each group of the domain admits work again once it has installed them, and a relaunch that fails closes the domain's groups. A group that keeps a standby (`worker_config.standby`) is replaced by promoting it instead: its ranks started beside the group's, mapped the group's weights and exclusive storages without write access, captured their graphs on the warmup scratch units, which the scheduler never allocates, and parked; on promotion each takes write access once the Storage Server has the failed rank out and serves at once, and the group starts a new standby (`crates/engine/src/worker/group/standby.rs`). A group on one host without an expert world keeps a standby rank group of its own and promotes it within the step. The groups of an expert world, and a group on several nodes, keep a standby world instead: once every group of the domain serves, the domain launches each of them a second time at a rendezvous of its own, so the standby ranks form their own communicators and capture graphs over their own workspaces, and parks that world. A loss in the domain stops only the serving launches, and the replacement round promotes the standby world instead of relaunching: every rank is asked to promote before any answer is awaited, since a suspended world restores its expert workspaces together, and the groups install the promoted ranks and offer the next standby world. A suspended world's transport workspaces that cannot keep their addresses (DeepEP's windows, the NVSHMEM heap of colocated MegaMoE) are freed while it parks; its promotion creates them again and captures the graphs that run expert steps anew, on the scratch units, before it serves. A promotion that fails relaunches the domain.

A lost engine process takes its workers with it. Its client ends every request it held as migratable, the leader's daemon holds new requests and starts a new engine process under the same claims, whose workers find their weights retained, and the hold then serves the new engine every held and migrated request. A request survives `migration_config.max_migrations` migrations caused by losses; when the new engine does not start, held and later requests fail.

A driver call that does not return stops only its lane's execution thread. The control thread keeps serving the channel and, once a job has stayed in flight for the stall bound (half the engine's watchdog timeout, `worker_config.watchdog_timeout`, sent in the launch descriptor), reports to the engine the lane (or the builder thread), the batch, its runner method, its calls and how long it has run (`WorkerResponse::Stalled`). The engine logs the report, fails the affected requests with an error naming the lane, and replaces the group. The engine's watchdog covers a worker that stops answering altogether.

A worker's orderly close ends with a reset of its primary contexts before the process exits. The reset releases the driver state the process created, including the shared-memory file (`/dev/shm/cuda.shm.*`) the CUDA driver makes for a process's interprocess events and removes only when the context is destroyed. A worker that loses its engine with nothing in flight takes the aborted close and then the reset; with work in flight it ends at once. A worker that ends without its orderly close first removes the driver file and the NCCL shared-memory names (`/dev/shm/nccl-*`) its mappings still link. The daemon that reaps a worker observes the death before reaping and removes that worker's driver files and recorded NCCL names while the zombie still holds its pid. A worker's startup failure, the interpreter's included, reaches the engine as the worker's own error.

