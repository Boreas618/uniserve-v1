# Architecture

UniServe is a Rust serving system with a Python numerical library. Rust owns the control and data planes: HTTP, scheduling, the worker processes and the channel to them, requests and their progress, storage and device storage, CUDA streams, transfers, host groups and observability. The Python package `uniserve` owns numerical computation: model definitions, layers, kernel bindings, samplers and solvers. A worker rank's numerical execution is Python's whole, behind one executor per rank (`uniserve.executor.Executor`): each batch's metadata, buckets and padding, CUDA graph capture and replay, sampling, slot state, expert steps, and media codecs and containers, for every model family. The two languages meet only in function calls through TVM-FFI.

This document describes how a deployment is organized, how a worker divides its work between Rust and Python, and how a request travels through it. A host is one machine; a worker is one process that executes batches, holding one device or none; a worker group is the workers launched, connected and replaced together; a rank is a worker's index within its group; a scheduler is the scheduling of one DP rank (data-parallel rank).

## Principles

1. **Rust owns the control and data planes.** Requests, admission, slots, every request's progress, batch order, storage and its lifetime, streams, transfers, host groups and failure handling are Rust's. Rust knows no model, component shape or CUDA graph.
2. **Python owns the numerics.** The executor makes every numerical decision of a batch: buckets and padding, graph capture and replay, attention planning, sampling and its random draws (keyed by the request's seed and token position), and the device state of each slot. It keeps each admitted request's numerical constants (sampling parameters, seeds) by slot from `start` until `release`, and reports everything a request's progress depends on back to Rust in each batch's results.
3. **The languages meet only in function calls.** A call passes tensors, scalars, flat lists, JSON strings and opaque handles, and returns the same. The few layouts both sides read, a token batch's columns and completion records, are defined once in Python (`uniserve/executor/text/protocol.py`) and mirrored by Rust (`crates/worker/src/executor/records.rs`), which checks the layout's version.
4. **Each behavior is implemented once.** A forward's computation is one method of a runner, used by serving, by graph capture and by Python callers alike. A rule both languages need is written in one of them and called from the other.
5. **Python never runs concurrently with itself.** In a worker at most one thread executes Python at any instant, so no thread waits for the GIL. An expert step with several microbatches is the one exception, and its threads take the host in turns.

## Processes

| Process | Language | Role |
| --- | --- | --- |
| `uniserve serve` (daemon) | Rust | One per node, for the deployment's lifetime. Every node's daemon starts, reaps and reports the processes of its node and holds the node's Storage Server claim. The leader's (node rank 0) also serves the HTTP API, processes every request's input (the model profile, chat templates, tokenization, multimodal inputs, request lowering) and output (detokenization, stop strings, reasoning and tool parsing, response assembly), and starts the engine process |
| `uniserve engine` (engine process) | Rust | One per deployment, on the leader's node, started by the leader's daemon. Runs one scheduler per DP rank (scheduling, the KV cache, the worker groups it drives), routes each request to a scheduler and serves the request interface to the leader's daemon |
| `uniserve worker` | Rust, hosting a Python interpreter | One per GPU worker and per CPU worker; executes the batches the engine sends |
| `uniserve storage serve` | Rust | One per host and serving user; keeps the storage that outlives the engine and the workers (see Storage and storage) |

A deployment of several nodes starts `uniserve serve` on each with `--nnodes`, its `--node-rank` and the leader's `--dist-init-addr HOST:PORT`; the leader binds that address and waits until the daemon of every node rank below `--nnodes` has joined it. The leader keeps the address bound while it serves, so a deployment that names it (of one node included) also takes a node whose daemon joins later with a node rank no node holds: the engines that connect from then on learn it, and the next world change may run ranks there. While nodes may join, every node's Storage Server also listens on TCP, so that the other nodes' Transfer Servers read its storage. Only the leader takes a model; another node's daemon serves the leader until the leader's connection closes, then ends its processes and exits.

Every process runs the one `uniserve` executable, installed into the Python environment's `bin/`, as one of its commands. The daemon and the engine process contain no Python. A worker starts as `uniserve worker`; the executable raises its descriptor limit, bounds the parallel jobs of its kernel compilations (`MAX_JOBS`, see [worker_config](configuration.md#worker_config)), finds the environment from its own path, asks the environment's interpreter where its shared `libpython`, `libtvm_ffi` and the worker library `uniserve/_worker` (a TVM-FFI library, not a Python extension module) are, loads the first two into the process's global scope and then the library, the very file Python resolves `uniserve._worker` to, and calls the library's `worker_main` on the process's main thread. `worker_main` spawns the worker's builder thread, which initializes CPython with the environment's interpreter as its executable and no signal handlers, calls `uniserve.worker.attach()` (logging, faulthandler dumps on SIGQUIT and SIGUSR1, and the TVM-FFI global function `uniserve.worker.import_path`, the one function through which Rust reaches the library), releases the GIL and serves Python calls; the main thread is the control thread. The process exits with the status `worker_main` returns, without Python finalization. Python processes still load the library, for tests, harnesses and the video rules it exports, and in a worker that load returns the instance the executable loaded.

### The request interface

The leader's daemon and the engine process exchange the request interface (`crates/proto/src/request.proto`), Protobuf that changes only by additions, so a daemon keeps serving engines of later builds.

- **Start.** The leader's daemon binds its request socket and asks the node named by `engine_host` to start `uniserve engine --requests ADDRESS --processes ADDRESS --engine N`, where `N` numbers the deployment's engine processes. Without `engine_host`, the engine runs on the leader. A local deployment uses Unix sockets in the user's runtime directory; a deployment with `dist_init_addr` uses TCP sockets on the leader's network interface, so engines can move between joined nodes. The engine connects and says hello with its protocol version, build and number; the daemon compares major versions and answers with the engine spec: the serving options that concern the engine and what the daemon resolved from the checkpoint (its generation limits, control tokens, context length, a block-diffusion model's canvas sampling). The engine reports `Starting`, starts its schedulers and workers, and reports `Ready` with its generation limits, video denoiser description and scheduler count, or `Failed` with the error. The daemon serves HTTP only once its engine is ready. Every request passes the leader's hold (`RequestHold`): while an engine is ready it goes straight to it, and while none is it waits; once the engine is lost and none takes its place, held and later requests fail with the reason and `/health` answers `503`.
- **Requests.** A submission carries tokenized requests under the daemon's identities. The engine routes each to its least loaded live scheduler and answers `Accepted`, naming the scheduler, or ends it at once with a `Rejected` event. Every event names its request. A request's events flow under a credit window: the engine sends at most 64 events (`EVENT_WINDOW`) beyond those the daemon reports consumed, so a slow client holds back its own request only.
- **Commands.** Per request: cancel (the client went away), stop (the daemon's decoder matched a stop string), acknowledge (this many public tokens complete no stop string), abort and consumed. For the engine: drain, after which it admits nothing more, reports `Draining` and ends every token request that generates text alone as migratable while the others finish; and shutdown, which ends every request as aborted, closes the workers and exits.
- **Migration.** A token request can move between engines; a readout cannot. Its engine ends it with a `Migratable` event, naming the cause (a drain or a loss of the workers that held it), after every token and image it generated there; the leader's `Migrator` submits it again through the hold, carrying them, to the engine that serves next. The tokens are every token the engine counted as generated, in order: the text it published and the control tokens it did not (`ControlToken`: a token that opens an image or closes a round, or a token of a request that publishes no text), carried as `generated_token_ids`. A request that generates text alone continues its prompt with them: the engine computes their cache as part of the prompt, reusing the pages of them its cache holds as for any prompt, and generates after the last of them at the position the request had reached. Every token counts as generated: against the token limit and `min_tokens`, in the penalties and bad words, and in the request's usage, which charges only its own prompt as prompt. The daemon keeps its own state (the detokenizer, the stop-string matcher, the response being assembled), so the client reads one uninterrupted stream. A request that names no seed takes one from the migrator when it is first submitted, so its draws, keyed by its seed and token positions, repeat on every engine. Migrations caused by a drain are not counted; a request survives `migration_config.max_migrations` migrations caused by losses. An image-generating request carries its images too (below), and a video request migrates at a denoising step boundary (below).
- **Recompute preemption.** When every running token request of a scheduler waits for KV cache units the others hold and no batch is in flight, none could end and let units go: the scheduler ends the one of the lowest priority admitted last as migratable (`Scheduler::recompute_starved`), as vLLM's recompute preemption does, and the `Migrator` submits it again with its tokens; its units go to the others. A request running alone is not recomputed.
- **Image preemption.** An engine preempts an image-generating token request at a completed call boundary: it offers no further call, waits for calls in flight, stores the unfinished image's committed latent trajectory in the host latent pools, and ends as migratable. Completed denoising steps remain visible to the client; an image decoding that completes during preemption publishes its image before the request leaves. The migrator carries a trajectory identity, stored step and layout record for the unfinished image. The successor rebuilds its conditioning context, pins the stored pages and continues at that step. A lost worker or missing optional pages causes recomputation from the request's image seed and image index; a numerics change follows the update's `keep` or `recompute` policy. Each completed image is a fact: `ImageDone` carries the decoded feedback input (`ImagePixels`, BF16 `[3, height, width]` values and their range), or the PNG when feedback reads the artifact. The migrator retains it with its token position (`GeneratedImage`) and clears the unfinished trajectory metadata. To rebuild context, `crates/engine/src/scheduler/generation/continuation.rs` follows the token and image decisions over the carried tokens, extends the prompt by decoded tokens, and writes each carried image through its cache close, feedback encodings and feature writes at their original logical positions. It samples nothing until the request reaches its continuation point. Feedback encoders reuse their host pools when available; otherwise they use the original posterior draw, determined by the request's input and generated image encoding order (`Call::latent_draw`). Image numbering, limits and usage include carried images. A rebuilt context with carried images shares no prefix-cache page, as for input images. The daemon preserves the response stream, suppresses repeated image starts and steps, and never exposes control tokens.
- **Video preemption.** An engine preempts a video request the same way whatever preempts it: a park for a world change, a sleep, an in-place weight update, or a loss of its workers. The request offers no further call, and its calls in flight complete, which ends it at a step boundary; a request whose denoising is scheduled whole finishes instead. A trajectory past its first step and short of its last is then written to the host latent pools of its denoising ranks (see Storage and storage), unless its workers were lost, and the request ends `Migratable`, naming the steps stored (`denoised_steps`, zero for none) and the engine's record of where their pages lie and how each denoising rank laid its part of the samples out (`stored_layout`). The migrator gives every video request the identity of its trajectory (`Trajectory::id`) when it first submits it, and submits it again naming the steps stored and the record, or what it named before when the engine stored none. The engine admits a request that resumes a stored trajectory before every request that starts one, and pins the pages the record names before its latent preparation, which prepares the request as for step zero (its prompt's and conditions' encoder outputs read from the host encoder pools where another admission stored them and encoded otherwise, its prompt refined and its noise drawn, which compute what they computed before) and then copies the stored values into the bank it initializes, laid out in its own rank's pages whatever parallel configuration stored them, and commits the trajectory at the stored step, from which it denoises the steps left; when a page is missing, it starts from noise. A trajectory's state at a step follows from the request alone (its noise from its seed, and an Euler step from the samples and the step), so both continue the trajectory the uninterrupted request takes, and a resumed request's video is that request's.
- **Artifacts.** A generated image or video reaches the daemon as an artifact event whose shared memory travels as a file descriptor beside its frame (`SCM_RIGHTS`); the daemon maps it read-only and serves its bytes.
- **Statistics.** Each scheduler's statistics travel once a second as a snapshot the daemon exports as metrics.

### Worlds

A world is an engine and its workers, their communicators, CUDA graphs and the storage they created. The leader's daemon moves the deployment to a configuration another world executes without failing a request (`PUT /admin/config`, `Leader::apply`, `crates/daemon/src/worlds.rs`; `docs/admin.md`). The engine's world identity is the engine number of the world's first engine (`EngineSpec::world`), which keys its workers' storage at the Storage Server.

1. **Preparation.** The leader plans the change on every GPU's storage ledger (`ResizeCache`, `Plan`, `crates/engine/src/scheduler/ledger.rs`) and refuses a successor that does not fit; the serving engine then withdraws the tail of its KV cache past the limit each ledger leaves it beside the successor (`Shrink`) and describes its cache segments (`DescribeCache`). The leader starts the successor with a spec naming its predecessor and those segments (`EngineSpec::predecessor`). The successor's workers start beside the serving ones under the same claim of the deployment, extended by the successor's world: they map the retained weights of the same keys and the predecessor's held cache segments read-only, under hardware protection, lay out their planes as a head segment of their own, then the predecessor's segments, then tail segments of their own created as storage frees, warm up and capture their graphs on their own head, and the engine reports `Standby`.
2. **Promotion.** The leader holds new requests and parks the serving engine (`Park`): at a step boundary each scheduler ends its token requests as migratable, image-generating ones included, whose migrations wait in the hold, preempts its video requests at their next denoising step boundary with their trajectories stored, lets its readouts finish, offloads its reserved pages to the host KV cache and answers with its prefix cache index, keeping its storage; the engine reports `Parked`. A park for a successor that maps its cache (`Park::lend`) also lends the successor every segment past the first that holds no page a request in flight continues from (no page under a private continuation alias): the scheduler forgets the pages there and allocates none of their units until a `Resume` retires the successor (`GroupIndex::lent`, `crates/engine/src/scheduler/world.rs`). The leader promotes the successor with that index (`Promote`): each worker copies the predecessor's cache flags and scales of the units it maps and maps the lent segments writable (`uniserve.adopt_cache`), each scheduler's pool imports the pages into those units and allocates the lent units as its own after its free ones, and the engine reports `Ready`. Hardware protection keeps the successor from writing every other segment of the predecessor until the commit; a VMM mapping changes its access only whole, so a segment is lent whole or not at all. The hold serves the successor, which takes every held and migrated request; a migrated request shares complete pages of its prompt and generated tokens, copies its stored partial tail into writable units, and computes only tokens after the stored extent, and a migrated video request continues the trajectory the parked engine stored. A successor whose numerics differ from the serving engine's (another prefix seed, or another latent seed of what its denoising computes, `EngineInfo::latent_seed`) finds none of its pages or trajectories: with `in_flight = keep` the requests in flight continue with the state they reached (a video request reads the trajectory under the parked engine's latent seed, `Trajectory::state_seed`, which the successor continues with its own numerics), and with `recompute` they compute it again (a video request from noise).
3. **Trial.** A parked previous world whose cache the successor maps none of evicts every segment past its first (`ResizeCache`'s `Evict`): its scheduler holds the idle cached pages there and has its host KV cache verify, or make again, each one's copy under the key it was offloaded with, with batches of page offloads alone while nothing runs, before its workers give the segments back; a resume at a rollback creates them again. The serving world's preparation evicts the idle cached pages of the tail it gives back the same way. A page a pool has no slot for (every slot reserved, pinned or uploading, as when the host's storage held a pool smaller than the pages evicted) is evicted uncopied, unless Mooncake keeps what the pools commit (`kv_cache_config.mooncake`): the page then waits for a slot, which the pool frees once the connector has uploaded its page, so every evicted page passes through the pool into Mooncake (`crates/engine/src/kv_cache/offload.rs`, Evictions). A host whose storage holds no pool of a world's still gives a server with Mooncake staging pools of at most 256 MiB on each rank (`STAGING_POOL_BYTES`), admitted from its reserve but never past its available storage, through which the pages pass the same way. A previous world kept as its weights exits, and its successor has every node's Storage Server keep its weights alone (`KeepWeights`) before it grows its cache (`ResizeCache`'s `keep_weights`): the GPUs' ledgers leave it what the previous world released. Kept in host storage (`keep_in_host_storage`), the weights the successor does not map then move there through each node's Transfer Server (the server's `Offload`), and the answer carries each node's report, with the reason a node kept them on its GPUs; a claim of the previous world started again at a rollback returns them first (`Restore`). Until its commit the successor's worker groups are not repaired: a worker fault closes the group, its scheduler stops and hands every request that resumes from its tokens back as migratable, and the engine reports `Failed` with the first error once any scheduler stopped; a scheduler whose batch computed non-finite logits (the completion's `finite` word) does the same. The leader rolls such a trial back, as it does on the engine process's exit, a stalled job and a threshold of `update_config.rollback` (`Observer`, from the schedulers' statistics). A rollback parks and closes the successor, resumes the previous engine (`Resume`, which retires the successor's storage first, and once the successor's processes are gone returns the lent units to allocation) or starts it again on its kept weights, and marks the configuration unavailable.
4. **Commit.** The previous engine exits; the pages its world committed stay in the host KV cache for any world whose keys reach them, a successor keyed otherwise included, until ordinary eviction; the successor retires the previous world's storage at the Storage Server, its workers take the segments they mapped read-only (`Commit`, `uniserve.take_cache`), its pools allocate their units, and its cache grows into the storage freed (`Grow`). The served spec records the committed layout (`EngineSpec::segments`), so a relaunch lays its planes out as they are.

The successor's writable head holds its warmup scratch, one page of each K/V group, and two checkpoints of each recurrent state group: a call keeps its input checkpoint until it finishes writing the next one. Preparation reserves these same pages before starting the successor, including when a configured token capacity limits the inherited and writable segments together.

When a successor uses another cache layout, the daemon warms complete pages through the shared copy manifest while each predecessor serves (`crates/daemon/src/worlds/warming.rs`). The scheduler pins the source pages, reserves destination units, and asks its workers to describe the borrowed regions of their retained cache planes. Dense attention pages declare token and global head regions; recurrent checkpoints declare the packed convolution and value-head fields of the numerical state. Each destination host submits the manifest's physical spans to its Transfer Server. The worker retains the transfer task until completion or cancellation, and only a completed copy permits publication and release of the source pins. Later rounds describe only pages beyond the successor's covered prefix. After the first round the source temporarily bounds its prefill token budget; promotion waits until every accepted request's uncovered extent is within `update_config.cache_tail_tokens`.

Transferred pages are private to the continuation's origin world and request handle (`CacheResume`), including requests that disable shared cache reads or carry images. That origin survives successive world changes, while each copy manifest identifies the current physical source. Planning and reservation assign the origin to the same target scheduler, so each rank admits only its assigned continuations. The successor acquires the reserved pages into ordinary block tables and releases the warming pins. A numeric change with `in_flight = keep` continues under the source's numerical seed and publishes subsequent mixed-state pages only in the private continuation index. An encoding without an exact conversion is reported as recomputation; a missing dense numerical region fails preparation. Standby engines use the ordinary control channel for these operations and accept requests only after promotion.

When the predecessor's reclaimable cache tail cannot admit a device-resident successor, preparation stages complete pages in Host allocations retained by the Storage Server. The worker allocates compact backing for the actual numerical views; the shared manifest binds each chunk to Host storage and retains its physical byte offset. Preparation retains both the predecessor layout for rollback and the successor layout for promotion. The successor maps only its writable head, sized from the executor's actual warmup layouts, while reserving virtual addresses for its full cache. Admission distinguishes copied value bytes from the GPU segments needed to materialize those values. If Host staging still cannot admit preparation, the predecessor releases its graph pool and serves eagerly; the selected policy and measured Host-link pause estimate appear in the storage report.

After the predecessor parks, its completed Host copies permit eviction of its device tail. The successor maps the admitted segments, copies its staged views into their fixed addresses, publishes the private pages, and releases its Host staging. Rollback restores the predecessor's retained layout before routing requests back to it. When the predecessor's processes exit during trial, their weights and the exact Host cache keys remain retained across restart; restoration releases those cache keys after physical copies finish. Without Host backups, a parked predecessor retains its device pages for rollback. Transfer sessions keep their contexts across preparation rounds, and cancellation waits for physical completion before releasing either source leases or destination backing.

The pause, from holding requests to the successor serving them, covers the serving engine's last step, its park and the promotion; the change reports it with the preparation's and the park's durations, and the leader logs how long each migrated request waited, from its migration to its first token on the successor. A successor that does not start leaves the serving engine serving, which creates its tail again; a park or promotion that fails resumes it.

### The channel

The engine and each worker exchange the messages of `ipc` (`NewRequest`, `Batch`, `BatchOutput`, `WorkerInfo`) over one stream connection per worker.

- **Connection.** The engine process listens on one Unix socket path and one TCP port. A worker connects to the engine when it starts: through the Unix socket on the engine's node, through TCP from any other node. Workers and daemons accept no channel connection; the connections workers accept are their group's peer mesh and its collective store.
- **Registration.** A worker's first frame registers it: worker group, rank, launch generation and build. The engine numbers each launch of a worker group, and a relaunch takes the next number; the build is the package version plus a digest of the sources every artifact is compiled from, so the engine and workers of one build carry the same value. The engine refuses a registration of another build or of a launch that is not the group's current one, and otherwise answers with the worker's launch descriptor, which carries every other launch value, among them the deployment's name of the worker's host, its identity in transfers.
- **Lifetime.** The same connection then carries requests and responses, and its close is the only death signal of a registered worker: the engine treats the worker as dead and the worker exits. Before a worker registers, the engine learns of its exit from the daemon that started it.
- **Frames.** A frame is a length followed by one message in a serde binary encoding (MessagePack). The engine and its workers are built from one workspace and replaced together, so the message types are the protocol's only definition. A frame carries a message of any size its `u32` length states; no launch setting bounds it further.
- **Waiting.** Each side blocks on its socket together with one local wake descriptor, which its own threads fire for work that did not arrive on the socket.
- **Processes.** The engine starts no process itself. It asks the leader's daemon, over the daemon's Unix socket, to start each worker on the node its parallel configuration names, to reserve the socket a group's first rank serves the group's collective store on, to stop a group ahead of its relaunch, and to claim the deployment at a node's Storage Server (an engine claims it at every node's, those that run none of its workers included, so that it retires another world's storage and keeps a world's weights wherever they lie, and each worker's launch names the other nodes' servers, whose worlds' weights it may receive); the leader serves its own node and forwards the rest to the node's daemon over that daemon's join connection, and every exit comes back the same way, naming the node, group, rank and launch generation. These messages are the process interface (`crates/proto/process.proto`), Protobuf that changes only by additions: a daemon keeps running while engines of later builds connect to it, and the two compare major versions when they connect. A worker is its daemon's child, leads a process group of its own and dies with the daemon; an engine whose connection closes takes its remaining workers on every node with it.
- **Data.** Tensors, prefix cache pages, latents and products move through the transfer mechanisms. Only a host product routed between hosts travels on the channel.

## The threads of a worker

A worker's threads are named by their role: the control thread and the builder thread.

| Thread | Name | Owner | Blocks only on | Does |
| --- | --- | --- | --- | --- |
| Control thread | the main thread | `Service`, `Computations`, `JobQueue`, the storage owners | Its socket and wake descriptor | Serves the channel, holds request state, admits batches, reserves their storage, builds their jobs, applies completions, retires storage |
| Builder thread | `builder` | `Interpreter`, the executor | The interpreter and the work of the job it performs | Executes every Python call, one at a time, and performs every job in submission order: it builds the worker (loading the model, binding its weights, constructing the executor, capturing its graphs, at startup and when a promotion captures again), issues each job's stream work (storage writes, event records and waits, output reads), runs every executor call of a batch (`start`, `prepare`, `execute`, `commit`) and releases |

Threads exchange messages only. The control thread submits jobs and receives completions; it calls neither the driver nor Python while it serves, so a slow launch, a driver call that waits on the device, or a job that does not end does not keep it from serving the channel, handling cancellation or reporting status. The builder thread is the only issuer of work on the rank's streams, so each stream's order is the order the jobs were submitted in. It posts a job's completion once it has issued the job's work, not once the device has finished it: storage a job used is read, rewritten or freed afterwards only behind something that waited for the device (a read in the job, a stream wait the job recorded, events the job completes after, or the fences that retire storage). Every Python call runs on the builder thread, in arrival order: a job makes its executor calls there itself; another thread hands it a call and waits for the result; the control thread submits work that owns what it uses and never waits for it; a released Python object is dropped there in queue order, and nobody waits for the drop.

An expert step with several microbatches is the one exception to the builder thread's single caller: the executor runs each microbatch's forward on a Python thread of its own, which passes the host turn to the next at its expert dispatch points and releases the GIL while it waits, so exactly one of them runs Python at a time.

Blocking host work runs on host pools, bounded pools of threads (`<pool>-<index>`) that each serve one kind of work and hand any Python call to the builder thread like every other thread: image preparation (`uniserve-image`), prefix cache imports (`worker-cache-import`), transfer reads (`uniserve-<kind>-read`) and shared-memory retirement (`uniserve-posix-shm-retire`). Signals (`worker-signals`), VMM descriptor grants (`worker-descriptor-grants`), a video executor's host reports (`uniserve-host-reports`) and, during startup, the engine watch (`uniserve-engine-watch`) are dedicated threads. The builder thread is created by Rust and is Python's main thread; Python installs no signal handlers in a worker. The builder thread releases the GIL while it waits for work, so the Python threads a video executor starts run beside it: its media thread (`uniserve-media`), which reads condition media and encodes and muxes video, and the thread it starts for each reference video's FFmpeg decode.

## How Rust calls Python

Rust reaches the library by import path, for example `uniserve.executor.Executor.execute`; there is no table of entry points and no map of named buffers.

- Arguments and results are tensors, scalars, flat lists, JSON strings and opaque handles. A call names every tensor it reads or writes as a parameter.
- Each view of Rust storage is wrapped once with `torch.from_dlpack`; the torch tensor crosses as an opaque Python object, so every call that takes the view receives that same tensor with no per-call conversion. The tensor retains the Rust allocation, and its handle is released on the builder thread with the view's last clone.
- Storage that lives as long as the executor (prefix cache tables, latent banks, relay staging, graph pools, scratch) is passed once, to `bind`; what changes per batch (host columns, leased products, output words) is passed to the batch's calls.
- A Python object that outlives a call is held by Rust as a handle: the loaded model, the executor, a process group.
- Within a call the executor calls back into Rust only through functions Rust gave it: the host group's collectives an expert step's agreement uses, and the copies of a layer's weights from peer or host storage.
- A Python exception crosses with its kind, message and traceback (`uniserve.errors`).

### The executor

A rank is served by one Python object, `uniserve.executor.Executor`, which Rust constructs once the model is loaded, with the rank's settings (`crates/worker/src/worker/computations.rs`), and calls through `PythonExecutor` (`crates/worker/src/executor/python.rs`). Rust holds no knowledge of the model's components, shapes or graphs: it reads what it plans from the executor's manifest and what each batch reads and writes from the executor's columns, preparations and records.

| Call | When | Does |
| --- | --- | --- |
| `manifest()` | after loading | the executor's computations and what capacity planning reads: the bytes a computation over the prefix cache allocates beside the cache pool, fixed and per request slot; for a video model the products every component publishes, the denoiser's description and each slot's latent pages |
| `expert_storage_bytes(host...)`, `connect_experts(storage, storages...)` | after loading, before planning, on a member of an expert union | configures the union's agreement over the host group Rust gives it and creates its exchanges over the peer storage Rust mapped |
| `bind(storage, values...)` | after capacity planning | constructs the runners and their columns on what Rust allocated: each computation's streams, the scratch and graph pool of each stream, the prefix cache's unit pool and block tables, each computation's relay staging, the latent banks, the report pipe, the stream groups' process groups and the distributed expert weights' prefetch schedule; returns the rows of one diffusion LM sampler chunk |
| `warmup_phases()`, `warmup_phase(index, pages...)`, `warmup_finish()` | startup | every computation's shapes warmed and captured, in phases every rank runs in the same order |
| `seal()` | after warmup's graph residency check | captures are refused from then on |
| `start(requests)` | a job before the batch that starts requests opens | admits them, keeping their numerical constants by slot, and returns those it refuses with the reason |
| `prepare(computation, step)` | a preparing computation's batch once its calls are bound | what each call reads and writes |
| `execute(computation, step, tensors...)` | the job that carries a batch's device work | computes the batch; returns a token computation's record words, or how each prepared call's forward ran |
| `commit(computation)` | that job, past the batch's commit point | advances a committing computation's slot state past the batch |
| `join_expert_step(leaving)` | a union member with no step of its own | joins the union's next step |
| `park_experts()`, `promote_experts()`, `rebuild_experts()` | a standby parks, is promoted | releases and restores the union's workspaces; a rebuild has the computations capture what uses them anew |
| `release(slots)` | when request slots retire | drops the slots' request state; Rust hands the call to the builder thread and does not wait |
| `kernels()`, `close(aborted)` | the kernel report, shutdown | |

### Computations and their batches

An executor computation is one kind of work the executor serves under its index: a component's call kinds on one of the rank's streams, or on the host. The manifest declares each computation: whether its batches are prepared (the executor first states what each call reads and writes), whether they commit (the executor advances its slot state past a batch's commit point), and the resources Rust keeps for it: the prefix cache's `pages`, a `latents` ledger of denoising trajectories, the `reports` pipe host tasks report through, and the `images` host pool that prepares inline input images and encodes decoded ones (`crates/worker/src/executor/image_inputs.rs`).

| Executor | Model family | Computations |
| --- | --- | --- |
| `uniserve/executor/text` | causal LMs, including vision blocks and latent conditioning | one per component, over `pages`; commits |
| `uniserve/executor/diffusion_lm` | block diffusion LMs | one per component, over `pages` |
| `uniserve/executor/video` | video models | one per component, prepared; the denoiser's over `latents`, host components' over `reports` |
| `uniserve/executor/image` | image generation models (BAGEL, SenseNova) | one per kind of work a component holds, prepared: a vision computation and a latent computation over `images`; the denoiser's over `pages` and `latents`, and `images` when it also decodes; a decoder's over `latents` and `images` |

Every computation's batch goes through one sequence of jobs (`crates/worker/src/executor/computations.rs`):

1. **Opening.** Bind the calls to their requests. A computation over the prefix cache orders first after the batches whose writes it reads on another stream and after the host KV cache reads issued for the batch on the copy stream.
2. **Preparation**, for a computation that prepares: a job asks the executor what each call reads and writes (`prepare`).
3. **Reservation.** Lease the output storage and each call's `uint8` predicate on the device, and reserve what the batch uses: the prefix cache's tables, units, extents and attention pages and the relays, or the products the preparation named and the trajectories' banks.
4. **Execution.** `execute` computes the batch on what was reserved.
5. **Seal.** End the read leases, publish the completion flags the host sets, validate every owner's update and seal the lease: the commit point. Past it, the executor advances a committing computation's slot state (`commit`).
6. **Completion.** The job's results become the calls' pending outputs, and the batch materializes once its fences completed and, for a computation whose calls run host tasks, every task reported.

A failure before the commit point retires everything the batch reserved and fails its calls; a failure at or past it is fatal to the worker.

**Predicates.** A call the engine queues behind an unresolved call carries a predicate: the predecessor's relayed token for a decode, otherwise its `uint8` completion flag. No host reads a predicate. The batch leases a call's `uint8` predicate on the device and copies it into the call's completion flag and into an output word of its own; the executor leaves every state the call would change as it was when the predicate is false: image and video denoising write the latent they read (the ledger flips the banks at the commit either way), latent preparation keeps its bank and its slot's tables and conditioning (a video request's refined prompt and encoded conditions), and a text prefill copies the predicate into its slot's continuation predicate and runs as a gated row, as a relayed decode does (`uniserve/executor/predicates.py`). Once the batch's fences completed, the host reads the word: a false one reports the call `Predicated`, without products.

**Token batches.** A computation over the prefix cache reads host columns: the call columns (`int64 [22, C]`: slot, kind, progress, the call's rows and tokens, flags, request identity, the drafts it asks the drafter for and the token after its tokens), the forward columns (`int64 [5 + 2G, R]`: each row's call, slot, sequence and query length and cache write, and per cache group its first selected page and page count), the flat tokens, the JSON of the rare per-call fields (a sampling state, vision blocks, latent conditions, a readout's slots) and the feature tensors that JSON names. It writes its results into page-locked output words the batch lent and into a record column: a header, one record per call (its progress, the extent of its selection and logprob words, its candidate range, the offset of its tail) and the segments and tails those name (`uniserve/executor/text/protocol.py`). The builder thread checks the records before the commit point; Rust decodes them into each call's pending output (`crates/worker/src/executor/records.rs`). Values the next batch reads, a decode's selected token or a denoising step's continuation, go to the computation's relay staging, which Rust copies into the products that carry them.

**Prepared batches.** A video batch's step names every call with its request, slot, inputs and outputs. The executor's preparation states what each call reads and writes: input indices, each output's shape, region and storage, whether a host task fills it, and its publication. Rust then leases every read, binds every write and takes each denoising trajectory's banks from its ledger (`LatentLedger`: which of a slot's two latent banks holds its committed sample and how many steps it took); `execute` runs the calls on those tensors, followed by the producer fences and exports of what they wrote, and the ledger applies the steps once the job completed. A write a host task fills (condition media, an encoded unit, the muxed MP4) is deferred: the executor's media thread fills it and sends one report per finished task through a pipe (batch, call, row, status, a value and a payload such as the MP4's bytes); the `uniserve-host-reports` thread reads them into a mailbox and wakes the control thread, which completes each deferred call once its reports arrived.

An image batch is prepared the same way. Its calls name their input images, features, decoded images and latents in fields of their own, which the worker's image hooks reserve beside the generic products (`crates/worker/src/executor/image.rs`): an input image's pixels prepared on the image host pool or a resident image product, the feature and image products at their prepared shapes, the decoded bytes lent from the batch's output words, and the trajectory's banks from the latent ledger. A denoising batch over the prefix cache also reserves the slots of its guidance prefixes and passes their attention rows; the executor's denoiser prefills a prefix through its component's text computation (`TextComputation.prefill_cache`) and writes the latent conditioning the text computations' prompts read.

### Runners

The executors compute through the Python runners of `uniserve/runner`, which a Python caller uses directly as well. A runner binds one component's model to an execution context and exposes its forwards as methods whose shapes are fixed by their scalar arguments, so the executor can capture them:

| Executor | Runners | Methods |
| --- | --- | --- |
| text | `CausalLMRunner` | `prefill`, `decode`, `select`, `score`, `score_prompt`, `verify`, `commit`; `plan_prefill` and `plan_decode` for a host-planned attention reader |
| diffusion LM | `DiffusionLMRunner` | `attend`, `finish`, `readout`, `denoise`; `plan_attention` for a host-planned reader |
| video | `EncoderRunner`, `DenoiserRunner`, `DecoderRunner` | `encode`, `prepare_layout`, `draw_noise`, `prepare_latents`, `encode_conditions`, `denoise`, `decode` |
| image | the components' modules in execution contexts of their own (`uniserve/executor/image/{vision,codec,denoiser}.py`) | the vision encoder's patch rows, the latent encoder and pixel decoder per image size, the denoiser's packed rows |

The denoising rank's ledger (`crates/worker/src/executor/latents.rs`) offloads committed image and video trajectories to its host latent pool. A resumed request's latent preparation receives the stored pages and the copies that lay them out in its own pages. The executor copies those bytes into the bank it initializes before the ledger commits the stored step. Image trajectories use scheduler-assigned pages and hold the whole latent on each denoising rank; video trajectories use fixed request slots with the rank's declared numerical layout.

Video request rules (canvases, frame counts, how each condition is prepared and the conditioner's presentation) are implemented in the `models` crate: the leader's daemon plans and presents every request with them before submission. The video executor reaches the canvas rule, the training buckets, the canvas a target names, the frame count of a duration and a condition image's vision grid through functions the worker library exports (`rules.rs`); it does not plan or present requests.

A method that can be captured meets four conditions: its shapes are fixed by its scalar arguments; every value that changes between forwards enters as tensor contents; it performs no host planning or synchronization; it draws no random numbers except from generators the capture registers, or from draws the executor computes from the request's seed.

### Library functions and functions Rust gives Python

Besides the executor, Rust calls:

- `uniserve.loading.rank`: read a checkpoint's configuration and the model's description, load this worker's modules;
- `uniserve.loading.host_weights`: the layer stack of a component that keeps its weights in host storage, its layout in a layer slot, the number of slots it streams through, and the rebinding of its projections to the host region and slots Rust allocates, which returns the stack's copy schedule (`HostStack`); Rust closes the schedule before it releases that storage;
- `uniserve.distributed`: process groups, created in the order Rust fixes, among them one process group per stream group that the forward's collectives run on (`collectives.group_collectives`); `experts`, with `uniserve.backends.experts.HostBootstrap`, for expert unions;
- `uniserve.bindings.context.Scratch`: the transient work area that the execution contexts serialized on one stream share;
- `uniserve.cuda_graph`: graph pools on the storage Rust reserves;
- `uniserve.prefix_cache`: the cache's page plan, unit resets, imported-page conversion;
- `uniserve.backends.kernel_choices`, `uniserve.profiling` and `uniserve.media`;
- `torch` and `gc` functions as they are.

In the other direction, Rust passes Python the host group's `all_gather`, `all_gather_fixed`, `broadcast`, `barrier` and `split`, the peer-mapped storage Rust allocates for split expert weights (a storage tensor and every member's address), and the views of distributed expert weights with the function that submits one expert layer's peer reads into its slots on a stream Python names. Python's schedules (`uniserve.weight_prefetch`) own the copy streams, the events that order each copy against the layers reading its slot, and, under graph capture, each distributed expert copy as the graph's break work.

### Attention providers

The library's provider registry (`uniserve.backends.attention.PROVIDERS`, with `resolve`) is the one list of attention providers: `auto` (a native kernel per call, chosen from the device and the installed kernel libraries), `flashinfer`, `trtllm`, `flash_attn_4`, `torch`, `prefix_block`, `flash_attn` and `sgl_kernel`. `attention_backend` passes its value to the workers unchanged, and a worker refuses a name the registry does not provide when it loads its model; the engine reports that startup error. A provider declares whether serving captures its calls (`Backend.captures`); the portable `torch` provider does not. A host-planned provider's plan is shared by every layer of one execution context that has the same layer shape and batch signature, so a forward plans once, before the replay of its graph.

## CUDA graphs

The executor captures and replays every graph it serves (`uniserve.cuda_graph`). A captured forward is a breakable CUDA graph: one or more torch CUDA graphs, its segments, and between two segments a graph break whose work the replay performs on the host after enqueuing the segment before it, such as the copy of a distributed expert layer's weight shards from its peers. Torch holds the graphs; their storage is Rust's.

- **Capture.** Each forward is run eagerly once at its shape, so kernels compile outside capture, then captured (`uniserve.cuda_graph.capture`) into the graph pool Rust reserved for its stream: a pool allocates from device storage Rust maps as torch's pluggable allocator asks for segments, at addresses that stay fixed while any graph addresses them (`crates/worker/src/cuda_graph`). Each executor captures its shapes largest first, so smaller captures reuse the pool blocks of larger ones. Warmup runs in phases the executor states and every rank of a group runs in the same order, because capture includes collectives: each phase names its computation, the scratch table lengths of slots `1..` and each step's attention rows, and Rust installs those tables on the scratch units the engine never allocates and selects each step's pages before the executor runs the phase.
- **Replay.** A forward with a graph writes its inputs into the executor's columns on the computation's stream, plans a host-planned provider's attention, and replays the graph; its outputs are read from the graph's output buffers into the batch's output words.
- **Keys and buckets.** Each executor keys its graphs by what fixes their shapes: the text executor by decode row bucket and sampler, by prefill row and token bucket, output selection and media variant, and its selections by task bucket, samplers and top width (`uniserve/executor/text/graphs.py`); the diffusion LM executor by `attend` row and token bucket, `finish` slot bucket and `denoise` row bucket; the video executor by layout, prompt capacity and unit shape; the image executor by the denoiser's row bucket (padded rows and tokens of the packed image rows), the vision encoder's patch-row bucket, and the latent encoder's and pixel decoder's image size, whose captured sizes the worker reports so the engine refuses an input image of another size. An expert step's graph is keyed besides by the capacity its union agreed: a computation captures each forward at every capacity an agreement can select for it, and a member without tokens replays the join graph of the agreed capacity.
- **Policy.** The graph policy is resolved after loading: with an attention provider whose calls are not captured (`Backend.captures`), `auto` serves every call eagerly and `full` is refused; `off` serves eagerly. A module declaring `captures_prompts = False` serves prompt forwards eagerly under `auto`, with captured decode and verification forwards; `full` requires prompt capture too. Qwen3.5's gated delta layers use this prompt restriction. A verification graph accepts different draft lengths per row and advances recurrent state over exactly the accepted tokens. Its drafter pass and reported log probabilities use separate graphs on the same computation stream. Startup captures every verification row bucket and both general sampling paths. Once startup seals the graph tables, a configured shape without a resident graph is an error. The workers of a group capture the same shapes in the same order. No host callback that enters Python is ever placed on a stream or inside a graph.
- **Residency.** Warmup grants each device's graph pools what they hold when capture begins plus the grant left after product storage not yet resident, and checks the pools against it before the executor seals.

## Storage and storage

| Owner | Allocated by | Contents |
| --- | --- | --- |
| Rust | the CUDA driver | everything that holds request state, is read or written natively, or crosses a process: the prefix cache unit pool, slot tables, the latent pool, product arenas, forward inputs and outputs, pinned staging, export ranges |
| Rust | the CUDA driver, through torch's caching allocator | graph pools and operator scratch: each a reserved address range whose physical storage Rust maps as torch's pluggable allocator asks for segments (`cuda::VirtualPool`, `crates/worker/src/cuda_graph/storage.rs`), at addresses that stay fixed while any graph addresses them; scratch has pools of its own, so no graph's activations share its blocks |
| PyTorch | its caching allocator | weights, activations of eager forwards |

Capacity planning measures device storage after loading and assigns the rest of the device's quota to the prefix cache and media storage (`crates/worker/src/capacity/device.rs`). The quota is `⌊total × mem_fraction_static⌋` of the whole GPU, which every world of the deployment and the host's Transfer Server share, and the host's Storage Server keeps the GPU's storage ledger of it (below): a rank's grant is the quota less everything the ledger books beside its own process (the storages the server retains, another world's items, the Transfer Server's) and less what its process holds as NVML reports it, never more than the device has free. Exclusive storages a predecessor of the rank's scope and world left that no owner has taken yet count as free, and an owner that allocates new storage first releases them. Once warm, the rank books its graph pools and its process storage in the ledger, which refuses them past the quota. Storage is organized by owner in `crates/worker/src/storage`:

- **Prefix cache** (`prefix_cache/`): the unit pool, block tables, unit accesses, transfer bases and pending imports of attention state, and the request slots' banks of the cache layers a model keeps per request (a recurrent state). Such layers' checkpoints fill the pool's state group: its page `k` holds every such layer's state after token `(k + 1) * block_size - 1`, and a table names units only for the pages that hold one: a prompt call keeps the state at the last page boundary it reaches, a decode call at the boundaries that are multiples of `kv_cache_config.state_interval`. A request whose reused prefix ends at a boundary resumes from its checkpoint there; reuse ends only at a boundary whose checkpoint the device, host or storage tier holds, and checkpoint pages publish, offload and import as K/V pages do (`uniserve/prefix_cache/checkpoints.py`, `crates/engine/src/kv_cache/mod.rs`). A deployment that speculates (`speculative_config.num_draft_tokens`) keeps its drafter's K/V, the draft cache, in the pool's draft group: optional derived state, whose entry at position `i` is the drafter's evaluation of the target's hidden state at `i` and the token at `i + 1`, so a draft page's prefix hash covers the token after the page. The group keeps the pool's columns and plane size (each of `L` drafter layers spans `columns / L` columns of a unit, `uniserve/prefix_cache/units.py`), so a world that adds it maps its predecessor's segments. Reuse boundaries and admission count the required groups alone; a request's draft pages are allocated as far as free units allow, released from running requests before another request's required pages would fail, and published, offloaded to the host KV cache and loaded back as the other groups' pages are.
- **Latent cache** (`latent/`): denoising trajectories in two banks of pages per slot, with versions exported to other workers, and a video denoising rank's host latent pool (`latent/host.rs`).
- **Product store** (`products/`): tensors one call produces and another consumes, with their reads, writes, exports and imports.
- **Request slots** (`request_slots.rs`): the per-slot state banks of the requests a runner holds.
- **Buffers** (`buffer.rs`): the `BufferPool` of cross-call buffers, bound at the offsets the scheduler placed them. Each worker backs its own pool, sized to the products of the components it executes and of the components that read them (`MediaCall::readers`), and reports its bytes; the engine places each media request's products in the pool of every worker that backs them, and a token computation's products at one offset on every worker.
- **Outputs and host buffers**: page-locked output words (one pool per executor computation, of one block per batch the computation may hold in flight, each the size of the computation's largest batch; a batch leases exactly its words, and a larger readout leases storage of its own), each computation's relay staging, and the `PinnedPool` of page-locked blocks that host-prepared inputs (decoded images) are written into.

### The Storage Server

Each host runs one Storage Server (`uniserve storage serve`) per serving user, which the host's daemon starts when the host has none, in a session of its own, so restarting the daemon never ends it. Clients connect through a Unix socket owned by the user (`$XDG_RUNTIME_DIR/uniserve/storage.sock`, else `/tmp/uniserve-<uid>/storage.sock`) and pass file descriptors with `SCM_RIGHTS`. The server holds storage and never interprets it: it keeps the descriptors of CUDA VMM allocations (POSIX file descriptor handles) and host memfds, never creates a CUDA context, and moves no bytes itself; clients compute every key and copy on their own streams, or have its Transfer Server copy for them.

- **Claims.** The engine has each host's daemon claim the deployment (its served model name) at that host's server and hands each worker the claim's token in its launch descriptor. The daemon holds the claim for as long as it runs. A claim releases the scopes the engine no longer places; `uniserve storage retire --deployment NAME` releases a deployment that is no longer served, and `list` prints what the server holds.
- **Committed worlds.** Each claimed world keeps its immutable outputs private until the daemon publishes it with `PublishWorlds`. Initial engines publish after warmup; a successor remains private throughout preparation and trial. Publication makes its immutable outputs readable by other worlds and uploads its completed host pages to the KV storage. Independent committed replicas share those outputs under the same deployment. A group commit publishes every successor together at each node before retiring any predecessor; world identifiers imply no ordering of visibility. Retiring a candidate discards its private pages, while a committed world's pages remain reusable after retirement. Storage Server hot restart preserves the committed set.
- **Weights.** A GPU worker keeps its loaded parameters and buffers in read-only retained storages (`crates/worker/src/storage/weights.rs`, `uniserve/loading/retained.py`): one per torch storage loading made, the smaller ones of a device packed into one. Every parameter is a part of a logical tensor, the whole matrix the checkpoint names: the module that partitions it declares the logical tensor's shape, the partition unit of each dimension (a head's channels, one expert) and the indices the rank holds (`logical_tensors()`, `uniserve/distributed/logical.py`, from the layer's `Distribution`, which besides PyTorch's `Shard` and `Replicate` divides position-mod-N, in named sub-blocks each split on its own, and strided compressed indices). A storage's storage is allocated in chunks, each a CUDA VMM allocation of its own mapped back to back with the next, cut where a configuration of the parallel degrees in use (`load_config.parallel_degrees`) cuts a logical tensor along a field's outermost dimension: stacked experts at expert blocks, attention projections at head groups, vocabulary rows at their shares, each cut rounded down and up to the allocation granularity (`crates/storage/src/manifest/layout.rs`). A chunk is retained under the key of what its bytes are: the regions of the logical tensors it holds, where in it they lie, and each tensor's loading fingerprint (the identities of the files supplying its inputs, assignment rectangles, dtype, encoding and declared derivations). A derivation names its output tensors, checkpoint inputs, numerical parameters and function revision (`uniserve.loading.weights.Derivation`). Constructor constants are keyed by their bytes. The exact manifest identity also includes the providers that determine encoded layouts: kernel library versions and plugin providers with their distribution versions. Tensor source identities exclude that choice, so an encoding change can reuse retained numerical values through canonical conversion. The key names neither the rank nor its GPU: the Storage Server keeps one copy of a key per location, and a worker asks for the copies on its own GPUs, so any world whose rank needs a region on a GPU finds the chunk holding it there. A manifest of each tensor's checkpoint source and representation and each storage's fields, their logical parts and its chunks is keyed by the structure and the rank's position in its parallel configuration, whatever GPUs it runs on. A change of code that keeps those revisions keeps the weights. An in-place weight update (`/admin/update_weights`) rewrites the tensors where they lie and renames the copies on the worker's GPUs after the new checkpoint at the server. A starting worker maps the storages whose chunks it finds on its GPUs read-only and binds their tensors instead of reading the checkpoint. Loading is collective, so the workers that load together agree on what to read: the tensors any of them misses, or everything when one has no manifest; a change to one tensor's loading inputs reloads only the affected tensors. Packed storage remains readable for its unchanged fields, and the transfer planner can copy those fields independently of changed neighbors. Each worker moves what it read into retained chunks, mapping instead each chunk the server retains on its GPU under the same key (another world's), publishes the chunks it created and maps all read-only; a chunk lives while any world retains it. When any of the workers that load together finds no manifest of its own and every one of them finds the weights the deployment's other worlds retain on the host or on the deployment's other nodes (each manifest names storages, each on the GPUs that hold all of its chunks, and their fields of tensors whose fingerprints are the model's; the fingerprints of the whole model select them, whatever tensors a rank holds, so every rank that loads with others selects the same storages in the same order, those their shared copy manifest names; another node's server is listed over TCP and its manifests read inline, `Request::Read`), they receive their weights instead of loading them (`crates/worker/src/storage/weights/received.rs`): each materializes the target shapes and encoded storage with `rank.load_model(unread=True)`, without reading checkpoint values or generating dummy values. The planning model is released before receiving storage is allocated. Unmeasured links use copies from available source chunks into scratch storage, repeating smaller chunks to collect two 64 MiB measurement windows. For an online change, planning ranks run through the deployment's process interface on their assigned nodes; the daemon reads the same source manifests as the workers, chooses the rank assignment within the declared device set, and supplies an executable `Transfer` containing the request and copy manifest. Cold-start ranks with no daemon plan gather their target layouts and measured links to plan the receive. Each rank then maps the chunks of the same key on its GPU, creates the rest under receiving keys, which the Transfer Server writes, submits its copies as one `Background` transfer (a copy from another node's GPU naming that node's region, `Region::Remote`, which the Transfer Server copies over the NVLink fabric or READs), zeroes the padding the manifest names, and binds its model while the bytes arrive; only tensors with numerical regions absent from the source manifests are read from the checkpoint. Encoded groups with declared canonical forms convert on the receiver: the Transfer Server gathers the source fields, a low-priority preparation stream reorders their encoded values and scales into canonical storage, the manifest copies the logical regions, and the stream writes the destination encoding. One target group and one source group are held at a time; the planner includes their rounded allocation sizes, and the Storage Server ledger tracks the retained scratch. Conversion kernels write borrowed buffers without device temporaries. Copies complete before conversion, and conversion completes before transfer, publication or release. Before capacity planning the worker waits for the transfer, retains the received chunks read-only under their keys with its manifest, and releases the receiving keys. The host region of a layer stack streamed from host storage is a read-only host storage among them. Loading stores every encoded weight in the layout its kernel provider declares (`uniserve/loading/layout.py`), and preparation verifies it, so the retained bytes are those the kernels read.
- **Copy manifests.** How one world's state becomes another world's under another parallel configuration is a manifest computed from both worlds' storages (`crates/storage/src/manifest`). Target ranks take the GPUs holding the most required regions, with ties resolved by the busiest link's completion time. Matching chunks in the same physical storage map read-only; other regions are assigned to sources using measured link bandwidth, then become strided byte copies through their numerical encodings. Encoded fields use canonical conversion storage where required, padding is zeroed, and missing regions are reported. A chunk's `Binding` separates its actual retained storage from its rank's execution GPU: `Rank` follows GPU assignment, `Local` names host or device storage, and `Remote` names a Storage Server endpoint and its host or device storage. `storage_offset` allows a chunk to borrow a region of a retained allocation. Planning charges each physical chunk's link, including Host↔Device and remote Host links; GPU UUIDs identify the same device storage across hosts. Host staging requests are planned per destination host, whose Transfer Server submits the READ. Expert redistribution uses the same conversion path on a background preparation thread, leaving inference on the original allocations until the common commit boundary. The daemon caches the numerical plan. `Manifest::bind(request, host_sources).spans()` resolves its sources from the submitting host's bindings while preserving GPU assignment and numerical copies. It produces `Region::Tensor` and `Region::Remote` directly, combining rows within chunk boundaries and splitting rows that cross them. Source and destination allocations remain retained until transfer completion. The worker library exports storage and manifest computation (`weight_storages`, `copy_manifest`).
- **Exclusive storages.** The prefix cache planes, the buffer pool and the latent banks are exclusive storages with one writer, keyed by their scope, name and shape; a device cache's value planes are eight segments of their units, each layer's part of a segment a storage of its own mapped back to back, so that the tail of the cache can be given back while a standby engine starts or the deployment sleeps and created again at its addresses (`docs/admin.md`): a restarted worker of the same scope takes the storage its predecessor left, after the server shoots that predecessor down if it still holds write access (SIGKILL to its process group, its exit, and NVML no longer listing it on the GPU). An owner resets only storage created for it; a storage a predecessor left keeps the finite values it last wrote. A standby maps them while its predecessor serves from them; after a crash the engine's cache index starts empty, so nothing reads them before a unit is recycled for its next owner.
- **Storage ledgers.** The server keeps one ledger per GPU (by UUID) for each deployment that uses it (`crates/storage-server/src/ledger.rs`), so that the deployment's two worlds and the host's Transfer Server stay within one quota on a GPU they share. The quota is `⌊total × fraction⌋` of the whole GPU for the fraction the deployment's workers configure (the smaller one while two worlds that state different fractions hold storage there). The server books what it retains, each device storage once however many scopes and worlds map it: read-only storages as the weights, a storage its worker marks with its KV cache segment as that segment, any other exclusive storage as the world's fixed part. The processes book what it cannot see (`Request::Book`): each warm worker its graph pool and its process storage under its scope and world, the processes of one scope and world (a rank, and its relaunch or promoted standby) counting as their largest booking, and the Transfer Server its staging, and its CUDA context while it holds one on the GPU, in every ledger of its GPUs (at the bytes it measured when it started, `Measured`, which every ledger of the GPU also reports as `transfer_context`, booked or not, so that a world change's preparation leaves room for the context its transfers will take); every ledger of a GPU also states the bandwidth the Transfer Server measured from host storage to it (`host_link_bytes_per_second`). A worker that ends in order withdraws its bookings, and the driver frees its storage with it; a worker's process that is lost leaves its bookings no other process of its scope and world books reserved under that scope and world, so a successor cannot take a lost rank's storage before its relaunch books it, which takes each item over as it books it, and the reservation otherwise ends with the world's retirement or the deployment; the Transfer Server's bookings end with its connection; a world's storages end when the head retires the world (all but its weights when the head keeps its weights alone; weights the head moved to host storage leave the GPU's ledger, and return to it when it moves them back), and a segment a successor maps, booked once for both worlds, is then the successor's alone: the commit's handover is a transfer on the ledger. The server refuses any booking or new device storage that would take a ledger past its quota, naming every entry. The ledgers survive a hot restart, and `list` prints them; the engine reads them through each worker (`uniserve.cache_storage`) to plan a world change (`crates/engine/src/scheduler/ledger.rs`), and through each node's daemon for `GET /admin/config`.
- **Host KV cache.** The server keeps page pools of host storage, one memfd of equal slots per deployment, page layout and NUMA node, shared by every worker of the deployment whose pages have that layout, a standby engine's included: a page's key is seeded with the model's fingerprint and the identity of what its forwards compute (`uniserve.numerics.identity`: every component's declared function revision and the formats of the tensors it holds), so pages of other weights or other numerics share the pool without matching; a worker takes the pool on the host NUMA node closest to its GPU, whose pages the server binds to that node. With `kv_cache_config.host_tier`, each GPU worker maps a pool for each of its cache groups once its engine sized the world's host KV cache: every rank holds one token count, the device KV cache's tokens times `kv_cache_config.host_ratio`, which each host's server lowers for the whole world to what its budget holds over the bytes a token takes on all of the world's ranks there (`HostCache`, `uniserve.host_cache`), since a reuse needs every rank's pool to hold its pages; a rank that replaces a lost one, relaunched or a promoted standby, maps the same pools at that count before it serves, so the pages the lost rank offloaded stay loadable. The scheduler decides reuse in the host KV cache with the rules of each group's attention type that decide it in the device cache (`crates/engine/src/kv_cache/manager.rs`): a reuse ends at a page boundary every group accepts, full attention needing every page before the boundary and a sliding window only the pages of its window before it. At admission the scheduler pins every group's pages that follow the request's device prefix match, takes the deepest boundary every group accepts with them (a boundary one group rejects does not end the walk), and has the request's first prefill batch load the pages the boundary needs into new units: a full-attention group's pages from the device match on, a sliding window's pages of its window that the device does not hold. A request publishes each page once its batch computed it: its prompt's pages, and for a request that generates text alone from a prompt without context images, the pages of the tokens it generated, each written by the decode that reads its last token and keyed as the same page of its migration's prompt, which continues with those tokens. Full attention offloads every published page into a reserved slot with a later batch, which its output commits; a sliding window offloads only the window before an aligned boundary: every `kv_cache_config.boundary_interval` pages of the largest block size, the last boundary a reissue of the prompt can reuse, and the last boundary of its published prompt pages. The window's pages are reserved while the request's table still holds them, as one window the pool evicts whole, and with the last full-attention page before its boundary, its anchor (`crates/engine/src/kv_cache/offload.rs`, `crates/storage-server/src/pages.rs`). A rank issues a batch's page loads and offloads on its copy stream, in a job of their own, as soon as the batch arrives, so they overlap the forward the previous batch runs; the batch's forward waits only for its loads, and its output for its offloads. Before the engine closes its workers at shutdown, it lets the batches in flight complete and sends each group's remaining reserved offloads in a batch of page offloads alone, so every page it reserved reaches the host KV cache. A published page keeps the key it was offloaded under, and a withdrawal of the cache's units (a world change's shrink, a parked world's eviction) holds the idle cached pages it evicts and offloads them again under those keys before the units go: the pool answers a page it holds as present, and the others are copied and committed. A rollback discards what the world on trial published: pages nobody reads leave the pools at once, the others when their readers unpin them. Committed pages of other numerics are not discarded at a commit, since other Replicas of the deployment share the pools; their keys never match a successor's, and ordinary eviction replaces them. A page is one page of one group on one rank, layer-major: keys, values, and FP8 scales.
- **Host encoder pools.** Every rank that executes an encoder (a video model's text, vision and condition encoders; an image model's vision and latent encoders) maps its host's encoder pool (`crates/worker/src/storage/encoders.rs`), a page pool shared by the deployment's ranks on the host in every world of the deployment, and reports it with the identity of what computes each encoder output it writes: the weights' values and the declared function and format identities of the encoder's modules, and for an image encoder the image transform its pixels are prepared by (`EncoderPoolInfo`). The scheduler keys an output's pages by its name, the identity and the digest of what the encoder read (`crates/engine/src/encoder_outputs.rs`), so requests that read the same in worlds that compute it the same, the same request resumed among them, find each other's outputs. The daemon names, in every video request, the digests of what each of its encoders reads (`DiffusionRequest::encoder_inputs`): the presentation's tokens for the text encoding, and the content and plan of each condition's media, but not where they are published, for the vision and latent encodings. An image request's encodings are keyed by the image (an input image's `ImageInput::digest`, which the daemon computes over its bytes, a request-dependent preprocessing parameter and the request's cache partition; a generated image's digest over the values or the PNG its feedback reads and the request's cache partition, which the engine knows once the image's decoding resolved: a feedback encoding queued behind its image's decoding is computed without the pools, and the continuation that carries the image looks it up and stores it) and, for an encoder that samples its posterior (`ImageEncoderOutput::draws`, BAGEL's latent encoder), the request's image seed and the encoding's draw (`Call::latent_draw`); an encoder that does not sample is keyed by the image alone, so requests of other seeds share its output (`crates/engine/src/scheduler/encodings.rs`). The engine's encoder cache keeps an image's encodings on the device under the same key and is the nearer tier: an input image's encoding it holds is pinned without a call. When a video request is admitted, every page of each of its outputs is pinned before its encoders are offered, and an image encoding's pages before its call is planned, on the replica the call runs on: when all are pinned, the output's encoder calls read their rows from the pool instead of computing them (`Call::host_output`); otherwise the pages are reserved, the calls compute the output and the rank that wrote rows copies them to the pool on its encoder's stream, and the pages are committed once every call of the output succeeded. An image's features take the pages of as many rows as the cache tokens of the block they write, whose rows the worker prepares from the image (`ImageEncoderOutput::row_bytes`). A request whose cache policy reads no cached output computes its encodings and stores them, and one that writes none stores nothing. A pool holds the outputs of twice its group's request slots (the requests a world runs and as many preempted ones waiting to resume) at their largest, for an image request one image's features; an output evicted beyond that is computed again.
- **Host latent pools.** Each video denoising rank maps a page pool of pages the size of one page of its latent banks (float32 values, its own share of a trajectory) on its device's NUMA node. The pool is the rank's: the same rank (worker group and rank) of every world of the deployment whose pages have that size maps it, whatever its parallel configuration, and it holds every trajectory the rank can have stored at once, twice its request slots: one preemption stores at most the trajectory of each slot's request, a request that resumes a stored trajectory is admitted before every request that starts one, so a world has at most its latest preemption's trajectories still to restore, and a world on trial stores its own while the trajectories of the world it succeeds stay for a rollback. A trajectory evicted beyond that is a miss, and its request starts from noise. It reports the pool with the identity of what it computes (the weights' values and the model's function and format identities, as its KV cache pages are keyed) and its region, what determines its share of every request's samples: the page geometry, the video plan that selects a request's layout, the rank's coordinates in the denoiser's mesh and its rows of every startup layout (`LatentPoolInfo`). A request's latent preparation reports how each denoising rank's slot pages hold the request's samples, as the copy manifest library describes a storage (`CallOutput::latent_layouts`, `uniserve.executor.video.plan.SampleLayout.storage`): each modality's complete sample is a logical tensor of rows by channels, the rank holds a run of its rows (the denoiser's division of the packed sequence), and its values lie row-major at the modality's offset of the slot's pages. The scheduler keys a stored page as that library keys a chunk of the slot's pages (`storage::manifest::Storage::paged`): the logical regions the page holds and where, with the content of the values, the deployment's latent seed (the distinct identities of its denoising ranks), the trajectory's identity and the steps it took (`crates/engine/src/trajectories.rs`). The key holds every input that determines a page's values and nothing else, neither the world nor the rank nor the parallel configuration, so a world whose denoising computes the same finds what another stored, a page two configurations lay out alike is one page, and a world that computes other numerics finds nothing. A preempted request's pages that hold its samples are reserved in every denoising rank's pool and copied from the bank holding its committed step on the rank's copy stream, behind the batches that used the banks, by a batch of latent offloads alone (`Batch::latent_offloads`), whose output commits them; the request leaves with the record of every rank's pool, host, region and layout. A resumed request's pages are pinned, from that record, until its latent preparation's result (`Call::latent_restore`): every restoring rank reads the stored pages of its own host, mapping another rank's pool on first use, and plans the copy manifest from the stored ranks' layouts to its own (`crates/worker/src/storage/latent/restore.rs`), in which a page it lays out as a stored rank did is one whole-page copy and every other region a run of bytes from the stored page that holds it, which the executor copies into the bank (`Denoiser.restore`). The same path serves a request resumed under the parallel configuration that stored it and under another (another Ulysses degree, other ranks): a change of distribution moves values and computes none. The restore hits only when every restoring rank's host holds what the rank needs, the pages of a stored rank of its own region or else the whole of every stored sample, so a resumed request whose stored ranks lie on other hosts than the ranks that need their rows starts from noise. A world on trial keeps the trajectories it stores its own until its commit, as it keeps its KV cache pages: a rollback discards them, and the previous world computes the requests it takes back from what they named before. Stored trajectories leave the pool least recently used first.
- **Transfer Server.** The server runs a Transfer Server (`uniserve storage transfer`, `crates/storage-server/src/transfer`), a child process it starts again 5 s after it ends, which copies bytes between the storage the server holds; the CUDA contexts the copies need are that process's, so a fault in a copy ends it and never the server. A head or a worker submits a task of spans, each a length of bytes from a source region and offset to a destination region and offset, with the update it serves and a priority, highest first: promotion (what a promotion waits for), warming (filled pages copied into the next world ahead of its promotion) and background (weight moves and the rest) (`Request::Transfer`). A region is a retained tensor's storage, offsets counted from the tensor's first byte; a page pool; or a device allocation of another host of the NVLink fabric, by a fabric handle its creating process exported, which imports only while that process holds the allocation (CUDA exports no fabric handle from an allocation imported through its POSIX descriptor); or, as a source only, a retained tensor or page pool of another host, named by that host's Storage Server endpoint (`Region::Remote`). The server checks that every region of this host is storage of the submitter's deployment and every span lies within it and writes no read-only tensor, refusing the task whole otherwise, gives the Transfer Server each allocation's descriptor before the first task that copies it, takes it back when it releases the allocation, and relays the task's progress and end as events. Another host's region is checked by that host when the task runs: the Transfer Server connects to its server's TCP endpoint as a peer (`Role::Peer`) and asks it to expose the task's regions there (`Request::Expose`); that server checks them as it checks a task's sources, has its own Transfer Server register their allocations with its NIXL agent (UCX backend, `crates/nixl`, which binds NIXL 1.5.1's C API, `libnixl_capi.so`, itself and resolves its entry points when the library loads), and answers with the agent's metadata and each region's address; the destination's Transfer Server loads the metadata, registers its destinations with its own agent, checks each span against its region, and posts NIXL READs, whose completion it polls on the host, since a READ passes through no CUDA stream; a span of rows at a pitch is one READ of a descriptor per row. A device allocation whose creating process recorded its fabric handle in its storage record (`StorageRecord::fabric`) is exposed with that handle, and the destination's Transfer Server copies its spans over the NVLink fabric on the copy engines of the destination's GPU, rows at a pitch as one pitched copy, whenever the handle imports there, and READs them otherwise. The agent registers storage pinned, at registration, and outside UCX's registration cache: under UCX's default on-demand paging the first READs' page faults hold a link to a few GB/s (host storage read between two GB200 hosts at 4.1 GB/s on demand, 79 GB/s pinned; pinning a 64 GiB host region takes 1.7 s), and the cache, which learns of an unmapping only through UCX's hooks of `munmap` that the Transfer Server's direct system calls bypass, would hand a region mapped again at a released address the released region's registration, so that READs into it land in storage no longer mapped. A read-only allocation's host storage is mapped read-only and registered for remote reads alone, which needs the UCX and NIXL builds with the read-only registration patches (`--nixl-library`, `docs/configuration.md`); with other builds its registration fails, and so does the task that READs it. A process of another host also reads a small tensor of bytes that a scope of its deployment retains read-only in host storage, such as a weight manifest, inline over the same TCP endpoint (`Request::Read`), up to 64 MiB (`READ_BYTES`); a longer one is refused. A task whose source host is unreachable, runs no Transfer Server or holds no such region fails, naming that host and the reason. The exposure lasts until the destination's Transfer Server ends it once its task ended (`Request::Unexpose`), or its connection closes, or the source's server takes the allocation back; the submitter keeps a remote source retained and unchanged until the task ends, as it does a local one. The submitter keeps the sources unchanged and the destinations unread until the end, which the Transfer Server reports only after the host saw every copy complete, so no CUDA event crosses a process. A copy runs on copy engines, never as a compute kernel: those of the destination's GPU, else the source's (the first GPU's between host storage and another host's GPU of the fabric), the CPU between host buffers, and the network adapters for a READ from another host. When the Transfer Server starts it measures every link (each GPU to itself, each pair of GPUs that can address each other, each GPU to and from host storage on its NUMA node, host to host) and the device storage NVML attributes to its CUDA context on each GPU, and `uniserve storage list` prints both; it then releases its contexts. It holds a GPU's context only while it has work on the GPU (`crates/storage-server/src/transfer/contexts.rs`): a task's pieces hold the GPUs their storage lies on or their copy engines run on, a lane's thread its GPU while it copies, an exposure to another host the GPUs of its device allocations until that host ends it; and an explicit transfer session the GPUs its operation uses across successive tasks. Cache warming opens a session on each source and target owner before copying and closes it after the final round or cancellation (`OpenTransfer`, `CloseTransfer`); closing the client also ends its sessions. Sessions create no context until a task first uses it. The first use of a GPU books the context in every ledger of the GPU at its measured bytes (`Request::Book` of `transfer_context`) and then retains it, so a ledger without room refuses the booking and the task that needed the GPU fails, naming the ledger; once the last hold ends, the device mappings, host registrations, NIXL registrations, streams and events made in the context are released, the context with them, and then its booking, so NVML lists the process on no GPU it does not use. The context's retain moves into the cost of the first task on an idle GPU. A link from another host (its GPU or its host storage to a GPU or host storage here) is measured at its first use: its chunks run one at a time, 64 MiB each, until the faster of its first two contiguous ones (the first READ over a new connection also sets the connection up) gives its bandwidth, which the listing then prints too. It cuts each copy into chunks lasting `--transfer-chunk-us` at the link's bandwidth, so a copy engine turns to the executing world's own copies and to a higher priority between chunks; each link runs the chunk of its highest priority first, tasks of one priority in submission order, and keeps a byte budget, its whole bandwidth at start, which a head halves (`Request::Throttle`), down to 1/64, and restores by 1/8 of the bandwidth per second; a head that names no link halves every link a task of its deployment copies over, and restores every link a halving reduced. While a successor world prepares, the leader halves the budgets of the change's links on every node of the deployment as the leader knows it then (a node that joined for the successor included), through the serving engine and each node's daemon's claim, each second a serving scheduler's step takes more than `update_config.transfer_slowdown` past its step of the same batch size and execution (graphs, or eager forwards with `update_config.eager_prepare`) before the preparation, and restores them once none does (`crates/daemon/src/interference.rs`). A task is cancelled by number or with every task of its update, and when its submitter's connection closes; it ends once its chunks in flight completed. The server submits tasks of its own to move a world's weights between its GPUs and host storage, at a head's request: an offload (`Request::Offload`) takes every device copy of read-only tensors the world alone retains, admits host storage of their whole size under the host-storage rule (refused whole otherwise), creates a memfd of each storage's size and copies each into it; a restore (`Request::Restore`) admits each storage's size against its GPU's ledger, has the Transfer Server create retainable device storage of that size on the GPU it came from, in that GPU's session (`Event::Allocate`, answered with its POSIX descriptor in `Request::Allocated`; the Transfer Server keeps no handle of it) and copies each back. Once every copy of a move ended, the tensors' copies lie at their new locations and the storages they left are released, so each GPU's ledger books the move's effect at once; a copy that fails leaves every tensor where it was and releases the copies. The head's request is answered when its move ends. When the Transfer Server ends, every task it held fails at once, and the next one maps what new tasks copy again; its NIXL agent ends with it, so another host's READ of this host's storage in flight fails, and the next agent, of another name, registers the regions again when a peer next asks, whose Transfer Server then forgets the previous agent and loads the new one's metadata.
- **KV storage.** With `kv_cache_config.mooncake`, the server runs a Mooncake connector, a child process it starts again when it ends (`crates/storage/src/connector.rs`). The connector maps every page pool, registers it with Mooncake, and writes each committed page to Mooncake as the object `uniserve_{page key}_{kv head offset}-{kv head count}`, which names no deployment or host. A lookup tells for each page key whether its page is in the pool, in Mooncake or absent. When the pages Mooncake holds would deepen the boundary every rank's pool holds by at least 256 tokens, admission prefetches them into reserved slots, waits for them at most 1 s plus 0.25 s per 1024 tokens, and computes the pages that did not arrive. Prefetches hold at most half of a pool's slots. Mooncake's master evicts objects; the connector never removes them.

Retained host allocations are admitted by the Storage Server before it creates their backing (`AllocateHost`). The worker receives an exclusive byte tensor and its writable descriptor through the ordinary storage reply; its world retains the allocation until it releases the key or retires. Host admission subtracts the server reserve and the unallocated bytes of both page pools and retained host storages from available storage (`HostStorage::unallocated`), so sparse allocations still awaiting their first write cannot each spend the same headroom.

### Transfers

Transfers go through one module per mechanism in `crates/worker/src/transfer`: `local` (in-process borrows), `posix_shm` (POSIX shared memory on one host), `vmm` (CUDA VMM allocations exported in place or through a pool, imported by fabric handle or by a descriptor from the exporter's grant socket) and `channel` (bytes carried in the location). A read runs on a transfer-pool thread with one stream per thread and device: it claims the chunk and waits on the host for the claim, orders its copy behind the handoff and the producer's event (a cross-device read waits for the producer on the host), copies, acknowledges, and drains its stream before its task completes, which returns its bytes and read credit. A VMM read imports the allocation's handle, maps it and opens its ready event. An export states whether its allocation is resident (the producer's arenas, pools and cache planes, kept until it closes) or made for that export alone: a reader keeps its mapping of a resident fabric allocation for every later read of it until its transport closes, and releases any other mapping with the read. A worker's transfers share one byte budget and one set of read credits; an exported product holds its bytes once, whatever number of mechanisms publish it, and they return when its last backing physically retires. A worker holds one read credit per queued call (a media worker at least one per concurrent artifact import of each slot and one per worker of the deployment) and reports their count (`WorkerInfo::transfer_tickets`); the engine keeps no more transfer calls reserved than the narrowest worker holds.

## Startup

Every worker of a group runs these phases in the same order, because several are collective:

1. The control thread connects to the engine, registers and receives the launch descriptor while the builder thread starts the interpreter; until serving starts, a watch ends the worker at once if the engine's connection closes. Once the interpreter is up, Rust checks the devices and makes their primary contexts current.
2. `read_config` describes the model; Rust validates the parallel configuration and the components each rank holds.
3. Rust plans the process groups; Python creates them.
4. `load_model`, or binding the weights retained for the same model at the rank's position in the same parallel configuration on its GPUs; the checkpoint reader reads each source file front to back into the page cache before mapping its tensors, so workers loading one cold file do not fault it page by page. A worker that loaded moves its weights into retained storage and publishes them.
5. Rust constructs the rank's executor with its settings and reads its manifest; creates the worker's streams; a member of an expert union configures the union's agreement and exchanges collectively (`expert_storage_bytes`, `connect_experts`); distributed expert weights start, and a component placed with `"weights": "host"` moves its layer projections into a page-locked host region and a ring of device slots that Rust allocates and Python copies each layer into ahead of its use.
6. Rust plans capacity from the manifest and measured storage, allocates request storage, and binds the executor to the streams, scratches, graph pools, prefix cache tables, relay staging, latent banks, report pipe and stream groups Rust allocated; the executor constructs its runners and, on the builder thread that runs every computation, creates each bound device's cuBLAS handle, whose creation frees device storage and so waits for the device, which no serving call may.
7. The batch executor and the profiler start.
8. Warmup: Rust grants each device's graph pools their budget; then the executor's warmup phases run, in which every captured forward runs eagerly once at its shape, so kernels compile outside capture, and is captured, each executor's shapes largest first. Paths that always run eagerly run once too, so no serving request selects a kernel first.
9. Rust checks the graph pools' residency and the executor seals its graph tables; Python's garbage collector is collected, frozen and disabled; the worker reports its capacities and the shapes it prepared to the engine: one image shape per captured guidance-branch count (`WorkerInfo::image_warmups`, a guided one with its model's framing of an empty negative prompt), the image and latent sizes its codec graphs hold (`captured_images`, `captured_latents`) and the bounds of one image step (`image_capacity`), which admission refuses requests beyond, the rows of one diffusion LM sampler chunk (`diffusion_lm_step_rows`), and the tokens its image denoiser's image-unconditional guidance branch attends to when that branch does not read the request's own context (`image_unconditional_token_ids`), which the engine reserves and prefills as a guidance prefix of its own beside the negative prompt's.
10. On GPU workers the engine warms the serving path with real requests through its scheduler (`crates/engine/src/warmup.rs`): a token request of a prefill and a decode, a group of equal one-block diffusion LM requests for each row count of a sampler chunk, each submitted in one command so its steps run with exactly that many rows (the one-row request generates a second block, so a commit prefill runs), and a two-step image request per image shape at the guidance scales of its branch count. A request the deployment's generation limits refuse a client is left out. Serving starts once every warmup request finished.

After startup the builder thread serves the executor's batch calls and the little resource work issued while serving.

## Serving

**A text decode step.** The engine sends a `Batch` whose decode calls name request slots. The control thread opens it (binds the calls to their requests), reserves the prefix cache's tables and attention pages and leases the output words, and submits the job. On the builder thread the text executor's `execute` reads the call and forward columns, gathers each call's request constants by slot, computes the Philox draws of each sampled position from the request's seed, picks the decode graph of the smallest row bucket that holds the batch, writes the forward's inputs into its columns (slot indices, finish flags, the rows' sampling parameters and draws) and replays it: the graph gathers tokens, positions and attention metadata from slot state on the device, runs the model, projects the final-position logits and selects each row's token: greedily, or by sampling under the row's temperature, top-k (up to 128 candidates), top-p, min-p and penalties, all of them tensor contents of the graph. A batch that needs token sets, logit biases, typical-p, reported logprobs or a sampled top-k beyond the 128 candidates selects after the forward with the `select` graph of its task bucket and samplers, whose controls are tensor contents (each task's sampler, parameters and draws, token sets as bitmasks, its slot's row of logit biases), with the same kept-set computation; its `score` graph reports logprobs, scored on the model's raw distribution. `execute` enqueues the copies of the selection words into the lent output words and of the selected tokens into the relay staging, and returns the records: each call's progress and where its words lie. Once the builder thread has checked the records and the batch is sealed, `commit` replays the commit graph, which installs the selections into slot state, so the next step can be queued before this one's result is read. When the job's event completes the control thread decodes the records and words and returns the `BatchOutput`. Prefill (which also carries verification rows) has its own graphs, and a verification selects eagerly; with tensor parallelism every worker replays the same graph and the collectives inside it were captured with it.

**A speculative decode step.** In a deployment that speculates, a decoding request's call is a verification: a prefill-kind row of its committed token followed by the drafts the drafter proposed after its previous step, as many as the scheduler chose for it (from zero to `num_draft_tokens`; zero, a row of one token, while its draft cache is incomplete), so the rows of one batch differ in length. Attention reads each row's query length from the forward columns as it does a prompt chunk's, and the recurrent layers (`uniserve/nn/gated_delta.py`) evaluate a verification row token by token without advancing the slot's state (`uniserve.prefix_cache.slots.Verification`). The `verify` selection returns each row's accepted draft prefix and the token after it (`CausalLMRunner.verify`), and for a request that asks for logprobs scores a row per position the verification may commit, each token under the logits it was selected at, of which the worker reports one per committed token (`CallOutput::token_logprobs`); the recurrent layers then advance the slot's state over exactly those tokens and write the checkpoints the request's tables hold at the page boundaries they pass. After every forward of a speculating computation, the drafter pass (`CausalLMRunner.draft`, over the model's `uniserve.models.Drafter`) writes the draft cache entries of the forward's positions whose next token is known (the row's next token, a prompt chunk's `lookahead` token after its last, the selected token after a verification's accepted ones) and, for each call that asks for proposals, chains its steps from the call's last committed position, each step reading the previous step's draft and hidden state; the pass indexes rows by the device's acceptance counts, so it reads nothing on the host. The proposals reach the engine in the call's record words, and a request's next verification, which carries them, waits for that result instead of being queued behind the call; it carries its current token among its host tokens rather than relayed, since the drafter pass reads a row's tokens on the host. A refill call (`DRAFT_REFILL`) is a prompt-kind row over positions whose target K/V the cache already holds: it evaluates the target again, writing neither the target's pages nor the slot's state (its recurrent layers start from the checkpoint at its first position), so that the drafter writes those positions' entries; the engine schedules refills in the prompt token budget a step leaves idle (`crates/engine/src/scheduler/speculation.rs`).

**A FastH3 video request.** The daemon plans the request with the `models` crate's rules. On every rank the executor admits it at its exact size (`start`), and a denoising rank holds the layout that serves it (without graphs, a request with conditions evaluates in a layout prepared for it). The text encoder's graph of the smallest prompt capacity that holds the prompt runs on its tensor-parallel group; latent preparation writes the request's noise and state rows; each denoising step copies the slot's committed latent pages from the bank the ledger names into the sample tensors, replays the layout's graph on every worker of the sequence-parallel group and copies the result into the other bank; video and audio decoding replay one graph per temporal unit; the decoded units transfer to the CPU workers, whose media thread encodes each unit and muxes the MP4.

**Batches.** Every computation's batch goes through the same steps on the batch skeleton (`crates/worker/src/executor/batch.rs`, sequenced by `crates/worker/src/executor/computations.rs`): open (bind calls to their requests), lease output storage and the calls' device predicates, bind completion flags, seal (end reads, validate every owner's update), commit once the job carrying the device work completed (writes become visible, calls pending), and materialize once the output fences complete, finishing any host work such as image or video encoding (a video batch's host work completes through the executor's reports). A failure before the commit point fails the batch's calls and the worker keeps serving; a failure at or past it is fatal to the worker.

## Parallelism

- **Streams and jobs.** A rank with a CUDA device issues every forward's work on its primary stream, the full-device stream of its primary device, in the jobs its builder thread performs (`crates/worker/src/job`). The components' module streams fork from it, so their work overlaps on the device while forwards follow one another on the host. A rank that maps a host page pool also has a copy stream, a full-device stream of the cache's device that the batches' page copies are issued on, in jobs of their own ahead of each batch's forward (`crates/worker/src/stream`).
- **Collectives.** A layer calls its communicator; in serving its functions are NCCL collectives of a torch process group bound to the forward's stream (one process group per stream group Rust plans, `uniserve.distributed.collectives`), captured with the forward.
- **Expert forwards.** The executor's expert union (`uniserve/executor/experts`) agrees on each step's source and capacity with the union's other members over their host group, then runs the step; a member without tokens replays the join graph of the agreed capacity. With several microbatches each runs on a Python thread of its own, taking the host in turns at the expert dispatch points. A distributed expert layer's weight copy from its peers is a graph break.
- **Schedulers.** Each DP rank has a scheduler: its own thread, KV cache and the worker groups it drives. A replica is one of the groups a deployment file's `replicas = N` expands a group into.

## Failure handling

Errors cross with a stable code, whether they are fatal to the worker, and the phase they occurred in. A Python exception in an executor call before a batch's commit point fails that batch, unless its kind marks a broken invariant (an `AssertionError`), which is fatal; at or past the commit point every failure is fatal. An error in resource work fails startup, or at serving time the batch that needed the resource. A launch failure or a driver error is fatal to the worker, and the engine replaces its failure domain: the worker group, or every group that shares an expert world, whose workers hold that world's communicators. Every group of the domain terminates its workers; the token requests they held end as migratable (`MigrationCause::Loss`), and the daemon submits them again with their generated tokens and images, to wait for the relaunched workers, while the readouts fail. The domain is relaunched together, its groups form their communicators again, and their weights and exclusive storage come back from the host's Storage Server: each relaunched rank lays its KV cache planes out as the lost rank held them, taking back the segments it held and leaving absent those it gave back, rather than sizing them afresh against a device whose storage a successor world prepared beside the serving one may share, and it must then report the lost rank's capabilities, its planes as they stood included, or the group closes. The relaunch runs on a thread of its own (`Relaunch`, `crates/engine/src/worker/group/relaunch.rs`), so the scheduler keeps serving the scheduler's other groups while the relaunched workers start; each group of the domain admits work again once it has installed them, and a relaunch that fails closes the domain's groups. A group that keeps a standby (`worker_config.standby`) is replaced by promoting it instead: its ranks started beside the group's, mapped the group's weights and exclusive storages without write access, captured their graphs on the warmup scratch units, which the scheduler never allocates, and parked; on promotion each takes write access once the Storage Server has the failed rank out and serves at once, and the group starts a new standby (`crates/engine/src/worker/group/standby.rs`). A group on one host without an expert world keeps a standby rank group of its own and promotes it within the step. The groups of an expert world, and a group on several nodes, keep a standby world instead: once every group of the domain serves, the domain launches each of them a second time at a rendezvous of its own, so the standby ranks form their own communicators and capture graphs over their own workspaces, and parks that world. A loss in the domain stops only the serving launches, and the replacement round promotes the standby world instead of relaunching: every rank is asked to promote before any answer is awaited, since a suspended world restores its expert workspaces together, and the groups install the promoted ranks and offer the next standby world. A suspended world's transport workspaces that cannot keep their addresses (DeepEP's windows, the NVSHMEM heap of colocated MegaMoE) are freed while it parks; its promotion creates them again and captures the graphs that run expert steps anew, on the scratch units, before it serves. A promotion that fails relaunches the domain.

A lost engine process takes its workers with it. Its client ends every request it held as migratable, the leader's daemon holds new requests and starts a new engine process under the same claims, whose workers find their weights retained, and the hold then serves the new engine every held and migrated request. A request survives `migration_config.max_migrations` migrations caused by losses; when the new engine does not start, held and later requests fail.

A driver call that does not return stops the builder thread inside its job. The control thread keeps serving the channel and, once a job has stayed in flight for the stall bound (half the engine's watchdog timeout, `worker_config.watchdog_timeout`, sent in the launch descriptor), reports to the engine the job's batch, its runner method, its calls and how long it has run (`WorkerResponse::Stalled`). The engine logs the report, fails the affected requests with an error naming the stalled job's forward, and replaces the group. A device whose context an illegal memory access or a device-side assert left unusable runs none of the work behind the failure, so the completions of the jobs in flight never post: while a job has been in flight for a second, the control thread probes each of the rank's devices once a second and, when the driver returns such an error, fails the rank with it at once. The engine's watchdog covers a worker that stops answering altogether.

A worker's orderly close ends with a reset of its primary contexts before the process exits. The reset releases the driver state the process created, including the shared-memory file (`/dev/shm/cuda.shm.*`) the CUDA driver makes for a process's interprocess events and removes only when the context is destroyed. A worker that loses its engine with nothing in flight takes the aborted close and then the reset; with work in flight it ends at once. A worker that ends without its orderly close first removes the driver file and the NCCL shared-memory names (`/dev/shm/nccl-*`) its mappings still link. The daemon that reaps a worker observes the death before reaping and removes that worker's driver files and recorded NCCL names while the zombie still holds its pid. A worker's startup failure, the interpreter's included, reaches the engine as the worker's own error.

## Repository layout

```text
crates/models/          the model families' request semantics: the family registry, the SenseNova, Bagel and DiffusionGemma checkpoint facts and prompt rules, the MiniMax-H3 video rules
crates/proto/           the interfaces across builds (Protobuf): the process interface between daemons and engines, and the request vocabulary
crates/ipc/             engine-to-worker messages, the channel, registration, launch descriptor
crates/storage/         the Storage Server's protocol and client
crates/storage-server/  the Storage Server, its Mooncake connector and its Transfer Server
crates/cuda/            CUDA driver, VMM, NVML and NCCL bindings and graph launch, loaded at run time
crates/nixl/            NIXL agents with the UCX backend: storage registration, agent metadata exchange and READs between hosts, through NIXL's C API library loaded at run time
crates/daemon/          a node's daemon: process supervision, the node's Storage Server claim, the process interface's service; on the leader, the HTTP/OpenAI API, model profiles, input and output processing, metrics and the engine's client
crates/engine/          the engine process: schedulers, KV cache allocation, worker groups and process launch through the daemons, the request interface's service
crates/worker/          the worker runtime, installed as the library uniserve/_worker
crates/uniserve/        the uniserve executable: serve, engine, worker and storage
uniserve/           the numerical library, the concrete models, the Python half of each runner and the worker's Python entry
uniserve_kernels/   Triton, CuTe and CUDA kernels, and the vendored DeepEP and DeepGEMM sources
uniserve_eval/      HTTP evaluation client
```

Dependency direction: `proto <- {ipc, models}`, `ipc <- {engine, worker}`, `{proto, storage, cuda, models} <- daemon`, `{proto, ipc, storage} <- engine`, `{ipc, cuda, storage, models} <- worker`, `{storage, cuda} <- storage-server`, `{daemon, engine, storage, storage-server} <- uniserve`. The daemon knows engines only through `proto`; the engine knows no model family: what a video request asks of its model (its conditions, the denoiser's description) crosses the engine as bytes the model family encodes (`models::video::Conditioning`, `models::video::DenoiserInfo`) beside the sizes the engine schedules by. The worker never depends on the engine or the daemon, the daemon never on the engine, `ipc` or the worker, and the engine never links CUDA.
