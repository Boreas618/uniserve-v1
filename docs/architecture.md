# Architecture

UniServe is a Rust serving system. Rust owns the control and data planes and the numerical computation alike: HTTP, scheduling, the main processes and the channel between them, requests and their progress, storage and device storage, CUDA streams and graphs, transfers, host groups and observability, and the model mathematics over the `nn` layers and the `ops` kernels. No serving process carries a Python interpreter: Python appears in the Build Server alone, as the compiler of Triton and CuTe DSL kernel packages, and in the evaluation client.

This document describes how a deployment is organized, how the main process divides its work between its threads, and how a request travels through it. A host is one machine; a main process is the `uniserve-engine` process of one node and epoch: its control thread, one scheduler per DP rank with its executor, one worker per device and its blocking pool (`crates/engine`); a worker is the thread of a main process that issues one device's work (`engine::worker::Worker`); an executor is what a scheduler hands its batches to, which numbers them per worker group and hands them to the group's workers (`engine::executor::Executor`); a group is the ranks that run one role's stages together, launched and replaced together; a rank is a group's member; a scheduler is the scheduling of one DP rank (data-parallel rank).

## Principles

1. **Rust owns the control and data planes.** Requests, admission, slots, every request's progress, batch order, storage and its lifetime, streams, transfers, host groups and failure handling are Rust's. The code that owns them names no model: it dispatches by a model's capabilities, never by its identity.
2. **The numerics are Rust.** A worker's runners (`crates/engine/src/runner`) make every numerical decision of a batch: buckets and padding, graph capture and replay, attention metadata, sampling and its random draws (keyed by the request's seed and token position), and the device state of each slot. They compute over the layers of `crates/nn` and the kernels of `crates/ops`, keep each admitted request's numerical constants by slot from `start` until `release`, and report everything a request's progress depends on back to the engine in each batch's results.
3. **A layout with two readers is defined once.** The batch a scheduler submits and a worker's runner reads is one type (`engine::batch::Batch`, `crates/engine/src/batch.rs`), whose host columns the scheduler builds (`crates/engine/src/scheduler/rows.rs`) and the runner copies into its input tensors (`crates/engine/src/runner/causal_lm/columns.rs`); neither side keeps a second copy of the layout.
4. **Each behavior is implemented once.** A forward's computation is one method of a runner, used by serving, by graph capture and by the shadow harness that proves an update alike. A rule the reference also states is written once and cited, never copied.
5. **One thread issues a device.** Each device has one worker thread, the only issuer of work on that device's streams, so a stream's order is the order the worker took its jobs in. Nothing else in the process touches the driver.

## Processes

| Process | Language | Role |
| --- | --- | --- |
| `uniserve serve` (daemon) | Rust | One per node, for the deployment's lifetime. Every node's daemon starts, reaps and reports the processes of its node and holds the node's Storage Server claim. The leader's (node rank 0) also serves the HTTP API, processes every request's input (the model profile, chat templates, tokenization, multimodal inputs, request lowering) and output (detokenization, stop strings, reasoning and tool parsing, response assembly), and starts the engine process |
| `uniserve-engine` (main process) | Rust | One per node per epoch, started by that node's daemon as `uniserve-engine --launch <fd>` (`crates/daemon/src/engine/control.rs`) on the leader's instruction (`Request::Spawn`, `crates/proto/src/process.proto`), and replaced with the epoch. The launch states the role the process holds, so the process never infers it (`crates/engine/src/process/start.rs`): the node that schedules runs one scheduler per DP rank (scheduling, the KV cache), and every node runs one worker per device with that node's models, runners and modules and its media encoding, muxing and reading. It serves the request interface to its daemon |
| `uniserve storage-server serve` | Rust | One per host and serving user, a host service; keeps the storage that outlives the engine and the workers (see Storage and device storage) |
| `uniserve build-server serve` | Rust | One per host and serving user, a host service; compiles packages, keeps their modules and hands them to the daemon and the main processes (see The Build Server) |

A deployment of several nodes starts `uniserve serve` on each with `--nnodes`, its `--node-rank` and the leader's `--dist-init-addr HOST:PORT`; the leader binds that address and waits until the daemon of every node rank below `--nnodes` has joined it. The leader keeps the address bound while it serves, so a deployment that names it (of one node included) also takes a node whose daemon joins later with a node rank no node holds: the engines that connect from then on learn it, and the next epoch change may run ranks there. While nodes may join, every node's Storage Server also listens on TCP, so that the other nodes' Transfer Servers read its storage. Only the leader takes a model; another node's daemon serves the leader until the leader's connection closes, then ends its processes and exits.

The daemon and the host services, the Storage Server and the Build Server, are commands of the base executable `uniserve` (`src/cli.rs`), installed into the environment's `bin/`; it links neither the engine nor a model, and is what an update of the deployment does not replace. A main process is the executable of the engine package, `uniserve-engine` (`crates/engine`, `package.toml`), which the Build Server builds and each node's daemon resolves at its own Build Server and starts with its launch. No process embeds a Python interpreter: the numerical library is Rust. A main process starts as `uniserve-engine --launch FD` (`crates/daemon/src/engine/launch.rs`) and reads its launch whole from the descriptor it inherits at that number: a sealed anonymous file (a memfd) its daemon wrote, which lives in no file system and cannot change once sealed. The launch states the epoch's build config, the model, the request address, the Storage Server namespacing, the Build Server's socket, the devices, the rank and the durations. It reads that launch, starts its control thread, one scheduler per DP rank, one worker per device and its blocking pool (`crates/engine/src/process`), and serves until its supervising daemon ends.

### The request interface

The leader's daemon and the engine process exchange the request interface (`crates/proto/src/request.proto`), Protobuf that changes only by additions, so a daemon keeps serving engines of later builds.

- **Start.** The leader's daemon binds its request socket and asks the node's daemon to start `uniserve-engine --launch FD` (`crates/daemon/src/engine/launch.rs`), whose launch carries the epoch's engine configuration (`proto::config::EngineArgs`: the serving options that build the engine processes and what the daemon resolved from the checkpoint, its generation limits, control tokens and context length), what the process takes over from the one it succeeds, the request address, the process address and the number that identifies the epoch's engine. Without `engine_host`, the engine runs on the leader. A local deployment uses Unix sockets in the daemon's instance directory; a deployment with `dist_init_addr` uses TCP sockets on the leader's network interface, so engines can move between joined nodes. The engine connects and says hello with its version of the engine interface, build and number; the daemon welcomes it when that is its own version (`proto::ENGINE_INTERFACE_VERSION`), and refuses it otherwise with a typed refusal naming both versions. The engine reports `Starting`, starts its schedulers and workers, and resolves the modules its launch's module set names, captures its graphs and reports `Serving` with its generation limits, video denoiser description and scheduler count (or `Parked`, when its launch names the engine it succeeds), or `Failed` with the error. The daemon serves HTTP only once its engine serves. Every request passes the leader's hold (`RequestHold`): while an engine serves it goes straight to it, and while none is it waits; once the engine is lost and none takes its place, held and later requests fail with the reason and `/health` answers `503`.
- **Requests.** A submission carries tokenized requests under the daemon's identities. The engine routes each to the scheduler the scheduling policy's `route` decision names — on a node with several data-parallel schedulers, the control thread's own instance of the epoch's policy package decides from the request and each scheduler's requests in flight and liveness, and a decision naming no live scheduler of the node is the policy's failure — and answers `Accepted`, naming the scheduler, or ends it at once with a `Rejected` event. Every event names its request. A request's events flow under a credit window: the daemon states in its welcome how many events of a request it takes ahead of its consumption reports (`event_window`, 64 for this daemon), and the engine sends a request no more events beyond those the daemon reports consumed, so a slow client holds back its own request only.
- **Commands.** Per request: cancel (the client went away), stop (the daemon's decoder matched a stop string), acknowledge (this many public tokens complete no stop string), abort and consumed. For the engine: shutdown, which ends every request as aborted, closes the workers and exits. Its lifecycle commands, `Promote` and `Drain` (after which it admits nothing more, reports `Draining`, steps its running requests until each ends or the drain's deadline ends it as migratable, and parks), travel on the process interface (Epochs).
- **Migration.** A token request can move between engines. Its engine ends it with a `Migratable` event, naming the cause (a drain or a loss of the ranks that held it), after every token it generated there; the leader's `Migrator` submits it again through the hold, carrying them, to the engine that serves next. The tokens are every token the engine counted as generated, in order, carried as `generated_token_ids`. The request continues its prompt with them: the engine computes their cache as part of the prompt, reusing the pages of them its cache holds as for any prompt, and generates after the last of them at the position the request had reached. Every token counts as generated: against the token limit and `min_tokens`, in the penalties and bad words, and in the request's usage, which charges only its own prompt as prompt. The daemon keeps its own state (the detokenizer, the stop-string matcher, the response being assembled), so the client reads one uninterrupted stream. A request that names no seed is given one at random when the daemon receives it, as every request is, so its draws, keyed by its seed and token positions, repeat on every engine. Migrations caused by a drain are not counted; a request survives `migration_config.max_migrations` migrations caused by losses. A video request migrates at a denoising step boundary (below).
- **Recompute preemption.** Admission reserves what a prompt takes and not what a request generates, so a cache filled while its requests decode leaves some of them unable to grow. The step's assembly notes each request it cannot grow with the units its growth needs, and the next step's preemption asks the policy for a victim (its `preempt` call, `crates/engine/src/scheduler/policy.rs`): the default policy names the migratable resident of the lowest priority admitted last, as vLLM's recompute preemption does. The victim ends as migratable, and the `Migrator` submits it again with its tokens; it resumes from the pages it published, and its partial last page is copied into a unit of its own before its first forward. The shortage subtracts the free units and the units of requests already leaving, so no extra victim is named, and admission waits while a resident is starved. A request whose held and needed units exceed the whole cache ends with the length it reached. When every running request is starved, no batch is in flight and no request is leaving, the scheduler recomputes the one admitted last itself (`crates/engine/src/scheduler/schedule.rs`).
- **Video preemption.** An engine preempts a video request the same way whatever preempts it: a park for an epoch change, a sleep, an in-place weight update, or a loss of its ranks. The request offers no further call, and its calls in flight complete, which ends it at a step boundary; a request whose denoising is scheduled whole finishes instead. A trajectory past its first step and short of its last is then written to the host latent pools of its denoising ranks (see Storage and device storage), unless its ranks were lost, and the request ends `Migratable`, naming the steps stored (`denoised_steps`, zero for none) and the engine's record of where their pages lie and how each denoising rank laid its part of the samples out (`stored_layout`). The migrator gives every video request the identity of its trajectory (`Trajectory::id`) when it first submits it, and submits it again naming the steps stored and the record, or what it named before when the engine stored none. The engine admits a request that resumes a stored trajectory before every request that starts one, and pins the pages the record names before its latent preparation, which prepares the request as for step zero (its prompt's and conditions' encoder outputs read from the host encoder pools where another admission stored them and encoded otherwise, its prompt refined and its noise drawn, which compute what they computed before) and then copies the stored values into the bank it initializes, laid out in its own rank's pages whatever parallel configuration stored them, and commits the trajectory at the stored step, from which it denoises the steps left; when a page is missing, it starts from noise. A trajectory's state at a step follows from the request alone (its noise from its seed, and an Euler step from the samples and the step), so both continue the trajectory the uninterrupted request takes, and a resumed request's video is that request's.
- **Media.** A video request's condition media and its generated video each live in a sealed anonymous memory file (`proto::MappedMedia`), which has no name and which the kernel frees with its last descriptor and mapping. Over a Unix socket the file travels as a descriptor beside its frame (`SCM_RIGHTS`): each condition's beside the request's `Submit`, in condition order, and the video beside its artifact event; over TCP its bytes precede the frame in bounded parts (`MediaPart`), which the receiver writes into a memory file of its own. The engine's media reader decodes the conditions from their files, and the daemon maps the video read-only and serves its bytes.
- **Statistics.** Each scheduler's statistics travel once a second as a snapshot the daemon exports as metrics.

### Epochs

An epoch is one engine build with its build configuration, executed: an engine process per node, its workers, their communicators, CUDA graphs and the storage they created. The daemon moves the deployment to another epoch without failing a request (`PUT /admin/config`; `crates/daemon/src/updates/` decides what a change needs and holds the update's phase machine, `updates/update.rs`; `docs/admin.md`). The epoch's number keys its ranks' storage at the Storage Server, and its engines are started by their node's daemon at a launch generation of the deployment's group and rank. An update in its epoch form covers the whole deployment, every node, main process and independent replica of both epochs, which need not have the same nodes, main processes, schedulers or ranks, and runs these phases, each ended by the engines' acknowledgements:

1. **Preparing.** The apply prepared the target's module set at the Build Server of every host the target runs on before this phase starts (see The Build Server). Every node's daemon starts the target's main processes for its host, every target replica's scheduler node and peers alike, each from a launch file the leader made (`EngineControl::target_world`) that states the epoch's module set, the engine it succeeds and its launch generation; a world of several hosts meets at the two sockets its scheduler node reserved, as at a start. Each engine opens its session with its host's buffer pool (`Open`), maps the weights it shares, resolves its modules, captures its graphs on its own graph pool, parks and reports `Parked`. Its preparation's transfers yield to the serving epoch's steps (`update_config.transfer_slowdown`), and serving goes on. A target that fails here is stopped, and the update is abandoned with nothing changed.
2. **Switching.** Both epochs step, and the buffer pool keeps them from writing one block (`specs/buffer-pool.md` §9). The leader sends `Promote` to every target engine, which opens admission and reports `Serving`; from the first `Serving` the daemon routes every new request to the target, through the target engine's routing policy, while the serving epoch goes on with the requests it holds, so no request waits. Once every target serves, the leader sends `Drain` to every serving engine with the deadline `update_config.drain_s` from then, and with `shrink` when the target's layout differs: the engine admits nothing, steps its running requests until each ends by itself, and at the deadline ends the rest as migratable, a token request with its blocks committed under their keys and its partial last block too, a video request at its next denoising step boundary with its trajectory saved. The daemon resubmits each to the target. With `shrink` the draining engine gives its device regions back by `Resize` as its requests end, and the target, promoted with `grow`, grows its own from the quota as that memory frees, one segment at a time. Every serving engine's `Drained` ends the switch.
3. **Trial.** The target serves on trial, with the previous epoch kept as `update_config.previous_epoch` states: drained and parked, or its processes exited and its weights kept, on the GPUs or in host storage. A fault of the target, a threshold of `update_config.rollback`, the deadline the apply stated or a rollback by decision runs the switch the other way: the previous epoch is promoted again, or started anew on its weights when its processes exited, new requests return to it from its first `Serving`, and the target then drains with the same deadline; a target that failed is stopped instead, and its requests end as migratable from what they committed.
4. **Committed.** The decision is recorded first; the previous epoch's processes then exit, and the claim of the target's epoch retires the previous epoch's storage at the Storage Server on every node either epoch used. What the previous epoch committed stays in the buffer pool for any epoch whose keys reach it, until ordinary eviction.

Nothing of the cache is handed over: the target learns the buffer pool's tables and cache by `List`. Two epochs of one layout name the same regions, so a request that migrates to a target of the same layout and numerics finds its committed blocks by their keys at once, pinning its full blocks and copying its partial last one: it costs one admission and that copy. The cache's size is no layout: a target that states another device capacity (`kv_cache_config.max_tokens`) or host pool (`host_gib`) states its sizes in its session at its start, and resizes the regions the two epochs share to them by `Resize` only when it is promoted, within the numbering the first epoch gave them; the serving epoch keeps its capacity while the target prepares, and an update abandoned before its switch resizes nothing. Each promotion resizes the regions to the promoted epoch's sizes, so a rollback that promotes the previous epoch again restores them and a commit keeps the target's. A shrink never takes a private or pinned block: while requests hold units past the new size, the scheduler allocates none of them and shrinks the region again as they come free. A target of another layout has regions of its own over the same device memory and reaches the serving epoch's blocks only through the host tier by keys the two share, which by default they do not; a target of other numerics, or one applied with `in_flight = recompute` (`Promote.recompute`), computes a migrated request's state again from its tokens. The daemon decides that the layouts differ when the two epochs' replicas differ in their parallel configuration, devices or number, their slot count, their KV layout or their graph buckets.

While both step, two epochs' contexts share each GPU and its time; the drain's deadline bounds that period. The update reports how long its switch took (`switch_ms`).

### The channel

An epoch whose worker groups have ranks on several hosts runs one main process per host: the scheduler node's, on the deployment's engine host, which holds rank 0 and the schedulers, and a peer on each other host, which holds the deployment's ranks on that host (`world_hosts`, `crates/daemon/src/engine/control.rs`; the deployment numbers its ranks over every group in the order the deployment file states them, and each process is launched with the first rank its host holds, in a world of every rank of the deployment: a media process serves every rank placed on its host wherever it lies in that numbering, and a text process the consecutive ranks from its first, one per device). A peer may hold ranks of one group spanning hosts, such as a tensor group of two hosts, or a group of its own, such as a decode group on another host than its prefill group. The scheduler node's main process and each peer exchange the messages of the peer link over one stream connection per peer (`crates/engine/src/executor/peers.rs`, the messages in `peers/messages.rs`). An epoch whose group lies on one host has one main process and no channel.

- **Start.** Once every host of the epoch prepared its module set (see The Build Server), the leader's daemon starts every process of the epoch together (`EngineControl::start_world`). It first reserves two routable sockets on the scheduler node (`Reserve`): the channel's listener and the rendezvous of the ranks' host group. The scheduler node's process inherits both (`Spawn::inherit`); every launch names their addresses and the scheduler node's engine number, and the scheduler node's states how many peers it accepts (`EngineArgs::world`). The launch travels in the spawn (`Spawn::launch`), and the daemon of the node that starts the process states its own Build Server in it and passes it to the process as the sealed memfd it inherits, so a process starts the same way on any node. Every process says hello on the leader's request interface; only the scheduler node's carries requests, and the daemon's client of the engine is the scheduler node's, which holds its peers' and ends with them.
- **Registration.** A peer connects once to the scheduler node's listener, which is live before any process of the epoch starts, before it loads anything and sends its `PeerRegistration`: the first rank it serves, the scheduler node's engine number and its build (the package version and a digest of the sources). The scheduler node accepts every peer its launch counts before its ranks load, refuses a registration of another engine or another build, and answers `PeerAccepted`; a peer that does not register within the epoch's join bound (`worker_config.join_timeout`) fails the start. The ranks of every process then form the deployment's host group, as members numbered by their group rank (`load_ranks`, `crates/engine/src/process/ranks.rs`, and `crates/engine/src/parallel.rs`): the scheduler node's process serves the rendezvous, every other process binds a listener, states it with the members it holds, and receives the endpoint of every member's process, and each member then connects once to every lower member of another process; two members of one process are connected by a socket pair. The ranks form their communicators over the host group.
- **The session.** The scheduler node opens the epoch's session with the buffer pool of its own host and relays the layout and the answer to every peer (`MainProcessRequest::Session`): the regions' numbers every completion, block table and copy names are that buffer pool's, which holds the tables of every group, whichever host its ranks are on (`specs/buffer-pool.md` §15). A peer opens the session's host regions alone at its own host's Storage Server, where each of its ranks takes its part of each host region and which closes that session once the epoch's processes have left. The ranks of every process then open over the relayed answer at once, mapping the segments it states and creating the rest, and warm up together. Each peer answers once its ranks are warm (`MainProcessResponse::Placed`): its Storage Server's endpoint, the segments its ranks created, where each rank's units lie, and what its ranks serve per group. The scheduler node grants each segment once every rank of its region, here and on peers, created the same, states where a peer's ranks keep their units at its own buffer pool (`PlaceRemote`), and schedules each group within what all of its ranks state. A peer that fails its start, or whose process exits or loses its host before it answers (its link closes), fails the scheduler node's.
- **Batches.** The connection carries the one batch type (`crates/engine/src/batch.rs`). A batch names the worker group it runs on (`Batch::group`). The scheduler's executor (`crates/engine/src/executor.rs` over the node's `Route`) numbers it among the group's jobs and hands it to every device of its own node that is a rank of that group and, as `MainProcessRequest::Submit` (or `Shadow`) in a frame the link numbers (`ToPeer`), to every peer that holds ranks of the group; the completions of the buffer pool a group's device block tables are fed by (`Map`) and the requests its ranks apply and stamp (`Stamp`) travel the same way. The peer hands each to its ranks of the group in the order it arrived and answers `MainProcessResponse::Result` with their `BatchOutput`, the requests they return and the last job they ended, or `Error`, in a frame of the same number (`FromPeer`); a batch that failed on the peer after copies had started with it returns their `Finish { ok: false }` and the last job ended, so its copies are given up as a local rank's are. A batch of a host phase whose rows name no rank (a media request's reading, encoding and muxing) runs on one rank of each process that runs it, the first of the process's ranks of the group that serves its phase: a video encode round in every process that holds ranks of the group, each encoding the units its own ranks decoded into those units' blocks there, and any other host batch once, on the scheduler node's ranks when one of them serves its phase and otherwise on the first peer that holds ranks of the group. The group's batch completes when every rank's did, a peer's failure fails it, a call any rank that ran it answered as failed fails, and the group's `completed` is the smallest over all of its ranks. Each end's connection is owned by one link thread, which sends what the other threads queued, reads what arrived and settles it; on the peer a responder thread waits for each job in the order it was handed and hands its answer back.
- **Operations.** Every operation of the data plane that acts on the ranks (`crates/engine/src/process/binding.rs`: segments released, created and counted, sleep and wake, graph pools suspended and restored, the kernels the cache and the state launch, the reservation in the GPUs' quotas, a weight update's pairing, load, staging and binding, an expert commit, the daemon's named operations) reaches the peers' ranks as `MainProcessRequest::Data`, which each peer runs on its own ranks, one at a time in the order they arrived, and answers with `MainProcessResponse::Operated`, the JSON of the operation's value. The scheduler node joins the values over every rank: segment tables must agree, rooms are listed, and the segments that fit are the fewest any rank has room for. A boundary operation is ordered against the batches of every rank by the schedulers' pause, and one that fails on a peer part of the way ends the epoch as a local rank's does. A weight load's replacement stays in each process.
- **Reports.** The scheduler schedules each group within what all of its ranks state they serve (`Capacity`: its phases, slots, buckets and cache groups), joined over the ranks of every process (`MainProcessResponse::Placed`). The pages, encoder outputs and trajectories every rank computes are keyed by the weights of every rank of the deployment, in rank order, which the scheduler node reads from its peers.
- **Generations.** The daemon commands every process of the epoch itself, over each process's own process interface (`crates/daemon/src/updates/update.rs`): each command of a generation update (`Prepare`, `Switch`, `Commit`, `Rollback`) goes to every process before any acknowledgement moves the phase. Each process prepares from its own host's Build Server; the scheduler node's preparation waits for every peer's before its shadow pass reaches the peers' ranks and, once the pass ended, adds to its own the operators the peers' ranks could not compare, in their preparation and on the shadow batches that reached them (`DataOperation::Uncompared`). A switch, a commit and a rollback act on the ranks of every process in the order of every group's jobs: the scheduler node hands each to its ranks and to every peer's (`MainProcessRequest::Switch`, `Commit`, `Rollback`) between the same two batches of each group, and a peer acknowledges its own daemon's command at once, the scheduler node's acknowledgement following every rank's.
- **Lifetime.** A connection's close is the only death signal of the process at its other end: the link marks it lost and wakes the control thread, whose next pass ends the process without its orderly close (its devices' collectives wait for ranks that are gone, so no close of its workers ends; a process whose control thread does not reach that pass is ended by its daemon, which replaces the failure domain). A peer's loss therefore ends the scheduler node's process, and the scheduler node's ends every peer; the requests in flight end with the scheduler node's request connection, which the daemon reads as the engine's loss and migrates them on. The scheduler node's orderly end closes its links with a `Close` frame first, which each peer reads as the epoch's end: it ends in order too.
- **Frames.** A frame is the one frame layout of every protocol of the workspace (`service::frame`): the payload's length and its descriptor count, each a little-endian `u32`, then the payload, here one message in a serde binary encoding (MessagePack); over TCP a frame carries no descriptor. The main processes are built from one workspace and replaced together, so the message types are the protocol's only definition. A frame carries a message of any size its `u32` length states; no launch setting bounds it further.
- **Waiting.** Each side blocks on its socket together with one local wake descriptor, which its own threads fire for work that did not arrive on the socket.
- **Processes.** The scheduler starts no process itself. Its daemon starts each node's main process on the node its parallel configuration names, through the node's daemon, reserves the sockets the scheduler node inherits, and claims the deployment at a node's Storage Server (an engine claims it at every node's, those that run none of its peers included, so that it retires another epoch's storage and keeps an epoch's weights wherever they lie, and each peer's launch names the other nodes' servers, whose epochs' weights it may receive); the leader serves its own node and forwards the rest to the node's daemon over that daemon's join connection, and every exit comes back the same way, naming the node, group, rank and launch generation. These messages are the process interface (`crates/proto/src/process.proto`), Protobuf of one version per release, which the daemon checks at each peer's hello and refuses another of with a typed refusal; the hello and the welcome are the one part no release changes, so that a peer of any version reads its refusal. A main process is its daemon's child, leads a process group of its own and dies with the daemon.
- **Data.** Prefix cache pages, latents and encoder outputs move between processes and hosts as Storage Server transfer tasks (see Transfers): a transfer, a prefetch or a put that touches a peer rank's units runs on that rank's host's Transfer Server or connector, which the scheduler node's Storage Server asks as a head of the deployment. Within one main process a media deployment's products pass in place. A product block lies in the product buffers of the ranks that back it, in their process's memory; a group that reads it in another process's memory receives it by a `Replicate`, which the scheduler submits once the writing call's output was applied, stamped by the workers of the groups that may hold its entry, and which the Transfer Server of the reading host runs from the run the writer wrote into the block's run there, or a run of the reading group's receiving region there; the reading call is offered only once it was answered `Replicated` (`specs/buffer-pool.md` §15, "A product read in another process"). The splice tail a decode round hands from one decoder rank to the next passes inside the call, over the decoder ranks' communicator.
- **Epoch switches.** An epoch switch starts every main process of its target, one launch per host, as a start does: the scheduler node's inherits the channel's listener and the rendezvous its node reserved, and every peer's names them (`EngineControl::target_world`). The leader commands every process of both epochs over its own process interface: `Promote` to every target process and `Drain` to every serving one, each acknowledged by that process.

## The threads of a main process

A main process's threads are named by their role: the control thread, the readers of its daemon's interfaces, the operations thread and the work threads, the scheduler threads, the executors' waiters, the workers and the blocking pool (`crates/engine/src/process`).

| Thread | One per | Blocks only on | Does |
| --- | --- | --- | --- |
| Control thread | process | One `Select` over its inbox and every scheduler's outputs, until the earliest of the watchdog's deadline and the next metrics second | Holds the engine's lifecycle and generation update, the requests and their event streams; serves the request interface's frames and the process interface's commands, routes and submits requests, writes events, states and reports, starts jobs, and reports a job that stopped making progress |
| Request readers | daemon front | A read of its request connection | Hands each frame to the control thread's inbox, then the front's close |
| Command reader | process | A read of the process interface | Hands each command to the control thread's inbox, then the interface's close |
| Start | process, once | The rank start | Loads the ranks, opens the session with the Storage Server and starts the schedulers, and hands the started epoch to the control thread |
| Operations | process | Its job channel, then the job's own waits | Runs, one at a time and in order, every job that pauses the schedulers or changes the ranks' device memory (a switch, a commit, a rollback, a weight update, sleep and wake, a flush, an expert commit, making room, growing, a release after a shrink, the start and the end of a drain), so two pause sequences never interleave; since a scheduler's `Resume` ends its drain as well as its pause, none that pauses the schedulers starts while the engine drains |
| Work | job beside the batches | The job's own waits | A preparation, an adapter, a profiling change, a drain's wait, an attach |
| Peer links | process, on an epoch of several hosts | One connection to another main process of the epoch (`crates/engine/src/executor/peers.rs`) | The scheduler node's: sends its schedulers' batches, a generation's switch, commit and rollback and the data plane's operations to a peer and settles their answers. A peer's: runs them on its devices, the operations one at a time on a thread of its own, and answers them. A loss tells the control thread, which ends the process; the scheduler node's orderly close ends a peer in order |
| Scheduler threads | DP rank | Its inbox and, after a step that formed no batch while it waits for the buffer pool, its queue pair's doorbell, which the buffer pool rings only while the scheduler sleeps (`crates/storage/src/queue.rs`) | Request state, the scheduling mechanism, each step's batches and the buffer pool's queue pair |
| Doorbell relays | DP rank | Its scheduler's queue pair doorbell | Forwards each ring to its scheduler's loop, which cannot wait on a descriptor beside its inbox |
| Executor waiters | worker group | The completion of the group's oldest job | Waits for each job a scheduler's executor handed the group's workers, in order, and posts its completion to the scheduler (`crates/engine/src/executor.rs`) |
| Workers | device | The device's work | The only issuer of work on the device's streams: forwards, graph replays, copies, captures and rebinds, in the order of its job queue (`crates/engine/src/worker.rs`) |
| Blocking pool | pool | One kind of host work | Media encoding and muxing, and condition media reads (`crates/engine/src/runner/thread_pool.rs`) |

Threads exchange messages only. The control thread never waits for a job, so a slow launch, a driver call that waits on the device or a job that does not end does not keep it from serving the channel, handling a cancellation or reporting status. The worker is the only issuer of work on its device's streams, so each stream's order is the order of its job queue; it posts a job's completion once it has issued the job's work, not once the device has finished it, and storage a job used is read, rewritten or freed afterwards only behind something that waited for the device (a read in the job, a stream wait the job recorded, events the job completes after, or the fences that retire storage). A runner is called only on its device's worker thread and only one job at a time, which is why the runner trait's job methods take `&mut self` and carry no synchronization (`crates/engine/src/runner.rs`).

Blocking host work runs on bounded pools of threads (`<pool>-<index>`) that each serve one kind of work: media. Signals, a video runner's host reports and the lifeline are dedicated threads (`crates/engine/src/runner/thread_pool.rs`, `crates/engine/src/main.rs`).

## The numerical library

The mathematics is Rust, and one forward runs the chain `runner → model → layer → operator → kernel` over three layers, as in PyTorch. `crates/tensor` is the tensor library: `Tensor`, `DType`, `Shape`, `Layout`, `Device` and `Storage`, the CPU backend and the open interface of a device backend; it knows nothing of UniServe. `crates/ops` is its device side: the CUDA and meta devices, the execution context a forward computes under (`ops::context`), the allocator of tensor memory, the collectives, and the operators, each an `ops::Op` with a name, a descriptor of the values one compilation bakes into a module, whose canonical text is its descriptor key (`ops::Key`), and its launch code; the kernel packages that fill an operator live under `crates/ops/kernels`, one per operator and backend. `crates/nn` is the shared computation library: the modules a model composes (`nn::modules`: `Linear`, `Embedding`, `LmHead`, `RmsNorm`, `LayerNorm`, `Mlp`, `MoE`, `SharedExpert` and their parallel forms), the fused operators and stateless functions (`nn::functional`), the flow-matching schedules and solver formulas (`nn::diffusion`), the tiles of a VAE raster and the tiled encode (`nn::vae`), checkpoint reading, weight loading, quantized formats and the fusion of a weight adapter into a checkpoint's tensors (`nn::checkpoint`, `nn::var_builder`, `nn::weights`, `nn::quantization`, `nn::adapter`), and both directions of the model library's boundary: the capability traits a model implements (`nn::capability`) and the family value execution loads it through (`nn::family`). `crates/models` holds the model families, one module each, with its configuration interpretation, checkpoint mapping, mathematical layouts and neural composition: `models::qwen3` (the Qwen3 decoder, Qwen3-MoE and the Qwen3.5-MoE language model with its drafter, the Qwen3-VL encoder and vision tower), `models::qwen4_exp` (Qwen3.8 Flash Next, which shares the vision tower and configuration readers of `qwen3`) and `models::minimax_h3` (MiniMax-H3 and FastH3, whose text encoder is the Qwen3-VL model). `crates/processing` holds request processing: the interfaces a family supplies to the daemon, the family-neutral rules a video request is processed with, each parameterized by values a family states (the frame rule `processing::FrameClips`, the canvas rule `processing::CanvasRule`, the cover crop `processing::cover_crop` and the resampled length of a track `processing::resampled_len`), and, as a stage beside each model's numerics, a family's own request preprocessing: the Qwen-VL processor rules that size media to patch grids (`processing::qwen_vl`) and MiniMax-H3's request rules, conditioner prompt and processor (`processing::minimax_h3`), whose request-level facts (output clock, frame rule, canvas rule, reference limits, condition-row arithmetic) the model family reads from there. `crates/engine` executes what the models compute.

What the library supplies to a model is numerical. A model computes with tensor operations and `nn` modules on tensors and receives nothing of the runtime: the worker builds one execution context per runner (`ops::context::Context`: the stream, the generation of loaded kernels its operators resolve their modules from, the allocator region its forwards' tensors come from, the input buffer, the communicator of the rank's group and the expert exchange) and installs it on its thread around a model call, as PyTorch's current stream and graph memory pool are the thread's. A module cannot create a stream, allocate device memory outside the context's allocator, capture a graph or select a package. A partitioned module reads this rank's share from its config (`nn::collective::Split`: this rank's index and the member count) and communicates only through the model-facing collectives of `nn::collective` (`all_reduce`, `all_gather`, `all_to_all`, `broadcast` and the started forms, each along the axis of its partition the module addresses with `along`); a family receives the deployment's partition as `nn::family::SequenceSplit` for a sequence-parallel text model and `nn::family::DenoiserSplit` for a denoiser. A module states its forward as a profiler range (`nn::profiler::range`) with its class and the path its builder loaded it under, the deployment chooses which modules carry fence probes (`docs/profiling.md`), and nothing a forward computes depends on a range. A model loads itself through `nn::VarBuilder`, which names each tensor under the module path as the reference model names its parameters, while `nn::WeightLoader` converts a tensor once into the layout its reading operator declares and publishes it to retained storage. On tensors of a GPU a forward launches kernels; on meta tensors under a meta context it checks its arguments, states the kernel it would launch and computes nothing, which is a profile run: the same `forward` is both. The worker creates the communicator, selects the stream, owns the allocator's region and orders the collectives of concurrent invocations.

What a model supplies to execution is its capabilities (`nn::capability`), and execution calls these and nothing else: `CausalLm` embeds input ids (`embed_input_ids`), runs the decoder stack over a `TokenBatch` and the paged cache `KvCache` (`forward`), projects hidden rows onto the vocabulary (`compute_logits`) and joins an expert step it has no tokens for (`join_expert_step`); `Drafter` proposes draft tokens over its own cache (`cache`, `forward`, `state`, `forward_stateful`, `logits_rows`); `Encoder` turns a prompt and the vision content it presents into conditioning rows (`layout`, `encode`); `Vision`, which a causal language model with a vision tower states through `TextModel::vision`, sizes an image by its processor rule, encodes it into rows of the hidden width and states the rotary coordinates of its rows (`image_grid`, `patch_format`, `image_rows`, `max_image_rows`, `position_axes`, `image_positions`, `encode_image`); `Denoiser` lays a request's latents out, states its fixed schedule, draws its noise, prepares its latents and conditioning and evaluates one step (`layout`, `schedule`, `draw_noise`, `condition_pieces`, `draw_condition_noise`, `prepare_latents`, `prepare_conditioning`, `forward`); `Decoder` turns latent frames into a clip of pixels or a soundtrack and states where a clip reads its latents and what it writes (`clip_start`, `layout_of`, `gather_latents`, `latent_rows`, `pcm_window`, `decode`); `Splicer` joins decoded clips into one timeline (`element_type`, `pixel_norm`, `splices`, `splice`). Every input and output is a borrowed view or a small plain value: no request identity, sampling state, pool slot or execution observation crosses the boundary, and a model's mathematical diffusion schedule and solver stay computation while selecting and committing a request's steps stays execution.

A model reaches the rest of the system through one family value, `nn::family::Family`, with two sides and nothing else. Its request side (`Family::request`, a `processing::Family` of `crates/processing`) names the root file its checkpoints declare their class in, the classes it claims there, and what request processing serves. To execution it states its model (`Family::model`): a `TextFamily` that opens a checkpoint and loads a causal language model (`TextModel`, a `CausalLm` that also states its widths, its cache shape and its routed experts), or a `VideoFamily` that opens a pipeline and loads its blocks (`VideoModel`: the text encoder, the denoiser, the video and audio decoders and the splicer, each absent when the rank does not place it) with the media format its conditions are read in. The model states the checkpoint's mathematical facts and receives only the deployment's mathematical partition (`Split`, `SequenceSplit`, `DenoiserSplit`) and serving bounds (`VideoServing`); it holds no runtime object. The main process (`crates/engine`) and the daemon resolve a checkpoint by what its root files declare, under one rule (`processing::Registry::resolve`: each family claims the classes the root file it declares in names, `architectures[0]` of a transformers checkpoint's `config.json` or `_class_name` of a diffusers modular pipeline's `modular_model_index.json`, and exactly one family must claim the checkpoint); the main process then dispatches by the family's model and the capabilities it implements; it names no model. To request processing the family states what it serves (`processing::Family::serving`, a `processing::Serving`): a chat profile (the reasoning and tool-call formats its outputs write) or a video family that binds a `VideoProcessor` once the workers have described the placed denoiser. The processor checks a model-agnostic video request (`VideoSpec`), processes it into a `processing::VideoInput`, with each condition in the shared vocabulary of `proto::video`, and reports the capabilities `GET /v1/capabilities` publishes; the daemon names no model either. Everything a model does not own, scheduling, admission, placement, capacity, storage, streams, graphs and media transfer, is the shared infrastructure of `crates/engine` and `crates/daemon`. Each executable names the concrete models in one place. The engine executable (`crates/engine/src/main.rs`) lists the families its main processes load and builds the `nn::family::Registry` from them. The base executable links no model: its daemon serves the `processing::Registry` of `processing::FAMILIES`, the request sides `crates/processing` states (`processing::qwen`, `processing::minimax_h3`), and each numerical family holds its value of that list. Adding a model is its module in `crates/models`, its request side in `crates/processing`, and one entry in each list.

### Runners

A runner serves one stage a rank holds (`crates/engine/src/runner.rs`): it holds its model through a capability trait of `nn` and dispatches on nothing else, owns its input tensors at fixed addresses and its `Graphs`, which hold the execution context its forwards compute under. There is one runner per capability, and everything the runners share, the profile run, capture, replay, the input buffer, generations and the shadow of a changed operator, is `Graphs`'s (`crates/engine/src/runner/graphs`), which reaches a runner through the `Runner` trait alone: `Runner::buckets` states what warm-up captures, and `Runner::forward` is the one function that is run on the meta device, captured, and run again before each replay.

| Runner | Capability | Serves |
| --- | --- | --- |
| `CausalLmRunner` (`runner/causal_lm.rs`) | `nn::family::TextModel` | A causal language model's batches: prefill, decode and verification, served in captured buckets, with the request slots and the KV cache its steps advance |
| `VisionRunner` (`runner/vision.rs`) | `nn::capability::Vision` of a `TextModel` | A token request's image encoding, into the encoder output its prefills read |
| `EncoderRunner` (`runner/encoder.rs`) | `nn::capability::Encoder` | A video request's text encoding |
| `DenoiserRunner` (`runner/denoiser.rs`) | `nn::capability::Denoiser` | A video request's latent preparation and its denoising steps, over its state in its slot's row |
| `DecoderRunner` (`runner/decoder.rs`) | `nn::capability::Decoder`, with `nn::capability::Splicer` for a video | A video request's decode of its clips and its audio track, from the latents in the rank's media products |
| `MediaHost` (`runner/media.rs`) | none | A video request's host work: reading its condition media, encoding its video and audio, muxing its artifact |

Each worker holds the runners of the stages the deployment places on its device; they share the graph tables, the input buffer and the staging rules and differ in the capability they call and in what a bucket of theirs means (`crates/engine/src/runner/buckets.rs`).

### The profile run

A main process installs exactly the kernels its forwards launch, and learns them from the forwards themselves rather than from a second enumeration written beside the model. At load, each runner's forward runs for every bucket it captures and every bucket it runs eagerly (`Runner::eager_buckets`) under a meta context: it launches nothing and yields the bucket's launch table (operator, descriptor key and module path of every launch, in launch order), the peak of the allocator region, the bytes of its host-to-device copies and the most one paired call of it carves from a shadow region (`crates/engine/src/runner/graphs`). The keys are what the engine asks the host's Build Server to select packages for (`cover`) and installs in the epoch's first generation, and the peaks and shadow bytes are what a device's memory is divided by. A key a device launches that its profile run did not state is a refusal of the generation, never a key learned and installed on a second attempt. An update changes implementations and never the set of descriptors: the engine selects again for the keys the serving generation holds and installs the operators whose selection changed. `uniserve keys` (`src/keys.rs`) runs the same start of each main process to the end of its profile runs without serving (`engine::record`) and prints the union of the keys, the key list `uniserve build-server build` compiles into a store before a deployment serves (`configuration.md`).

### Computations and their batches

A block's phases are served as jobs on the device's worker (`crates/engine/src/worker.rs`): a scheduler's executor hands it a batch under the number the engine gave it among the group's jobs, and the worker takes its jobs one at a time in the order they were submitted. A batch is plain data (`engine::batch::Batch`, `crates/engine/src/batch.rs`): one phase of one step on one worker group, the requests it advances, one call each, the host columns a token phase's runner copies into its input tensors (`engine::batch::Columns`), the rows of a media phase (`engine::batch::MediaRow`) and the requests the group starts (`engine::batch::NewSlot`). It holds no device address, block table, copy list or free list: a row names a request's memory by positions in the request's tables at the buffer pool, and the worker computes every address from its device block tables (`crates/engine/src/memory/tables.rs`), which only the buffer pool's completions feed. `Batch::validate` states the rules that span its parts, and a `BatchOutput` answers a batch with one `CallOutput` per request, in the batch's order. For every batch the worker hands each runner the changes of the device block tables, starts the queued copies the copy budget admits, and calls the batch's runner, which chooses the smallest captured bucket that holds the batch (`crates/engine/src/runner/buckets.rs`; a shape no bucket holds is refused), writes its input tensors from the columns and the tables, and replays the bucket's graph or runs its forward eagerly. A failed job fails its batch and the process keeps serving; a sticky device error fails every later job, and the main process is replaced.

**Token steps.** A step's outputs lie in its graph's memory, which the next replay of the bucket writes again, so each step's outputs are copied to page-locked host memory by one batched copy on the runner's stream right behind the step, and an event is recorded behind the copy (`crates/engine/src/runner/causal_lm/readback.rs`). A token step takes two turns of the worker's queue: the first issues the step, the second reads its outputs once that event completed, so the worker issues the next batch while the device computes this one. Values the next step reads, a decode's selected token, stay in the slot tables on the device (`crates/engine/src/runner/causal_lm/slots.rs`), which the step's commit advances.

**Media steps.** A media batch names each call's request, slot and inputs in its rows. Its runner reads and writes the request's products and encoder outputs in the blocks the rank's device block tables hold (`crates/engine/src/memory/buffers.rs`), and a denoising request's trajectory lives in its slot's row of the rank's trajectory rows from its latent preparation to its last step. Host work, a media request's reading, encoding and muxing, runs on the media host's thread pool (`crates/engine/src/runner/thread_pool.rs`) between two turns of the batch: the first starts it, the second writes it out, and the batch's number stays open meanwhile.

### Attention

Three attention operators are built from `crates/ops/kernels`, one package per implementation under `<operator>/<implementation>`: `paged_attention` (`triton`, `trtllm`), `dense_attention` (`f32`, `fa4`) and `sparse_attention` (`wgmma`, `tcgen05`, `flashinfer`, each named by the instruction set it is written for and building for the targets that have it). Which package fills an operator's descriptor keys is the Build Server's selection (`cover`), which prefers the backend the deployment names for the key's phase: `attention_backend`, or `prefill_attention_backend` and `decode_attention_backend` when they differ (`proto::config::EngineConfig`); the engine records the selection's answer and chooses nothing itself (`crates/engine/src/modules/select.rs`). A deployment that names a backend no installed package provides fails at startup with that name.

## CUDA graphs

A worker's runners capture and replay every graph they serve, through `Graphs` (`crates/engine/src/runner/graphs`). A captured forward may hold graph breaks (`ops::graph_break`), whose work the replay performs on the host between two captured segments. A runner's region is one range of device memory: the block of its input tensors at fixed addresses, then the region of the context's allocator, which is emptied at the start of every forward, so a forward of one bucket receives the same addresses when it is captured and whenever it runs again.

- **Capture.** At warm-up each bucket's forward runs eagerly once over idle inputs (`Runner::idle_inputs`), so kernels compile outside capture, and is then captured with its launch table, its input copies and its output tensors (`crates/engine/src/runner/graphs/capture.rs`). Each runner captures its buckets largest first, and every rank of a group captures the same buckets in the same order, because capture includes collectives.
- **Replay.** `Graphs::prepare_inputs` takes a slot of the input buffer, lets the runner write the bytes of its input tensors and, when the graph has input copies, runs the forward under a meta context over the same region, so the host values the model computes land in the slot at the offsets the capture recorded; `Graphs::replay` then issues the slot's copies as one batched copy and launches the graph. Nothing is called back from the stream or placed in a graph as a host callback (`crates/engine/src/worker.rs`).
- **Buckets.** A runner keys its graphs by buckets (`engine::runner::buckets::Bucket`): the batch's variant, its rows and tokens and, for a media computation, the extent it is captured for. A batch is served by the smallest captured bucket that holds it, never a larger one, and captures run largest first, so smaller captures reuse the allocator blocks of larger ones (`crates/engine/src/runner/buckets.rs`).
- **Policy.** Every bucket a runner states is captured at startup, and a bucket it states as eager is run eagerly; once startup seals the graph tables, a shape without a resident graph is refused.
- **Generations.** A new generation of kernels is prepared beside the serving graphs: a bucket whose launch table is unchanged is rebound, any other is recaptured, and a bucket none of whose kernels changed keeps its graph; every capture, as at warm-up, follows one eager run of the forward with the kernels it captures. The switch takes effect between two batches, and the replaced generation's graphs stay until the trial is committed. Before the switch each operator whose kernel changed runs a paired forward (`Graphs::shadow`): the new kernel beside the one it replaces on the same inputs, compared under the operator's tolerance.

## Storage and device storage

| Owner | Allocated by | Contents |
| --- | --- | --- |
| Rust | the CUDA driver | everything that holds request state, is read or written natively, or crosses a process: the KV cache's planes, slot tables, product buffers and trajectory rows, forward inputs and outputs, pinned staging |
| Rust | `platform`'s allocator | graph pools and operator scratch: each a reserved address range whose physical storage Rust maps as the pool asks for segments (`platform::VirtualPool`, `crates/platform/src/pool.rs`; a device's regions are `engine::memory::graph_pool::GraphPool`), at addresses that stay fixed while any graph addresses them; scratch has pools of its own, so no graph's activations share its blocks |
| Rust | the CUDA driver's virtual memory | weights, in retained storages (below) |

A rank divides its share of the device's quota when it starts, among the weights, the runners' regions, the scratch pool, the storages sized by request slots and the KV cache's units from what remains (`crates/engine/src/memory/division.rs`). The quota is `⌊total × mem_fraction_static⌋` of the whole GPU, which every epoch of the deployment and the host's Transfer Server share, and the host's Storage Server keeps the GPU's quota of it (below): a rank's grant is the quota less everything the quota reserves beside its own process (the storages the server retains, another epoch's items, the Transfer Server's) and less what its process holds as NVML reports it, never more than the device has free. Exclusive storages a predecessor of the rank's scope and epoch left that no owner has taken yet count as free, and an owner that allocates new storage first releases them. Once warm, the rank reserves its graph pools and its process storage in the quota, which refuses them past the quota. Storage is organized by owner in `crates/engine/src/memory`:

- **KV cache** (`crates/engine/src/memory/cache/`): the KV cache's planes, pooled page tables, host tier and scratch pages, lent to a causal forward as `nn::KvPlanes`. The checkpoints of the cache layers a model keeps per request (a recurrent state) fill the pool's state group: its page `k` holds every such layer's state after token `(k + 1) * block_size - 1`, and a table names units only for the pages that hold one: a prompt call keeps the state at the last page boundary it reaches, a decode call at the boundaries that are multiples of `kv_cache_config.state_interval`. A request whose reused prefix ends at a boundary resumes from its checkpoint there; reuse ends only at a boundary whose checkpoint the device, host or storage tier holds, and checkpoint pages publish, offload and import as K/V pages do (`crates/engine/src/scheduler/memory.rs`). The live state is the runner's: a live and a checkpoint bank of every field of every recurrent layer, a row per request slot, bound into every forward (`crates/engine/src/memory/state.rs`); the batch names each row's checkpoint boundary and the copies around its forward, a restore from the checkpoint its reused prefix ends at for a request's first call on its slot and a checkpoint into the page after it, which the runner launches through `cache_block_snapshot` and `cache_block_scatter` (`crates/engine/src/scheduler/rows.rs`). A deployment that speculates (`speculative_config.num_draft_tokens`) keeps its drafter's K/V, the draft cache, in the pool's draft group: optional derived state, whose entry at position `i` is the drafter's evaluation of the target's hidden state at `i` and the token at `i + 1`, so a draft page's prefix hash covers the token after the page. The group keeps the pool's columns and plane size (each of `L` drafter layers spans `columns / L` columns of a unit), so an epoch that adds it maps its predecessor's segments. Reuse boundaries and admission count the required groups alone; a request's draft pages are allocated as far as free units allow, released from running requests before another request's required pages would fail, and published, offloaded to the host KV cache and loaded back as the other groups' pages are.
- **Media memory** (`crates/engine/src/memory/buffers.rs`): a rank's product buffer, its slots' trajectory rows and its parts of the host encoder and latent regions, lent by the runs of the rank's device block tables; a preempted request's trajectory is saved from its row into the host latent region and restored from it, laid out in the resumed request's own pages whatever parallel configuration saved it (`crates/engine/src/memory/latent/`).

### Pages, units and slots

Three words name storage across the scheduler, the worker, the Storage Server and the batch, each with one meaning:

| Word | Meaning | Where it is named |
| --- | --- | --- |
| **page** | The scheduler's allocation quantum of one cache group: `block_size` consecutive token positions of one request in that group, a cache manifest's `page_tokens`. A state group's page holds the checkpoint at its last position; a draft page's hash covers the token after it. A host copy of a page lies in a host region of the deployment's buffer pool | the buffer pool's blocks of a cache group's class (`storage::runtime`) and `block_size` count pages: "block" in those names is a page. The device block tables (`crates/engine/src/memory/tables.rs`) map a slot's pages by position |
| **unit** | The physical storage quantum of the device KV cache: one page of a group occupies the group's `units_per_page` units; unit 0 is the padding sentinel no page holds | the worker's KV cache planes (`crates/engine/src/memory/cache/`), `engine::batch::cache::CacheGroup`. A product's units are its rows, not KV units |
| **slot** | A request slot: the row of the per-request state tables (slot tables, block-table rows, commit table, sampler parameters) a resident request occupies for as long as it runs, `1..` with row 0 unused | `engine::batch::Columns::slots`, `engine::batch::NewSlot::slot`, the slot a request's entries are kept under in the device block tables. A LoRA adapter's slot and an expert's slot are weight slots, named with the adapter or the expert |

A rank's `engine::memory::cache` is the device KV storage (its units and planes) and holds no index; which cached prefix a request reuses is decided by the scheduler from what it knows of the buffer pool's cache (`crates/engine/src/scheduler/cache.rs`), and "prefix" names that reuse only.

### Host services

Every runtime file of UniServe lives in UniServe's directory of the user's runtime directory (`$XDG_RUNTIME_DIR/uniserve`, mode `0700`, `service::RuntimeDirectory`); a process run without a runtime directory is refused rather than given a shared fallback. A daemon owns an instance directory there (`daemon.XXXXXX`, `service::Instance`) holding its admin sockets, its process socket and its request sockets, and removes it when it ends; a hot restart's successor takes it over. Every server binds all of its listeners when it starts, accepts port `0`, and reports the endpoints it bound in one typed readiness record (`service::Readiness`: its state, process, instance directory, endpoints and settings) written as a JSON line to the descriptor its caller passes (`--ready-fd`) and served by its status route or request, so no caller chooses a port or derives a path. Addresses are typed (`service::Endpoint`: a Unix socket by path, or TCP by host and port).

The Storage Server and the Build Server are host services (`crates/service/src/host.rs`): one server per host and serving user, listening on a Unix socket in the user's runtime directory. Each service's files are named after it beside the socket: `NAME.sock`; the lock `NAME.lock` that makes one server the socket's owner for its life; the lock `NAME.start` an owner holds while it starts, on which a second starter blocks until the first serves or dies, so no starter waits by probing; `NAME.ready`, the readiness record the owner publishes once it serves and removes when it stops, which is the service's entry in the host's registry; and the log `NAME.log` of a server started detached. A daemon whose host serves none starts it as `uniserve NAME serve --socket PATH --daemon`, which leaves the daemon's session and process tree, so a daemon's end or restart never ends a host service, and returns the record the server reports on its starter's standard output once it serves. The Storage Server serves with the settings its deployment states and reports them in its record; a daemon whose deployment states others refuses to share it. Each host service is stopped by its `stop` request over its socket (or SIGTERM), and `status` answers its record.

### The Build Server

Each host runs one Build Server (`uniserve build-server serve`, `crates/build-server`) per serving user. It compiles packages into the modules of their descriptors, keeps the modules in its store, and answers `install`, `prepare`, `resolve`, `list` and `cover`. An interface behind which packages are replaced has a version, which starts at 1 and is raised by any change that is not an addition: an operator's (`proto::module::operator::version`), the scheduling policy's (`scheduling::INTERFACE_VERSION`) and the engine's (`proto::ENGINE_INTERFACE_VERSION`, the version of its messages with the daemon; the Storage Server's protocol and the buffer pool's runtime interface have versions of their own, `storage::protocol::VERSION` and `storage::runtime::VERSION`, each checked at its own hello). A package's manifest states the version it implements (`interface_version`), except a cargo-built executable's, which the executable states itself in a section of its own (`build_server::interface_section!`, the engine's from `proto::ENGINE_INTERFACE_VERSION`) and the build reads; the Build Server records it with each module it builds and hands it over with the module's files, and the loader refuses a module of a version it does not speak: the engine when it loads a kernel module or instantiates the policy, and the daemon when it starts an engine's module and at an engine's hello; a policy module also states the version it was compiled against (`sched_interface_version`), which the engine checks before any other call. Every interface has one version per release: a daemon speaks its build's version of the engine interface alone, and a Storage Server its build's protocol and runtime versions alone, so a restart in place stays within a release. A refused module fails the update that names it and leaves what serves untouched. The engine is a package as well: `crates/engine/package.toml` names the interface `engine`, the toolchain `cargo` (whose release the workspace's `rust-toolchain.toml` pins), the form `executable` and the binary `uniserve-engine`, and its one module is built for the host's Rust target triple under the key `default`. Installing it snapshots the whole workspace as it is: every file `cargo package --list` lists of every workspace member, with the workspace's manifest, lockfile and pinned `rust-toolchain.toml`, nothing rewritten; the registry and git sources the lockfile names are vendored once per lockfile into the Build Server's cache (`cargo vendor --locked`), and the build is `cargo build --release --locked --offline` in that snapshot against them, so no crate is fetched and no version chosen, and any change to the workspace is a new revision. A `resolve` answers each file's path in the store with its descriptor, which is where a node's daemon starts the engine from. A server also serves read-only stores (`build_config.read_only_stores`), each a directory a store build made: their package revisions are selected and resolved beside the package root's and their modules found beside the store roots', nothing is written to them, and a host that holds none of their toolchains serves them, which is how a release ships the modules of its own packages. A kernel package's manifest states only what is its own: its operator, backend and interface version, its source kind, what it requires of a target (hardware features of the target description, such as `tensor_memory`, or an architecture family), its descriptors and parameters, and, for a Triton package, its launch table; the source kind fixes the toolchain (whose version is the Build Server environment's), the module's form, a cubin's metadata file, a native module's launch entry `uniserve_<op>` and the build module `src/build.py`, and a package builds for every target of the description that meets its requirements. What several packages compile, such as the dependent-launch prologue and the strided-operand arithmetic, is one library the environment installs (`uniserve_kernels`, `crates/ops/python`). A Triton, CuTe DSL or CUDA package is compiled by the Build Server's toolchain environment (`crates/build-server/python`), from its launch table or its build module, with a typed compile request on standard input: the package, the descriptor's fields already read and typed (`Descriptors::typed_fields` in `crates/build-server/src/manifest.rs`, so the key grammar is read in that one place), the target with its architecture's hardware facts (`targets.toml` of the environment's package), the job limit, the cache of pinned third-party sources and the toolchain description the server checked; the server reads that description once at start from the environment's program, `uniserve-build-server toolchain --json`, and no option or environment variable names a compiler. A scheduling policy is a package of the same kind as the engine: a crate (`crates/scheduling/policies/<name>`) whose installation snapshots its whole workspace, which the Build Server builds from that snapshot for `wasm32-unknown-unknown`, locked and offline; its module is the wasm32 binary, which the engine compiles under its own wasmtime configuration when it loads the policy. Nothing is built in the tree a package is installed from. Each build reserves the peak host memory its toolchain declares (`build_config.peak_memory`), and counts against the same bound on concurrent builds as every other. `cover` is the one place a package is selected: for each of an operator's descriptor keys it answers the installed package that builds it, among each backend's latest revision that builds for the requested targets and whose `[kernel.descriptors]` cover the key, preferring a backend the deployment names for the key's phase, then the higher manifest `priority`, then the backend whose name sorts first. The selection of a deployment happens once, when a configuration is applied: the leader's daemon asks `cover` for every interface the deployment uses (the engine, the scheduling policy and each kernel operator of the build) and fixes the answer as the epoch's module set (`proto::module::ModuleSet`): the engine package, the policy package and each named kernel package at a revision, and every installed candidate of every operator at its revision (`with_store_modules`, `crates/daemon/src/engine/control.rs`). The set is part of the epoch's record and of the launch file of every main process started from it (`EngineArgs::modules`), and the main processes are told the whole of it; when a main process asks `cover` for its recorded keys it states the set's revisions, and the Build Server selects among exactly those. A relaunch and a standby therefore run what their epoch runs, and a package or a revision installed later is run by nobody until a configuration is applied again. `prepare` builds each slot's package for exactly the keys named for that slot; it launches no kernel and allocates no device memory, and builds for the `--target`s it is given or else for the architectures of the host's devices. A module is stored under the digest of what built it, recorded when its package was installed: the package's files, the toolchain's version and the environment's compile driver with its pins, the kernel packages' shared sources, every compiler it describes and the versions its lock fixes (`crates/build-server/src/inputs.rs`), so a store never serves a module built from other inputs, and a host whose toolchain or driver differs from a revision's record does not build that revision. The daemon prepares an epoch's modules at the socket `build_config.socket` names, the default socket when unset, and before it starts the deployment's engines it starts the host's Build Server with the rest of `build_config` when none serves there. Every host an epoch's main processes run on prepares the fixed set before any of them is spawned, at a start and at every apply (`prepare_epoch`, `crates/daemon/src/engine/control.rs`): the leader's daemon prepares at its own host's socket, and has the daemon of every other host prepare at that host's Build Server with the node request `PrepareModules` (`crates/proto/src/process.proto`), which that daemon serves at its own `build_config`, starting the Build Server when none serves, on a thread of its own, so its other requests and its processes' exits are served while the Build Server builds. The hosts prepare at once, each for its own platform and devices, so the set is ready when the slowest host's store is, within 20 minutes; each host answers the set as its Build Server prepared it, which must be the leader's host's. A host whose Build Server refuses or cannot build a module, one whose daemon is lost before it answers (the leader fails every request it forwarded to a node lost before replying), and one that prepares other modules fail the start or refuse the apply before anything starts. A spawn therefore reads the engine's module from its node's store and builds nothing, and the leader's 90-second wait for a spawn's reply (`DAEMON_TIMEOUT`) covers starting a process, never a build; a store that lost a module builds it again at the spawn. A main process resolves its modules there when it starts and when a package changes. A Build Server that stops while it answers a request ends that request with the connection's error; the daemon starts the host's Build Server again at its next preparation.

### The Storage Server

Each host runs one Storage Server (`uniserve storage-server serve`) per serving user, which the host's daemon starts when the host has none, in a session of its own, so restarting the daemon never ends it. Clients connect through a Unix socket owned by the user (`$XDG_RUNTIME_DIR/uniserve/storage-server.sock`) and pass file descriptors with `SCM_RIGHTS`. The server holds storage and never interprets it: it keeps the descriptors of CUDA VMM allocations (POSIX file descriptor handles) and host memfds, never creates a CUDA context, and moves no bytes itself; clients compute every key and copy on their own streams, or have its Transfer Server copy for them.

- **Claims.** The engine has each host's daemon claim the deployment (its served model name) at that host's server and hands each main process the claim's token in its launch descriptor. The daemon holds the claim for as long as it runs. Each claim is made by its claimant (`storage::Claimant`): the engine that asked, by its number, or the updater on its epoch's behalf. The server retains an epoch's storage of every scope some claimant of the epoch names, so one engine's claim (another replica's, a relaunch's, a standby's) never ends the retention of another's; a claimant's later claim releases the scopes it no longer places, and an epoch's retirement releases the epoch's storage; `uniserve storage-server retire --deployment NAME` releases a deployment that is no longer served, and `list` prints what the server holds.
- **Committed epochs.** Each claimed epoch keeps its immutable outputs private until the daemon publishes it with `Publish`. Initial engines publish after warmup; a successor remains private throughout preparation and trial. Publication makes its immutable outputs readable by other epochs and uploads its completed host pages to the KV storage. Independent committed replicas share those outputs under the same deployment. A group commit publishes every successor together at each node before retiring any predecessor; epoch identifiers imply no ordering of visibility. Retiring a candidate discards its private pages, while a committed epoch's pages remain reusable after retirement. Storage Server hot restart preserves the committed set.
- **Weights.** A main process keeps each rank's loaded parameters and buffers in read-only retained storages (`crates/engine/src/memory/weights.rs`): one CUDA VMM allocation per published weight region (an `nn::WeightKey`: a rank's shard of a checkpoint tensor, a fused stack or a computed constant), its length rounded up to the device's allocation granularity (2 MiB), each GPU holding its own copy under the weight's key (`storage::key::device_weight`). A weight smaller than the granularity is packed instead: the rank copies it into a granule shared with other small weights, at a 256-byte aligned offset, maps the granule read-only once per weight, and publishes the granule as one storage whose tensor records lie at their offsets once its load ends (`engine::memory::weights::WeightStore`, published by `WeightStore::finish`). A load that replaces a packed weight places its successor at the same offset of a granule of its own, so an update maps the new granule at the old weight's address. Every parameter is a part of a logical tensor, the whole matrix the checkpoint names: the module that partitions it declares the logical tensor's shape, the partition unit of each dimension (a head's channels, one expert) and the indices the rank holds (`logical_tensors()`, from the layer's `Distribution`, which besides PyTorch's `Shard` and `Replicate` divides position-mod-N, in named sub-blocks each split on its own, and strided compressed indices). The copy-manifest library describes a storage allocated in chunks, each a CUDA VMM allocation of its own mapped back to back with the next, cut where a configuration of the parallel degrees in use cuts a logical tensor along a field's outermost dimension (`crates/storage/src/manifest/layout.rs`); the weight path does not allocate its weights in such chunks. A chunk is retained under the key of what its bytes are: the regions of the logical tensors it holds, where in it they lie, and each tensor's loading fingerprint (the identities of the files supplying its inputs, assignment rectangles, dtype, encoding and declared derivations). A derivation names its output tensors, checkpoint inputs, numerical parameters and function revision (`uniserve.loading.weights.Derivation`). Constructor constants are keyed by their bytes. The exact manifest identity also includes the providers that determine encoded layouts: kernel library versions. Tensor source identities exclude that choice, so an encoding change can reuse retained numerical values through canonical conversion. The key names neither the rank nor its GPU: the Storage Server keeps one copy of a key per location, and a rank asks for the copies on its own GPUs, so any epoch whose rank needs a region on a GPU finds the chunk holding it there. A manifest of each tensor's checkpoint source and representation and each storage's fields, their logical parts and its chunks is keyed by the structure and the rank's position in its parallel configuration, whatever GPUs it runs on. A change of code that keeps those revisions keeps the weights. An in-place weight update (`/admin/update_weights`) rewrites the tensors where they lie and renames the copies on the rank's GPUs after the new checkpoint at the server. A starting rank maps the storages whose chunks it finds on its GPUs read-only and binds their tensors instead of reading the checkpoint. Loading is collective, so the ranks that load together agree on what to read: the tensors any of them misses, or everything when one has no manifest; a change to one tensor's loading inputs reloads only the affected tensors. Packed storage remains readable for its unchanged fields, and the transfer planner can copy those fields independently of changed neighbors. Each rank moves what it read into retained chunks, mapping instead each chunk the server retains on its GPU under the same key (another epoch's), publishes the chunks it created and maps all read-only; a chunk lives while any epoch retains it. When any of the ranks that load together finds no manifest of its own and every one of them finds the weights the deployment's other epochs retain on the host or on the deployment's other nodes (each manifest names storages, each on the GPUs that hold all of its chunks, and their fields of tensors whose fingerprints are the model's; the fingerprints of the whole model select them, whatever tensors a rank holds, so every rank that loads with others selects the same storages in the same order, those their shared copy manifest names), they receive their weights instead of loading them (`crates/engine/src/memory/weights.rs`): each materializes the target shapes and encoded storage with `rank.load_model(unread=True)`, without reading checkpoint values or generating dummy values. The planning model is released before receiving storage is allocated. A link from another node takes the rate its host's transfer calibration states for copies from another host into the receiving end, and is listed once a copy first runs over it. For an online change, planning ranks run through the deployment's process interface on their assigned nodes; the daemon reads the same source manifests as the ranks, chooses the rank assignment within the declared device set, and supplies an executable `Transfer` containing the request and copy manifest. Cold-start ranks with no manifest from the daemon gather their target layouts and measured links and compute the receive's manifest themselves. Each rank then maps the chunks of the same key on its GPU, creates the rest under receiving keys, which the Transfer Server writes, submits its copies as one `Background` transfer (a copy from another node's GPU naming that node's region, `Region::Remote`, which the Transfer Server copies over the NVLink fabric or READs), zeroes the padding the manifest names, and binds its model while the bytes arrive; only tensors with numerical regions absent from the source manifests are read from the checkpoint. Encoded groups with declared canonical forms convert on the receiver: the Transfer Server gathers the source fields, a low-priority preparation stream reorders their encoded values and scales into canonical storage, the manifest copies the logical regions, and the stream writes the destination encoding. One target group and one source group are held at a time; the planner includes their rounded allocation sizes, and the Storage Server quota tracks the retained scratch. Conversion kernels write borrowed buffers without device temporaries. Copies complete before conversion, and conversion completes before transfer, publication or release. Before capacity planning the rank waits for the transfer, retains the received chunks read-only under their keys with its manifest, and releases the receiving keys. The host region of a layer stack streamed from host storage is a read-only host storage among them. Loading stores every encoded weight in the layout its kernel provider declares, and preparation verifies it, so the retained bytes are those the kernels read.
- **Copy manifests.** How one epoch's state becomes another epoch's under another parallel configuration is a manifest computed from both epochs' storages (`crates/storage/src/manifest`). Target ranks take the GPUs holding the most required regions, with ties resolved by the busiest link's completion time. Matching chunks in the same physical storage map read-only; other regions are assigned to sources using measured link bandwidth, then become strided byte copies through their numerical encodings. Encoded fields use canonical conversion storage where required, padding is zeroed, and missing regions are reported. A chunk's `Binding` separates its actual retained storage from its rank's execution GPU: `Rank` follows GPU assignment, `Local` names host or device storage, and `Remote` names a Storage Server endpoint and its host or device storage. `storage_offset` allows a chunk to borrow a region of a retained allocation. The assignment charges each physical chunk's link, including Host↔Device and remote Host links; GPU UUIDs identify the same device storage across hosts. Host staging requests are assigned per destination host, whose Transfer Server submits the READ. Expert redistribution uses the same conversion path on a background preparation thread, leaving inference on the original allocations until the common commit boundary. The daemon caches the computed manifest. `Manifest::bind(request, host_sources).spans()` resolves its sources from the submitting host's bindings while preserving GPU assignment and numerical copies. It produces `Region::Tensor` and `Region::Remote` directly, combining rows within chunk boundaries and splitting rows that cross them. Source and destination allocations remain retained until transfer completion. The copy manifests are computed in `crates/storage/src/manifest`.
- **Exclusive storages.** The prefix cache planes, the buffer pool and the latent banks are exclusive storages with one writer, keyed by their scope, name and shape; a device cache's value planes are segments of their units, each the fewest units whose part of a layer's plane is whole allocation granules, each layer's part of a segment a storage of its own mapped back to back, so that the tail of the cache can be given back while a standby engine starts or the deployment sleeps and created again at its addresses (`docs/admin.md`): a restarted rank of the same scope takes the storage its predecessor left, after the server shoots that predecessor down if it still holds write access (SIGKILL to its process group, its exit, and NVML no longer listing it on the GPU). An owner resets only storage created for it; a storage a predecessor left keeps the finite values it last wrote. A standby maps them while its predecessor serves from them; after a crash the engine's cache index starts empty, so nothing reads them before a unit is recycled for its next owner.
- **Storage quotas.** The server keeps one quota per GPU (by UUID) for each deployment that uses it (`crates/storage-server/src/quota.rs`), so that the deployment's two epochs and the host's Transfer Server stay within one quota on a GPU they share. The quota is `⌊total × fraction⌋` of the whole GPU for the fraction the deployment's ranks configure (the smaller one while two epochs that state different fractions hold storage there). The server reserves what it retains, each device storage once however many scopes and epochs map it: read-only storages as the weights, a storage its rank marks with its KV cache segment as that segment, any other exclusive storage as the epoch's fixed part. The processes reserve what it cannot see (`Request::Quota`): each warm rank its graph pool and its process storage under its scope and epoch, the processes of one scope and epoch (a rank's worker, and its relaunch or promoted standby) counting as their largest reservation, and the Transfer Server its staging, and its CUDA context while it holds one on the GPU, in every quota of its GPUs (at the bytes it measured when it started, `Measured`, which every quota of the GPU also reports as `transfer_context`, reserved or not, so that an epoch change's preparation leaves room for the context its transfers will take); every quota of a GPU also states the bandwidth the Transfer Server measured from host storage to it (`host_link_bytes_per_second`). A rank that ends in order withdraws its reservations, and the driver frees its storage with it; a rank's process that is lost leaves its reservations no other process of its scope and epoch reserves reserved under that scope and epoch, so a successor cannot take a lost rank's storage before its relaunch reserves it, which takes each item over as it reserves it, and the reservation otherwise ends with the epoch's retirement or the deployment; the Transfer Server's reservations end with its connection; an epoch's storages end when the head retires the epoch (all but its weights when the head keeps its weights alone; weights the head moved to host storage leave the GPU's quota, and return to it when it moves them back), and a segment a successor maps, reserved once for both epochs, is then the successor's alone: the commit's handover is a transfer on the quota. The server refuses any reservation or new device storage that would take a GPU past its quota, naming every entry. The quotas survive a restart in place, and `list` prints them; the engine reads them when it divides a rank's quota (`crates/engine/src/process/ranks/rank/memory.rs`), and through each node's daemon for `GET /admin/config`.
- **Host KV cache.** The host copies of a deployment's KV pages are blocks of its buffer pool's host regions (`crates/storage-server/src/buffer_pool/`, `crates/storage-server/src/sessions.rs`): a host region is one memfd per host part (a part index on one host: a KV rank's index in its group, or part 0 for a block one rank holds whole), which the server of that host creates on the host's huge pages when it has them and admits against the host's storage when a session first states the region (`Request::HostPart`). A page has one key at every level, the key the device cache chains it under (`crates/storage/src/key.rs`: each page's key digests the key of its group's page before it, the group, the modality and the page's tokens, from a root of the group's page seed and the request's isolation key), so pages of other weights or another shape never match. The engine's schedulers decide which blocks a request holds, loads, stores and reuses and ask the buffer pool for them on their queue pairs (`storage::runtime`); a rank's worker copies between its device and its part of a host region on its device's copy stream.
- **Encoder outputs.** An encoder's output (a prompt's conditioning, an image's vision or latent features) is a block of the deployment's buffer pool (`crates/engine/src/memory/encoders.rs`), keyed by the output's name, the identity of what computes it and the digest of what the encoder read (`storage::key::encoder_output`), so requests that read the same in epochs that compute it the same find each other's outputs.
- **Trajectories.** A preempted video request's trajectory is saved into blocks of the deployment's buffer pool and restored from them when the request resumes, keyed by what computes it (the deployment's latent seed), the trajectory and the steps it took (`crates/storage/src/key.rs`), so an epoch whose denoising computes the same finds what another stored; a restore that misses starts the request from noise.
- **Transfer Server.** The server runs a Transfer Server (`crates/storage-server/src/transfer`), a child process of its own executable image that it connects to over a socket pair it makes (the child inherits one end, `crates/storage-server/src/child.rs`, and is told which child it is with its settings as the first message there), and starts again when it ends, after `storage_config.child_restart_s`, doubled for each process in a row that ended before it connected up to `child_restart_max_s`, as `uniserve storage-server list` shows; which copies bytes between the storage the server holds; the CUDA contexts the copies need are that process's, so a fault in a copy ends it and never the server. A head or a rank submits a task of spans, each a length of bytes from a source region and offset to a destination region and offset, with the update it serves and a priority, highest first: promotion (what a promotion waits for), warming (filled pages copied into the next epoch ahead of its promotion) and background (weight moves and the rest) (`Request::Submit`). A region is a retained tensor's storage, offsets counted from the tensor's first byte; a rank's part of a host region; or a device allocation of another host of the NVLink fabric, by a fabric handle its creating process exported, which imports only while that process holds the allocation (CUDA exports no fabric handle from an allocation imported through its POSIX descriptor); or, as a source only, a retained tensor or host region's part of another host, named by that host's Storage Server endpoint (`Region::Remote`). The server checks that every region of this host is storage of the submitter's deployment and every span lies within it and writes no read-only tensor, refusing the task whole otherwise, gives the Transfer Server each allocation's descriptor before the first task that copies it, takes it back when it releases the allocation, and relays the task's progress and end as events. Another host's region is checked by that host when the task runs: the Transfer Server connects to its server's TCP endpoint as a peer (`Role::Peer`) and asks it to expose the task's regions there (`Request::Expose`); that server checks them as it checks a task's sources, has its own Transfer Server register their allocations with its NIXL agent (UCX backend, `crates/storage-server/src/transfer/nixl`, which binds NIXL 1.5.1's C API, `libnixl_capi.so`, itself and resolves its entry points when the library loads), and responds with the agent's metadata and each region's address; the destination's Transfer Server loads the metadata, registers its destinations with its own agent, checks each span against its region, and posts NIXL READs, whose completion it polls on the host, since a READ passes through no CUDA stream; a span of rows at a pitch is one READ of a descriptor per row. A device allocation whose creating process recorded its fabric handle in its storage record (`StorageRecord::fabric`) is exposed with that handle, and the destination's Transfer Server copies its spans over the NVLink fabric on the copy engines of the destination's GPU, rows at a pitch as one pitched copy, whenever the handle imports there, and READs them otherwise. The agent registers storage pinned, at registration, and outside UCX's registration cache: under UCX's default on-demand paging the first READs' page faults hold a link to a few GB/s (host storage read between two GB200 hosts at 4.1 GB/s on demand, 79 GB/s pinned; pinning a 64 GiB host region takes 1.7 s), and the cache, which learns of an unmapping only through UCX's hooks of `munmap` that the Transfer Server's direct system calls bypass, would hand a region mapped again at a released address the released region's registration, so that READs into it land in storage no longer mapped. A read-only allocation's host storage is mapped read-only and registered for remote reads alone, which needs the NIXL and UCX packages with read-only registration (`docs/nixl.md`); with other builds its registration fails, and so does the task that READs it. A task whose source host is unreachable, runs no Transfer Server or holds no such region fails, naming that host and the reason. The exposure lasts until the destination's Transfer Server ends it once its task ended (`Request::Unexpose`), or its connection closes, or the source's server takes the allocation back; the submitter keeps a remote source retained and unchanged until the task ends, as it does a local one. The submitter keeps the sources unchanged and the destinations unread until the end, which the Transfer Server reports only after the host saw every copy complete, so no CUDA event crosses a process. A copy runs on copy engines, never as a compute kernel: those of the destination's GPU, else the source's (between host storage and another host's GPU of the fabric, those of the GPU on the storage's NUMA node whose calibrated link with host storage is fastest), the CPU between host buffers, and the network adapters for a READ from another host. The Transfer Server copies by its host's calibration (`storage_config.transfer_calibration`, which `uniserve storage-server calibrate` writes, `crates/storage-server/src/transfer/calibration`): the GPUs it copies on, the bandwidth and per-copy cost of every link (each GPU to itself, each pair of GPUs that can address each other, each GPU to and from host storage on its NUMA node, host to host), the device storage NVML attributes to its CUDA context on each GPU, and the rate of copies from other hosts; it reports the links and the contexts when it connects, creating no context to do so, and `uniserve storage-server list` prints both. A server whose settings name no calibration runs no Transfer Server. It holds a GPU's context only while it has work on the GPU (`crates/storage-server/src/transfer/contexts.rs`): a task's pieces hold the GPUs their storage lies on or their copy engines run on, a copy thread its GPU while it copies, an exposure to another host the GPUs of its device allocations until that host ends it; and an explicit transfer session the GPUs its operation uses across successive tasks. Cache warming opens a session on each source and target owner before copying and closes it after the final round or cancellation (`OpenSession`, `CloseSession`); closing the client also ends its sessions. Sessions create no context until a task first uses it. The first use of a GPU reserves the context in every quota of the GPU at its measured bytes (`Request::Quota` of `transfer_context`) and then retains it, so a quota without room refuses the reservation and the task that needed the GPU fails, naming the quota; once the last hold ends, the device mappings, host registrations, NIXL registrations, streams and events made in the context are released, the context with them, and then its reservation, so NVML lists the process on no GPU it does not use. The context's retain moves into the cost of the first task on an idle GPU. A link from another host (its GPU or its host storage to a GPU or host storage here) takes the calibrated rate of READs into its end here, or of copies over the fabric into the GPU that runs them, which the listing prints once a task first copies over it; a task over a path the calibration does not state fails. It cuts each copy into chunks lasting `storage_config.transfer_chunk_us` at the link's bandwidth, and at least the link's calibrated per-copy cost, so a copy engine turns to the executing epoch's own copies and to a higher priority between chunks; each link runs the chunk of its highest priority first, tasks of one priority in submission order, and keeps a byte budget, its whole bandwidth at start, which a head halves (`Request::Throttle`), down to 1/64, and restores by 1/8 of the bandwidth per second (the protocol's `Throttle::FLOOR` and `Throttle::RESTORE_PER_SECOND`); a head that names no link halves every link a task of its deployment copies over, and restores every link a halving reduced. While a successor epoch prepares, the leader halves the budgets of the change's links on every node of the deployment as the leader knows it then (a node that joined for the successor included), through the serving engine and each node's daemon's claim, each second a serving scheduler's step takes more than `update_config.transfer_slowdown` past its step of the same batch size and execution (graphs, or eager forwards with `update_config.eager_prepare`) before the preparation, and restores them once none does (`crates/daemon/src/interference.rs`). A task is cancelled by number or with every task of its update, and when its submitter's connection closes; it ends once its chunks in flight completed. The server submits tasks of its own to move an epoch's weights between its GPUs and host storage, at a head's request: an offload (`Request::Offload`) takes every device copy of read-only tensors the epoch alone retains, admits host storage of their whole size under the host-storage rule (refused whole otherwise), creates a memfd of each storage's size and copies each into it; a restore (`Request::Restore`) admits each storage's size against its GPU's quota, has the Transfer Server create retainable device storage of that size on the GPU it came from, in that GPU's session (`Event::Allocate`, responded with its POSIX descriptor in `Request::Allocated`; the Transfer Server keeps no handle of it) and copies each back. Once every copy of a move ended, the tensors' copies lie at their new locations and the storages they left are released, so each GPU's quota reserves the move's effect at once; a copy that fails leaves every tensor where it was and releases the copies. The head's request gets its response when its move ends. When the Transfer Server ends, every task it held fails at once, and the next one maps what new tasks copy again; its NIXL agent ends with it, so another host's READ of this host's storage in flight fails, and the next agent, of another name, registers the regions again when a peer next asks, whose Transfer Server then forgets the previous agent and loads the new one's metadata.
- **KV storage.** With `kv_cache_config.mooncake`, the server runs a Mooncake connector, a child process it starts again when it ends (`crates/storage-server/src/mooncake.rs`). The connector maps every rank's part of a host region and registers it with Mooncake; a put to the remote store writes a block's pages to Mooncake and a prefetch from it reads them back, each page an object named by its key and its part's layout, which names no deployment or host. Mooncake's master evicts objects; the connector never removes them.

Retained host allocations are admitted by the Storage Server before it creates their backing (`AllocateHost`). The rank receives an exclusive byte tensor and its writable descriptor through the ordinary storage reply; its epoch retains the allocation until it releases the key or retires. Host admission subtracts the server reserve and the unallocated bytes of host regions and retained host storages from available storage (`HostStorage::unallocated`), so sparse allocations still awaiting their first write cannot each spend the same headroom.

### Transfers

A main process moves no bytes to another process itself. Every copy between processes or hosts is a Storage Server transfer task (`Request::Submit`), run by the host's Transfer Server; a rank's own copies between its device and its part of a host region run on the rank's copy stream (`crates/engine/src/memory/cache/host.rs`).

- **Prefill/decode hand-off.** Every worker group of a scheduler indexes one unit space of its KV region, which exists in every group's device memory, so a request's blocks keep their units when it moves from its prefill group to its decode group. Each rank states where the Storage Server retains its cache planes, run by run (`PrefixCacheInfo::plane_runs`: for every field, the retained exclusive tensor and offset holding each unit), and places them at its host's buffer pool (`Place`, or `PlaceRemote` relayed by the head for a rank of another host). Once the prefill group's call that sampled the request's first token was accepted, the scheduler places the request's decode on a decode group and submits `Transfer { owner, group }` for its owner on the prefill group, stamped by that group's worker, which removes the owner's entries from its device block tables (`specs/buffer-pool.md` §11). Once the prefill group's `completed` reaches the stamp, the buffer pool gives the Transfer Server of each decode rank's host a task at `Priority::Request` that copies the owner's blocks not valid in the decode group's memory: one span per field and run of consecutive units, from the prefill rank of the same rank index (`Region::Tensor`, or its `Region::Remote` when the prefill rank lives on another host, which the Transfer Server reads through NIXL with the device storage registered there) into the decode rank's planes, device to device (`crates/storage-server/src/sessions.rs`). The copy carries every byte of the units, the prompt's last partial page, the flags and the FP8 scales included. On `Transferred { slot, runs }` the request's next call is a decode on the decode group, with that slot; on `Failed` the request ends as migratable (`MigrationCause::Loss`) and the daemon submits it again. The prefill and decode groups have the same number of ranks and the same cache layout. One scheduler drives both groups (see Parallelism, Schedulers): the prefill group's ranks run its prompts' batches and the decode group's ranks its decodes, on their own devices, of this host or of another.
- **Peer reads of host copies.** A deployment that names other hosts' Storage Servers (`kv_cache_config.peers`), which serve the same model under the same served name, prefetches host copies from them: the buffer pool asks each peer's server, over its TCP endpoint as a `Role::Peer`, to hold the copies' keys (`Request::PeerHold`), has this host's Transfer Server READ each held copy from the peer's parts of its host region, and keeps what was read only from a peer whose holds stood until the read ended (`Request::PeerRelease`, `crates/storage-server/src/sessions/hosts.rs`). Each held copy states the encoding the class that wrote it states, and the buffer pool reads it into a block of the region of that encoding (`BufferPool::peer_copies`): the class's host region for its own encoding, and for an FP8 cache that converts from the dense compute dtype its converted-load source region (`storage::runtime::Class::source`), whose part on each rank is the rank's source buffer and whose copies a load converts on the device (`crates/engine/src/memory/cache/conversion.rs`); a copy of any other encoding is not read. The peer endpoints are not authenticated: a process that reaches a host's Storage Server endpoint can read the host copies it holds, and the hosts rely on the isolation of their network.

## Startup

Every rank of a group runs these phases in the same order, because several are collective:

1. The main process reads its launch from the descriptor it inherits, says hello on the daemon's request interface and states `Starting`, and claims the node's Storage Server on the process interface (`crates/daemon/src/engine/launch.rs`, `crates/engine/src/process/daemon.rs`); its lifeline ends the process at once if the daemon is gone. Each worker makes its device's primary context current.
2. The checkpoint resolves to its model family by the class it declares (`crates/engine/src/process/catalogue.rs`), the family reads the model's configuration, and the parallel configuration is validated against the stages each rank holds (`crates/models`).
3. Each rank, on a thread of its own, connects its Storage Server client and takes its share of the GPU's quota, agrees the host groups and forms its tensor group's communicator (`crates/engine/src/process/ranks.rs`, `crates/engine/src/parallel`, `crates/platform`).
4. The model is loaded on the meta device and each runner's profile run states the kernels its forwards launch ([The profile run](#the-profile-run)). The engine resolves them at its host's Build Server within its launch's module set and installs them as its first generation: starting is not an update, and nothing is kept for a rollback.
5. The weights are loaded, or bound from what the same model at the same rank position in the same parallel configuration retained (`crates/engine/src/memory/weights.rs`): the checkpoint reader reads each source file front to back into the page cache before mapping its tensors, so ranks loading one cold file do not fault it page by page. A rank that loaded moves its weights into retained storage and publishes them.
6. The rank divides its share of the quota among the weights, the runners' regions, the scratch pool, the storages sized by request slots and the units of its cache, agreed over its host group (`crates/engine/src/memory/division.rs`).
7. The head opens the epoch's session with its host's buffer pool (`Open`), and every rank maps the segments the answer's table states, creates the whole segments its quota holds free, and opens its graph pool, the KV cache, the recurrent state and the serving runners over them (`crates/engine/src/process/ranks.rs`, `crates/engine/src/memory`); a stage placed with `"weights": "host"` moves its layer projections into a page-locked host region and a ring of device slots.
8. The workers warm up: every captured forward runs eagerly once over idle inputs, so kernels compile outside capture, and is captured, each runner's buckets largest first; buckets that always run eagerly run once too, so no serving request selects a kernel first. The groups of a process warm up one after another, in the order of their group ids on every host: a kernel's first use takes a lock of the whole process and waits for the work in flight to drain, so a rank making one while a collective spins on a device until its peers arrive would hold those peers queued on the lock. A generation's preparation runs its eager forwards in the same way. The ranks of a media group's text encoder and denoiser, and the stages of a text pipeline, also meet on the host before each collective an eager forward issues (`ops::Group::with_meet`), so no rank's device waits in a collective for a peer whose thread has not reached it. Once warm, the ranks of each KV region give back the tail segments their quotas no longer hold beside their warm processes and reserve those processes. A process's figure on a device is its whole there, as NVML states it, less the pools of all its ranks on the device: the first of its ranks on the device reserves it, and its other ranks there reserve none.
9. The runners seal their graph tables, and each worker group states what it serves (`engine::batch::Capacity`): its phases, request slots, buckets and rows, its cache groups and their seeds, the denoiser's steps, and the bytes of its features and media products.
10. When admission first opens, the engine warms the serving path with real requests (`crates/engine/src/process/requests.rs`, `warm_up`): one token request per scheduler of one prompt token and two generated tokens, greedy, reading and writing no cache, so every scheduler's prefill and decode path runs before a client's request does; their events are dropped. A deployment that launches nothing on a device warms nothing.

## Serving

**A text decode step.** The engine sends a `Batch` whose decode calls name request slots. The control thread opens it (binds the calls to their requests), reserves the prefix cache's tables and attention pages and leases the output words, and submits the job. On the device's worker thread the causal-LM runner's forward reads the call and forward columns, gathers each call's request constants by slot, computes the Philox draws of each sampled position from the request's seed, picks the decode graph of the smallest row bucket that holds the batch, writes the forward's inputs into its columns (slot indices, finish flags, the rows' sampling parameters and draws) and replays it: the graph gathers tokens, positions and attention metadata from slot state on the device, runs the model, projects the final-position logits and selects each row's token: greedily, or by sampling under the row's temperature, top-k (up to 128 candidates), top-p, min-p and penalties, all of them tensor contents of the graph. Before the penalties, in vLLM's order, the shaper applies the row's logit adjustments, which greedy rows honour as well: its slot's row of the bias table (the request's logit bias, `-inf` outside its allowed token set), installed once by the batch that carries the request's first call on the worker, and its banned tokens as a bitmask (the last token of each bad word whose prefix the generated tokens end with, the end-of-sequence tokens under `min_tokens`). A batch that needs typical-p, reported logprobs or a sampled top-k beyond the 128 candidates selects after the forward with the `select` graph of its task bucket and samplers, whose controls are tensor contents (each task's sampler, parameters and draws), with the same kept-set computation; its `score` graph reports logprobs, scored on the model's raw distribution. `execute` enqueues the copies of the selection words into the lent output words and of the selected tokens into the relay staging, and returns the records: each call's progress and where its words lie. Once the worker has checked the records and the batch is sealed, the commit replays the commit graph, which installs the selections into slot state, so the next step can be queued before this one's result is read. When the job's event completes the control thread decodes the records and words and returns the `BatchOutput`. Prefill has its own graphs, and a deployment that speculates serves its batches eagerly (below); with tensor parallelism every rank replays the same graph and the collectives inside it were captured with it.

**A speculative decode step.** In a deployment that speculates, a decoding request's call is a verification: one row of its committed token followed by the drafts the drafter proposed after its previous step, as many as the scheduler chose for it (from zero to `num_draft_tokens`; zero, a row of one token, while its draft cache is incomplete). The causal-LM runner serves every batch of such a deployment in one eager step (`crates/engine/src/runner/causal_lm/speculation.rs`) rather than a captured graph. The target forward evaluates a verification's tokens as one-token attention rows of the decode phase, each the decode step at its position, while one state row per call walks them in order through the recurrent layers (the rows of `nn::RecurrentState`) and keeps the recurrent state after every token in a trail (`ops::recurrent::Trail`). Every position samples through the sampling module with the draw its request's seed and position address, its penalties counting the drafts before it; the drafter proposes the argmax of its logits, so accepting a draft exactly when the position's sample equals it is the rejection rule for a point-mass draft distribution, which keeps the target distribution and, for a greedy request, commits the tokens it generates without speculation, up to the decode kernels' rounding of rows batched differently. The runner then settles each slot on the trail's entry of its last accepted token, commits the accepted tokens through `slot_commit` (a `VERIFY` row installs the token after the accepted drafts and advances the slot's lengths by the accepted span, a `COUNT` row adds each accepted draft to the slot's penalty history), and runs the drafter (`nn::capability::Drafter`): its entries over the positions whose next token is now known (a prompt row's next token, its sampled token or `lookahead` after its last, a verification's committed tokens), then each call's proposals, chained on the device from its last entry, each step embedding the draft the step before chose and reading the hidden state it left. The draft cache is the pool's draft group, each drafter layer lying over a run of a unit's columns (`CacheLayout::with_draft`, `crates/engine/src/memory/cache/layout.rs`). The proposals reach the engine in the call's output (`CallOutput::draft_token_ids`), and a request's next verification, which carries them, waits for that result. A refill call (`DraftWork::refill`) evaluates the target again over positions whose target K/V the cache already holds, writing none of them, so that the drafter writes those positions' entries; the engine schedules refills in the prompt token budget a step leaves idle (`crates/engine/src/scheduler/schedule.rs`), except for a model that keeps a recurrent state per slot, which has no scratch state to evaluate them in: its requests verify no drafts until their draft cache is whole.

**A chat request.** A request passes `route handler -> Processor -> hold -> engine -> OutputProcessor -> response`, and the API server's imports (`crates/daemon/src/api`) follow that direction: input processing imports no output processing, and neither imports the route handlers. The route handler (`api::openai::chat_completions`) parses the wire schema (`api::protocol`), checks the model the request names and writes the response; it holds no model knowledge. The deployment's `Processor` (`api::input`) lowers the parsed request under the served family's rules: it checks the request, lowers its sampling controls over the checkpoint's defaults into the engine's `SamplingParams`, renders the chat template with the tools the model may call, tokenizes, sizes images, and resolves the generation length; it returns the engine's `GenerationRequest` and the request's lowering (`handoff::Lowering`): the prompt, the decode options, the parsers and the response's fields. The leader submits the request through the hold and the migrator, which are why a client sees one stream across updates, and builds the request's `OutputProcessor` (`api::output`) from the lowering. The response body (`api::openai::run::GenerationRun`) pushes one engine event at a time through it: it detokenizes incrementally with the stop strings, parses reasoning and tool calls, assembles the content blocks, keeps the timings and records the request's statistics, and the body's sink writes the resulting deltas as server-sent chunks or one document. Because a processor is built from a lowering, a successor daemon rebuilds the same one from a handed-over response's state.

**Output formats.** A family's chat profile (`processing::ChatProfile`) names the formats its checkpoints write, each for what the model writes and none for a model: a `ReasoningFormat` states the delimiters its reasoning is written between (`<think>` and `</think>` for the Qwen families), which one reasoning parser reads and a handoff carries as they are, and its tool calls are `ToolCallFormat::Json` (one JSON object naming the function and its arguments between `<tool_call>` and `</tool_call>`: Qwen3-MoE) and `ToolCallFormat::Xml` (`<function=NAME>` and `<parameter=ARG>` tags between `<tool_call>` and `</tool_call>`: Qwen3.6 and Qwen3.8 Flash Next, `processing::qwen`). The API server holds one parser per format behind `api::output::tools::ToolParser` (`JsonToolParser`, `XmlToolParser`) and never reads a template's text to find the format. The function-and-parameter parser types each value by the JSON schema the request's tool declares for the argument, so the lowering carries the request's tools to it, across a handoff too.

**A chat request with an image.** The leader's daemon fetches each `image_url` part and reads its displayed size, the chat template writes the family's image markup (`<|vision_start|><|image_pad|><|vision_end|>` for Qwen), and request processing replaces each image's placeholder token by the image's block (`Processor::process`, the family's `processing::ImageProcessor`): an `ImageInput` at the prompt position of the token after the placeholder, with the merged tokens the processor sizes it to as its cache tokens and the larger merged side as its logical positions, and a digest over its bytes and the request's cache partition. The scheduler encodes every image a context prefill reaches before it (a `VisionEncode` batch, whose media row carries the image's bytes and the position of the request's encoder output), pins an encoding the buffer pool holds under the image's key, on the device or loaded from the host encoder region, before it encodes one, and writes the prompt's tokens and each encoded block in one causal row of the prefill (`engine::batch::Columns::vision`): a block's rows embed no id, take the cache positions after the text before them and rotate from the logical position after it, and the text after a block continues the image's span later, so a request's logical position and its cache length differ past its first image. On the rank, a host lane decodes, resizes and patches the image while the device thread serves other work; the device thread encodes the patches with the model's tower into the request's encoder-output block (`crates/engine/src/runner/vision.rs`), with the block's multi-axis rotary coordinates beside its features, which a later prefill copies into its hidden rows before the stack runs (`TokenBatch::rope_positions`). The request gives its encoder-output entries up with its other entries; an encoding committed under its key stays cached for other requests until it is evicted. A request with context images shares no prefix-cache page; its images' encodings are what other requests share.

**A FastH3 video request.** The daemon checks and processes the request with the video processor MiniMax-H3's request processing binds (`crates/processing/src/minimax_h3`). On every rank the worker admits it at its exact size (`start`), and a denoising rank holds the layout that serves it (without graphs, a request with conditions evaluates in a layout prepared for it). The text encoder's graph of the smallest prompt capacity that holds the prompt runs on its tensor-parallel group; latent preparation writes the request's noise and state rows; each denoising step copies the slot's committed latent pages from the bank the quota names into the sample tensors, replays the layout's graph on every rank of the sequence-parallel group and copies the result into the other bank; video and audio decoding replay one graph per temporal unit; the decoded units transfer to the CPU ranks, whose media runner encodes each unit and muxes the MP4.

**Batches.** Every batch, of every computation, is an `engine::batch::Batch` served as described in [Computations and their batches](#computations-and-their-batches): its runner stages the columns, replays the bucket's graph or runs the eager forward on the batch's stream, and answers its `Submission` with the step's `BatchOutput` once the device work completed (a video batch's host work completes in the batch's second turn).

## Parallelism

- **Streams and jobs.** A rank with a CUDA device issues every forward's work on its primary stream, the full-device stream of its primary device, in the jobs its worker performs (`crates/engine/src/worker.rs`). The stages' module streams fork from it, so their work overlaps on the device while forwards follow one another on the host. A rank that maps a host region's part also has a copy stream, a full-device stream of the cache's device that the copies of the buffer pool's `Copy` answers are issued on: each starts with a later numbered batch that every rank of the group runs, within the copy budget, and the batch's end covers it (`crates/engine/src/worker.rs`).
- **Collectives.** A layer calls its communicator; in serving its functions are NCCL collectives of a `platform` communicator bound to the forward's stream (one communicator per stream group Rust creates, `crates/platform/src/nccl`), captured with the forward.
- **Expert forwards.** A rank's member of an expert union (`crates/engine/src/runner/causal_lm/experts.rs`) agrees on each step's source and capacity with the union's other members over their host group (`crates/engine/src/parallel`), then runs the step; a member without tokens replays the join graph of the agreed capacity. A distributed expert layer's weight copy from its peers is a graph break.
- **Schedulers.** Each DP rank has a scheduler: its own thread, KV cache and the groups it drives. A text deployment's groups that serve requests form the schedulers as equal consecutive blocks of `data_parallel_size` (`WorkerGroupConfig::scheduler_blocks`): a prefill/decode deployment's two groups are one scheduler's, and each data-parallel group of the command-line shorthand (`model-<i>`) is one scheduler's alone. The scheduler addresses each of its groups by the group's id, through its executor, and each of a main process's ranks is a rank of one group (`ModelRunner::ranks`): a group's ranks form its tensor group's communicator, and every rank of the deployment agrees its cache's units over the one host group of the epoch, so all groups size their caches to the same units and a unit is the same request's in every group. A media deployment's groups are all its one scheduler's, whose devices serve the blocks the deployment file places on them. Independent data-parallel replicas run an engine each, and the leader routes a request to the replica with the fewest in flight; replicas that exchange experts (`moe_config.expert_parallel`) run in one engine, whose control thread asks the policy's `route` (see The request interface). A replica is one of the groups a deployment file's `replicas = N` expands a group into.

## Failure handling

Errors cross with a stable code, whether they are fatal to the process, and the phase they occurred in. An error in a runner call before a batch's commit point fails that batch, unless it marks a broken invariant, which is fatal; at or past the commit point every failure is fatal. An error in resource work fails startup, or at serving time the batch that needed the resource. A launch failure or a driver error is fatal to the process, and the engine replaces its failure domain: the rank's group, or every group that shares an expert epoch (`expert_world_size`), whose ranks hold that epoch's communicators. Every group of the domain terminates its ranks; the token requests they held end as migratable (`MigrationCause::Loss`), and the daemon submits them again with their generated tokens and images, to wait for the relaunched ranks. The domain is relaunched together, its groups form their communicators again, and their weights and exclusive storage come back from the host's Storage Server: each relaunched rank lays its KV cache planes out as the lost rank held them, taking back the segments it held and leaving absent those it gave back, rather than sizing them afresh against a device whose storage a successor epoch prepared beside the serving one may share, and it must then report the lost rank's capabilities, its planes as they stood included, or the group closes. The relaunch leaves the scheduler serving the scheduler's other groups while the relaunched ranks start; each group of the domain admits work again once it has installed them, and a relaunch that fails closes the domain's groups.

An engine that keeps a standby (`worker_config.standby`) is replaced by promoting it instead of relaunching it. The daemon's failure-domain rules decide (`crates/daemon/src/standby/mod.rs`, `Standbys`, which the leader's replica applies): the serving engine's main processes, one per host its worker group spans, are one failure domain, which keeps a standby of every member or of none. Once the engine serves its epoch, the domain starts a standby epoch beside it: every member's next launch generation from the deployment's one counter, then a second process on every host, started together as the serving engine was, at a channel and a rendezvous of its own, so the standby ranks form their own communicators. Each standby claims its scope's storage read-only, maps the epoch's weights, resolves the modules its launch file states (the epoch's module set), captures its graphs on its own graph pool and parks, as an epoch update's target does. Its graph pools' device storage is kept as `worker_config.standby_storage` says, one mode for the whole domain (`EngineArgs::standby_storage`): `resident`, `suspended` (moved to host storage at unchanged addresses once the graphs are captured, and back at the promotion), or `auto`, which suspends when a device of a member is crowded (its quota leaves less unreserved than the graph pools the deployment reserves there) and keeps no standby when the host's Storage Server cannot hold them suspended. When the serving engine is lost (any of its processes: a peer's loss ends the scheduler node's process), the rules promote the domain's parked standbys together, every promotion issued before any is awaited; each takes write access once the Storage Server has its predecessor out and serves, the leader moves its hold onto the promoted engine, and the domain starts a new standby. A domain with a member that has no parked standby, or whose promotion fails, is relaunched instead. An epoch that no longer serves keeps no standby: its standby ends with it.

A lost main process takes its workers with it. Its client ends every request it held as migratable, the leader's daemon holds new requests and starts a new engine process under the same claims, whose ranks find their weights retained, and the hold then serves the new engine every held and migrated request. A request survives `migration_config.max_migrations` migrations caused by losses; when the new engine does not start, held and later requests fail.

A driver call that does not return stops the worker inside its job. The control thread keeps serving the channel and, once a job has stayed in flight for the stall bound (`worker_config.watchdog_timeout`, which the epoch's engine configuration states), reports to the engine the job's batch, its runner method, its calls and how long it has run (the process interface's `Stalled` report). The engine logs the report, fails the affected requests with an error naming the stalled job's forward, and replaces the group. A device whose context an illegal memory access or a device-side assert left unusable runs none of the work behind the failure: the worker of that device finds the error at its own wait on its stream's event, which returns it as the context faults, states it as its device's fault, and the control thread fails the epoch at once, whatever job of another device of the process waits behind the failure.

A main process's orderly close destroys what it holds of the host: its workers destroy the NCCL communicators they own, and the close ends with a reset of its primary contexts before the process exits, which releases the driver state the process created, including the shared-memory file (`/dev/shm/cuda.shm.*`) the CUDA driver makes for a process's interprocess events and removes only when the context is destroyed. A main process that loses its daemon with nothing in flight takes the aborted close and then the reset; with work in flight it ends at once. Neither library offers a cleanup for a process that ends without its orderly close: a main process that is killed, or that ends at once, leaves the driver file and its communicators' proxy pools (`/dev/shm/nccl-*`) in `/dev/shm` for the host's cleanup, and the daemon that reaps it releases nothing on its behalf. A main process's startup failure reaches the engine as the process's own error.

Dependency direction, as the crates' manifests state it (a crate on the right depends on those on the left): `service <- {proto, storage, build-server}`; `proto <- processing`; `{platform, proto, tensor} <- ops`; `{ops, processing, proto, tensor} <- nn`; `{nn, processing, proto, tensor} <- models`; `scheduling <- scheduling/policies/*`; `{build-server, media, models, nn, ops, platform, processing, proto, scheduling, service, storage, tensor} <- engine`; `{build-server, media, processing, proto, service, storage} <- daemon`; `{platform, service, storage} <- storage-server`; and the root package over `build-server`, `daemon`, `platform`, `processing`, `service` and `storage-server`, so the base executable links no tensor, kernel or model code. `tensor`, `platform`, `media`, `scheduling` and `manager` depend on no workspace crate. No crate but `models` and the engine executable's list of families names a model: the engine reaches a model through its `nn::family::Family` and the daemon through that family's request side, a `processing::Family`. What a video request asks of its model crosses the engine without the engine reading it: a request's conditions travel as the encoding of their Protobuf message (`VideoConditions` in `crates/proto/src/request.proto`, the vocabulary of `proto::video`'s `Conditions`) beside the sizes the engine schedules by, and the placed denoiser's description reaches request processing as bytes its model family encodes.

### The engine's modules

| Module (`crates/engine/src`) | What it holds | Thread |
| --- | --- | --- |
| `process` | The control thread: the daemon's request and process interfaces, the lifecycle, routing to schedulers, event streams, reports and metrics; the start (`process::ranks`, one rank's resolution in `ranks::rank`, the session with the Storage Server, the `Engine`); jobs of generation updates, epochs and operations; the weight updates' staging and binding on the operations thread (`process::binding`); `catalogue`, which resolves a checkpoint's family; `record`, the start `uniserve keys` runs | control, operations, start |
| `scheduler` | One scheduler per data-parallel rank: requests, admission, the memory decisions over the buffer pool, batches, updates, drains; the scheduling policy host (`scheduler::policy`) | one per DP rank |
| `batch` | What a scheduler hands its executor and gets back: `Batch`, `BatchOutput` and its validation error, `Capacity`, the cache groups' kinds, the products and their order, the philox draws, shared media | — |
| `executor` | A scheduler's executor: the `Executor` trait the scheduler calls (`submit`, `map`, `stamp`) and `WorkerExecutor`, which implements it with one waiter per worker group over the node's `Route`; `Route` numbers each group's jobs and hands them to its workers on this node and to peers on other nodes; the peer link with its listener (`executor/peers`) | one waiter per worker group |
| `worker` | One `Worker` per device, the only thread that issues on its streams: its job queue, sequences, watchdog, the completion of its jobs, errors | one per device |

| `memory` | A rank's memory: block tables, product buffers, the KV cache's planes, recurrent state, weights, the division of the quota, the graph pool, the client of the Storage Server (`memory::client::StorageClient`, for the head and a rank) | worker, start |
| `profiling`, `parallel` | Profiling sessions, range markers and always-on counters; host collectives of a rank's groups | worker |
| `modules` | Resolution of packages at the Build Server | start, jobs |
