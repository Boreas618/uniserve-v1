# Architecture

UniServe is a Rust serving system. Rust owns the control and data planes and the numerical computation alike: HTTP, scheduling, the main processes and the channel between them, requests and their progress, storage and device storage, CUDA streams and graphs, transfers, host groups and observability, and the model mathematics over the `nn` layers and the `ops` kernels. No serving process carries a Python interpreter: Python appears in the Program Server alone, as the compiler of Triton and CuTe DSL kernel programs, and in the evaluation client.

This document describes how a deployment is organized, how the main process divides its work between its threads, and how a request travels through it. A host is one machine; a main process is the `uniserve engine` process of one node and epoch: its control thread, one scheduler per DP rank, one executor per device and its blocking pool (`src/engine_main.rs`); an executor is the thread of a main process that issues one device's work; a group is the ranks that execute one role's components together, launched and replaced together; a rank is a group's member; a scheduler is the scheduling of one DP rank (data-parallel rank).

## Principles

1. **Rust owns the control and data planes.** Requests, admission, slots, every request's progress, batch order, storage and its lifetime, streams, transfers, host groups and failure handling are Rust's. Rust knows no model, component shape or CUDA graph.
2. **The numerics are Rust.** The executor's runners (`crates/worker/src/runners`) make every numerical decision of a batch: buckets and padding, graph capture and replay, attention planning, sampling and its random draws (keyed by the request's seed and token position), and the device state of each slot. They compute over the layers of `crates/nn` and the kernels of `crates/ops`, keep each admitted request's numerical constants by slot from `start` until `release`, and report everything a request's progress depends on back to the engine in each batch's results.
3. **A layout with two readers is defined once.** The batch the engine submits and the executor reads is one type of `crates/ipc`, whose host columns the engine builds (`crates/scheduler/src/scheduler/batching/columns.rs`) and the executor stages (`crates/worker/src/runners/columns.rs`); neither side keeps a second copy of the layout.
4. **Each behavior is implemented once.** A forward's computation is one method of a runner, used by serving, by graph capture and by the shadow harness that proves an update alike. A rule the reference also states is written once and cited, never copied.
5. **One thread issues a device.** Each device has one executor thread, the only issuer of work on that device's streams, so a stream's order is the order the executor submitted in. Nothing else in the process touches the driver.

## Processes

| Process | Language | Role |
| --- | --- | --- |
| `uniserve serve` (daemon) | Rust | One per node, for the deployment's lifetime. Every node's daemon starts, reaps and reports the processes of its node and holds the node's Storage Server claim. The leader's (node rank 0) also serves the HTTP API, processes every request's input (the model profile, chat templates, tokenization, multimodal inputs, request lowering) and output (detokenization, stop strings, reasoning and tool parsing, response assembly), and starts the engine process |
| `uniserve engine` (main process) | Rust | One per node per epoch, started by that node's daemon as `uniserve engine --launch <path>` (`crates/daemon/src/engine/control.rs:503-509`) on the leader's instruction (`Request::Spawn`, `crates/proto/src/process.proto`), and replaced with the epoch. The launch file states the role the process holds, so the process never infers it (`src/engine_main.rs:497`): the node that schedules runs one scheduler per DP rank (scheduling, the KV cache), and every node runs one executor per device with that node's models, runners and modules and its media encoding, muxing and reading. It serves the request interface to its daemon |
| `uniserve storage serve` | Rust | One per host and serving user; keeps the storage that outlives the engine and the workers (see Storage and device storage) |

A deployment of several nodes starts `uniserve serve` on each with `--nnodes`, its `--node-rank` and the leader's `--dist-init-addr HOST:PORT`; the leader binds that address and waits until the daemon of every node rank below `--nnodes` has joined it. The leader keeps the address bound while it serves, so a deployment that names it (of one node included) also takes a node whose daemon joins later with a node rank no node holds: the engines that connect from then on learn it, and the next epoch change may run ranks there. While nodes may join, every node's Storage Server also listens on TCP, so that the other nodes' Transfer Servers read its storage. Only the leader takes a model; another node's daemon serves the leader until the leader's connection closes, then ends its processes and exits.

Every process runs the one `uniserve` executable, installed into the environment's `bin/`, as one of its commands (`src/cli.rs`). No process embeds a Python interpreter: the numerical library is Rust. A main process starts as `uniserve engine --launch FILE` (`crates/daemon/src/engine/launch.rs`), whose launch file states the epoch's build config, the model, the request address, the Storage Server namespacing, the Program Server's socket, the devices, the rank and the durations. It reads that file, starts its control thread, one scheduler per DP rank, one executor per device and its blocking pool (`src/engine_main.rs`), and serves until its supervising daemon ends.

### The request interface

The leader's daemon and the engine process exchange the request interface (`crates/proto/src/request.proto`), Protobuf that changes only by additions, so a daemon keeps serving engines of later builds.

- **Start.** The leader's daemon binds its request socket and asks the node's daemon to start `uniserve engine --launch FILE` (`crates/daemon/src/engine/launch.rs`), whose launch file carries the epoch's engine configuration (`proto::config::EngineArgs`: the serving options that build the engine processes and what the daemon resolved from the checkpoint, its generation limits, control tokens and context length), what the process takes over from the one it succeeds, the request address, the process address and the number that identifies the epoch's engine. Without `engine_host`, the engine runs on the leader. A local deployment uses Unix sockets in the user's runtime directory; a deployment with `dist_init_addr` uses TCP sockets on the leader's network interface, so engines can move between joined nodes. The engine connects and says hello with its protocol version, build and number; the daemon compares major versions and welcomes it or refuses it. The engine reports `Starting`, starts its schedulers and executors, and reports `Ready` with its generation limits, video denoiser description and scheduler count, or `Failed` with the error. The daemon serves HTTP only once its engine is ready. Every request passes the leader's hold (`RequestHold`): while an engine is ready it goes straight to it, and while none is it waits; once the engine is lost and none takes its place, held and later requests fail with the reason and `/health` answers `503`.
- **Requests.** A submission carries tokenized requests under the daemon's identities. The engine routes each to its least loaded live scheduler and answers `Accepted`, naming the scheduler, or ends it at once with a `Rejected` event. Every event names its request. A request's events flow under a credit window: the engine sends at most 64 events (`EVENT_WINDOW`) beyond those the daemon reports consumed, so a slow client holds back its own request only.
- **Commands.** Per request: cancel (the client went away), stop (the daemon's decoder matched a stop string), acknowledge (this many public tokens complete no stop string), abort and consumed. For the engine: drain, after which it admits nothing more, reports `Draining` and ends every token request that generates text alone as migratable while the others finish; and shutdown, which ends every request as aborted, closes the executors and exits.
- **Migration.** A token request can move between engines; a readout cannot. Its engine ends it with a `Migratable` event, naming the cause (a drain or a loss of the ranks that held it), after every token and image it generated there; the leader's `Migrator` submits it again through the hold, carrying them, to the engine that serves next. The tokens are every token the engine counted as generated, in order: the text it published and the control tokens it did not (`ControlToken`: a token that opens an image or closes a round, or a token of a request that publishes no text), carried as `generated_token_ids`. A request that generates text alone continues its prompt with them: the engine computes their cache as part of the prompt, reusing the pages of them its cache holds as for any prompt, and generates after the last of them at the position the request had reached. Every token counts as generated: against the token limit and `min_tokens`, in the penalties and bad words, and in the request's usage, which charges only its own prompt as prompt. The daemon keeps its own state (the detokenizer, the stop-string matcher, the response being assembled), so the client reads one uninterrupted stream. A request that names no seed takes one from the migrator when it is first submitted, so its draws, keyed by its seed and token positions, repeat on every engine. Migrations caused by a drain are not counted; a request survives `migration_config.max_migrations` migrations caused by losses. An image-generating request carries its images too (below), and a video request migrates at a denoising step boundary (below).
- **Recompute preemption.** Admission reserves what a prompt takes and not what a request generates, so a cache filled while its requests decode leaves some of them unable to grow. The step's assembly notes each request it cannot grow with the units its growth needs, and the next step's reclaim asks the policy for a victim (`Scheduler::reclaim_shortage`): the default policy names the migratable resident of the lowest priority admitted last, as vLLM's recompute preemption does. The victim ends as migratable, and the `Migrator` submits it again with its tokens; it resumes from the pages it published, and its partial last page is copied into a unit of its own before its first forward. The shortage subtracts the free units and the units of requests already leaving, so no extra victim is named, and admission waits while a resident is starved. A request whose held and needed units exceed the whole cache ends with the length it reached. When every running request is starved, no batch is in flight and no request is leaving, the scheduler recomputes the one admitted last itself (`Scheduler::recompute_starved`).
- **Image preemption.** An engine preempts an image-generating token request at a completed call boundary: it offers no further call, waits for calls in flight, stores the unfinished image's committed latent trajectory in the host latent pools, and ends as migratable. Completed denoising steps remain visible to the client; an image decoding that completes during preemption publishes its image before the request leaves. The migrator carries a trajectory identity, stored step and layout record for the unfinished image. The successor rebuilds its conditioning context, pins the stored pages and continues at that step. A lost rank or missing optional pages causes recomputation from the request's image seed and image index; a numerics change follows the update's `keep` or `recompute` policy. Each completed image is a fact: `ImageDone` carries the decoded feedback input (`ImagePixels`, BF16 `[3, height, width]` values and their range), or the PNG when feedback reads the artifact. The migrator retains it with its token position (`GeneratedImage`) and clears the unfinished trajectory metadata. To rebuild context, `crates/scheduler/src/scheduler/generation/continuation.rs` follows the token and image decisions over the carried tokens, extends the prompt by decoded tokens, and writes each carried image through its cache close, feedback encodings and feature writes at their original logical positions. It samples nothing until the request reaches its continuation point. Feedback encoders reuse their host pools when available; otherwise they use the original posterior draw, determined by the request's input and generated image encoding order (`Call::latent_draw`). Image numbering, limits and usage include carried images. A rebuilt context with carried images shares no prefix-cache page, as for input images. The daemon preserves the response stream, suppresses repeated image starts and steps, and never exposes control tokens.
- **Video preemption.** An engine preempts a video request the same way whatever preempts it: a park for an epoch change, a sleep, an in-place weight update, or a loss of its ranks. The request offers no further call, and its calls in flight complete, which ends it at a step boundary; a request whose denoising is scheduled whole finishes instead. A trajectory past its first step and short of its last is then written to the host latent pools of its denoising ranks (see Storage and device storage), unless its ranks were lost, and the request ends `Migratable`, naming the steps stored (`denoised_steps`, zero for none) and the engine's record of where their pages lie and how each denoising rank laid its part of the samples out (`stored_layout`). The migrator gives every video request the identity of its trajectory (`Trajectory::id`) when it first submits it, and submits it again naming the steps stored and the record, or what it named before when the engine stored none. The engine admits a request that resumes a stored trajectory before every request that starts one, and pins the pages the record names before its latent preparation, which prepares the request as for step zero (its prompt's and conditions' encoder outputs read from the host encoder pools where another admission stored them and encoded otherwise, its prompt refined and its noise drawn, which compute what they computed before) and then copies the stored values into the bank it initializes, laid out in its own rank's pages whatever parallel configuration stored them, and commits the trajectory at the stored step, from which it denoises the steps left; when a page is missing, it starts from noise. A trajectory's state at a step follows from the request alone (its noise from its seed, and an Euler step from the samples and the step), so both continue the trajectory the uninterrupted request takes, and a resumed request's video is that request's.
- **Artifacts.** A generated image or video reaches the daemon as an artifact event whose shared memory travels as a file descriptor beside its frame (`SCM_RIGHTS`); the daemon maps it read-only and serves its bytes.
- **Statistics.** Each scheduler's statistics travel once a second as a snapshot the daemon exports as metrics.

### Epochs

An epoch is one build of the main process serving a deployment: a main process per node, its executors, their communicators, CUDA graphs and the storage they created. The daemon moves the deployment to another epoch without failing a request (`PUT /admin/config`; the entry is `crates/daemon/src/updates/`, which decides the layer, and the switch is `crates/daemon/src/updates/switch.rs`; `docs/admin.md`). The epoch's identity is the engine number of its first engine (`EngineArgs::epoch`), which keys its ranks' storage at the Storage Server, and its processes are children of their node's daemon at a launch generation of the deployment's group and rank. The four steps below are the engine side of the switch: the daemon starts the target's processes and commands theirs (`crates/scheduler/src/process_link.rs`).

1. **Precopy.** Each node starts the target's main process as a standby beside the serving one (`crates/daemon/src/updates/switch.rs`): it maps the weights it shares and the serving epoch's cache storage read-only, takes its programs, captures its graphs on its own graph pool and parks. Its preparation's transfers yield to the serving epoch's steps (`update_config.transfer_slowdown`), and serving goes on.
2. **Switchover.** The requests in flight warm the target's cache (below), the target is promoted and the serving epoch drains at a step boundary: its token requests end as migratable, image-generating ones included, its video requests are preempted at their next denoising step boundary, and a request that moves waits until the epoch that serves next takes it. The target admits nothing until the serving epoch stopped stepping.
3. **Probation.** The target serves on trial, with the previous epoch kept as `update_config.previous_epoch` states: drained and alive, or its processes exited and its weights kept, on the GPUs or in host storage. A fault of the target, or a threshold of `update_config.rollback`, reverts the update: the target drains, a target that failed is stopped, and the previous epoch serves again, started anew on its weights when its processes exited.
4. **Commit.** The previous epoch's processes exit; the pages its epoch committed stay in the host KV cache for any epoch whose keys reach them, until ordinary eviction; the claim of the target's epoch retires the previous epoch's storage at the Storage Server.

A target's cache warms through the host KV cache. A serving scheduler publishes each page of a request to the host KV cache as it completes, under a key of the page's tokens and of what computes them (`crates/scheduler/src/kv_cache/offload.rs`): the copy rides the next batch on the rank's copy stream, and the batch's output waits for it. A request that migrates carries its tokens, so the target's admission finds its pages there, loads them before its first forward and computes only what follows the last page the host holds. Before the switchover the daemon reads, in rounds, how far each request in flight reached the host (`crates/daemon/src/updates/warming.rs`, `Operation::Warmed`): it promotes once every tail is within `update_config.cache_tail_tokens`, and after the first round past that limit it caps the source's prefill at `cache_prefill_tokens`, which the promotion restores. The wait ends after a minute whatever is left, since a tail costs a recomputation and no correctness.

A target of another cache layout, or of other numerics, keys its pages otherwise and finds none of these: its requests compute their state again. So does a deployment without a host KV cache, and a main process of several devices, which keeps none yet.

A target runs on the serving epoch's cache storage, so the two must not write it at once, and a park gives none of it back. That storage keeps the name of the epoch that created it, which the serving process states when the target is built (`DescribeCache`); a process started again after a loss or a revert creates its own. A request reaches the target only once the previous epoch drained, and an epoch that serves again after a revert flushes its prefix index, since its target overwrote what it named; the pages it published stay in the host KV cache. When the previous epoch's processes exit during the trial (`update_config.previous_epoch`), its weights stay retained across their exit, and a revert stops the target and starts the epoch on them.

The pause, from the first promote to the last drained process, covers the serving epoch's last step and the drain; the update reports it (`pause_ms`), and the leader logs how long each migrated request waited.

### The channel

The scheduler's main process and each peer main process exchange the messages of `ipc` (`NewRequest`, `Batch`, `BatchOutput`, `MainProcessInfo`) over one stream connection per peer main process.

- **Connection.** The scheduler's main process listens on one Unix socket path and one TCP port. A peer connects to the scheduler when it starts: through the Unix socket on the scheduler's node, through TCP from any other node. Main processes and daemons accept no channel connection; the connections a main process accepts are its group's peer mesh and its collective store.
- **Registration.** A peer's first frame registers it: the group it serves (`worker_id`), its rank, the launch generation and the build. The scheduler numbers each launch of a group, and a relaunch takes the next number; the build is the package version plus a digest of the sources every artifact is compiled from, so the peers of one build carry the same value. The scheduler refuses a registration of another build or of a launch that is not the group's current one, and otherwise answers with the peer's launch descriptor, which carries every other launch value, among them the deployment's name of the peer's host, its identity in transfers.
- **Lifetime.** The same connection then carries requests and responses, and its close is the only death signal of a registered peer: the scheduler treats it as dead and the process exits. Before a peer registers, the scheduler learns of its exit from the daemon that started it.
- **Frames.** A frame is a length followed by one message in a serde binary encoding (MessagePack). The main processes are built from one workspace and replaced together, so the message types are the protocol's only definition. A frame carries a message of any size its `u32` length states; no launch setting bounds it further.
- **Waiting.** Each side blocks on its socket together with one local wake descriptor, which its own threads fire for work that did not arrive on the socket.
- **Processes.** The scheduler starts no process itself. It asks the leader's daemon, over the daemon's Unix socket, to start each node's main process on the node its parallel configuration names, to reserve the socket a group's first rank serves the group's collective store on, to stop a group ahead of its relaunch, and to claim the deployment at a node's Storage Server (an engine claims it at every node's, those that run none of its peers included, so that it retires another epoch's storage and keeps an epoch's weights wherever they lie, and each peer's launch names the other nodes' servers, whose epochs' weights it may receive); the leader serves its own node and forwards the rest to the node's daemon over that daemon's join connection, and every exit comes back the same way, naming the node, group, rank and launch generation. These messages are the process interface (`crates/proto/process.proto`), Protobuf that changes only by additions: a daemon keeps running while engines of later builds connect to it, and the two compare major versions when they connect. A main process is its daemon's child, leads a process group of its own and dies with the daemon; a scheduler whose connection closes takes its remaining peers on every node with it.
- **Data.** Tensors, prefix cache pages, latents and products move through the transfer mechanisms. Only a host product routed between hosts travels on the channel.

## The threads of a main process

A main process's threads are named by their role: the control thread, the scheduler threads, the executors and the blocking pool.

| Thread | One per | Blocks only on | Does |
| --- | --- | --- | --- |
| Control thread | process | The daemon's request interface, the daemon's process supervision and the epoch's peer main processes (`crates/worker/src/control.rs`), at the latest for the watchdog's deadline | Serves the process interface and the program commands, and reports a job that stopped making progress while the channels go on being served |
| Scheduler threads | DP rank | Its own queue and wake descriptor | Request state, the scheduling mechanism, each step's event batch and plan, batch assembly and completions |
| Executors | device | The device's work | The only issuer of work on the device's streams: forwards, graph replays, copies, captures and rebinds, in submission order (`crates/worker/src/job.rs`) |
| Blocking pool | pool | One kind of host work | Module loading, transfer reads, shared-storage retirement, media encoding and muxing, and condition media reads (`crates/worker/src/blocking.rs`) |

Threads exchange messages only. The control thread never waits for a job, so a slow launch, a driver call that waits on the device or a job that does not end does not keep it from serving the channel, handling a cancellation or reporting status. The executor is the only issuer of work on its device's streams, so each stream's order is the order the jobs were submitted in; it posts a job's completion once it has issued the job's work, not once the device has finished it, and storage a job used is read, rewritten or freed afterwards only behind something that waited for the device (a read in the job, a stream wait the job recorded, events the job completes after, or the fences that retire storage). A runner is called only on its device executor's thread and only one job at a time, which is why the runner trait takes `&mut self` and carries no synchronization (`crates/worker/src/runner.rs`).

Blocking host work runs on bounded pools of threads (`<pool>-<index>`) that each serve one kind of work: image preparation, prefix cache imports, transfer reads and shared-memory retirement. Signals, VMM descriptor grants, a video runner's host reports and, during startup, the engine watch are dedicated threads (`crates/worker/src/blocking.rs`).

## The numerical library

The mathematics is Rust, in three crates. `crates/nn` holds the layers and the tensor views a batch is computed over; `crates/ops` holds the kernels and their launch code, one package per operator and backend under `crates/ops/kernels`; `crates/models` holds the model families — their configuration, checkpoint mapping, layouts and the request semantics of the video rules (`crates/models/rules`), which the daemon plans and presents requests with before submission. The Python tree this repository replaced, whose last commit is `7c6b75e9b`, stated the same mathematics, and the numeric diagnosis still compares against it (`crates/models/minimax-h3/tools`). A comment or a section below that cites a `uniserve/…` or `uniserve_kernels/…` path names a file of that tree, the reference that states the rule; the implementation is the Rust module beside it.

### Runners

A runner serves one block's phases: it owns the captured graphs of those phases, the arena their activations live in and the slot state a token batch advances (`crates/worker/src/runner.rs`). `submit` turns one batch into the device work that serves it after staging the batch's host columns; `precopy` prepares the graphs the next generation needs of the program layer's update, `switchover` takes effect at a batch boundary, and `purge` releases the graphs that still reference a replaced generation after its last batch.

| Runner | Serves |
| --- | --- |
| `CausalLmRunner` (`runners/causal_lm.rs`) | A causal language model's batches: prefill, decode, verification, selection and scoring, planned into captured buckets, with the request slots and the KV cache views its steps advance |
| `EncoderRunner`, `DenoiserRunner`, `DecoderRunner` (`runners/{encoder,denoiser,decoder}.rs`) | A video or image model's encoders, denoiser and decoder, each in its own bucket space |
| `MediaRunner` (`runners/media.rs`) | Host-side media work: decoding condition media, encoding and muxing the produced units |

Each device executor holds the runners of the blocks the deployment places on that device (`crates/worker/src/runners/mod.rs`); they share the graph tables, the pools and the staging rules and differ in the capability they call and in what a bucket of theirs means.

### Computations and their batches

A block's phases are served as jobs on the device's executor (`crates/worker/src/job.rs`): the engine submits a batch, the executor stages its host columns into the pinned arena, builds the device views the kernels read (`nn::TokenBatch`, `nn::KvView`) and issues the forward, the graph replay or the copies on the batch's stream (`crates/worker/src/runners/causal_lm.rs`). Every batch goes through one sequence of steps (`crates/worker/src/batch.rs`): open (bind the calls to their requests), lease output storage and the calls' device predicates, bind completion flags, seal (end reads, validate every owner's update), commit once the job carrying the device work completed (writes become visible, calls pending), and materialize once the output fences complete, finishing any host work such as image or video encoding. A failure before the commit point fails the batch's calls and the process keeps serving; a failure at or past it is fatal to the process.

**Predicates.** A call the engine queues behind an unresolved call carries a predicate: the predecessor's relayed token for a decode, otherwise its `uint8` completion flag. No host reads a predicate. The batch leases a call's `uint8` predicate on the device and copies it into the call's completion flag and into an output word of its own; a false predicate leaves every state the call would change as it was: image and video denoising write the latent they read (the ledger flips the banks at the commit either way), latent preparation keeps its bank and its slot's tables and conditioning, and a text prefill copies the predicate into its slot's continuation predicate and runs as a gated row, as a relayed decode does. Once the batch's fences completed, the host reads the word: a false one reports the call `Predicated`, without products.

**Token batches.** A computation over the prefix cache reads host columns the engine built: the call columns, the forward columns, the flat tokens, the JSON of the rare per-call fields and the feature tensors that JSON names (`crates/worker/src/runners/columns.rs`). It writes its results into page-locked output words the batch lent and into a record column: a header, one record per call (its progress, the extent of its selection and logprob words, its candidate range, the offset of its tail) and the segments and tails those name. The executor checks the records before the commit point and the engine decodes them into each call's pending output. Values the next batch reads, a decode's selected token or a denoising step's continuation, go to the computation's relay staging, which the batch copies into the products that carry them.

**Prepared batches.** A video batch's step names every call with its request, slot, inputs and outputs. The runner's preparation states what each call reads and writes: input indices, each output's shape, region and storage, whether a host task fills it, and its publication. The batch then leases every read, binds every write and takes each denoising trajectory's banks from its ledger (`crates/worker/src/memory/latent`); the job runs the calls on those tensors, followed by the producer fences and exports of what they wrote, and the ledger applies the steps once the job completed. A write a host task fills (condition media, an encoded unit, the muxed MP4) is deferred: the media runner fills it and reports each finished task (batch, call, row, status, a value and a payload such as the MP4's bytes); the report thread reads them into a mailbox and wakes the control thread, which completes each deferred call once its reports arrived.

An image batch is prepared the same way (`crates/worker/src/runners/products.rs`): an input image's pixels prepared on the image host pool or a resident image product, the feature and image products at their prepared shapes, the decoded bytes lent from the batch's output words, and the trajectory's banks from the latent ledger. A denoising batch over the prefix cache also reserves the slots of its guidance prefixes and passes their attention rows.

### Attention

An attention kernel is chosen from the device and the installed kernel libraries by the executor's plan (`crates/worker/src/plan.rs`), which names the operator a step launches and the implementation of it. Three attention operators are built from `crates/ops/kernels`, one package per implementation under `<operator>/<implementation>`: `paged_attention` (`triton`, `trtllm`), `dense_attention` (`f32`, `fa4`) and `sparse_attention` (`sm90`, `sm100`, `sm120`, one package per compute capability). `attention_backend` is the attention provider name of the rank's model (`crates/ipc/src/launch.rs:167`), which the executor receives unchanged; a deployment that names a backend the build does not provide fails at startup with that name. A host-planned kernel's plan is shared by every layer of one execution context that has the same layer shape and batch signature, so a forward plans once, before the replay of its graph.

## CUDA graphs

The executor captures and replays every graph it serves (`crates/worker/src/graph.rs`). A captured forward is a breakable graph: one or more captured segments and, between two segments, a graph break whose work the replay performs on the host after enqueuing the segment before it. The graph's storage is Rust's, mapped through `platform`'s allocator.

- **Capture.** Each forward is run eagerly once at its shape, so kernels compile outside capture, then captured into the graph pool the rank reserved for its stream: a pool allocates device storage Rust maps as segments are asked for, at addresses that stay fixed while any graph addresses them (`crates/platform/src/allocator.rs`). Each runner captures its shapes largest first, so smaller captures reuse the pool blocks of larger ones (`crates/worker/src/runners/warm.rs`). Warmup runs in phases the runner states and every rank of a group runs in the same order, because capture includes collectives: each phase names its computation, the scratch table lengths of slots `1..` and each step's attention rows, and Rust installs those tables on the scratch units the engine never allocates and selects each step's pages before the runner runs the phase.
- **Replay.** A forward with a graph writes its inputs into the executor's columns on the computation's stream, plans the attention kernels the step launches, and replays the graph; its outputs are read from the graph's output buffers into the batch's output words.
- **Keys and buckets.** Each runner keys its graphs by what fixes their shapes: the causal-LM runner by decode row bucket and sampler, by prefill row and token bucket, output selection and media variant, and its selections by task bucket, samplers and top width (`crates/worker/src/plan.rs`); the denoising and decoding runners by layout, prompt capacity and unit shape. A verification graph accepts different draft lengths per row, and its drafter pass and reported log probabilities use separate graphs on the same computation stream.
- **Policy.** The graph policy is resolved after loading: `auto` serves eagerly a path that declares no capture, `off` serves eagerly, and `full` requires every path captured. Once startup seals the graph tables, a configured shape without a resident graph is an error. The ranks of a group capture the same shapes in the same order. No host callback is ever placed on a stream or inside a graph (`crates/worker/src/captured.rs`).
- **Residency.** Warmup grants each device's graph pools what they hold when capture begins plus the grant left after product storage not yet resident, and checks the pools against it before the runner seals (`crates/worker/src/graph.rs`).

## Storage and device storage

| Owner | Allocated by | Contents |
| --- | --- | --- |
| Rust | the CUDA driver | everything that holds request state, is read or written natively, or crosses a process: the prefix cache unit pool, slot tables, the latent pool, product arenas, forward inputs and outputs, pinned staging, export ranges |
| Rust | `platform`'s allocator | graph pools and operator scratch: each a reserved address range whose physical storage Rust maps as the pool asks for segments (`cuda::VirtualPool`, `crates/platform/src/allocator.rs`), at addresses that stay fixed while any graph addresses them; scratch has pools of its own, so no graph's activations share its blocks |
| Rust | the CUDA driver's virtual memory | weights, in retained storages (below) |

Capacity planning measures device storage after loading and assigns the rest of the device's quota to the prefix cache and media storage (`crates/worker/src/capacity/device.rs`). The quota is `⌊total × mem_fraction_static⌋` of the whole GPU, which every epoch of the deployment and the host's Transfer Server share, and the host's Storage Server keeps the GPU's storage ledger of it (below): a rank's grant is the quota less everything the ledger books beside its own process (the storages the server retains, another epoch's items, the Transfer Server's) and less what its process holds as NVML reports it, never more than the device has free. Exclusive storages a predecessor of the rank's scope and epoch left that no owner has taken yet count as free, and an owner that allocates new storage first releases them. Once warm, the rank books its graph pools and its process storage in the ledger, which refuses them past the quota. Storage is organized by owner in `crates/worker/src/memory`:

- **Prefix cache** (`prefix_cache/`): the unit pool, block tables and imports of attention state. The checkpoints of the cache layers a model keeps per request (a recurrent state) fill the pool's state group: its page `k` holds every such layer's state after token `(k + 1) * block_size - 1`, and a table names units only for the pages that hold one: a prompt call keeps the state at the last page boundary it reaches, a decode call at the boundaries that are multiples of `kv_cache_config.state_interval`. A request whose reused prefix ends at a boundary resumes from its checkpoint there; reuse ends only at a boundary whose checkpoint the device, host or storage tier holds, and checkpoint pages publish, offload and import as K/V pages do (`uniserve/prefix_cache/checkpoints.py`, `crates/scheduler/src/kv_cache/mod.rs`). A deployment that speculates (`speculative_config.num_draft_tokens`) keeps its drafter's K/V, the draft cache, in the pool's draft group: optional derived state, whose entry at position `i` is the drafter's evaluation of the target's hidden state at `i` and the token at `i + 1`, so a draft page's prefix hash covers the token after the page. The group keeps the pool's columns and plane size (each of `L` drafter layers spans `columns / L` columns of a unit, `uniserve/prefix_cache/units.py`), so an epoch that adds it maps its predecessor's segments. Reuse boundaries and admission count the required groups alone; a request's draft pages are allocated as far as free units allow, released from running requests before another request's required pages would fail, and published, offloaded to the host KV cache and loaded back as the other groups' pages are.
- **Latent cache** (`latent/`): denoising trajectories in two banks of pages per slot, with versions exported to other ranks, and a video denoising rank's host latent pool (`latent/host.rs`).

### The Storage Server

Each host runs one Storage Server (`uniserve storage serve`) per serving user, which the host's daemon starts when the host has none, in a session of its own, so restarting the daemon never ends it. Clients connect through a Unix socket owned by the user (`$XDG_RUNTIME_DIR/uniserve/storage.sock`, else `/tmp/uniserve-<uid>/storage.sock`) and pass file descriptors with `SCM_RIGHTS`. The server holds storage and never interprets it: it keeps the descriptors of CUDA VMM allocations (POSIX file descriptor handles) and host memfds, never creates a CUDA context, and moves no bytes itself; clients compute every key and copy on their own streams, or have its Transfer Server copy for them.

- **Claims.** The engine has each host's daemon claim the deployment (its served model name) at that host's server and hands each main process the claim's token in its launch descriptor. The daemon holds the claim for as long as it runs. A claim releases the scopes the engine no longer places; `uniserve storage retire --deployment NAME` releases a deployment that is no longer served, and `list` prints what the server holds.
- **Committed epochs.** Each claimed epoch keeps its immutable outputs private until the daemon publishes it with `PublishEpochs`. Initial engines publish after warmup; a successor remains private throughout preparation and trial. Publication makes its immutable outputs readable by other epochs and uploads its completed host pages to the KV storage. Independent committed replicas share those outputs under the same deployment. A group commit publishes every successor together at each node before retiring any predecessor; epoch identifiers imply no ordering of visibility. Retiring a candidate discards its private pages, while a committed epoch's pages remain reusable after retirement. Storage Server hot restart preserves the committed set.
- **Weights.** A main process keeps each rank's loaded parameters and buffers in read-only retained storages (`crates/worker/src/memory/weights.rs`, `uniserve/loading/retained.py`): one per torch storage loading made, the smaller ones of a device packed into one. Every parameter is a part of a logical tensor, the whole matrix the checkpoint names: the module that partitions it declares the logical tensor's shape, the partition unit of each dimension (a head's channels, one expert) and the indices the rank holds (`logical_tensors()`, `uniserve/distributed/logical.py`, from the layer's `Distribution`, which besides PyTorch's `Shard` and `Replicate` divides position-mod-N, in named sub-blocks each split on its own, and strided compressed indices). A storage's storage is allocated in chunks, each a CUDA VMM allocation of its own mapped back to back with the next, cut where a configuration of the parallel degrees in use (`load_config.parallel_degrees`) cuts a logical tensor along a field's outermost dimension: stacked experts at expert blocks, attention projections at head groups, vocabulary rows at their shares, each cut rounded down and up to the allocation granularity (`crates/storage/src/manifest/layout.rs`). A chunk is retained under the key of what its bytes are: the regions of the logical tensors it holds, where in it they lie, and each tensor's loading fingerprint (the identities of the files supplying its inputs, assignment rectangles, dtype, encoding and declared derivations). A derivation names its output tensors, checkpoint inputs, numerical parameters and function revision (`uniserve.loading.weights.Derivation`). Constructor constants are keyed by their bytes. The exact manifest identity also includes the providers that determine encoded layouts: kernel library versions. Tensor source identities exclude that choice, so an encoding change can reuse retained numerical values through canonical conversion. The key names neither the rank nor its GPU: the Storage Server keeps one copy of a key per location, and a rank asks for the copies on its own GPUs, so any epoch whose rank needs a region on a GPU finds the chunk holding it there. A manifest of each tensor's checkpoint source and representation and each storage's fields, their logical parts and its chunks is keyed by the structure and the rank's position in its parallel configuration, whatever GPUs it runs on. A change of code that keeps those revisions keeps the weights. An in-place weight update (`/admin/update_weights`) rewrites the tensors where they lie and renames the copies on the rank's GPUs after the new checkpoint at the server. A starting rank maps the storages whose chunks it finds on its GPUs read-only and binds their tensors instead of reading the checkpoint. Loading is collective, so the ranks that load together agree on what to read: the tensors any of them misses, or everything when one has no manifest; a change to one tensor's loading inputs reloads only the affected tensors. Packed storage remains readable for its unchanged fields, and the transfer planner can copy those fields independently of changed neighbors. Each rank moves what it read into retained chunks, mapping instead each chunk the server retains on its GPU under the same key (another epoch's), publishes the chunks it created and maps all read-only; a chunk lives while any epoch retains it. When any of the ranks that load together finds no manifest of its own and every one of them finds the weights the deployment's other epochs retain on the host or on the deployment's other nodes (each manifest names storages, each on the GPUs that hold all of its chunks, and their fields of tensors whose fingerprints are the model's; the fingerprints of the whole model select them, whatever tensors a rank holds, so every rank that loads with others selects the same storages in the same order, those their shared copy manifest names; another node's server is listed over TCP and its manifests read inline, `Request::Read`), they receive their weights instead of loading them (`crates/worker/src/memory/weights.rs`): each materializes the target shapes and encoded storage with `rank.load_model(unread=True)`, without reading checkpoint values or generating dummy values. The planning model is released before receiving storage is allocated. Unmeasured links use copies from available source chunks into scratch storage, repeating smaller chunks to collect two 64 MiB measurement windows. For an online change, planning ranks run through the deployment's process interface on their assigned nodes; the daemon reads the same source manifests as the ranks, chooses the rank assignment within the declared device set, and supplies an executable `Transfer` containing the request and copy manifest. Cold-start ranks with no daemon plan gather their target layouts and measured links to plan the receive. Each rank then maps the chunks of the same key on its GPU, creates the rest under receiving keys, which the Transfer Server writes, submits its copies as one `Background` transfer (a copy from another node's GPU naming that node's region, `Region::Remote`, which the Transfer Server copies over the NVLink fabric or READs), zeroes the padding the manifest names, and binds its model while the bytes arrive; only tensors with numerical regions absent from the source manifests are read from the checkpoint. Encoded groups with declared canonical forms convert on the receiver: the Transfer Server gathers the source fields, a low-priority preparation stream reorders their encoded values and scales into canonical storage, the manifest copies the logical regions, and the stream writes the destination encoding. One target group and one source group are held at a time; the planner includes their rounded allocation sizes, and the Storage Server ledger tracks the retained scratch. Conversion kernels write borrowed buffers without device temporaries. Copies complete before conversion, and conversion completes before transfer, publication or release. Before capacity planning the rank waits for the transfer, retains the received chunks read-only under their keys with its manifest, and releases the receiving keys. The host region of a layer stack streamed from host storage is a read-only host storage among them. Loading stores every encoded weight in the layout its kernel provider declares (`uniserve/loading/layout.py`), and preparation verifies it, so the retained bytes are those the kernels read.
- **Copy manifests.** How one epoch's state becomes another epoch's under another parallel configuration is a manifest computed from both epochs' storages (`crates/storage/src/manifest`). Target ranks take the GPUs holding the most required regions, with ties resolved by the busiest link's completion time. Matching chunks in the same physical storage map read-only; other regions are assigned to sources using measured link bandwidth, then become strided byte copies through their numerical encodings. Encoded fields use canonical conversion storage where required, padding is zeroed, and missing regions are reported. A chunk's `Binding` separates its actual retained storage from its rank's execution GPU: `Rank` follows GPU assignment, `Local` names host or device storage, and `Remote` names a Storage Server endpoint and its host or device storage. `storage_offset` allows a chunk to borrow a region of a retained allocation. Planning charges each physical chunk's link, including Host↔Device and remote Host links; GPU UUIDs identify the same device storage across hosts. Host staging requests are planned per destination host, whose Transfer Server submits the READ. Expert redistribution uses the same conversion path on a background preparation thread, leaving inference on the original allocations until the common commit boundary. The daemon caches the numerical plan. `Manifest::bind(request, host_sources).spans()` resolves its sources from the submitting host's bindings while preserving GPU assignment and numerical copies. It produces `Region::Tensor` and `Region::Remote` directly, combining rows within chunk boundaries and splitting rows that cross them. Source and destination allocations remain retained until transfer completion. The copy manifests are computed in `crates/storage/src/manifest`.
- **Exclusive storages.** The prefix cache planes, the buffer pool and the latent banks are exclusive storages with one writer, keyed by their scope, name and shape; a device cache's value planes are eight segments of their units, each layer's part of a segment a storage of its own mapped back to back, so that the tail of the cache can be given back while a standby engine starts or the deployment sleeps and created again at its addresses (`docs/admin.md`): a restarted rank of the same scope takes the storage its predecessor left, after the server shoots that predecessor down if it still holds write access (SIGKILL to its process group, its exit, and NVML no longer listing it on the GPU). An owner resets only storage created for it; a storage a predecessor left keeps the finite values it last wrote. A standby maps them while its predecessor serves from them; after a crash the engine's cache index starts empty, so nothing reads them before a unit is recycled for its next owner.
- **Storage ledgers.** The server keeps one ledger per GPU (by UUID) for each deployment that uses it (`crates/storage-server/src/ledger.rs`), so that the deployment's two epochs and the host's Transfer Server stay within one quota on a GPU they share. The quota is `⌊total × fraction⌋` of the whole GPU for the fraction the deployment's ranks configure (the smaller one while two epochs that state different fractions hold storage there). The server books what it retains, each device storage once however many scopes and epochs map it: read-only storages as the weights, a storage its rank marks with its KV cache segment as that segment, any other exclusive storage as the epoch's fixed part. The processes book what it cannot see (`Request::Book`): each warm rank its graph pool and its process storage under its scope and epoch, the processes of one scope and epoch (a rank's executor, and its relaunch or promoted standby) counting as their largest booking, and the Transfer Server its staging, and its CUDA context while it holds one on the GPU, in every ledger of its GPUs (at the bytes it measured when it started, `Measured`, which every ledger of the GPU also reports as `transfer_context`, booked or not, so that an epoch change's preparation leaves room for the context its transfers will take); every ledger of a GPU also states the bandwidth the Transfer Server measured from host storage to it (`host_link_bytes_per_second`). A rank that ends in order withdraws its bookings, and the driver frees its storage with it; a rank's process that is lost leaves its bookings no other process of its scope and epoch books reserved under that scope and epoch, so a successor cannot take a lost rank's storage before its relaunch books it, which takes each item over as it books it, and the reservation otherwise ends with the epoch's retirement or the deployment; the Transfer Server's bookings end with its connection; an epoch's storages end when the head retires the epoch (all but its weights when the head keeps its weights alone; weights the head moved to host storage leave the GPU's ledger, and return to it when it moves them back), and a segment a successor maps, booked once for both epochs, is then the successor's alone: the commit's handover is a transfer on the ledger. The server refuses any booking or new device storage that would take a ledger past its quota, naming every entry. The ledgers survive a hot restart, and `list` prints them; the engine reads them through each rank's executor (`crates/scheduler/src/scheduler/cache_storage.rs`) to plan an epoch change (`crates/scheduler/src/scheduler/ledger.rs`), and through each node's daemon for `GET /admin/config`.
- **Host KV cache.** The server keeps page pools of host storage, one memfd of equal slots per deployment, page layout and NUMA node, shared by every rank of the deployment whose pages have that layout, a standby engine's included: a page's key is seeded with the model's fingerprint and the identity of what its forwards compute (`crates/storage/src/manifest`: every component's declared function revision and the formats of the tensors it holds), so pages of other weights or other numerics share the pool without matching; a rank takes the pool on the host NUMA node closest to its GPU, whose pages the server binds to that node. With `kv_cache_config.host_tier`, each GPU rank maps a pool for each of its cache groups once its engine sized the epoch's host KV cache: every rank holds one token count, the device KV cache's tokens times `kv_cache_config.host_ratio`, which each host's server lowers for the whole epoch to what its budget holds over the bytes a token takes on all of the epoch's ranks there (`HostCacheSize` in `crates/scheduler/src/kv_cache`), since a reuse needs every rank's pool to hold its pages; a rank that replaces a lost one, relaunched or a promoted standby, maps the same pools at that count before it serves, so the pages the lost rank offloaded stay loadable. The scheduler decides reuse in the host KV cache with the rules of each group's attention type that decide it in the device cache (`crates/scheduler/src/kv_cache/manager.rs`): a reuse ends at a page boundary every group accepts, full attention needing every page before the boundary and a sliding window only the pages of its window before it. At admission the scheduler pins every group's pages that follow the request's device prefix match, takes the deepest boundary every group accepts with them (a boundary one group rejects does not end the walk), and has the request's first prefill batch load the pages the boundary needs into new units: a full-attention group's pages from the device match on, a sliding window's pages of its window that the device does not hold. A request publishes each page once its batch computed it: its prompt's pages, and for a request that generates text alone from a prompt without context images, the pages of the tokens it generated, each written by the decode that reads its last token and keyed as the same page of its migration's prompt, which continues with those tokens. Full attention offloads every published page into a reserved slot with a later batch, which its output commits; a sliding window offloads only the window before an aligned boundary: every `kv_cache_config.boundary_interval` pages of the largest block size, the last boundary a reissue of the prompt can reuse, and the last boundary of its published prompt pages. The window's pages are reserved while the request's table still holds them, as one window the pool evicts whole, and with the last full-attention page before its boundary, its anchor (`crates/scheduler/src/kv_cache/offload.rs`, `crates/storage-server/src/pages.rs`). A rank issues a batch's page loads and offloads on its copy stream, in a job of their own, as soon as the batch arrives, so they overlap the forward the previous batch runs; the batch's forward waits only for its loads, and its output for its offloads. Before the engine ends its ranks at shutdown, it lets the batches in flight complete and sends each group's remaining reserved offloads in a batch of page offloads alone, so every page it reserved reaches the host KV cache. A published page keeps the key it was offloaded under, and a withdrawal of the cache's units (an epoch change's shrink, a parked epoch's eviction) holds the idle cached pages it evicts and offloads them again under those keys before the units go: the pool answers a page it holds as present, and the others are copied and committed. A rollback discards what the epoch on trial published: pages nobody reads leave the pools at once, the others when their readers unpin them. Committed pages of other numerics are not discarded at a commit, since other Replicas of the deployment share the pools; their keys never match a successor's, and ordinary eviction replaces them. A page is one page of one group on one rank, layer-major: keys, values, and FP8 scales.
- **Host encoder pools.** Every rank that executes an encoder (a video model's text, vision and condition encoders; an image model's vision and latent encoders) maps its host's encoder pool (`crates/worker/src/memory/encoders.rs`), a page pool shared by the deployment's ranks on the host in every epoch of the deployment, and reports it with the identity of what computes each encoder output it writes: the weights' values and the declared function and format identities of the encoder's modules, and for an image encoder the image transform its pixels are prepared by (`EncoderPoolInfo`). The scheduler keys an output's pages by its name, the identity and the digest of what the encoder read (`crates/scheduler/src/encoder_outputs.rs`), so requests that read the same in epochs that compute it the same, the same request resumed among them, find each other's outputs. The daemon names, in every video request, the digests of what each of its encoders reads (`DiffusionRequest::encoder_inputs`): the presentation's tokens for the text encoding, and the content and plan of each condition's media, but not where they are published, for the vision and latent encodings. An image request's encodings are keyed by the image (an input image's `ImageInput::digest`, which the daemon computes over its bytes, a request-dependent preprocessing parameter and the request's cache partition; a generated image's digest over the values or the PNG its feedback reads and the request's cache partition, which the engine knows once the image's decoding resolved: a feedback encoding queued behind its image's decoding is computed without the pools, and the continuation that carries the image looks it up and stores it) and, for an encoder that samples its posterior (`ImageEncoderOutput::draws`, a latent encoder), the request's image seed and the encoding's draw (`Call::latent_draw`); an encoder that does not sample is keyed by the image alone, so requests of other seeds share its output (`crates/scheduler/src/scheduler/encodings.rs`). The engine's encoder cache keeps an image's encodings on the device under the same key and is the nearer tier: an input image's encoding it holds is pinned without a call. When a video request is admitted, every page of each of its outputs is pinned before its encoders are offered, and an image encoding's pages before its call is planned, on the replica the call runs on: when all are pinned, the output's encoder calls read their rows from the pool instead of computing them (`Call::host_output`); otherwise the pages are reserved, the calls compute the output and the rank that wrote rows copies them to the pool on its encoder's stream, and the pages are committed once every call of the output succeeded. An image's features take the pages of as many rows as the cache tokens of the block they write, whose rows the executor prepares from the image (`ImageEncoderOutput::row_bytes`). A request whose cache policy reads no cached output computes its encodings and stores them, and one that writes none stores nothing. A pool holds the outputs of twice its group's request slots (the requests an epoch runs and as many preempted ones waiting to resume) at their largest, for an image request one image's features; an output evicted beyond that is computed again.
- **Host latent pools.** Each video denoising rank maps a page pool of pages the size of one page of its latent banks (float32 values, its own share of a trajectory) on its device's NUMA node. The pool is the rank's: the same rank (group and rank) of every epoch of the deployment whose pages have that size maps it, whatever its parallel configuration, and it holds every trajectory the rank can have stored at once, twice its request slots: one preemption stores at most the trajectory of each slot's request, a request that resumes a stored trajectory is admitted before every request that starts one, so an epoch has at most its latest preemption's trajectories still to restore, and an epoch on trial stores its own while the trajectories of the epoch it succeeds stay for a rollback. A trajectory evicted beyond that is a miss, and its request starts from noise. It reports the pool with the identity of what it computes (the weights' values and the model's function and format identities, as its KV cache pages are keyed) and its region, what determines its share of every request's samples: the page geometry, the video plan that selects a request's layout, the rank's coordinates in the denoiser's mesh and its rows of every startup layout (`LatentPoolInfo`). A request's latent preparation reports how each denoising rank's slot pages hold the request's samples, as the copy manifest library describes a storage (`CallOutput::latent_layouts`, `uniserve.executor.video.plan.SampleLayout.storage`): each modality's complete sample is a logical tensor of rows by channels, the rank holds a run of its rows (the denoiser's division of the packed sequence), and its values lie row-major at the modality's offset of the slot's pages. The scheduler keys a stored page as that library keys a chunk of the slot's pages (`storage::manifest::Storage::paged`): the logical regions the page holds and where, with the content of the values, the deployment's latent seed (the distinct identities of its denoising ranks), the trajectory's identity and the steps it took (`crates/scheduler/src/trajectories.rs`). The key holds every input that determines a page's values and nothing else, neither the epoch nor the rank nor the parallel configuration, so an epoch whose denoising computes the same finds what another stored, a page two configurations lay out alike is one page, and an epoch that computes other numerics finds nothing. A preempted request's pages that hold its samples are reserved in every denoising rank's pool and copied from the bank holding its committed step on the rank's copy stream, behind the batches that used the banks, by a batch of latent offloads alone (`Batch::latent_offloads`), whose output commits them; the request leaves with the record of every rank's pool, host, region and layout. A resumed request's pages are pinned, from that record, until its latent preparation's result (`Call::latent_restore`): every restoring rank reads the stored pages of its own host, mapping another rank's pool on first use, and plans the copy manifest from the stored ranks' layouts to its own (`crates/worker/src/memory/latent/restore.rs`), in which a page it lays out as a stored rank did is one whole-page copy and every other region a run of bytes from the stored page that holds it, which the executor copies into the bank (`Denoiser.restore`). The same path serves a request resumed under the parallel configuration that stored it and under another (another Ulysses degree, other ranks): a change of distribution moves values and computes none. The restore hits only when every restoring rank's host holds what the rank needs, the pages of a stored rank of its own region or else the whole of every stored sample, so a resumed request whose stored ranks lie on other hosts than the ranks that need their rows starts from noise. An epoch on trial keeps the trajectories it stores its own until its commit, as it keeps its KV cache pages: a rollback discards them, and the previous epoch computes the requests it takes back from what they named before. Stored trajectories leave the pool least recently used first.
- **Transfer Server.** The server runs a Transfer Server (`uniserve storage transfer`, `crates/storage-server/src/transfer`), a child process it starts again 5 s after it ends, which copies bytes between the storage the server holds; the CUDA contexts the copies need are that process's, so a fault in a copy ends it and never the server. A head or a rank submits a task of spans, each a length of bytes from a source region and offset to a destination region and offset, with the update it serves and a priority, highest first: promotion (what a promotion waits for), warming (filled pages copied into the next epoch ahead of its promotion) and background (weight moves and the rest) (`Request::Transfer`). A region is a retained tensor's storage, offsets counted from the tensor's first byte; a page pool; or a device allocation of another host of the NVLink fabric, by a fabric handle its creating process exported, which imports only while that process holds the allocation (CUDA exports no fabric handle from an allocation imported through its POSIX descriptor); or, as a source only, a retained tensor or page pool of another host, named by that host's Storage Server endpoint (`Region::Remote`). The server checks that every region of this host is storage of the submitter's deployment and every span lies within it and writes no read-only tensor, refusing the task whole otherwise, gives the Transfer Server each allocation's descriptor before the first task that copies it, takes it back when it releases the allocation, and relays the task's progress and end as events. Another host's region is checked by that host when the task runs: the Transfer Server connects to its server's TCP endpoint as a peer (`Role::Peer`) and asks it to expose the task's regions there (`Request::Expose`); that server checks them as it checks a task's sources, has its own Transfer Server register their allocations with its NIXL agent (UCX backend, `crates/nixl`, which binds NIXL 1.5.1's C API, `libnixl_capi.so`, itself and resolves its entry points when the library loads), and answers with the agent's metadata and each region's address; the destination's Transfer Server loads the metadata, registers its destinations with its own agent, checks each span against its region, and posts NIXL READs, whose completion it polls on the host, since a READ passes through no CUDA stream; a span of rows at a pitch is one READ of a descriptor per row. A device allocation whose creating process recorded its fabric handle in its storage record (`StorageRecord::fabric`) is exposed with that handle, and the destination's Transfer Server copies its spans over the NVLink fabric on the copy engines of the destination's GPU, rows at a pitch as one pitched copy, whenever the handle imports there, and READs them otherwise. The agent registers storage pinned, at registration, and outside UCX's registration cache: under UCX's default on-demand paging the first READs' page faults hold a link to a few GB/s (host storage read between two GB200 hosts at 4.1 GB/s on demand, 79 GB/s pinned; pinning a 64 GiB host region takes 1.7 s), and the cache, which learns of an unmapping only through UCX's hooks of `munmap` that the Transfer Server's direct system calls bypass, would hand a region mapped again at a released address the released region's registration, so that READs into it land in storage no longer mapped. A read-only allocation's host storage is mapped read-only and registered for remote reads alone, which needs the UCX and NIXL builds with the read-only registration patches (`--nixl-library`, `docs/configuration.md`); with other builds its registration fails, and so does the task that READs it. A process of another host also reads a small tensor of bytes that a scope of its deployment retains read-only in host storage, such as a weight manifest, inline over the same TCP endpoint (`Request::Read`), up to 64 MiB (`READ_BYTES`); a longer one is refused. A task whose source host is unreachable, runs no Transfer Server or holds no such region fails, naming that host and the reason. The exposure lasts until the destination's Transfer Server ends it once its task ended (`Request::Unexpose`), or its connection closes, or the source's server takes the allocation back; the submitter keeps a remote source retained and unchanged until the task ends, as it does a local one. The submitter keeps the sources unchanged and the destinations unread until the end, which the Transfer Server reports only after the host saw every copy complete, so no CUDA event crosses a process. A copy runs on copy engines, never as a compute kernel: those of the destination's GPU, else the source's (the first GPU's between host storage and another host's GPU of the fabric), the CPU between host buffers, and the network adapters for a READ from another host. When the Transfer Server starts it measures every link (each GPU to itself, each pair of GPUs that can address each other, each GPU to and from host storage on its NUMA node, host to host) and the device storage NVML attributes to its CUDA context on each GPU, and `uniserve storage list` prints both; it then releases its contexts. It holds a GPU's context only while it has work on the GPU (`crates/storage-server/src/transfer/contexts.rs`): a task's pieces hold the GPUs their storage lies on or their copy engines run on, a lane's thread its GPU while it copies, an exposure to another host the GPUs of its device allocations until that host ends it; and an explicit transfer session the GPUs its operation uses across successive tasks. Cache warming opens a session on each source and target owner before copying and closes it after the final round or cancellation (`OpenTransfer`, `CloseTransfer`); closing the client also ends its sessions. Sessions create no context until a task first uses it. The first use of a GPU books the context in every ledger of the GPU at its measured bytes (`Request::Book` of `transfer_context`) and then retains it, so a ledger without room refuses the booking and the task that needed the GPU fails, naming the ledger; once the last hold ends, the device mappings, host registrations, NIXL registrations, streams and events made in the context are released, the context with them, and then its booking, so NVML lists the process on no GPU it does not use. The context's retain moves into the cost of the first task on an idle GPU. A link from another host (its GPU or its host storage to a GPU or host storage here) is measured at its first use: its chunks run one at a time, 64 MiB each, until the faster of its first two contiguous ones (the first READ over a new connection also sets the connection up) gives its bandwidth, which the listing then prints too. It cuts each copy into chunks lasting `--transfer-chunk-us` at the link's bandwidth, so a copy engine turns to the executing epoch's own copies and to a higher priority between chunks; each link runs the chunk of its highest priority first, tasks of one priority in submission order, and keeps a byte budget, its whole bandwidth at start, which a head halves (`Request::Throttle`), down to 1/64, and restores by 1/8 of the bandwidth per second; a head that names no link halves every link a task of its deployment copies over, and restores every link a halving reduced. While a successor epoch prepares, the leader halves the budgets of the change's links on every node of the deployment as the leader knows it then (a node that joined for the successor included), through the serving engine and each node's daemon's claim, each second a serving scheduler's step takes more than `update_config.transfer_slowdown` past its step of the same batch size and execution (graphs, or eager forwards with `update_config.eager_prepare`) before the preparation, and restores them once none does (`crates/daemon/src/interference.rs`). A task is cancelled by number or with every task of its update, and when its submitter's connection closes; it ends once its chunks in flight completed. The server submits tasks of its own to move an epoch's weights between its GPUs and host storage, at a head's request: an offload (`Request::Offload`) takes every device copy of read-only tensors the epoch alone retains, admits host storage of their whole size under the host-storage rule (refused whole otherwise), creates a memfd of each storage's size and copies each into it; a restore (`Request::Restore`) admits each storage's size against its GPU's ledger, has the Transfer Server create retainable device storage of that size on the GPU it came from, in that GPU's session (`Event::Allocate`, answered with its POSIX descriptor in `Request::Allocated`; the Transfer Server keeps no handle of it) and copies each back. Once every copy of a move ended, the tensors' copies lie at their new locations and the storages they left are released, so each GPU's ledger books the move's effect at once; a copy that fails leaves every tensor where it was and releases the copies. The head's request is answered when its move ends. When the Transfer Server ends, every task it held fails at once, and the next one maps what new tasks copy again; its NIXL agent ends with it, so another host's READ of this host's storage in flight fails, and the next agent, of another name, registers the regions again when a peer next asks, whose Transfer Server then forgets the previous agent and loads the new one's metadata.
- **KV storage.** With `kv_cache_config.mooncake`, the server runs a Mooncake connector, a child process it starts again when it ends (`crates/storage/src/connector.rs`). The connector maps every page pool, registers it with Mooncake, and writes each committed page to Mooncake as the object `uniserve_{page key}_{kv head offset}-{kv head count}`, which names no deployment or host. A lookup tells for each page key whether its page is in the pool, in Mooncake or absent. When the pages Mooncake holds would deepen the boundary every rank's pool holds by at least 256 tokens, admission prefetches them into reserved slots, waits for them at most 1 s plus 0.25 s per 1024 tokens, and computes the pages that did not arrive. Prefetches hold at most half of a pool's slots. Mooncake's master evicts objects; the connector never removes them.

Retained host allocations are admitted by the Storage Server before it creates their backing (`AllocateHost`). The executor receives an exclusive byte tensor and its writable descriptor through the ordinary storage reply; its epoch retains the allocation until it releases the key or retires. Host admission subtracts the server reserve and the unallocated bytes of both page pools and retained host storages from available storage (`HostStorage::unallocated`), so sparse allocations still awaiting their first write cannot each spend the same headroom.

### Transfers

Transfers go through one module per mechanism in `crates/worker/src/transfer`: `local` (in-process borrows), `posix_shm` (POSIX shared memory on one host), `vmm` (CUDA VMM allocations exported in place or through a pool, imported by fabric handle or by a descriptor from the exporter's grant socket) and `channel` (bytes carried in the location). A read runs on a transfer-pool thread with one stream per thread and device: it claims the chunk and waits on the host for the claim, orders its copy behind the handoff and the producer's event (a cross-device read waits for the producer on the host), copies, acknowledges, and drains its stream before its task completes, which returns its bytes and read credit. A VMM read imports the allocation's handle, maps it and opens its ready event. An export states whether its allocation is resident (the producer's arenas, pools and cache planes, kept until it closes) or made for that export alone: a reader keeps its mapping of a resident fabric allocation for every later read of it until its transport closes, and releases any other mapping with the read. A rank's transfers share one byte budget and one set of read credits; an exported product holds its bytes once, whatever number of mechanisms publish it, and they return when its last backing physically retires. A rank holds one read credit per queued call (a media rank at least one per concurrent artifact import of each slot and one per rank of the deployment) and reports their count (`MainProcessInfo::transfer_tickets`); the engine keeps no more transfer calls reserved than the narrowest rank holds.

## Startup

Every rank of a group runs these phases in the same order, because several are collective:

1. The main process reads its launch file, and its control thread connects to the daemon (`crates/daemon/src/engine/launch.rs`, `crates/worker/src/control.rs`); until serving starts, a watch ends the process at once if the daemon's connection closes. The executor makes its device's primary context current.
2. The model's configuration is read from the checkpoint and the parallel configuration validated against the components each rank holds (`crates/models`).
3. The ranks' communicators are planned and created (`crates/nn`, `crates/platform`).
4. The weights are loaded, or bound from what the same model at the same rank position in the same parallel configuration retained (`crates/worker/src/memory/weights.rs`): the checkpoint reader reads each source file front to back into the page cache before mapping its tensors, so ranks loading one cold file do not fault it page by page. A rank that loaded moves its weights into retained storage and publishes them.
5. The executor's runners are constructed with the rank's settings and bound to the streams, scratches, graph pools, prefix cache tables, relay staging and latent banks Rust allocated (`crates/worker/src/runners`, `crates/worker/src/memory`); a component placed with `"weights": "host"` moves its layer projections into a page-locked host region and a ring of device slots.
6. Capacity is planned from the runners' manifests and measured storage, and the rank's storage owners are allocated (`crates/worker/src/capacity`).
7. Warmup runs in the runners' phases: every captured forward runs eagerly once at its shape, so kernels compile outside capture, and is captured, each runner's shapes largest first. Paths that always run eagerly run once too, so no serving request selects a kernel first.
8. The graph pools' residency is checked and the runners seal their graph tables; the rank reports its capacities and the shapes it prepared to the engine: one image shape per captured guidance-branch count (`MainProcessInfo::image_warmups`), the image and latent sizes its codec graphs hold (`captured_images`, `captured_latents`), the bounds of one image step (`image_capacity`), the rows of one diffusion LM sampler chunk (`diffusion_lm_step_rows`), and the tokens its image denoiser's image-unconditional guidance branch attends to when that branch does not read the request's own context (`image_unconditional_token_ids`), which the engine reserves and prefills as a guidance prefix of its own beside the negative prompt's.
9. The engine warms the serving path with real requests through its scheduler (`crates/scheduler/src/warmup.rs`): a token request of a prefill and a decode, a group of equal one-block diffusion LM requests for each row count of a sampler chunk, each submitted in one command so its steps run with exactly that many rows (the one-row request generates a second block, so a commit prefill runs), and a two-step image request per image shape at the guidance scales of its branch count. A request the deployment's generation limits refuse a client is left out. Serving starts once every warmup request finished.

## Serving

**A text decode step.** The engine sends a `Batch` whose decode calls name request slots. The control thread opens it (binds the calls to their requests), reserves the prefix cache's tables and attention pages and leases the output words, and submits the job. On the device's executor thread the causal-LM runner's forward reads the call and forward columns, gathers each call's request constants by slot, computes the Philox draws of each sampled position from the request's seed, picks the decode graph of the smallest row bucket that holds the batch, writes the forward's inputs into its columns (slot indices, finish flags, the rows' sampling parameters and draws) and replays it: the graph gathers tokens, positions and attention metadata from slot state on the device, runs the model, projects the final-position logits and selects each row's token: greedily, or by sampling under the row's temperature, top-k (up to 128 candidates), top-p, min-p and penalties, all of them tensor contents of the graph. A batch that needs token sets, logit biases, typical-p, reported logprobs or a sampled top-k beyond the 128 candidates selects after the forward with the `select` graph of its task bucket and samplers, whose controls are tensor contents (each task's sampler, parameters and draws, token sets as bitmasks, its slot's row of logit biases), with the same kept-set computation; its `score` graph reports logprobs, scored on the model's raw distribution. `execute` enqueues the copies of the selection words into the lent output words and of the selected tokens into the relay staging, and returns the records: each call's progress and where its words lie. Once the executor has checked the records and the batch is sealed, the commit replays the commit graph, which installs the selections into slot state, so the next step can be queued before this one's result is read. When the job's event completes the control thread decodes the records and words and returns the `BatchOutput`. Prefill (which also carries verification rows) has its own graphs, and a verification selects eagerly; with tensor parallelism every rank replays the same graph and the collectives inside it were captured with it.

**A speculative decode step.** In a deployment that speculates, a decoding request's call is a verification: a prefill-kind row of its committed token followed by the drafts the drafter proposed after its previous step, as many as the scheduler chose for it (from zero to `num_draft_tokens`; zero, a row of one token, while its draft cache is incomplete), so the rows of one batch differ in length. Attention reads each row's query length from the forward columns as it does a prompt chunk's, and the recurrent layers (`crates/nn`) evaluate a verification row token by token without advancing the slot's state (`crates/worker/src/memory/prefix_cache`). The `verify` selection returns each row's accepted draft prefix and the token after it (`crates/worker/src/runners/causal_lm.rs`), and for a request that asks for logprobs scores a row per position the verification may commit, each token under the logits it was selected at, of which the executor reports one per committed token (`CallOutput::token_logprobs`); the recurrent layers then advance the slot's state over exactly those tokens and write the checkpoints the request's tables hold at the page boundaries they pass. After every forward of a speculating computation, the drafter pass (`crates/worker/src/runners/causal_lm.rs`) writes the draft cache entries of the forward's positions whose next token is known (the row's next token, a prompt chunk's `lookahead` token after its last, the selected token after a verification's accepted ones) and, for each call that asks for proposals, chains its steps from the call's last committed position, each step reading the previous step's draft and hidden state; the pass indexes rows by the device's acceptance counts, so it reads nothing on the host. The proposals reach the engine in the call's record words, and a request's next verification, which carries them, waits for that result instead of being queued behind the call; it carries its current token among its host tokens rather than relayed, since the drafter pass reads a row's tokens on the host. A refill call (`DRAFT_REFILL`) is a prompt-kind row over positions whose target K/V the cache already holds: it evaluates the target again, writing neither the target's pages nor the slot's state (its recurrent layers start from the checkpoint at its first position), so that the drafter writes those positions' entries; the engine schedules refills in the prompt token budget a step leaves idle (`crates/scheduler/src/scheduler/speculation.rs`).

**A FastH3 video request.** The daemon plans the request with the `models` crate's rules. On every rank the executor admits it at its exact size (`start`), and a denoising rank holds the layout that serves it (without graphs, a request with conditions evaluates in a layout prepared for it). The text encoder's graph of the smallest prompt capacity that holds the prompt runs on its tensor-parallel group; latent preparation writes the request's noise and state rows; each denoising step copies the slot's committed latent pages from the bank the ledger names into the sample tensors, replays the layout's graph on every rank of the sequence-parallel group and copies the result into the other bank; video and audio decoding replay one graph per temporal unit; the decoded units transfer to the CPU ranks, whose media runner encodes each unit and muxes the MP4.

**Batches.** Every batch goes through the same steps on the batch skeleton (`crates/worker/src/batch.rs`, sequenced by `crates/worker/src/plan.rs`): open (bind calls to their requests), lease output storage and the calls' device predicates, bind completion flags, seal (end reads, validate every owner's update), commit once the job carrying the device work completed (writes become visible, calls pending), and materialize once the output fences complete, finishing any host work such as image or video encoding (a video batch's host work completes through the executor's reports). A failure before the commit point fails the batch's calls and the process keeps serving; a failure at or past it is fatal to the process.

## Parallelism

- **Streams and jobs.** A rank with a CUDA device issues every forward's work on its primary stream, the full-device stream of its primary device, in the jobs its executor performs (`crates/worker/src/job.rs`). The components' module streams fork from it, so their work overlaps on the device while forwards follow one another on the host. A rank that maps a host page pool also has a copy stream, a full-device stream of the cache's device that the batches' page copies are issued on, in jobs of their own ahead of each batch's forward (`crates/worker/src/stream`).
- **Collectives.** A layer calls its communicator; in serving its functions are NCCL collectives of a `platform` communicator bound to the forward's stream (one communicator per stream group Rust plans, `crates/platform/src/nccl`), captured with the forward.
- **Expert forwards.** The executor's expert union (`crates/worker/src/parallel`) agrees on each step's source and capacity with the union's other members over their host group, then runs the step; a member without tokens replays the join graph of the agreed capacity. A distributed expert layer's weight copy from its peers is a graph break.
- **Schedulers.** Each DP rank has a scheduler: its own thread, KV cache and the groups it drives. A replica is one of the groups a deployment file's `replicas = N` expands a group into.

## Failure handling

Errors cross with a stable code, whether they are fatal to the process, and the phase they occurred in. An error in a runner call before a batch's commit point fails that batch, unless it marks a broken invariant, which is fatal; at or past the commit point every failure is fatal. An error in resource work fails startup, or at serving time the batch that needed the resource. A launch failure or a driver error is fatal to the process, and the engine replaces its failure domain: the rank's group, or every group that shares an expert epoch (`expert_world_size`, `crates/scheduler/src/core.rs`), whose ranks hold that epoch's communicators. Every group of the domain terminates its ranks; the token requests they held end as migratable (`MigrationCause::Loss`), and the daemon submits them again with their generated tokens and images, to wait for the relaunched ranks, while the readouts fail. The domain is relaunched together, its groups form their communicators again, and their weights and exclusive storage come back from the host's Storage Server: each relaunched rank lays its KV cache planes out as the lost rank held them, taking back the segments it held and leaving absent those it gave back, rather than sizing them afresh against a device whose storage a successor epoch prepared beside the serving one may share, and it must then report the lost rank's capabilities, its planes as they stood included, or the group closes. The relaunch runs on a thread of its own (`Relaunch`, `crates/scheduler/src/executors/group/relaunch.rs`), so the scheduler keeps serving the scheduler's other groups while the relaunched ranks start; each group of the domain admits work again once it has installed them, and a relaunch that fails closes the domain's groups. A group that keeps a standby (`worker_config.standby`) is replaced by promoting it instead: its ranks started beside the group's, mapped the group's weights and exclusive storages without write access, captured their graphs on the warmup scratch units, which the scheduler never allocates, and parked; on promotion each takes write access once the Storage Server has the failed rank out and serves at once, and the group starts a new standby (`crates/scheduler/src/executors/group/standby.rs`). A group on one host without an expert epoch keeps a standby rank group of its own and promotes it within the step. The groups of an expert epoch, and a group on several nodes, keep a standby epoch instead: once every group of the domain serves, the domain launches each of them a second time at a rendezvous of its own, so the standby ranks form their own communicators and capture graphs over their own workspaces, and parks that epoch. A loss in the domain stops only the serving launches, and the replacement round promotes the standby epoch instead of relaunching: every rank is asked to promote before any answer is awaited, since a suspended epoch restores its expert workspaces together, and the groups install the promoted ranks and offer the next standby epoch. A suspended epoch's transport workspaces that cannot keep their addresses (DeepEP's windows, the NVSHMEM heap of colocated MegaMoE) are freed while it parks; its promotion creates them again and captures the graphs that run expert steps anew, on the scratch units, before it serves. A promotion that fails relaunches the domain.

A lost main process takes its executors with it. Its client ends every request it held as migratable, the leader's daemon holds new requests and starts a new engine process under the same claims, whose ranks find their weights retained, and the hold then serves the new engine every held and migrated request. A request survives `migration_config.max_migrations` migrations caused by losses; when the new engine does not start, held and later requests fail.

A driver call that does not return stops the executor inside its job. The control thread keeps serving the channel and, once a job has stayed in flight for the stall bound (half the engine's watchdog timeout, `worker_config.watchdog_timeout`, sent in the launch descriptor), reports to the engine the job's batch, its runner method, its calls and how long it has run (`MainProcessResponse::Stalled`). The engine logs the report, fails the affected requests with an error naming the stalled job's forward, and replaces the group. A device whose context an illegal memory access or a device-side assert left unusable runs none of the work behind the failure, so the completions of the jobs in flight never post: while a job has been in flight for a second, the control thread probes each of the rank's devices once a second and, when the driver returns such an error, fails the rank with it at once. The engine's watchdog covers a main process that stops answering altogether.

A main process's orderly close ends with a reset of its primary contexts before the process exits. The reset releases the driver state the process created, including the shared-memory file (`/dev/shm/cuda.shm.*`) the CUDA driver makes for a process's interprocess events and removes only when the context is destroyed. A main process that loses its daemon with nothing in flight takes the aborted close and then the reset; with work in flight it ends at once. A process that ends without its orderly close first removes the driver file and the NCCL shared-memory names (`/dev/shm/nccl-*`) its mappings still link. The daemon that reaps a main process observes the death before reaping and removes that process's driver files and recorded NCCL names while the zombie still holds its pid. A main process's startup failure reaches the engine as the process's own error.

```text
crates/models/          the model families: rules/ (family registry, Qwen3 checkpoint facts and prompt rules, MiniMax-H3 video rules), minimax-h3/, qwen3-moe/
crates/proto/           the interfaces across builds (Protobuf): the process interface between daemons and main processes, and the request vocabulary
crates/ipc/             the channel to a main process's peers: messages, registration, launch descriptor
crates/storage/         the Storage Server's protocol and client, and the copy manifests
crates/storage-server/  the Storage Server, its Mooncake connector and its Transfer Server
crates/platform/        the only crate that calls CUDA: devices, memory and its allocator, streams and events, graphs, kernel loading and launch, NCCL, cuBLASLt, cuDNN, NVML, loaded at run time
crates/ops/             operators and their launch code; kernels/<operator>/<backend>/ holds one package per kernel
crates/nn/              tensor views, layers, capability traits, checkpoint reading and weight layouts

crates/media/           H.264/AAC encoding, MP4 muxing, condition media decoding and host resamplers (libav* FFI)
crates/scheduler/          the main process's mechanism: schedulers, KV cache allocation, executor groups, process launch through the daemons, the request interface's service
crates/worker/        the executors and the numerics they issue: runners, graphs, arenas, the memory owners, capacity, transfers, the program-layer update
crates/daemon/          a node's daemon: process supervision, the node's Storage Server claim, the process interface's service; on the leader the HTTP/OpenAI API, model profiles, input and output processing, metrics and the engine's client
crates/frontend/        the deployment's application process: the HTTP and OpenAI API, input and output processing, facts and migration
crates/program-server/  the Program Server: protocol and client, the package manifest format, storage, the compile queue

```

Dependency direction, as the crates' manifests state it: `proto <- {ipc, models, engine, executor}`;
`ipc <- {engine, executor}`; `{ipc, nn, ops, proto, storage, platform, media} <- executor`;
`{executor, ipc, nn, proto, scheduling, program-server, storage} <- engine`;
`{engine, frontend, models, ops, platform, program-server, proto, storage} <- daemon`;
`{platform, nixl, storage} <- storage-server`; and the root package over all of them. The engine
knows no model family: what a video request asks of its model (its conditions, the denoiser's
description) crosses the engine as bytes the model family encodes (`models::video::Conditioning`,
