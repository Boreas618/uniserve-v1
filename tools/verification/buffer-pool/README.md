# The buffer pool's design model

The model of `specs/buffer-pool.md` and what checks it. Nothing here needs a device.

| File | What it is |
| --- | --- |
| `KvCore.tla` | The design model: the buffer pool's handlers, the work it defers until a stamp is reached, copies and tasks in flight, tiers, regions, the trial of an epoch, the loss of an engine, crossings (`Replicate`: a block's content brought to the memory of a group that reads its owner's class, `Readers`) and host copies valid per host part (`HostParts`, `GroupParts`); and its neighbours: an executor that meets A1 to A4 with batches of unbounded delay and a control plane that issues any request in any order. Each rule R1 to R11 is a guard in force when its name is in `Rules`; each hazard H1 to H14 (`specs/kv-cache-s0.md` §6, and H14 of `artifacts/buffer-pool/p4-design.md`) is behaviour switched on by its name in `Hazards` |
| `KvP1.tla`, `KvP2.tla`, `KvP3.tla`, `KvP5.tla`, `KvP6.tla`, `KvP7.tla`, `KvP8.tla`, `KvSafety.tla` | The safety properties as formulas over `KvCore`, one module per property; `KvSafety` is the conjunction of P1, P2, P3, P5, P6 and P8 that `KvProof` proves `IndInv` implies |
| `KvFinality.tla` | P4 as two temporal properties under stated fairness |
| `properties.toml`, `pins.sha256`, `pins.py` | The property list; each entry and its module are pinned by hash, and `pins.py check` fails when one differs |
| `KvInductive.tla` | `IndInv`, the inductive invariant under the design (every rule in force, no hazard) |
| `KvProof.tla` | The TLAPS proof, under the assumptions `Design` and `Sizes` |
| `KvProofP7.tla` | `IndInv => P7`, under `Design`, `Sizes` and `Finite` |
| `KvFrame.tla` | Typing and frame lemmas the step proofs share: what an action that leaves a part of the state alone keeps of each conjunct of `IndInv`, and what taking a stamped request, retiring a deferred item and filling an owner's position keep |
| `KvStep1.tla` to `KvStep11.tla` | The inductive step for each group of actions (`Next1` to `Next11` of `MC_Apalache`; `Next11` is the crossing's): `IndInv /\ NextN => IndInv'` |
| `KvStep.tla` | The step for all of `[Next]_vars`, `Spec => []IndInv`, `Spec => []Safety` and `Spec => []P8` |
| `KvSafeP7.tla` | `Spec => []P7` from `Spec => []IndInv` and `IndInv => P7` |
| `MC_*.tla`, `MC_*.cfg` | The configurations TLC searches; `MC_Apalache.tla` fixes constants and generates the states for Apalache |
| `addresses.smt2` | The address arithmetic as thirteen goals for z3 |
| `predictions.md` | Every run with the prediction written before it and its outcome |
| `suite.sh` | The whole suite, with the verdict expected of every run |
| `tlc.sh`, `trace.py` | Run one configuration (`RULES=NoRn` leaves a rule out, `HAZARDS=Hn` switches a hazard on); print a counterexample from a TLC log |
| `MC_Pool.tla`, `MC_Pool{Core,Copies,Transfer,Tiers}.cfg` | The buffer pool alone: its handlers taken with requests of any stamps, with no batch, executor or scheduler; the relation the Rust buffer pool is compared with |
| `agreement.sh`, `agreement.py` | L1: the Rust buffer pool's enumeration of every request sequence (`buffer-pool-verify enumerate`, `crates/storage-server/src/buffer_pool/enumeration.rs`) against the states of `MC_Pool`, per configuration (`MC_PoolCross`, `MC_PoolParts`, `MC_PoolTrial` for those with constants of their own) |
| `KvTrace.tla`, `steps.py` | Steps of the Rust buffer pool against `MC_Pool`'s steps: each transition, from its recorded state, must be a path of `PoolNext` to the next state, checked on each part of the pool it touches (closed under what holds what, renamed in order); `steps.py` writes the windows of a run, by layout and size, as `MC_Trace` runs and runs TLC on them in parallel |
| `agreement_steps.sh` | L1 step by step: every transition of the enumeration (a state, its input, the next state) of `core`, or of the configurations named, is a path of `MC_Pool`'s steps; a transition made by hand that the model does not allow is reported |
| `replay.sh` | The trace of a run of the Storage Server (`storage_config.buffer_pool_trace`, `crates/storage-server/src/buffer_pool/trace.rs`): replayed (`buffer-pool-verify replay`, `crates/storage-server/src/buffer_pool/replay.rs`) on a new Rust buffer pool with every completion checked against the run's and `check()` after every input, and every transition between its states checked against `MC_Pool`'s steps |
| `mutations.py` | L4: one replacement per rule R1 to R10 in the Rust buffer pool's source, each of which the crate's tests must catch |
| `apalache_step.sh`, `cti.py` | The inductive step under Apalache per group of actions; print a counterexample to induction |

The tools are TLC (`tla2tools.jar` 1.8.0) under a JDK 21, Apalache 0.63.0, TLAPS (`tlapm`) and z3 4.8.9; the scripts read their directory from `TLA_TOOLS`.

```bash
tools/verification/buffer-pool/suite.sh                         # everything; about 50 minutes on 144 cores
tools/verification/buffer-pool/suite.sh pins mutations hazards  # the quick parts
tools/verification/buffer-pool/tlc.sh MC_Trial                  # one configuration
tools/verification/buffer-pool/agreement.sh                     # L1; about 25 minutes
tools/verification/buffer-pool/agreement_steps.sh               # L1 step by step, core; about 4 minutes, most of it the enumeration
tools/verification/buffer-pool/replay.sh TRACE_DIR              # a run's trace: its replay, and its states against the model
tools/verification/buffer-pool/mutations.py                     # L4; about 5 minutes, edits the crate in place and restores it
tlapm --threads 48 --stretch 6 KvProof.tla                # the proof, in this directory: then KvFrame,
                                                          # KvStep1..KvStep11, KvStep, KvProofP7, KvSafeP7
apalache-mc check --init=Init --inv=IndInv --length=0 --cinit=ConstInit MC_Apalache.tla
apalache-mc check --init=IndInit --inv=Safety --length=0 --cinit=ConstInit MC_Apalache.tla
apalache-mc check --init=IndInit --inv=IndInv --length=1 --cinit=ConstInit \
    --tuning-options='search.invariantFilter=1->.*' MC_Apalache.tla
```

## What is established

Terms. Checked: no violation in a complete search of a stated configuration. Proved: safety of the design model, under the stated assumptions. Not proved: liveness; that the implementation refines the model. A run that times out or stops at a bound is INCONCLUSIVE.

- **Checked (TLC).** P1, P2, P3, P5, P6, P7 and P8 hold in the fourteen configurations of `suite.sh`, among them `MC_Cross` (a group that reads, in a memory of its own, what owners of another group hold), `MC_HostParts` (two groups copying with the same part index on two hosts), `MC_HostSplit` (a group on one host beside a group across both) and `MC_Tiers` (the host region resized beside prefetches, puts, saves and restores); P4 holds in `MC_Finality`. P7 is violated by the hazard H12 and by leaving out R2, P8 by leaving out R3 or, for a store's fill, R5 (the part `validation`). Each rule R1 to R11 left out, and each hazard H1 to H14 but H6 and H13's safety side, violates the property `suite.sh` states for it; H6 and H13 violate P4. `IndInv` is an invariant of `MC_Cross`, `MC_HostParts` and `MC_HostSplit` (`predictions.md` entry 43); the other configurations were checked against it before crossings and host parts (entry 41).
- **Proved (TLAPS), under `Design`, `Sizes` and, for P7, `Finite`.** `Spec => []Safety`, where `Safety` is P1, P2, P3, P5, P6 and P8: `Init => IndInv` and `IndInv => Safety` (`KvProof`, 217 obligations), the step `IndInv /\ [Next]_vars => IndInv'` group by group (`KvFrame` and `KvStep1` to `KvStep11`, 13,882 obligations) and its assembly by PTL (`KvStep`, 146), which also states `Spec => []P8`; `IndInv => P7` (`KvProofP7`, 139) and `Spec => []P7` (`KvSafeP7`, 6). Every module proved from a clean cache, every obligation proved, none omitted (`predictions.md` entry 45), and proved again, over earlier runs' fingerprints, after `ReclaimedWith` and `Lose` took their present forms (entry 54) and after `Resize` of the host region was modelled (entry 55). `Sizes` states, of the configuration, that each group's host parts are host parts, that a memory is not a host part, and that a group reads only groups of its own epoch.
- **Checked (Apalache), for the constants of `MC_Apalache` and collections of at most three elements.** `Init => IndInv`; `IndInv => Safety`; the inductive step of `IndInv` for each group `Next1` to `Next11` (entry 44).
- **Proved (z3).** The thirteen goals of `addresses.smt2`, under A8.
- **How `IndInv` was found.** Apalache and TLAPS gave counterexamples to induction from states no behaviour reaches, each answered by strengthening `IndInv` with a clause TLC then checks on every configuration (`predictions.md`, entries 28 to 34, 36, 41); for crossings and host parts, it was extended from the design's argument and checked by TLC, Apalache and TLAPS (entries 43 to 45).
- **Not established.** Liveness (P4 is checked, not proved, and its `TaskFinality` states neither a transfer's nor a crossing's task), and that the implementation refines the model (below).

## The implementation against the model

- **L1, states (`agreement.sh`).** The Rust buffer pool is driven through every sequence of requests, `completed` values, task results and deadlines of six small configurations (`core`, `copies`, `transfer`, `tiers`, `cross`: two memories, the second group reading what owners of the first hold; `parts`: two host parts, a group copying with one and a group with both). After every step the pool's own check holds: every unit is in exactly one place, a block's references equal its holders, a private block is in one place, a pin is of a cached block, an entry is valid in its owner's group, memory is in one region. Every state reached, written in the model's terms (with the free units as runs, each group and owner named under its session's epoch, each epoch's trial and whether its session is closed, the epoch on trial each cached copy is visible to alone, the stamps each piece of waiting work still waits for, one line per release and stamp, the keys of commits, copies and tasks, and the host parts a store, a save or a prefetch writes), is a state of `MC_Pool` under the same configuration: 1,825 states against the model's 5,944 projected states (core), 44,383 against 247,976 (copies), 136,092 against 189,586 (transfer; the enumeration tells apart states that differ only in what the model does not state, such as the order of freed slot rows), 1,364 against 4,738 (tiers), 1,348 against 2,336 (cross, `MC_PoolCross`), 1,936 against 3,988 (parts, `MC_PoolParts`). It compares states, not steps.
- **L1, an update (`trial`, `MC_PoolTrial`), by states and step by step.** Two sessions of two layouts over one device memory: the serving epoch with its group and region A, and the target, on trial, with its group, its own memory and region B over A's memory with units of the same size; one chunk of that memory, which A's unit 1 and B's unit 1 both occupy (R10), in A at first; an owner each, one key, one position, no copies. Besides the requests of `core`: a resize of either region by one unit, which relays the chunk between them, the target's update committed (`publish`), its session ended (`close`: its engine lost and its regions closed, the model's `Lose`) and its update rolled back after it (`roll-back`). The enumeration reaches 1,214 states and 6,241 transitions. By states, each is a state of `MC_PoolTrial`, of 10,654 projected states (3,998,272 distinct states of the model, 5 min 37 s through TLC's dump). Step by step, every transition is followed, in 6,793 windows (4 s with 12 jobs), none outside the model: among them 525 commits of the update (91 with a copy visible to the target alone, R8), 1,050 ends of the target's session, 82 rollbacks and 608 resizes (342 of A, 266 of B). The configuration has one chunk because a second, held by one region while the other relays, takes the model past 91 million distinct states, which TLC's dump, written by one thread at about 900,000 states a minute, would take hours to pass to the projection; such a configuration also reaches a key cached on the device in both regions, which is outside the model, since the model caches a key in one device block (it would need a key's copies per region).
- **L1, steps (`agreement_steps.sh core copies transfer tiers cross parts trial`).** Every transition the enumeration reaches in the configurations is a path of `MC_Pool`'s steps from the transition's state to the next (`KvTrace.tla`), each checked on the parts of the pool it touches: 6,563 transitions of `core` (7,810 windows, 3 s), 184,341 of `copies` (209,370 windows, 88 s), 640,598 of `transfer` (821,282 windows, 243 s), 3,791 of `tiers`, 4,490 of `cross`, 5,696 of `parts`, with 32 jobs, and those of `trial` above; a transition made by hand in which a commit takes effect before its stamp is reported. Outside the model, which has one class: the transitions from a state with a key cached as a stored trajectory (25,698 in `copies`, 1,872 in `tiers`, 1,518 in `parts`), since the enumeration names a trajectory and a KV block by one key, which A6 excludes. The Rust buffer pool's R1 for owners is stronger than the model's (a number below one taken on the queue pair is refused), so an owner the Rust pool states as gone matches a model owner never attached.
- **Traces (`replay.sh`).** With `storage_config.buffer_pool_trace` the Storage Server's buffer pool thread records every input it acts on and every completion its pools produce (`specs/buffer-pool.md` §18). The replay drives a new pool with the inputs, runs its `check()` after every input, and stops at the first completion that differs from the run's or the first inconsistency; every transition between the states it writes is checked against `MC_Pool`'s steps from its recorded state, on the parts of the pool it touches (`specs/buffer-pool.md` §18, `steps.py`). E2's traces of a serving deployment (E1's Qwen3-30B-A3B load), on rank-1 at nice 19 with 32 jobs: the smoke slice on `478aaf612` (14,813 inputs: replay 91 s, every transition followed in 20,168 windows, 51 TLC runs, 20 s), the failed control on `478aaf612` (26,742 inputs: 259 s; 37,848 windows, 95 runs, 60 s), and the smoke slice on `da78a9be9` (27,073 inputs: 221 s; 23,894 windows, 61 runs, 41 s; `replay.sh` end to end in 292 s), each with every completion equal and every check clean; the model part kept host memory within a few gigabytes. E5's smoke traces (a 32,768-token prompt of 512 blocks held by one owner, with fill prompts of its size: windows with up to 257 copies in flight and allocations and pins of 128 positions), with 16 jobs: rank-2's (31,540 inputs, replay 319 s; every transition followed in 33,264 windows, 86 TLC runs, 151 s) and rank-1's (63,994 inputs, replay 1,260 s; 65,668 windows, 166 runs, 535 s), the prefetches from the peers and the loads of several keys outside; E2's smoke on `da78a9be9` again after the change (23,894 windows, 70 s). A state states its free units as runs, so it grows with what is held and waiting: the traces of E7's refused starts of a Qwen3.6 hybrid deployment, with a 65,792-unit host region and a 2,103,296-unit region of another class, write 97 KB and 87 KB of states for 916 and 821 inputs (15 GB in 7 minutes when every free unit was listed), and every transition is followed (a resize's 12,927 grown units each in a window of its own); E5's rank-2 smoke writes 11.2 GB, every transition followed with 12 jobs in 159 s. States with several sessions are checked as the model states epochs: E4's smoke (75,720 inputs, an update's target open beside the serving epoch over the same layout, the serving epoch's update committed) and E3's restart (79,294 inputs, a pool's image handed over), every transition followed but the opens, closes and images (45,741 and 47,320 windows, 181 s and 211 s with 12 jobs). A state there takes about half a megabyte, so a run's states take gigabytes in `$REPLAY_WORK`. E7's draft point, a Qwen3.6-35B-A3B deployment speculating with a draft model whose cache pages are blocks of the class 1 taken from the KV region (228,708 inputs, replay 6 min, 21 GB of states), and its smoke slice (72,924 inputs): every completion equal and every check clean, and every transition the model has terms for followed (47 and 49, 68 s and 22 s with 12 jobs); outside, among others, the class 1's requests (5,395 and 3,568), the states with a key cached in it (222,997 and 69,104), and the states in which an owner holds a draft page in the KV region (58 and 55). E13's traces of deployments with a parked standby, whose serving engine and standby each open a session of one engine epoch (named `e1` and `e1-2`, each one of the model's epochs) until the serving engine is killed and the standby takes over: the standby smoke slice (18,419 inputs) and the TP2 slice's two ranks (26,198 inputs, and 18 on the host whose sessions have no group there), every completion equal and every check clean, and every transition followed (18,412, 26,093 and 12, in 116 s, 211 s and 1 s with 12 jobs) but the opens, the images, the closes that close a KV region (the last session's, and the TP2 slice's second loss, before a standby had parked) and loads and stores of several keys; the serving engine's close beside its standby is the model's `Lose` of its session's epoch. E13's whole kill-standby and promote traces (64,657 and 83,706 inputs, and 14 on promote's second host), whose serving engine's session closes beside its standby with 32 owners live and about a thousand gone: every completion equal and every check clean, and every transition followed (64,650 in 39,942 windows, 62 s; 83,700 in 50,620 windows, 82 s; 10, 1 s; with 32 jobs) but the opens, the image, the last close (it closes a KV region) and stores of several keys; each loss is one window of 32 owners, which TLC checks in about a second. E4's epoch commit on `67b145cac` (131,917 inputs, an update's target on trial beside the serving session over one KV region, its update committed): every transition followed but the opens, the image and the last close, the target's close among them (131,913 in 77,723 windows, 350 s with 12 jobs). E12's host point on `4aa52f7b9` (235,624 inputs), whose epochs state their host tier on the shared host region by `Resize` (a shrink of free host units and a grow back): every completion equal and every check clean, and every transition followed but the opens, the image, the last close (it closes a KV region) and the prefetches from the peers (235,427 in 152,564 windows, 1,123 s with 12 jobs). The Storage Server's integration test of a session, recorded, replays with every completion equal. Outside the model: an open, a pool's image, a close that closes a KV region (the last session's, or one whose KV region no session that stays names: its evictions and shrinks are one step to the pool and, in every order, as many to the model), classes other than 0 (a request of one, a key cached in one, and a state in which an owner holds a unit of the model's region in one, which the state states beside the model's terms: the model has one class, so that unit would be neither free nor held in them), prefetches from the peers, loads and stores of several keys, states with no session open, a key cached on the device in several regions, a resize over regions of two unit sizes in one memory space; a prefetch of several keys is checked as one per key in order, and a task of several keys is stated as one per key. The serving server runs no check of its own; the replay checks every state.
- **L4, mutations (`mutations.py`).** The guard of each rule R1 to R11 replaced in the Rust source is caught by the crate's tests.
- **Not established.** That the implementation refines the model: L1 is an enumeration of six bounded configurations, and a trace is checked transition by transition, each from its recorded state, not as one behaviour.

The model leaves out `Victims` and `List` (eviction takes any shared block without a pin, which includes every installed order), a peer's own pins on this host, and blocks of more than one unit. A handler that evicts to make room, a `Store` or a `Prefetch` on the host tier, is the model's `EvictHost` steps of host copies nothing but the cache holds followed by the handler: the steps between are states of the model, so the properties, all of them state predicates, hold through it; `steps.py` follows such an input that way. It also leaves out a private block whose runs lie in several memories (A9 names the run its writer wrote), a crossing of a host copy between hosts, a prefetch into a host block that holds other host parts, and a resize of a group's slot region (a slot row is in its slot region throughout; `Resize` moves device and host units only), so a trace's step in which a slot row leaves its region or joins it is not followed.
