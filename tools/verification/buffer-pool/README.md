# The buffer pool's design model

The model of `specs/buffer-pool.md` and what checks it. Nothing here needs a device.

## Layout

| Folder | What it holds |
| --- | --- |
| `model/` | `KvCore.tla`, the design model: the buffer pool's handlers, the work it defers until a stamp is reached, copies and tasks in flight, tiers, regions, the trial of an epoch, the loss of an engine, crossings (`Replicate`: a block's content brought to the memory of a group that reads its owner's class, `Readers`) and host copies valid per host part (`HostParts`, `GroupParts`); and its neighbours: an executor that meets A1 to A4 with batches of unbounded delay and a control plane that issues any request in any order. Each rule R1 to R11 is a guard in force when its name is in `Rules`; each hazard H1 to H14 (`specs/kv-cache-s0.md` §6, and H14 of `artifacts/buffer-pool/p4-design.md`) is behaviour switched on by its name in `Hazards`. `MC_Pool.tla`, the buffer pool alone: its handlers taken with requests of any stamps, with no batch, executor or scheduler, the relation the Rust buffer pool is compared with. `KvTrace.tla`, the steps of a recorded transition checked against `MC_Pool`'s |
| `properties/` | The safety properties as formulas over `KvCore`, one module per property (`KvP1` to `KvP8`, no P4); `KvSafety`, the conjunction of P1, P2, P3, P5, P6 and P8; `KvFinality`, P4 as two temporal properties under stated fairness. `properties.toml` lists them; each entry and its module are pinned by hash in `pins.sha256` |
| `proof/` | `KvInductive`, the inductive invariant `IndInv` under the design (every rule in force, no hazard); the TLAPS proof under the assumptions `Design` and `Sizes`: `KvProof` (`Init => IndInv`, `IndInv => Safety`), `KvFrame` (typing and frame lemmas the steps share), `KvStep1` to `KvStep11` (the inductive step for each group of actions, `Next1` to `Next11` of `MC_Apalache`; `Next11` is the crossing's), `KvStep` (the step for all of `[Next]_vars`, `Spec => []IndInv`, `Spec => []Safety`, `Spec => []P8`), `KvProofP7` (`IndInv => P7` under `Finite`) and `KvSafeP7` (`Spec => []P7`); `addresses.smt2`, the address arithmetic as thirteen goals for z3 |
| `configs/` | The configurations TLC searches (`MC_*.tla`, `MC_*.cfg`; `MC_Pool*.cfg` are `MC_Pool`'s), and `MC_Apalache.tla`, which fixes the constants and generates the states for Apalache |
| `scripts/` | The runners (below) |
| `log.md` | Every run with the prediction written before it and its outcome |

The tools are TLC (`tla2tools.jar` 1.8.0) under a JDK 21, Apalache 0.63.0, TLAPS (`tlapm`) and z3 4.8.9; the scripts read their directory from `TLA_TOOLS`. A configuration runs from `configs/` with `model/`, `properties/` and `proof/` as TLC's library; TLAPS proves a module in `proof/` with the other two folders on its include path; Apalache, which reads a module's imports only beside it, runs on links to every module in a directory of its own.

## Running the checks

| Script | What it runs |
| --- | --- |
| `suite.sh [pins\|design\|mutations\|hazards\|validation\|addresses]...` | The whole suite with the verdict expected of every run (about 50 minutes on 144 cores; `pins mutations hazards` are the quick parts) |
| `tlc.sh MODULE [CONFIG]` | One configuration (`RULES=NoRn` leaves a rule out, `HAZARDS=Hn` switches a hazard on, `ONLY="Inv..."` checks only those invariants); `trace.py` prints a counterexample from a TLC log |
| `prove.sh [MODULE...]` | The TLAPS proof, every module in order by default |
| `apalache.sh ARGUMENT...` | Apalache on `MC_Apalache`; `apalache_step.sh OUT [GROUP...]` runs the inductive step per group of actions, and `cti.py` prints a counterexample to induction |
| `pins.py check` | The property list against its pins |
| `agreement.sh` | L1: the Rust buffer pool's enumeration of every request sequence (`buffer-pool-verify enumerate`, `crates/storage-server/src/buffer_pool/enumeration.rs`) against the states of `MC_Pool`, per configuration (`agreement.py`; about 25 minutes) |
| `agreement_steps.sh [CONFIGURATION...]` | L1 step by step: every transition of the enumeration of `core`, or of the configurations named, is a path of `MC_Pool`'s steps (`steps.py`); a transition made by hand that the model does not allow is reported |
| `replay.sh TRACE_DIR` | A run's trace of the Storage Server (`storage_config.buffer_pool_trace`, `crates/storage-server/src/buffer_pool/trace.rs`) replayed (`buffer-pool-verify replay`, `crates/storage-server/src/buffer_pool/replay.rs`) on a new Rust buffer pool, every completion checked against the run's and `check()` after every input, and every transition between its states checked against `MC_Pool`'s steps |
| `mutations.py` | L4: one replacement per rule R1 to R11 in the Rust buffer pool's source, each of which the crate's tests must catch (about 5 minutes; it edits the crate in place and restores it) |

```bash
tools/verification/buffer-pool/scripts/suite.sh
tools/verification/buffer-pool/scripts/tlc.sh MC_Trial
tools/verification/buffer-pool/scripts/prove.sh
tools/verification/buffer-pool/scripts/apalache.sh --init=Init --inv=IndInv --length=0 --cinit=ConstInit
tools/verification/buffer-pool/scripts/apalache.sh --init=IndInit --inv=Safety --length=0 --cinit=ConstInit
tools/verification/buffer-pool/scripts/apalache_step.sh OUT
tools/verification/buffer-pool/scripts/replay.sh TRACE_DIR
```

## What is established

Terms. Checked: no violation in a complete search of a stated configuration. Proved: safety of the design model, under the stated assumptions. Not proved: liveness; that the implementation refines the model. A run that times out or stops at a bound is INCONCLUSIVE. `log.md` holds each claim's runs and figures.

- **Checked (TLC).** P1, P2, P3, P5, P6, P7 and P8 hold in the fourteen configurations of `suite.sh`, among them `MC_Cross` (a group that reads, in a memory of its own, what owners of another group hold), `MC_HostParts` (two groups copying with the same part index on two hosts), `MC_HostSplit` (a group on one host beside a group across both) and `MC_Tiers` (the host region resized beside prefetches, puts, saves and restores); P4 holds in `MC_Finality`. P7 is violated by the hazard H12 and by leaving out R2, P8 by leaving out R3 or, for a store's fill, R5 (the part `validation`). Each rule R1 to R11 left out, and each hazard H1 to H14 but H6 and H13's safety side, violates the property `suite.sh` states for it; H6 and H13 violate P4. `IndInv` is an invariant of `MC_Cross`, `MC_HostParts` and `MC_HostSplit` (`log.md` entry 43); the other configurations were checked against it before crossings and host parts (entry 41).
- **Proved (TLAPS), under `Design`, `Sizes` and, for P7, `Finite`.** `Spec => []Safety`, where `Safety` is P1, P2, P3, P5, P6 and P8: `Init => IndInv` and `IndInv => Safety` (`KvProof`), the step `IndInv /\ [Next]_vars => IndInv'` group by group (`KvFrame` and `KvStep1` to `KvStep11`) and its assembly by PTL (`KvStep`), which also states `Spec => []P8`; `IndInv => P7` (`KvProofP7`) and `Spec => []P7` (`KvSafeP7`). Every obligation is proved, none omitted. `Sizes` states, of the configuration, that each group's host parts are host parts, that a memory is not a host part, and that a group reads only groups of its own epoch.
- **Checked (Apalache), for the constants of `MC_Apalache` and collections of at most three elements.** `Init => IndInv`; `IndInv => Safety`; the inductive step of `IndInv` for each group `Next1` to `Next11`.
- **Proved (z3).** The thirteen goals of `addresses.smt2`, under A8.
- **How `IndInv` was found.** Apalache and TLAPS gave counterexamples to induction from states no behaviour reaches, each answered by strengthening `IndInv` with a clause TLC then checks on every configuration; for crossings and host parts, it was extended from the design's argument and checked by TLC, Apalache and TLAPS.
- **Not established.** Liveness (P4 is checked, not proved, and its `TaskFinality` states neither a transfer's nor a crossing's task), and that the implementation refines the model (below).

## The implementation against the model

- **L1, states (`agreement.sh`).** The Rust buffer pool is driven through every sequence of requests, `completed` values, task results and deadlines of seven small configurations: `core`, `copies`, `transfer`, `tiers`, `cross` (two memories, the second group reading what owners of the first hold), `parts` (two host parts, a group copying with one and a group with both) and `trial` (`MC_PoolTrial`: two sessions of two layouts over one device memory, the target on trial, its regions resized, its update committed, its session ended or its update rolled back). After every step the pool's own check holds: every unit is in exactly one place, a block's references equal its holders, a private block is in one place, a pin is of a cached block, an entry is valid in its owner's group, memory is in one region. Every state reached, written in the model's terms, is a state of `MC_Pool` under the same configuration.
- **L1, steps (`agreement_steps.sh`).** Every transition the enumeration reaches in the seven configurations is a path of `MC_Pool`'s steps from the transition's state to the next (`KvTrace`), each checked on the parts of the pool it touches; a transition made by hand in which a commit takes effect before its stamp is reported. The Rust buffer pool's R1 for owners is stronger than the model's (a number below one taken on the queue pair is refused), so an owner the Rust pool states as gone matches a model owner never attached.
- **Traces (`replay.sh`).** With `storage_config.buffer_pool_trace` the Storage Server's buffer pool thread records every input it acts on and every completion its pools produce (`specs/buffer-pool.md` §18). The replay drives a new pool with the inputs, runs its `check()` after every input, and stops at the first completion that differs from the run's or the first inconsistency; every transition between the states it writes is checked against `MC_Pool`'s steps from its recorded state, on the parts of the pool it touches. A prefetch of several keys is checked as one per key in order, and a task of several keys is stated as one per key. A state states its free units as runs, so it grows with what is held and waiting: a serving run's states take gigabytes in `$REPLAY_WORK`. The serving server runs no check of its own; the replay checks every state.
- **Outside the model**, in an enumeration or a trace: an open, a pool's image, a close that closes a KV region (the last session's, or one whose KV region no session that stays names: its evictions and shrinks are one step to the pool and, in every order, as many to the model), classes other than 0 (a request of one, a key cached in one, a state in which an owner holds a unit of the model's region in one), a key cached as a stored trajectory (the enumeration names a trajectory and a KV block by one key, which A6 excludes), prefetches from the peers, loads and stores of several keys, states with no session open, a key cached on the device in several regions, a resize over regions of two unit sizes in one memory space.
- **L4, mutations (`mutations.py`).** The guard of each rule R1 to R11 replaced in the Rust source is caught by the crate's tests.
- **Not established.** That the implementation refines the model: L1 is an enumeration of seven bounded configurations, and a trace is checked transition by transition, each from its recorded state, not as one behaviour.

The model leaves out `Victims` and `List` (eviction takes any shared block without a pin, which includes every installed order), a peer's own pins on this host, and blocks of more than one unit. A handler that evicts to make room, a `Store` or a `Prefetch` on the host tier, is the model's `EvictHost` steps of host copies nothing but the cache holds followed by the handler: the steps between are states of the model, so the properties, all of them state predicates, hold through it; `steps.py` follows such an input that way. It also leaves out a private block whose runs lie in several memories (A9 names the run its writer wrote), a crossing of a host copy between hosts, a prefetch into a host block that holds other host parts, and a resize of a group's slot region (a slot row is in its slot region throughout; `Resize` moves device and host units only), so a trace's step in which a slot row leaves its region or joins it is not followed.
